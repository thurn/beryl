INCIDENT: command the fleet during an operator-declared emergency

The operator appoints one incident commander. Record the timeline and one
outcome per mitigation on the incident ticket. Link a root-cause ticket with
evidence of why the normal handler failed, or explain why no fix is needed.

1. File and claim a root incident ticket. Its ID starts with I.
   ignite ticket create "<fault>" --labels incident --pending --independent
   ignite start <ticket>
   Record the operator's declaration, the evidence and your session ID.
   When master stalls while green advances, run
   ignite emergency declare <ticket> --landings-only
   Only new landings refuse (exit 6). Hand-offs, builds and checks continue.
   For broken builds, hub or daemon faults, or resource exhaustion, omit the
   flag to pause hand-offs and all new heavy verbs. Renew with the same scope.
   Use ignite emergency allow <repair-ticket> land to let a repair land.
   If Ignite is down, keep the record locally and continue recovery.

2. Locate affected work with ignite status, ignite pool list, ignite fleet and
   ignite ticket list --status in_progress. Record fleet settings first.
   Unwind over-allocation (pool list: held N of limit M build tickets) with
   ignite pool shed --machine <name>, not by telling workers to release.
   Stop harmful commands with ignite stop <handle> --force. Use ignite tell
   or ignite tell --all. Contact desktop sessions without tickets directly.
   Include both IDs, the facts and the action. Recipients verify your claim
   with ignite ticket show. Refused sessions can run ignite wait emergency.

3. Stop the harm first. You may take over work, claims or dependencies.
   Back up affected refs, tickets and state before destructive steps. Prefer
   a revert or fast-forward. Use a lease for force pushes. Keep the operator
   informed.
   Target moving master within 30 minutes of declaring the incident. If it
   still waits on a slow secondary platform at 30 minutes, defer the platform
   and record which checks to rerun. Revert known culprits blocking promotion.

4. If Ignite blocks its own repair, use an available tree and the smallest
   check that proves the fix. Deploy a hotfix to both release and integration
   refs or use ignite install. Push to main only if integration is broken.
   Record old and new commits, skipped checks and any rules you relaxed.

5. Verify the repair with ignite status and ignite doctor. If master stalled,
   confirm it advanced before restoring fleet settings. Run
   ignite pool resume --all and verify claims and tip verification.
   Withdraw orders. End the pause at once if the operator directs it.

6. If master stalled, close the incident ticket once master advances. Record
   the recovery and file follow-ups for skipped checks and remaining fixes.
   If stopping before recovery, record what fails and keep the pause only
   if resuming would cause harm. The operator can appoint a replacement.
