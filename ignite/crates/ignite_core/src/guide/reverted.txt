REVERTED: a landing a tip round took back off the integration branch

Landings are checked on the tree they were written in, not on the newest
commit, so two landings that each build alone can leave a tip that does
not build. A tip round can revert the one landing that broke the build
and reopen its ticket. With [revert] stall_minutes set, a required non-build
check can also trigger a revert once the oldest unverified landing has
waited that long. The round confirms the failure again at the tip and
checks that the revert passes before pushing it.

Your own ticket came back reverted (its brief has a reverted line):
- Run ignite start <ticket>. The tree starts without your work: the
  revert commit removed it.
- Apply the work again with the command the reverted line gives:
  git revert --no-edit <revert commit>.
- Read the failing check's output on the ticket, fix the failure, commit,
  and run the failing check with ignite test before you land.
- Land with ignite land. A reverted ticket's landing rebases onto the
  newest commit and checks there, build checks included, so it is slower
  than usual. That is expected.

You were told that a ticket yours depends on was reverted:
- Its code is gone from the tip, and your tree may not build. Commit what
  you have and run ignite release with a note saying where you stopped.
  Your ticket is handed out again when the reverted one lands.
- The session that takes the reverted ticket fixes the failure.

A revert commit (subject starting "revert: ") is never reverted. When the
tip fails with one, a regression ticket is filed instead.
