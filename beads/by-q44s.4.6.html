Close reason

Beryl 3D test steps stop themselves before the hard limit (330e986af). Run-log query, script=check lanes beryl3d-tests/interface since 2026-11-16T21:35Z, pushes grouped by commit+worktree+place: 40 pushes, 3 (8%) with cargo-test or interface test cut at the wall limit, vs 195 of 346 (56%) in the day before. Token priority was not the cause, so no change there.

Description

Symptom: in milestone 2 (2026-11-15 21:00 to 2026-11-16 21:00 UTC) the fast check ran Beryl 3D's lanes on 330 pushes. In 186 of them (56%), cargo-test (162) or the interface tests (141) were killed at the 180 s wall limit before they finished, so those changes reached staging with Beryl 3D's tests unrun. The Beryl 3D sweep then found the breaks 1.5 to 3 hours later and filed about 45 beads in the same day, and 14 of those closed as obsolete.

Why, from the run log ($BERYL_CACHE/ci/runs/*.jsonl, script=check, lanes beryl3d-tests and beryl3d-interface): the shared build step record took a median of 80 s and a p90 of 180 s, but its median CPU time was about 1 s. 141 record steps spent over 60 s while using under 5 CPU-seconds. The step was queued for CPU tokens (tools/src/beryl_tools/tokens.py), not building. Commit b0328a39c (2026-11-16 20:15 UTC) began logging waits that never get a lease (outcome gave_up and abandoned in leases.jsonl), and 0e850d9ab (21:01 UTC) lets agent cargo builds start on free tokens. Neither had landed during milestone 2, so their effect is unmeasured.

Proposed change: first measure a day of pushes after 0e850d9ab with the same query (record wall seconds against CPU seconds, and the count of wall-cut cargo-test and interface tests per push). If more than 10% of pushes still cut a test step, use the new gave_up/abandoned lines to find which class holds the tokens, and give the fast check's record step push-class priority over agent and sweep builds. by-br5xr owns the lane's 60 s budget. This bead is about tests not running at all, which by-br5xr does not cover.

Files: tools/src/beryl_tools/tokens.py, tools/src/beryl_tools/beryl3d/lane.py, tools/src/beryl_tools/beryl3d/cli.py (build lock, cli.build), tools/src/beryl_tools/cargo_pool.py, docs/checks.md 'Beryl 3D'.

Expected gain: Beryl 3D changes are tested before they land, and most sweep beads disappear.

Acceptance criteria

Over at least 40 Beryl 3D pushes measured after the change, fewer than 10% have cargo-test or the interface tests cut at the wall limit. The query used and its result are in the close reason.

Diagnosis differs from the bead: the record steps with ~1 CPU-second are the two lanes waiting on the checkout's build lock (cli.build) while the third lane's record builds for real (130-370 CPU-s, 20-130 s wall). Push token waits since 12:00 UTC were median 3 s, p90 14 s for cargo builds, so token priority is not the cause. The cuts come from the time left after the shared build: cargo-test planned against estimates and read the deadline before nextest listed the tests, so it ran past 180 s even after cutting tests (21:14-21:19 UTC, 4 cuts with skips). Before the change, 21:05-21:20 UTC: 4 of 5 pushes cut. Fix (330e986af): cargo-test re-reads the deadline after listing and SIGTERMs nextest 8 s before the hard limit (nextest still writes JUnit; finished tests logged, rest skipped as cut); b3d test gets --stop-after, set by the fast check to 20 s before the limit. No token-priority change made. Measuring 40 pushes after 330e986af (landed ~21:47 UTC) with the run-log query in the close reason.
