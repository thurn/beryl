Slow CI holds a fixed share of the machine as commits rise

Close reason

slow_min_gap in Enact spaces slow-CI runs; Beryl sets 300 s; share figures need recorder data

Description

What we see

Slow CI tests the tip of staging whenever its runner is free, which today means one run for about every 2.4 commits. Each run uses about 11 checks' worth of CPU at once for five to ten minutes. As the commit rate rises, the runner becomes continuously busy and competes with the agents' builds and with the fast checks that gate their pushes.

Change

Once the machine-wide CPU scheduler exists, run slow CI under it at a lower priority than push checks and agent commands, and give it a configurable ceiling on the tokens it may hold. Enact's part is to keep back-to-back runs from starving everything else: a setting in .enact.toml for the least time between the end of one slow-CI run and the start of the next, so that more commits make larger batches instead of more runs. ci_run_once and start_ci in scripts/enact.py are where runs start.

Beryl's part is to start by ci through the scheduler with the slow-CI priority.

Done when

With the commit rate doubled, the CPU recorder shows slow CI's average share of the machine no higher than today's 1.7 cores, and master still advances within an hour of a commit reaching staging. This change is in the Enact repository at ~/enact (scripts/enact.py, tests in tests/test_unit.py and tests/test_integration.py), not in Beryl. Read ~/enact/AGENTS.md first and follow that repository's workflow. The measurements behind this bead are in its parent, by-gdn3.
