Close reason

changes query, marks on metric series, seeded data/efficiency-changes.json; pushed 978bcbd4

Description

Record each change made to save time or tokens, and show on the trend it was meant to move whether it did.

Design section: "Efficiency changes".

What to build

  • data/efficiency-changes.json and its entry in data/AGENTS.md: entries with label, metric (a name from the metrics registry, optionally with a cohort filter such as bead.dollars[tier=sonnet]) and expect (up or down). An entry's commit is the one that added it to the file, found from the file's history, since a commit cannot hold its own hash and enact push rebases. An optional commit field names an earlier commit on staging, for the seeded changes.
  • Validation as a test in the efficiency check lane: each commit given is on staging, each metric is known, each label is one sentence.
  • The changes query: for each entry, the median of its metric over the seven days before the commit reached staging and the seven days after, the sample counts, and whether it moved as expected. Trend results carry the marks, so that the page can draw them.
  • A rule in the root AGENTS.md, one line: a change made to save time or tokens adds its entry in the same commit.
  • Seed the list from the first week's history. Find the candidates with git log --grep over subjects beginning perf, and the history of .enact.toml, tools/src/beryl_tools/tokens.py, deadline.py, warm.py, caches.py, rust_fit.py and check_value.py. Examples the comments in those files describe: slow CI reusing one worktree and its target directory; the fast check held to 60 s with a 180 s hard limit; the merge queue removed from enact push; the CPU token pool; the tests step taking free tokens once its build is done; slow CI's minimum gap between runs. Choose for each the metric it was meant to move.

Shared context

  • The design is docs/efficiency-dashboard.md. Read the sections named above before anything else; the rest can wait. The decisions taken with the user are in the epic, bd show by-ig5e.
  • The dashboard's code is the separate Python project in efficiency/ (package beryl_efficiency, standard library only, pyre strict, black). It imports nothing from tools/ and nothing imports it. Read efficiency/AGENTS.md first once it exists.
  • Tests use small synthetic sources built in the test itself or kept under efficiency/tests/. The repository is public: never commit a real transcript, session record or command line from this machine.
  • Real data exists only on the main Mac (host jarvis). Where the acceptance criteria name a check against real data, run it there; if this session is on another machine, record that the check was not run in a comment on this bead and close on the tests.
  • Collection must stay free for agents: no hook, wrapper or prompt text may be added to any session, and ingest must never run inside another command.

Acceptance criteria

Tests: an unknown metric name or a missing commit fails validation; before and after medians are computed from the commit's time on staging; an entry with too few samples on one side says so and gives no verdict. On the main Mac, just efficiency changes lists at least six seeded changes, each with medians and sample counts.
