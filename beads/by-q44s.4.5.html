Close reason

Timeline parity compares each step's sounds; no recording newly differs (09869af1)

Description

Symptom: nothing checks that Beryl 3D plays the same sound for a step as the web interface does. beryl_scene/src/sound.rs (cues) is a hand port of stepCues in ui/src/audio/steps.ts, which picks each step's sound from its act, the table as the step found it, the earlier steps of its beat and its timing. The web interface keeps changing at about 500 commits a week (epic by-q44s, plan review). When steps.ts changes, the Rust port silently drifts, which is the same kind of drift that moving step timing into the session (lane:timing) removed for durations.

Current design: timeline parity (tools/src/beryl_tools/beryl3d/timeline.py, EXACT = ("verb", "case", "effects")) compares each step's start, end, verb, case, effects and place between ui/scripts/timeline.mjs and just b3d timeline (beryl_inspect/src/cli/timeline.rs). Sounds are in neither timeline.

Proposed design: both timelines print each step's cues as a sorted list of [sound, edge, into] (the web's Cue from stepCues; Beryl 3D's sound::Cue from sound::cues), and timeline.py adds "sounds" to EXACT. A step whose sounds differ counts as one differing step, like any other field, so data/beryl3d/timeline-parity.json's counts keep their meaning. Any recording that newly differs is fixed in sound.rs in the same change where the port is wrong, or listed with its cause where the web is the one to follow later. Moving the cue rules into the session's StepTiming (as timing was) would remove the port entirely, but it changes the protocol, which the epic's rule 5 forbids without a bead of its own; this bead does not do that.

What it removes: an unchecked duplicate rule set between the two clients.

Behavior that must not change: timeline parity's other fields and counts; no change to steps.ts behavior. ui/scripts/timeline.mjs is the one ui/ file Beryl 3D owns (epic Code map), so editing it is within the rules.

Files: ui/scripts/timeline.mjs, ui/src/audio/steps.ts (read only), rust/beryl3d/crates/beryl_inspect/src/cli/timeline.rs, rust/beryl3d/crates/beryl_scene/src/sound.rs, tools/src/beryl_tools/beryl3d/timeline.py, tools/tests/test_beryl3d_timeline.py, data/beryl3d/timeline-parity.json, docs/beryl-3d.md 'Timeline parity' and 'Sound'.

Acceptance criteria

  1. just b3d timeline prints a sounds field per step, and timeline.mjs the same field for the web. 2. A tools test plants a timeline pair that differs only in one step's sound and the parity comparison counts that step. 3. just b3d timeline-parity (with and without --fixtures) passes; any entry raised says why in the commit body.
