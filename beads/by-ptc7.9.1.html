Description

Audit the architecture of the whole epic as built. Read the plan, the two contracts, the first Mason's comments (the baseline audit and the foundations gate) and every Warden's close reason.

Answer, with evidence, in a comment on this bead:

  1. For each of P1 to P16 of the plan: was it built as decided, and if not, is what was built better? Amend the plan where the code is right and the plan is stale.
  2. The question the epic was planned around: would this work with a full implementation of the Comprehensive Rules and 50,000 card definitions? Answer it for compile and check time (just efficiency compile, just scale with the new mix), for the per-card test cost, for the vocabulary's size and how a writer finds an entry, for the module layout (just citations coverage: how much of the rules is owned, and where the rest would go), and for the state's size.
  3. The card workflow's numbers: tokens, minutes and lines per card for the pilot's twelve cards against the 121 before; the share of cards with no hand-written scenario; the share of sentences the brief drafts. What would most reduce the cost of a set of 300 cards now? Run just set plan ths again and say how its tiers moved.
  4. One-card logic: every variant, field, branch, capability or prompt purpose that exists for exactly one keystone of this epic and that no second card could use.
  5. The bug log: every entry added during this epic, and whether a guard of milestone 1 should have refused it. A class that recurred gets its guard or its reason.
  6. The other modes: for each row of the plan's table ("What each other mode would still need"), is the "values of Format" column true of the code, and did anything built here make a mode harder?
  7. The numbers: the count from the epic's first bead to its last, State<Small>'s size against 20,480, each family's present-cost ratio, the stall rate under random play and in the keystone pool, non-test lines of the three engine crates before and after.
  8. Whole-run acceptance, line by line, from the epic.

File each important finding as a child of this gate. A finding that is a follow-up and not a defect is filed outside the epic at P3.

Bars (every bead of this epic)

  • The plan is docs/project-50k-part-2.md. If its design is wrong for the code, build what is right and amend the plan's section in the same push. Never wait for an answer: record the choice in this bead.
  • The absent-cost gate holds with no bump (just count-gate). When you touched the kernel, the rules or the card vocabulary, report the count before and after in the close reason. If it cannot hold after three attempts, stop and say so on the epic: this is the one thing that stops the run.
  • size_of::<State<Small>>() stays within 20,480 bytes. Report the size if you changed it.
  • The frozen saves replay and rollouts_never_change holds (just test-rust).
  • Rules code cites the Comprehensive Rules with a quotation (just citations). A card file cites a rule only for a card-specific ruling.
  • A new card follows the card-writing skill and passes just card check <name> (Beryl, XMage and Forge). A keystone or partner is listed in data/rulings-ledger.json once that file exists, with every ruling a scenario or a reason.
  • No UI work. beryl_cli script-check must pass for a new card from both seats with the verbs and prompt shapes that exist.
  • A rules bug found on the way gets its docs/bugs.md entry, naming the guard that now stops its class.
  • A bead you file is tier:opus for design, keystones and reviews, tier:sonnet for partner cards, sweeps and measurements, and never tier:fable.

Acceptance criteria

A comment answers the eight questions with evidence. Defects are filed as children; the epic's acceptance is checked line by line.
