Close reason

beryl_card_store embeds and seeks the store; card_records over IPC, in both servers and every fixture

Description

Rust reads the card store and serves records over IPC on demand (plan: docs/project-50k.md, Card pool pipeline; Acceptance, "App startup and the UI bundle do not grow with the card store"). Second bead of lane:card-store: the first (the pipeline) wrote the store and its format; its handoff names the files and the Python reader.

Read first: the pipeline bead's handoff and the store format's header; rust/crates/beryl_session/src/ipc.rs (316 lines: every command's name, request and result, and the TypeScript it generates); rust/crates/beryl_app/src/lib.rs lines 180 to 240 (the handlers! macro and registration) and games.rs; rust/crates/beryl_cli/src/serve.rs near line 180 and specs/serve.rs near line 270 (the two browser servers that answer the same commands); rust/crates/beryl_cli/src/fixture.rs near line 900 (what a recorded fixture holds). Need not read: the engine, the search, the UI beyond ui/src/cards.ts's types.

Do

  • A small library crate (suggested name beryl_card_store; say in its Cargo.toml what each dependency replaces) that looks a record up by card name, face name or token name. Default: embed the store with include_bytes! and binary search the bytes, so the desktop app, both phone apps, beryl_cli's servers and the tests all read it the same way, nothing is bundled as a resource, and nothing is read or parsed at startup. If you choose a file on disk instead, it must work in the iOS and Android apps (Android packs resources inside the APK, where a path cannot be opened) and you verify it with just ios-smoke and just android-smoke.
  • A lookup never scans: a test over 50,000 synthetic records shows one lookup probes at most 32 lines, and that opening the store parses no record.
  • The record type mirrors what the UI draws (ui/src/cards.ts: CardEntry, CardFace) and derives ts-rs's TS, so ui/src/generated/protocol.ts regenerates (a test fails when it is stale; its header says how). Expand each face's image URLs (art_crop, normal, large) and the card back's when serving, so the UI's types need not change. rust/crates/beryl_app/src/art.rs's cache is unchanged.
  • One IPC command in beryl_session::ipc (suggested: card_records, a list of names in, the records found out, each under the name asked for, with the card back's image). Register it in beryl_app (handlers! checks the name), and answer it in beryl_cli/src/serve.rs and specs/serve.rs, where a spec frame (?relay) asks too.
  • beryl_cli record-fixture (fixture.rs) records, in each fixture, one card_records response holding the record of every name its views and events show, so a fixture page needs no server. The UI bead that follows makes the fixture transport answer by name from it; put the response's exact shape in your handoff.
  • rust/crates/beryl_cards/src/tests.rs line 174 checks that every name the engine gives a face, token or emblem is in data/cards.json: move that check to the store (in the new crate or beryl_session, with beryl_cards as a dev-dependency) and delete the old one. That one test is the only edit this bead makes in beryl_cards.
  • specs/serve.rs is on data/file-length-allowlist.json at 888 lines: do not grow it; put new server code in a new file.
  • Measure and put in the handoff: the store's size, the app binary's size before and after (cargo build -p beryl_app, debug and release), and just smoke's time to ready before and after. Then file a bead labelled human under by-w8gv.18, which nothing depends on: "Look at: the card store is committed (N MB) and embedded in the app (+M MB)", with the alternative (a download on first run).

Verify

cargo test for the new crate, beryl_session and beryl_cli; just smoke; one fixture re-recorded (just ui-shots <one name>) still renders, since the UI ignores the new response until the next bead.

Parity and policy

This is the data track: it edits no engine-track file (nothing under rust/crates/beryl_engine, beryl_kernel, beryl_card or a card file), and nothing here creates a Rust file per card (K2: an unimplemented card is a record in the store). Parity (plan K11) at the push: just check passes; the frozen save corpus replays (cargo test -p beryl_session --test corpus); rollouts_never_change holds; slow CI's counts lane (just count-gate, bar 405,276,238 instructions, 1% tolerance, rust/crates/beryl_bench/count-gate.toml) passes with no bump to the bar. Nothing waits on the user (K31): proceed on a default and file a non-blocking bead labelled human, parented to by-w8gv.18, where his judgement is wanted. Record decisions and deviations as comments on this bead.

Acceptance criteria

A crate looks a record up by card, face or token name; a test over 50,000 synthetic records shows a lookup probes at most 32 lines and that opening the store parses nothing; a card_records command is named in beryl_session::ipc, registered in beryl_app, answered by beryl_cli's two servers and recorded in fixtures; ui/src/generated/protocol.ts is regenerated; the engine-names check reads the store; store size, binary sizes and just smoke's time before and after are in the handoff, and the human bead is filed; just smoke and just check pass.

Decisions: tokens map holds the FIRST printing the store has for a token name (store order: oracle id then Scryfall id), so a token may show different art than cards.json picked; records carry no made_by; image URLs carry no ?timestamp (art.rs ignores the query anyway). Names come from every string in the fixture's events that the store answers (so a button label "Done" also gets a record, harmless); about 8 KB a fixture. The engine-names check moved from beryl_cards tests.rs to beryl_session card_records::tests (every_face_token_and_emblem_name_is_in_the_card_store), plus a test that served records equal data/cards.json's entries less timestamps and made_by (delete it with cards.json).
