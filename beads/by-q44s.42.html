Description

The user asked whether running the exact-count performance gates against every regression is useful while Beryl 3D is still gaining a verb every hour or so. This bead answers that and changes the gates to match. Default decision (change it if the evidence below says otherwise): keep exact counting, but during the build-out make the sweep's frame-counts and gpu steps fail only on what a feature commit cannot explain: a change in how cost scales, or a large jump. Tighten them back to 1% when feature velocity drops, at the latest when the user calls the switch (C11).

What the gates cost and caught (2026-11-14 to 2026-11-16)

  • The Beryl 3D sweep filed 21 step-failure beads for epic by-q44s in about a day: gpu 5, timeline-parity-all 3, frame-counts 2, cargo-test 2, every-tick 2, and one each for timeline-parity, gate, smoke and clippy.
  • The gpu step failed all 11 of its runs in the last 30 days (by-q44s.41's record line). A gate that is never green tells nobody anything; each failure was settled by raising the fragment limit (for example a14fc4be0).
  • data/beryl3d/gates.json had 43 commits since 2026-11-14. Most raise native work counters for a new verb, as the rule in rust/beryl3d/AGENTS.md allows.
  • by-q44s.40 (frame-counts) found two different things in one failure:
    1. A rise of 5-66% at 58f2c989 that was new work: text runs went from 0 to about 19 per frame, records rose 75% and layout nodes went from 1 to 9. The only fix for that is a limit raise, and the bisector ran out of time over 261 commits.
    2. A real algorithmic regression from ba64a25c5 (contact shadows): Table::floor scanned every card twice per moving card per frame, which is O(n^2). stress-255 went from 69M to 225M instructions in total, and stress-1024 to 761M. It was found only because the session bisected by hand in the bench VM, at about 10 minutes per measurement.
  • So the signal worth having was "cost grew faster than the board": stress-1024 went up about 10x while stress-255 went up about 3x. The 1% tolerance turned that signal into the same failure as every legitimate verb.

Proposed change (default)

  • Add a scaling check to just b3d gate --counts (tools/src/beryl_tools/beryl3d/counts.py): the ratio of stress-1024's total instructions to stress-255's must stay within a fixed bound (linear work gives about 4 for 4x the cards; record today's ratio after by-q44s.40's fix lands and allow, say, 15% over it). This catches O(n^2) work at any feature velocity and needs no raise when a verb lands. The native gate (just b3d gate, rust/beryl3d/crates/beryl_inspect/src/gate.rs) can hold the same ratio over its placed and records counters on every push, in seconds, so the regression is caught in the fast check instead of hours later.
  • During the build-out, raise tolerance_percent in frames.<board> from 1% to about 20% for the instruction counts, and make the tiers' fragment limits in gpu warnings instead of failures, unless a frame passes the target itself (1.75 screens). Write the build-out tolerance as one named constant with a comment that says when it goes back to 1%.
  • Keep "a count below its limit fails" off while the tolerance is loose, or every cut would file a bead too.
  • Leave the work counters in the native gate as they are: they are exact, cheap and explained by the commit that raises them.
