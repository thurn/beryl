Fix (stage-side, deviating from the notes' suggested session-side swap). Cause confirmed: Priority::open gives each stand-in twin the offered card's ways, so a click/drop on Plains slot 2 answers with the candidate for Plains slot 0; the script truthfully moves slot 0 and the stage keys nodes by slot. A session-side rename was rejected: slots are permanent identities in every view, script, prompt and replay (K24 replay check), so naming the handled twin as the mover would need a per-seat slot permutation across the whole protocol. Instead the stage remembers the hand card the last click/drop was on (Prompts.#handled); when the next script's first fly from a hand is a different card whose ObjectView equals the handled one's but for slot (twinOf, ui/src/stage/prompt.ts), ScriptStage.trade swaps the two in the hand order (table.ts traded), their poses and tracks, the pointer's names (Pointer.trade) and the DOM raise/heft (DomSurface.trade, RaisedCopy.trade) before the script plays. No protocol change. Covers drag and click, any twin set in a hand (not Plains-specific), desktop and phone (same Prompts and DomSurface). Opponent seat: unchanged; it sees identical card backs, so which back flies carries no information.

Evidence: (1) fixture hand-pair-twin (board hand-pair, new click grammar 'last Plains' = the non-offered twin) records click ON(2) answered and the next view moving slot 0 — the bug reproduced. (2) Browser check 'of two Plains in hand, the one dragged out is the one that plays' (ui/scripts/kept-pointer.mjs) fails with the trade disabled and passes with it. (3) stage-prompt.test.mjs: drag and click twin tests fail before, pass after; a non-twin control. (4) Filmstrips of drag and of hover+click in the fixture: the handled Plains flies from where it was let go/raised to the battlefield, the other Plains never moves, the fan closes up. arena-pixel-match not run: the motion (land flight, fan close) is the existing play-a-land motion unchanged; only which node takes it changed. Limitation: a pick of identical permanents on the battlefield (e.g. targets via with_stand_ins) still shows the engine's twin; trading battlefield positions would make the row re-sort visibly, and no report asks for it.
