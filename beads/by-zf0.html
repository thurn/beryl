Description

Auto-save the game in progress and resume it on launch, in a save format that a build a year from now still plays correctly.

What exists

  • Each game's replay (seed, decklists, the choice log) is written whole at every human decision and at the end, to ~/Library/Application Support/ca.thurn.beryl/replays/<start>-<seed>.json (beryl_session session.rs run, ReplayFile::save in replay.rs; the directory comes from beryl_app games.rs).
  • Game::from_replay (game.rs) replays a file to its open decision and returns the live view. Only the session tests call it; the app never resumes.

Why the current format is fragile

The log is Entry::Choice(u16): an index into the open decision's candidates. Randomness comes from the seed (rng.rs, architecture §14). Neither the rules nor the deck changing, many engine changes still break an old file: a card bug fix changes the candidate list, a reordered candidate list or an added/removed prompt shifts every later index, and one extra RNG draw changes every shuffle after it.

Design (decided)

A save depends only on what the rules of Magic define:

  1. Semantic actions. Each choice is recorded by what it is (cast this card, target that player, attack with this creature), and replay picks the candidate that matches. beryl_scenario's Action/Pick vocabulary and answer() (run.rs) already do this for scenarios and are the starting point.
  2. Reveals, not the seed. Randomness is recorded by its outcome: the identity of each hidden card at the moment someone learns it (draw, look, reveal, search; the knowledge chokepoints of §13), coin flips, random discards. A shuffled library's order never matters until a card of it is revealed, so replay binds the recorded card to the slot then, as determinization (observation.rs) already deals unknown cards into unknown slots.
  3. Turn-start checkpoints. A rules-level board at each turn start, to check replay against and to rebuild from when replay can't go on.
  4. Versioned format with migrations, and a frozen corpus of saves that tests hold playable, with perturbation tests (another RNG derivation, reordered candidates, other object ids) proving the format doesn't secretly depend on them.

Rejected: a full state snapshot. It would carry engine internals (effect records, ability indexes, object ids, the State layout tuned for speed), which change often; every change would need a migration or break old saves, and a broken snapshot can load quietly wrong.

Order

The children run in sequence (one lane): resume first, on today's format, so auto-save and resume work now; then the format layers; then the corpus and the tests that pin it.
