Close reason

Saves (v4) record each turn's board; replay checks it and rebuilds from the latest turn start, refusing when an effect lingers

Description

Part of the durable-saves epic (read it first). Depends on the reveals bead.

Record a rules-level board at the start of each turn, check replay against it, and rebuild from the latest one when replay can't go on.

Build

  • A checkpoint: turn, active player, life totals, each zone's cards by name (library as a count plus the cards known in it), tapped, counters, damage, attachments, face-down state. Modelled on beryl_scenario's Setup / PlayerSetup / Permanent (lib.rs), which position() (run.rs) can already turn into a State; share the type rather than writing a second one (the semantic-actions bead moves that vocabulary).
  • Write one into the save at each turn's untap step.
  • On replay, compare each checkpoint with the rebuilt board; a mismatch is divergence and is reported with the turn and the first difference.
  • Rebuild: when replay stops (an illegal action, an unbindable reveal, a checkpoint mismatch), resume from the latest checkpoint at or before it. State that isn't on the board (delayed triggers, "until your next turn" effects, per-turn counts) must be either in the checkpoint or detected: refuse to rebuild rather than rebuild wrong, and say which effect blocked it.
  • The UI says nothing extra when a resume rebuilt from a checkpoint, beyond journaling it.

Tests

  • Checkpoints of a long seeded game match on replay.
  • A save with an action made illegal on purpose resumes at the turn start before it, with the board equal to the checkpoint.
  • A checkpoint taken with a lingering effect active refuses to rebuild.

Derek Thurn2026-11-08

Decisions and deviations: (1) Type not shared with beryl_scenario's Setup: Setup is const/&'static and Serialize-only for the oracle exporters, and by-zf0.2 settled that save vocabulary lives in beryl_session with its own rules-level names. The shared part is the engine's setup API (setup.rs: begin_before_turn, place_token, set_controller/sick/damage/impending/known, attach, set_exiled_until, add_emblem) that both arrange through. (2) The checkpoint is taken as the upkeep begins (the untap step has no priority, so the session first sees a turn there). A rebuild puts the board back just before the turn (turn-1 cleanup, cleanup_check set) so the engine begins the turn again and its upkeep triggers fire as before; the active player's permanents are untapped already, so untapping changes nothing. Non-active permanents' summoning sickness is recorded (sick). (3) State::off_board names what a rebuild would lose (effects, delayed triggers, permissions, sorceries-as-flash, anything on the stack or pending); stored as Checkpoint.lingering and refuses that rebuild. (4) The checkpoint comparison is canonical, not exact, because another-seed replay exposed slot ties: like permanents in another order, graveyard order, a noncreature's sick flag, and knowledge are not differences (commented on by-zf0.8, which owns those ties). Rebuilds restore all of them exactly (every_board_rebuilds_as_it_was asserts equality). (5) Format version 4; ReplayFile.from holds the board a rebuilt save starts from; Entry::Checkpoint in the log. Undo past a turn start yields two checkpoints of a turn, matched in order.
