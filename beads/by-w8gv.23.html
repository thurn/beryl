Close reason

untap_up_to_lands untaps in battlefield order via State::in_game_order; test under every slot numbering; staging 9a2ab024

Description

Found by by-w8gv.5.6 (order-free sets) and left as it was for parity: the same class as the newest entry of docs/bugs.md (declared attackers tapped in slot order).

The bug

EffectCtx::untap_up_to_lands (rust/crates/beryl_engine/src/effect.rs, used by Teferi, Hero of Dominaria's +1 and Time Spiral) asks for up to N lands, gets the chosen set back as a Bitboard and untaps each in the candidate order (ascending slot): for slot in self.state.in_candidate_order(chosen) { self.untap(land) }. Each untap goes through event::set_tapped, so the order of the untap events, which the UI animates and a 'becomes untapped' trigger would follow, is decided by slot numbers. Slots are no order the rules can see: the deal and every shuffle put cards in them at random (architecture §14). The lands untap together (CR 701.26b, 'To untap a permanent, rotate it back to the upright position from a tapped position'; one effect untaps them at once), so like the attackers of CR 508.1f they should go in battlefield order.

The scenario that shows it

Teferi, Hero of Dominaria on P0's battlefield with a tapped Plains and a tapped Island (different cards, so the events can be told apart), entered in that order. P0 activates +1, and at the end step chooses both lands. Watch the events (beryl_scenario::watch walks with Slots::Dealt; walk takes the numbering) under each of Slots::ALL: with the decks' slots reversed (Slots in beryl_scenario/src/setup.rs) the two untap events name the lands in the other order. The existing scenario '+1 draws, and at the end step untaps up to two lands' (beryl_cards/src/azorius/teferi_hero_of_dominaria.rs) untaps two Plains, which are alike, and every_card_has_scenarios_and_they_pass compares positions, not events, so nothing catches it today.

The fix

Untap the chosen lands in battlefield order (walk State::battlefield() and take those in the set, as combat::finish_attack and interpret/run.rs's each_permanent do; prefer one shared helper to a third copy). The comment at the site names this bead: remove it. Add the docs/bugs.md entry (AGENTS.md, Conventions). Check that the frozen save corpus and rollouts_never_change still hold: events are not choices, so they should.

Files

rust/crates/beryl_engine/src/effect.rs (untap_up_to_lands), rust/crates/beryl_engine/src/combat.rs (finish_attack, the pattern), rust/crates/beryl_engine/src/interpret/run.rs (each_permanent), rust/crates/beryl_cards/src/azorius/teferi_hero_of_dominaria.rs and blue/time_spiral.rs (scenarios), rust/crates/beryl_scenario/src/run.rs (watch, walk), docs/bugs.md.

Acceptance criteria

A test untaps two different lands with one effect and sees their untap events in the order the lands entered the battlefield under every numbering of Slots::ALL; it fails on the code before the fix; untap_up_to_lands no longer walks the candidate order; docs/bugs.md has the entry; cargo test for the workspace passes, including the corpus replay and rollouts_never_change.
