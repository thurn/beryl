Close reason

b3d links no engine or cards (11 MB, was 108); edit-to-output median 2.5 s, no edit 1.1 s; recorder is beryl_record's record program

Description

Symptom: after a one-line edit to a function body in beryl_scene, just b3d tree verbs-zones --at 1500ms takes a median of 8.5 s at load ~54 (target 3 s, docs/beryl-3d.md "Edit-to-output time"), and about 4.5 s with no edit at all.

Why (measured on 2026-11-15 by by-q44s.1.20):

  • macOS checks every newly written executable before its first run, in time that grows with its size: 0.2 s for an empty C program, 3 to 4 s for the 108 MB target/debug/b3d. Cargo copies the binary into target/debug (a new inode) on every build, even one that changed nothing, so every just b3d run pays this. Running target/debug/b3d a second time takes 0.4 s.
  • b3d is 108 MB because it links the engine, the rules and every card. It reaches them through beryl_session (rust/crates/beryl_session depends on beryl_engine, beryl_cards, beryl_search, beryl_table...), whose protocol types beryl_scene needs, and through beryl_cli, the recorder that beryl_inspect::recordings::open calls when the recordings pack is missing (pack::ensure with recorder::Cli).
  • The rebuild itself (beryl_scene, beryl_inspect and the link) takes about 4.4 s at load 60; uv and the tools package take about 1 s.

What to do:

  1. Move the protocol types beryl_scene and beryl_inspect read (beryl_session::protocol, script, prompt, ipc::FixtureMessage, GameUpdate) into a crate of their own in the main workspace that depends on no engine crate, with beryl_session re-exporting them so the main workspace does not change. Regenerate ui/src/generated/protocol.ts if ts-rs paths move.
  2. Run the recorder as a separate program: b3d without a beryl_cli dependency; when the pack is missing it says so with the command that builds it, or just b3d (tools/src/beryl_tools/beryl3d/cli.py, run_b3d) builds and runs a record binary first. just b3d gate and the tests keep working.
  3. Re-measure with the same method: the five-run loop described in the doc section, with the load beside each run, and update the table.

Files: rust/crates/beryl_session, rust/beryl3d/crates/beryl_inspect/src/{recordings.rs,pack,recorder.rs,main.rs}, rust/beryl3d/crates/beryl_scene/Cargo.toml, tools/src/beryl_tools/beryl3d/cli.py, docs/beryl-3d.md.

Acceptance criteria

target/debug/b3d links neither beryl_engine nor beryl_cards (cargo tree -p beryl_inspect -e normal --bin b3d shows neither); the edit-to-output median and the no-edit time are re-measured and in the doc table; at or under 3 s, or the bead says what stops it; just b3d lane passes.

D
Derek Thurn2026-11-15

Decisions: (1) beryl_protocol depends on beryl_card, beryl_kernel and beryl_table, not on beryl_rules/engine/cards. The kernel holds the state enums the protocol mirrors (MulliganStatus, Reason, StallReason, Stops), so the From impls stayed beside the types with no call-site churn; the kernel is no rules code and the linker drops what b3d does not reach. The one impl on a rules type, From<NextStop> for PassTo, became the private fn wire_pass_to in beryl_session's protocol/decide.rs. StartRequest::game became beryl_session's private requested_game. ui/src/generated/protocol.ts is unchanged (its test passes). (2) The recorder is beryl_record's 'record' program. b3d exits 3 when the pack is missing (recordings::MISSING), and just b3d runs record and retries; cargo-test, gate and the VM fragments script run record first. (3) Not in the bead: just b3d now runs the linker's binary in target/debug/deps instead of cargo's copy, which is a new file on every build. That copy's first-run macOS check cost 1 to 9 s per command under load even at 37 MB. Results: b3d is 37 MB (was 108). Edit-to-output median 6.3 s (load 77-83), no edit 3.1 s (load 73-79), in the doc table. What stops 3 s: the compiler (beryl_scene, then beryl_inspect, then the link: 6 to 11 s timed alone at load 36-40) plus the one macOS check of each newly linked binary.
