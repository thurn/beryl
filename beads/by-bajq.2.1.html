Description

What is wrong today

static_ability::applied refuses any static ability that affects more than its own permanent or the one it is attached to (Unapplied::Affected), and any "as long as" that reads a layer result (Unapplied::Condition). layers::recompute builds one list of every effect, sorts it by layer and timestamp and applies it, so what an effect applies to is settled before any layer has run. "Creatures you control get +1/+1" cannot be played.

What to build

Plan: Designs 2, the loop at its head and "Sets"; decision R5. This bead builds the structure the rest of the group fills in.

  1. recompute runs one layer at a time: 2, 4, 6, 7a, 7c today, with room for 3, 5, 7b and 7d. At each layer it begins the static abilities whose first layer this is, then applies that layer's effects in timestamp order, finding what each applies to against the results so far.
  2. Objects::All { zone: Battlefield, filter } is a legal LayerSpec::affected. The filter is read by layers::passes against the Derived rows, for the controller of the permanent with the ability as layer 2 left it. Filter::Tapped and the mana-value filters read the object, which no layer changes.
  3. A condition that reads the game (Condition::Compare of a count of permanents, Condition::Is) is read the same way as its layer applies.
  4. The fast path stays: with no static layer ability on the battlefield and no layer entry in the Effects store, the results are the base values. Find the first with a bitboard the table gives (the cards with a static layer ability) so the check is one AND.
  5. The list of effects is as long as the effects are many, whatever a set's size, as it is for a locked-in set today.
  6. The reference recompute (beryl_rules/src/reference.rs) is kept honest: it must stay an independent, slow implementation of the same rules.

Glorious Anthem ("Creatures you control get +1/+1."), the first static ability over a set. Its scenarios include a creature entering and leaving under it and two Anthems.

Derek Thurn2026-11-14

Decisions so far: (1) The recompute keeps one list sorted by (layer, timestamp, order, position), which is the per-layer loop of the plan: every layer-L effect applies before any layer-L+1 effect. A static ability on This/AttachedTo with a base-only condition is settled in the scan as before; one over Objects::All{Battlefield} or with a condition that reads layer results (Condition::Is(This, f), Compare of Count(All{Battlefield, f})) is listed as Target::Static(position) and finds its set/condition in apply::static_members when it comes up. (2) No FaceFacts/bitboard fast path was added: outlining the per-ability listing (list_static) and the apply loop (apply_in_order) left the count 0.19% BELOW the staging tip, so the extra AND was not needed. (3) reference.rs check_layers was never an independent recompute (it reruns layers::refresh on a clone with the cache forgotten, which catches stale caches). I left it as is rather than write a second layers engine that every later G2 bead would have to keep in step; XMage/Forge scenarios are the independent check of layer rules. (4) The renderer drops 'all' for a static over permanents some players control ('creatures you control get +1/+1').
