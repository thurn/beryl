Close reason

Sweep replays failed steps at a newer staging tip and files only what still fails

Description

Symptom: the Beryl 3D sweep (tools/src/beryl_tools/beryl3d/sweep.py) filed about 45 beads under by-q44s on 2026-11-16. 14 of them closed as obsolete or already fixed on the staging tip (for example by-q44s.24, .31, .33, .36, .41, .44, .51, .60, .61, .62, .63, .65, .66, .73). Each one still started a session that had to rebuild and replay the step before closing it, at 5 to 60 minutes each.

Why: sweep.file comments on an open sweep bead that names the same check, but it files a new bead without checking whether the failure still happens on a newer origin/staging. Sweeps run for tens of minutes, and in that time another session often lands the fix (most often a gates.json re-pin; by-q44s.80 addresses the re-pin churn itself).

Proposed change: before filing, if origin/staging has moved past the swept commit, replay only the failed steps at the new tip, as slow CI does when it retests a newer tip before filing a Steward bead. File only what still fails, and log the rest as 'fixed on the tip'. Keep the replay inside the sweep's token class and lock.

Files: tools/src/beryl_tools/beryl3d/sweep.py (file, reproduce, run), tools/tests/test_beryl3d_sweep.py, tools/src/beryl_tools/nightly_failures.py.

Acceptance criteria

A sweep whose failed step passes at a newer origin/staging tip files no bead, and a test in tools/tests/test_beryl3d_sweep.py shows it.
