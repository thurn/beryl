Android: give the frame thread priority over search

Close reason

Android sets nice values per class: frame -10, search 0. Vulkan late share while searching 24.2% to 2.3-2.8%

Description

Read first: docs/beryl-3d.md 'Threads' (decision C9: search threads use every core at a lower scheduling priority than the thread that draws); rust/beryl3d/crates/beryl_host/src/threads.rs (the cfg(not(any(target_vendor = "apple", windows))) branch is a no-op, so on Android no class is applied); beryl_host/src/phone.rs (where interactive_thread is called on the frame thread); beryl_3d/src/session.rs and app.rs phone_live_feed (the session thread is spawned in Class::Default and the search threads inherit it); tools/src/beryl_tools/beryl3d/phone_search.py (just b3d phone-search).

Why. On Android, set_class does nothing, so the AI's search threads run at the same priority (nice 0) as the frame thread, and C9 does not hold there. just b3d phone-search --gles on 2026-11-16 (Mac load 20-48, software rendering) against mcts-hidden: Android Vulkan (llvmpipe) 1797 frames while searching, 24.2% late, against 131 frames while not, 13.0% late (1.86x, just under the 2x starvation rule); worst gap while searching 258.9 ms. Android GLES (SwiftShader) 69.5% against 51.2%. iOS Simulator (Metal) 0 late of 1976 while searching, where the QoS classes are applied.

Build: an Android branch in threads.rs that maps the four classes to setpriority(PRIO_PROCESS, gettid(), nice) with Android's values (Interactive: -8, THREAD_PRIORITY_URGENT_DISPLAY, or -4, THREAD_PRIORITY_DISPLAY, choose and say why; Initiated: -2; Default: 0; Utility: 10), and current_class reading getpriority back. A debug log line on Android saying the frame thread's and the session thread's priorities once each. A test on the mapping. Then rerun just b3d phone-search and compare the Android late shares with the numbers above.

Note: lowering priority below 0 for the frame thread needs no permission on Android for an app's own threads; check that setpriority succeeds in the emulator and log when it fails.

Acceptance criteria

threads.rs applies a class on Android and current_class reads it back; a debug log line in the emulator shows the frame thread above and the session thread at default; just b3d android-smoke passes; just b3d phone-search is rerun and its Android numbers are compared with the 24.2% / 13.0% baseline in a comment on this bead.

Interactive maps to nice -4 (THREAD_PRIORITY_DISPLAY), the value Android gives an app's own RenderThread, not -8 (URGENT_DISPLAY), which Android reserves for SurfaceFlinger. At -4 the frame thread's CFS weight is about 2.4x a nice-0 search thread's, and wakeup preemption favours it either way. Initiated -2, Default 0, Utility 10 (THREAD_PRIORITY_BACKGROUND). Logging goes to logcat tag Beryl3dThreads through ndk-sys's __android_log_write (std already links liblog). Deviation: android-smoke on staging panicked in beryl_scene lay_row from 9c38c8bff, so I added a guard for empty rows and filed the layout cause. phone-search lives on by-q44s.7.13's unmerged branch; I cherry-picked its two commits locally to measure and do not push them.

phone-search --gles reruns (Mac load 22-39, software rendering, against mcts-hidden; by-q44s.7.13's tool cherry-picked locally).

Finding: Android already had the frame thread (the app's main thread) at nice -10, the boost it gives a foreground app's UI and render threads. The session thread was started from it, so before this change the session and search threads inherited -10 too, level with drawing. The logcat line (tag Beryl3dThreads) shows it: 'thread 2888 (unnamed) is in class interactive at nice -10, from -10', 'thread 2946 (session) is in class default at nice 0, from -10', 'frame log ... utility at nice 10'. setpriority succeeds in the emulator. A first try with Interactive at -4 lowered the frame thread and measured 36.3% / 20.9% late while searching, so Interactive is -10 (and Initiated -4).

Final mapping, two runs:

  • Android Vulkan (llvmpipe): while searching 34 of 1472 late (2.3%), while not 4 of 106 (3.8%), worst gap 67.4 ms; second run 51 of 1809 (2.8%), while not 0 of 65 (0.0%), worst gap 96.3 ms. Baseline: 24.2% against 13.0%, worst gap 258.9 ms. The second run prints STARVED only because no idle frame was late.
  • Android GLES (SwiftShader): 280 of 1282 late (21.8%), while not 2 of 106 (1.9%), worst gap 166.3 ms. Baseline: 69.5% against 51.2%. The first GLES run's game ended after 6 s (24 frames) and says nothing. GLES draws through the host's SwiftShader, which runs alongside the emulator's vCPU threads at the same host priority, where guest nice values cannot help.
  • iOS Simulator: 0 late, as before.
