Description

Design and build the imperative stage (plan K25) far enough to draw any view with no motion and to run steps on a clock it owns, behind a URL switch. The first real motion is by-w8gv.21.14.

Read first: the epic by-w8gv.21 (the user's decisions, what was agreed with the CI track, the code map); docs/project-50k.md, Target architecture, Presentation (K22 to K31); docs/ui-conventions.md (generated from data/ui-conventions.json: edit the data). Then, in full, the findings comment on by-w8gv.21.3 (bd comments by-w8gv.21.3). It chose the mechanism and wrote the interfaces; build them as written:

  • The stage computes each node's pose from its own clock and writes style.transform and style.opacity itself, on nodes that carry will-change: transform, opacity. No CSS transition, no el.animate left to play, no motion animate() on the stage. The motion package stays as pure curve functions (spring, cubicBezier, mix).
  • StageClock: now, advance(ms), hold(), release(). Live, a requestAnimationFrame loop feeds it frame deltas, so Playwright's paused page.clock drives it unchanged (the harness pauses its clock by default, by-w8gv.20.2).
  • Stage: clock, idle(), settle(limit), step, pose(object).
  • Steps are sequenced inside the tick at their exact end, with the remainder carried into the next step; never on a promise (that started the next step 200 ms late in the probe).

Build, in ui/src/stage/ (new)

ui/src/game/Stage.tsx already exists and is something else: the 1600 by 900 frame scaled to the window. Leave it, and keep the new exports from clashing with it.

  • Clock: pure TypeScript, no DOM.
  • Model: one entry per game object, keyed as by-w8gv.21.8's script names objects (view slots are reused after a zone change: see cardId in ui/src/game/CardLayer.tsx). Its pose (position, scale, rotation, opacity, depth, face) is a function of stage time: a resting pose from the layout, or the running step's track. pose(object) reads the model, never the DOM.
  • Layout: an interface from a view to each object's resting pose and to the anchors motion needs (pile tops, stack places, life orbs, mana pools). Here, the desktop one, adapting layout() in ui/src/game/layout.ts (about line 1735; Placement and Layout at 118 to 150; stackPlace; PILES; STAGE) without copying it. layout.ts is 1,979 lines and by-w8gv.19.2's to split: put new code in ui/src/stage/.
  • Nodes: one persistent DOM node per object for the game's life, made and removed only by a step or a reset. The face inside is the existing skin, ui/src/components/Card.tsx: decide between React rendering each face into a stage-owned node and building the face's DOM once, by measuring 80 nodes, and record it. React never sets transform or opacity on a stage node.
  • Player: a queue of scripts; steps in order, grouped steps together; a step is a set of tracks whose durations come from the verb's values in data/ui-conventions.json (import the data as ui/src/cards.ts imports data/cards.json); a reset snaps. In this bead every verb may snap, plus one real track to prove the sequencing.
  • Switch: ?stage in the URL (ui/src/mobile/phone.ts reads ?phone the same way) makes ui/src/screens/Game.tsx (about line 618, <Board>) mount the stage board for the desktop layout. Default off; without it nothing changes.
  • Test hook: window.berylStage, the Stage interface, when navigator.webdriver (as window.berylShown in ui/src/game/playback.ts).

Decisions and measurements (stage core)

Code: ui/src/stage/ (clock.ts, pose.ts, table.ts, layout.ts, stage.ts are plain TypeScript with no DOM; desktop.ts, dom.ts, Faces.tsx, StageBoard.tsx, switch.tsx, timing.ts, stage.css are the browser side). Tests: ui/scripts/stage.test.mjs (node --test, 13 tests, 0.1 s).

Faces: React portals from one root (measured)

80 faces of the late-game fixture's cards, headless WebKit (Playwright 1.64), 1600x900, load average 4 of 18 cores, each strategy in a fresh page, min / median of 15 rounds in ms (WebKit rounds performance.now to 1 ms), a forced layout included:

  • One React root, a portal into each stage-owned node: mount 25 / 27, change all 80 records 4 / 5, change one 0 / 0.
  • A React root per node: mount 37 / 42, all 4 / 5, one 0 / 0.
  • The face's DOM built once as markup (renderToStaticMarkup into innerHTML): mount 4 / 5, all 4 / 5, one 1 / 2.

Chosen: one root with portals. Markup mounts five times faster, but a mount happens once a game (a reset), and it costs what React does on every change after; it also drops what the skin does in hooks and effects (the art arriving late in useFace, the text fits, the counter pop) and pulls react-dom/server into the app. A root per node is slower to mount and loses context (MotionConfig, the stage width). Faces are memoised on the record's and the dress's identity, which the stage keeps when nothing in them changed, so motion never re-renders a face: a test counts the notifications.

What differs from the bead's text

  • Pose is x, y, width, rotation, skew, opacity, depth, face. Width (the frame's drawn width in stage pixels) stands for the bead's scale: a hand frame (160) and a battlefield frame (128) have different scales for the same size on screen, and the oracle wants peak size. Skew is the table's lean.
  • The switch is ui/src/stage/switch.tsx, a Board that picks the stage's board or the old one; Game.tsx changes one import. Game.tsx is on the file-length allowlist at 1,189 lines and may not grow.
  • Stage nodes keep the old layer's class names (card-el, card-el-<look>, in .card-layer) beside stage-node: the skin's styles and the shots' audits (screenFaults, crowdedControls) go by them, and the epic says those audits stay.
  • The "no CSS transition or animation on any stage node" test is a generic audit, stageFaults in ui/scripts/capture.mjs, run by every shot at all three window sizes (errors prefixed stage:), not a scripted check. stage.css also forces transition and animation off on .stage-node. I checked by hand that the audit reports an injected transition and a running Web Animation.
  • Verb durations stay null in data/ui-conventions.json: none is measured from Arena yet, so live every verb snaps. The one real track is the glide (any entry whose resting place a step moved goes there over the step's duration); the tests give verbs durations themselves. timing.ts reads duration, delay and stagger as stage milliseconds; a curve's number has no meaning yet (linear).
  • At a script's end the stage takes the view whole, table included. Replay equality is the session's check (by-w8gv.21.9); the stage does not compare.
  • The life orbs are drawn (from the stage's table, so a count step shows) because screenFaults checks nothing on a page without [data-life]; the rest of the chrome is by-w8gv.21.16's.

Verified by hand (scratch scripts, not committed)

  • Every card's box, depth, zone, name and look classes on the stage equal the old board's, for the fixtures combat-blockers, late-game, stack-counter, first-target, opponent-turn and game-over-jace (38, 82, 32, 80, 24 and 15 cards; nodes = objects in each).
  • In the browser, a 600 ms step then 400 ms back reads the same pose at 800 ms in ticks of 16, 100 and 1000 ms, the node's style.transform is the model's pose, a held clock does not move in 100 ms of wall time, and released it gained 499 ms in 500.
  • A tap step and a life count step show within two frames (the skin's tap spring is off under the stage).

For by-w8gv.21.14 and the rest of lane:stage:

  • No script is on the wire here: StageBoard takes a script prop and switch.tsx passes only the view, so today every view is a reset. Pass by-w8gv.21.9's field through switch.tsx. Game.tsx still paces views with playback.ts's beats under ?stage; that goes at the cut-over.
  • How a step plays: at its start the act is applied to the table, the layout is run again, and every entry whose resting place moved glides there for the verb's duration from wherever it is (stage.ts #begin, #lay). A verb of its own (emerge, vanish, flip, strike) is a track of its own: put it where #lay makes the glide. A step with no duration snaps but leaves a glide under way running to the new resting place.
  • Nodes are made and removed by what the layout rests after a step, at the step's start. A vanish that takes time must keep its node until the step's end: steps have no end hook yet (ends are implicit: a track clamps to rest), so add one there.
  • A tapped permanent is drawn by the skin from its record (Card's tapped), not by the pose: Faces.tsx turns the skin's own tap spring off with MotionConfig reducedMotion="always". A tap verb with a track needs the turn in the pose (the combat chevron sits in the card's slot outside the turning frame, which is why I did not just rotate the node).
  • While it glides a node is drawn ALOFT (900, CardLayer's FLYING_Z) over what rests, and shows its destination's face from the start.
  • A hand lies in slot order (desktop.ts NO_ORDER): the table keeps no order of arrival.
  • Abilities on the stack have a number in the table (table.ts) and no node; spans (point, mark, lift) change nothing and draw nothing; anchors() is written and unused.
  • settle() cannot yet meet a script that waits on the player: nothing does.
  • Verb values are null in the data, so nothing moves live. Fill a verb's duration there (milliseconds) and it glides.

A reviewer should check: the sequencing rule (a beat begins at the stage time the last ended, #tick; the tests fail if it begins at the tick's end instead, I tried); play()'s reset path while a script is under way; table.ts against script/mod.rs's replay rules (by-w8gv.21.9's Rust replay is the authority, and nothing compares the two yet); that stage nodes reuse the card-el class names on purpose.
