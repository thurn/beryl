Cards, Machine, CI, Changes and Findings views with change marks on trends; pushed 1c6f5bb6

Description

Add the page's other five views and the marks on trend lines, each a rendering of a query that already exists.

Design sections: "The page", and the result examples under "CPU accounting", "CI accounting", "Rework", "Efficiency changes" and "Findings".

What to build

  • Cards: cost per card by tier with direct cost and rework side by side, and the parallel capacity estimate.
  • Machine: cores in use over time, saturation, queued core hours by command kind, shared CPU by context and kind, and the tool's own cost.
  • CI: the tree script, check lane, family, check, opened level by level, with CPU by kind of process, the fast check per push and the cost of failures.
  • Changes: each change with its trend, mark and before and after medians.
  • Findings: the ranked list; opening one shows its evidence query's result in place.
  • Marks on every trend line that has an efficiency change, with the label and medians on hover.
  • The same quiet rules, colours and copy-command control as the first screen. Reuse its components; add no new kind of chart unless a view cannot be read without it.

Look at every view with just efficiency shot at desktop and narrow widths, in both appearances, before closing.

Shared context

  • The design is docs/efficiency-dashboard.md. Read the sections named above before anything else; the rest can wait. The decisions taken with the user are in the epic, bd show by-ig5e.
  • The dashboard's code is the separate Python project in efficiency/ (package beryl_efficiency, standard library only, pyre strict, black). It imports nothing from tools/ and nothing imports it. Read efficiency/AGENTS.md first once it exists.
  • Tests use small synthetic sources built in the test itself or kept under efficiency/tests/. The repository is public: never commit a real transcript, session record or command line from this machine.
  • Real data exists only on the main Mac (host jarvis). Where the acceptance criteria name a check against real data, run it there; if this session is on another machine, record that the check was not run in a comment on this bead and close on the tests.
  • Collection must stay free for agents: no hook, wrapper or prompt text may be added to any session, and ingest must never run inside another command.

Acceptance criteria

Tests: each view renders for the fixture and the empty store, and its numbers equal its query's JSON; a trend with a change on it carries a mark with the change's label. On the main Mac, shots of the five views show real data with no overlapping or clipped text at 1280 and 420 pixels wide, and the CI view's oracle check lane opens to Forge and XMage.
