Fast check's Rust lane waits on a small fixed CPU lease

  • Description
  • Comments9
  • Changelog

Description

Symptom

The fast check's Rust lane is the critical path of every push that touches Rust, and it is mostly waiting. On 2026-11-14 between 14:20 and 16:45 UTC, six fast checks with a Rust change took 376-1,083 s from start to end of the rust lane (runs.jsonl, script=check, span of the lane's records per commit). The other lanes finished within 40-275 s.

In those runs rust:clippy took 109-259 s wall but only 61-187 CPU-seconds, and the tests step (cargo build of the test binaries, then nextest) took another 250-830 s. Their test runs summed to 92-228 s. This happened even when the machine was nearly idle: e5127d1e ran at load 6, and its clippy took 259 s wall for 135 CPU-seconds. A clippy with a fully warm cache after a kernel change takes about 15 s wall on its own.

The merge queue (.worktrees/.merge-queue, [push] queue = true) runs one batch at a time, so this time adds directly to every queued push. At 16:40 UTC four enact push processes had been waiting 22-25 minutes.

Likely cause: leases fixed at the step start

tools/src/beryl_tools/tokens.py hands each heavy step a lease of CPU tokens when the step starts, and passes its size to cargo as CARGO_BUILD_JOBS. The Rust lane starts at the same time as the browser lanes, motion, oracle and scripts, so clippy gets a few tokens. It keeps that small -j after the other lanes end about 40-270 s in. Only the tests step tops up its lease (top_up), and only once its build is done, so the test build is starved too. Wall time running at about twice CPU time at low load fits this cause.

This has not been confirmed: runs.jsonl does not record each step's lease size or the time it waited for tokens (Lease.waited exists but is not logged).

Work

  1. Log each step's lease size, its wait for tokens and any top-ups in runs.jsonl (the step records written by checks.py/step_runner.py). This gives later runs the data.
  2. Give the critical-path step the cores. Options, cheapest first: start the rust lane's clippy and test build before the browser lanes take tokens; give cargo steps a lease sized for the whole pool share their class may take (cargo idles threads itself when other work holds the cores, while the token count only caps it); or run cargo under the jobserver for the length of the build. Record the choice on this bead.
  3. Measure the same six-run window again: rust lane span and clippy wall/CPU ratio in the fast check.

Done

In the fast check, clippy's wall time is within 1.3x of its CPU-seconds at load under 10, and the rust lane after a beryl_kernel change ends within 150 s at load under 15.

Found and fixed the "10x CPU" half (0f4d8325, fix: prune crowded targets before each check).

Cause: the merge queue's tree (.worktrees/.merge-queue) is never removed, and warm.prune only ran when Enact removed a worktree. Its target/debug/deps had grown to 604,302 files, 597,465 of them codegen-unit objects (.rcgu.o) from earlier builds, and the target held 93 GB. Every rustc invocation lists deps/ to find the crates it depends on, so the time went to the kernel, not to compiling.

Measurements on 2026-11-14, same commit, load 13-21, after touching crates/beryl_card_build/src/printed.rs. Every card crate build-depends on beryl_card_build, so this re-checks 59 units:

  • queue tree before pruning: 130 s wall, 62 s user, 329 s sys, 14.5M involuntary context switches
  • fresh worktree: 12 s wall, 18 s user, 12 s sys
  • queue tree after pruning (deps/ at 16,817 files, target at 13 GB): first run 53 s (it rebuilt some evicted units), then 14 s wall, 21 s user, 17 s sys

Fix: checks.run calls caches.tidy_target, which runs warm.prune on the checkout's target when any deps/ folder holds over 50,000 files (CROWDED_DEPS). It holds <profile>/.cargo-lock, so it skips while a cargo build is running. Counting the files takes milliseconds, while a full prune takes about 2.7 s even on a fresh worktree.

Other findings, all small:

  • beryl-mobile is dirty on every build: its build script writes crates/beryl_mobile/permissions, which it also watches with rerun-if-changed ("has changed 1s after last build"). This costs about 3 s.
  • beryl_app re-checks on every commit because its build script watches .git/worktrees/<tree>/HEAD.
  • The machine had 18.1 of 18.4 GB swap in use and about 140 MB free, which inflates system time everywhere.

Still open on this bead: the small fixed lease, where wall time runs at 2-3.5x CPU. Measure the fast check's clippy over the next few queue batches to see how much of that gap is left now that the system time is gone.

2026-11-15 run (CI structure review): much of the wall-over-CPU gap in the fast check's rust:clippy was lock waiting, not the lease. In runs.jsonl for 14:00 UTC 2026-11-14 to 14:00 UTC 2026-11-15, 86 of 176 rust:clippy runs are recorded as failures, and 69 of those ended 150-210 s after the run started. Their recorded CPU was 0.06 s (median), so they were killed at the 180 s hard limit while waiting on Cargo's lock on the target directory. The script and browser lanes held that lock while they built beryl_cli a second time (cargo build/run -p beryl_cli: dev profile, different feature set). 61448988 makes those builds share the tests step's units (paths.CLI_BUILD), so clippy no longer queues behind a duplicate chain build. What is left for this bead is the lease itself. Measure it again on runs after 15:40 UTC 2026-11-15, which have this change. Note also that a step killed at the hard limit is logged with outcome 'fail' and about 0 CPU-seconds (the killed child's rusage is lost), which makes kills look like failures in the run log.

Data from 2026-11-16 (CI structure run, 06:05-07:00 UTC). In $BERYL_CACHE/cpu-tokens/leases.jsonl after 04:30 UTC, the 'agent'-class leases for the Beryl 3D program b3d (the interface tests and timeline playback) got a median of 1 core of the 12 they asked for and held it for a median of 64 s. Direct measurement: 'b3d test' (every interface test, about 150 CPU-seconds) took 11-13 s run without a lease and 153 s inside a 1-core lease granted after a 47 s wait, at load 15-20. A program's lease is sized when it starts and never grows (tokens.run_program), so in a fast check the beryl3d-interface lane's test step cannot finish inside the 180 s limit whenever it starts while other lanes hold the pool. This is now the main remaining cause of Beryl 3D fast-check kills, after 13ac73cc5 removed the extra b3d build that held the build lock. Suggested direction: let run_program top up its lease while running (the program sizes its threads once, so start it with the pool share its class may take, or re-check before each test batch), or give the push class a floor of cores per program step.
