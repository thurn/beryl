Close reason

ci query: tree by script/lane/family/check, verdicts, flake cost, oracle engines, CPU by kind; run log worktree field; pushed a8e91472

Description

Show what CI costs and what each part of it buys: CPU by script, check lane, family and check, with catches, stale failures, flaky failures and misses beside the cost, and which kind of process the CPU went to (compiling, tests, the Java oracles, browsers).

Design sections: "CI accounting" up to and including "What kind of process the CPU went to".

Existing pieces

  • The run log, <cache>/ci/runs.jsonl, written by tools/src/beryl_tools/runlog.py: one line per check per run with time, host, commit, tree, script (check, ci, the sweep, the nightly, bisect), lane, check, outcome, seconds, cpu_seconds, load, chosen. The file was 770 MB on 2026-11-15: read it by offset, in a stream, and store one row per check per day per script, never per line.
  • Verdicts: tools/src/beryl_tools/verdicts.py. Each check that has failed has a closed bead labeled ci-check, and each failure's verdict (catch, stale, flaky, mixed, miss) is a comment on it. Read that module for the comment format.
  • tools/src/beryl_tools/check_value.py (just ci-value) already computes catches per CPU second and groups checks that always fail together. The dashboard must agree with it; read how it estimates CPU for lines with no cpu_seconds.
  • Check names: rust:<binary>::<test path>, oracle:<card>/<scenario>/<xmage|forge>, ui-test:<title>, verb:..., shape:..., shots:<name>, script:<card>/..., motion:<verb>/<layout>, and <lane>:<step> for a step that reports no checks.

What to build

  • In tools/ (a separate small commit): the run log gains a worktree field, the name of the checkout directory the run was made in, with a test in tools/tests/.
  • The checks table and its ingest, with failures counted by verdict. Also one row per fast-check run per check lane (worktree, start time, wall seconds, CPU seconds, outcome), which the next bead joins to pushes; no other individual run-log lines are kept.
  • The tree script, check lane, family, check, with the figures of the design at every level: CPU seconds, runs and skip share, the four failure counts, CPU seconds per catch ("never caught anything" with the date of the first run where there is none), and flake cost (the reruns' CPU and wall seconds, plus the cost of the sessions that worked the beads labeled flaky-check for that check).
  • The oracle check lane split by engine, and into scenarios run against scenarios skipped because an earlier run recorded their outcome.
  • CPU by kind of process per script and check lane, joining the cpu table (the sampler's contexts for slow CI and the fast check) by minute. This bead needs the CPU bead's table; if it has not landed, build the tree first and add the join after it.
  • The ci query with --script, --lane and --family, and metrics slow-ci.cpu-seconds-per-run, slow-ci.runs-per-day, fast-check.cpu-seconds.

Shared context

  • The design is docs/efficiency-dashboard.md. Read the sections named above before anything else; the rest can wait. The decisions taken with the user are in the epic, bd show by-ig5e.
  • The dashboard's code is the separate Python project in efficiency/ (package beryl_efficiency, standard library only, pyre strict, black). It imports nothing from tools/ and nothing imports it. Read efficiency/AGENTS.md first once it exists.
  • Tests use small synthetic sources built in the test itself or kept under efficiency/tests/. The repository is public: never commit a real transcript, session record or command line from this machine.
  • Real data exists only on the main Mac (host jarvis). Where the acceptance criteria name a check against real data, run it there; if this session is on another machine, record that the check was not run in a comment on this bead and close on the tests.
  • Collection must stay free for agents: no hook, wrapper or prompt text may be added to any session, and ingest must never run inside another command.

Acceptance criteria

Tests on a synthetic run log and verdict comments: daily rows aggregate correctly across an offset boundary; each failure is counted under its verdict; families are derived from names as in the design's examples; a family with no catch shows its first run's date. On the main Mac, just efficiency ci --since 7d reports the same number of slow-CI runs, the same total CPU seconds within 2% and the same catches per check lane as just ci-value --days 7; the oracle check lane shows Forge and XMage separately; CPU by kind of process shows an oracle line.

Real-data check on jarvis (store copy in a scratch cache, so the live store is not migrated ahead of staging): just efficiency ci --since 7d reports 446 slow-CI runs, the same as ci-value's 446 (distinct host and commit), and 1,253,664 CPU seconds against ci-value's 1,243,699 (sum of its runs' CPU, stand-ins excluded): +0.8%, within 2%. The oracle lane shows oracle:forge and oracle:xmage separately, and CPU by kind of process has an oracle line (with a Java split by engine). DEVIATION on catches per lane: they do not equal ci-value's, by definition. The dashboard counts each verdict under the script that recorded it (the design's tree puts script at the top), while ci-value credits a check with catch verdicts from any script and counts a group of checks that fail together once per commit. Example: rust has 3 slow-CI catches here and 39 in ci-value (36 are fast-check verdicts); oracle has 111 catch verdicts here and 78 in ci-value (grouped). The design's CI section now says so. Other choices: per-run CPU is a mean, since checks are kept added up per day; flake cost is one rerun per flaky failure at the check's mean (rerun lines are not marked in the run log); the oracle 'remembered' scenarios are estimated as lane runs x scenarios seen - played - skipped, since memory-skipped scenarios are not logged. First ingest of the 794 MB run log took about 70 s wall, 50 s CPU, once.
