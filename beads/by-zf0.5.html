Close reason

Saves migrate v1->v2->v3->v4 on load via migrate::CHAIN; breaks list data/save-breaks.json with policy

Description

Part of the durable-saves epic (read it first). Depends on the checkpoints bead.

A migration chain for old saves, and a recorded list of the breaks no migration can fix.

Build

  • format_version (added by the semantic-actions bead) drives a chain of pure functions, each upgrading one version on serde_json::Value, each with its own test. Loading always migrates to the current version first (ReplayFile::load or its successor).
  • The first migration, v1 → v2: replay the index-based file on the current build and re-record it semantically. It fails when the v1 file doesn't replay on this build, which is the reason v1 is fragile.
  • A breaks list, modelled on data/oracle-divergences.json: each entry names a save in the corpus, the step where it stops matching and why (CR citation when it's a rules fix), with the fixing commit. The corpus test (next bead) holds a listed save to its recorded step instead of to the end.
  • Policy, in a doc comment on the module: a change that breaks a save either adds a migration or a breaks entry, in the same commit.

Tests

  • v1 → v2 on the replays in the session tests.
  • A synthetic v2 → v3 (field rename) proves the chain mechanism, then is deleted or kept as a fixture of the mechanism, not a real version.
