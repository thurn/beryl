Beryl 3D lane runs its steps one after another past the 180 s limit

  • Close reason

Close reason

Landed in 6e9cce0dc and 58f2c989d. The beryl3d steps now run as four lanes at once: beryl3d (fmt, clippy in rust/beryl3d/target/clippy, source rules), beryl3d-tests (record, cargo-test, gate), beryl3d-interface (record, test) and beryl3d-timeline (record, timeline-parity). Builds in a checkout's Beryl 3D target go through cli.build, which waits on a per-checkout file lock before the cargo shim takes CPU tokens, so lanes waiting on another lane's build hold no tokens. Each step's first run-log record now has step_seconds and step_cpu_seconds. b3d export now runs on runner::each threads, which takes the slowest workspace test from 40 s to about 2 s. In the push's own fast check at load 25, the lanes took 11, 90, 59 and 70 s (load-adjusted) with nothing deferred. Two caveats: right after a rebase that changes Beryl 3D code, record still spends about 150 s compiling, and that can push the later steps past 180 s. The first cargo command in a fresh worktree also clones the cached target (fmt took 57 s), which by-3xpq's cache pruning should shrink. Reopen if kills, measured the same way, stay near half.

Description

Symptom: the fast check's beryl3d lane is now the lane most often cut off at the 180 s hard limit. In runs.jsonl it ran in 13 of the 20 fast checks between 00:30 and 02:10 UTC 2026-11-16 and was killed in 9 of them; over the 24 hours before, 49 of 130. Every killed push waits the full 180 s, and the killed steps go to the Beryl 3D sweep instead of being checked.

Cause: tools/src/beryl_tools/beryl3d/lane.py runs fmt, clippy, cargo-test, gate, test, scene-purity, lints-match, data-names and timeline-parity in sequence. Typical offsets from the check's start (beryl3d steps of fast checks since 20:00 UTC 2026-11-15): clippy ends at about 20 s; then 50-110 s pass with no whole-step record (the shared build in cli.SHARED_BUILD, record and cargo-test's nextest); gate takes 5-30 s; the interface test step takes 30-60 s; timeline-parity takes 20-65 s. These add up to more than 180 s at load 20-60.

Also missing data: a passing cargo-test or test step writes only its per-check records (b3d:*), never a whole-step record with seconds and cpu_seconds, so its time can only be inferred from gaps. Only killed runs record them.

Proposed: (1) run clippy in its own target directory (as 0fccd6d1 did for the main workspace's clippy) beside the shared build instead of before it; (2) after the shared build, run cargo-test's nextest, gate, test and timeline-parity as parallel steps or separate lanes, since none of them writes the build directory; (3) write a whole-step record for every step. Done when beryl3d kills in fast checks fall well below half, measured the same way.
