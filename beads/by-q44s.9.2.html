Close reason

b3d modules register their own COMMANDS; listing unchanged, cli.py 684 lines

Description

Several beads of this milestone add just b3d commands. Today every command is an entry of the one tuple COMMANDS in tools/src/beryl_tools/beryl3d/cli.py, which is 778 lines against the 800-line file-length limit, so the second bead to add a command would fail the check, and every bead would edit the same lines.

Change, in tools/src/beryl_tools/beryl3d:

  • New module command.py holding the Command dataclass, moved unchanged from cli.py (cli.py imports it from there; nothing else changes its fields).
  • cli.py builds COMMANDS as its own entries followed by the COMMANDS tuple of each module in a tuple MODULES declared just above it, in that order. listing, parser and main keep working on the joined tuple.
  • Move the four phone commands (ios-smoke, android-smoke, phone-search, ios-device, about lines 638 to 699 of cli.py) into a COMMANDS tuple in phone.py, and put phone in MODULES, so the listing keeps its order and cli.py loses about 60 lines.

A later bead adds a command by writing COMMANDS in its own module and adding one name to MODULES. Do not add any new command here.

Test in tools/tests/test_beryl3d_cli.py: listing() names every command exactly once, and the phone commands appear in it. Run: just test-py tests/test_beryl3d_cli.py tests/test_beryl3d_phone.py.

Acceptance criteria

just b3d prints the same listing before and after (diff the two outputs, put the empty diff in a comment); cli.py is at most 720 lines; just test-py tests/test_beryl3d_cli.py tests/test_beryl3d_phone.py passes; enact push passes.
