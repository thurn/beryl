How to write each bead

Whoever works a bead has nothing but the bead, the doc and the code. Write for that reader.

  • Decide everything that can be decided now. A bead never says 'choose', 'pick', 'find out whether' or 'in X or Y'. Where the answer needs a measurement, the bead says what to measure, the threshold, and what to do on each side of it.
  • Name the crate, the file and the function or type for every piece, and which crate each test goes in. Give exact versions for any new dependency.
  • Name the web interface's files that hold the behavior, and say what to take from each. Open each file yourself first and quote the function names: do not name a file you have not read.
  • List the tests by what each one asserts, and give the commands that run them.
  • Write acceptance criteria that a command can show true or false.
  • Say what the bead must not build, when a later bead builds it.
  • Keep a bead to what one session can hold: about 600 lines of new code, or one module.
  • Before filing, check the dependencies: no bead's Run: line uses a command that a bead it does not depend on creates. Run bd dep cycles.
  • The epic's rules 14 to 16 say what a worker does when a bead is wrong and when it is done. Do not repeat them in each bead.

What this milestone's beads must cover

Each numbered item is at least one bead. The indented lines are what that bead must say; add the function names you find when you read the code. The web interface's files named below come from a listing of ui/src on 2026-11-14 and from reading the headers of the stage's files; that code changes every day, so open each file before you quote it, and replace a name that has moved. Where an item says 'one bead each', file that many.

What exists when you start: everything on the table plays from both seats on the desktop layout, with one prompt bar, panels and glyphs in the flat layer. This milestone builds the rest of the flat layer and everything round a game.

  1. Design tokens, one bead. A new file data/design-tokens.json (described in data/AGENTS.md) holding every variable of ui/src/design/tokens.css; a generator in tools/src/beryl_tools that writes tokens.css and beryl_scene/src/tokens.rs; a check that both are current. This is one of the exceptions in the doc's 'Checks and isolation': it changes a file the web interface reads, so it is a bead of its own and its push runs the web interface's checks once.   2. The element tree in full, two beads: (a) reconciliation by name and position, grid layout, absolute positioning and anchoring to a table object; (b) scrolling lists with clips, transitions of an element's opacity and position as segments, focus, and keyboard shortcuts (ui/src/table/shortcuts.ts, bindings.ts).

  5. The prompt shapes, one bead each for: pick and zone; pile and split; order; pay; declare; yesNo, number and mode; catalog; divide. For each: read beryl_session/src/prompt/<shape>.rs for the state the session holds and ui/src/stage/PromptBar.tsx, Choose.tsx, Tray.tsx and Aim.tsx for what is drawn; build a screen function from the prompt's state; run the shape's recordings in ui/shapes.json from both seats under just b3d test, answering with the recorded clicks.   10. Beryl's drawn card frame, one bead: tiny-skia and swash in beryl_assets, from ui/src/components/Card.tsx and ui/src/design/components/card-frame.css, at both face sizes; a face with no scan shows it, and a late scan replaces it only while the table is still.
