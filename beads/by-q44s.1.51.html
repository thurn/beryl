Close reason

gpu gate builds from sources sent into the VM (source.py shared with counts); gate --gpu passes from a worktree; sweep --step gpu not run, other sweep in progress

Description

Symptom (expected on the first sweep that runs it): the Beryl 3D sweep's gpu step (just b3d gate --gpu, tools/src/beryl_tools/beryl3d/gpu.py, count_fragments) runs bench.vm_command(fragments_script(...), vm.NAME), which runs in the beryl3d-bench machine with --workdir set to the checkout's rust/ directory and then cd beryl3d. The machine mounts only the main checkout (bench.vm_ensure's --mount-only), and the sweep checks its commit out under $BERYL_CACHE/b3d/sweep/work (sweep.run_in_tree), which is not mounted, so the step cannot see the sweep's sources and fails or counts the wrong tree.

The instruction-count gate (just b3d gate --counts, tools/src/beryl_tools/beryl3d/counts.py) already solves this: counts.sources() lists the files the build reads, counts.measure sends them as a tar stream (--no-xattrs --no-mac-metadata, COPYFILE_DISABLE=1) into the machine and rsync -r --checksum --deletes them over $HOME/b3d-source, then builds there, all inside bench.locked. Factor that sending into a helper both gates use, and build the fragments example from $HOME/b3d-source (its own CARGO_TARGET_DIR is fine). gpu.py's script already holds bench.locked so it takes turns with the counts.

Acceptance criteria

just b3d sweep --step gpu passes on the staging tip (a tree outside the main checkout); just b3d gate --gpu still passes from a worktree; tools tests cover the shared helper.
