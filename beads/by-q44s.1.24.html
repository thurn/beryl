Description

Read first: docs/beryl-3d.md 'Timing a script' (the StepTiming and StepEffect records and the three changes; this bead is change 1). Then, in full: ui/src/stage/timing.ts (434 lines: caseOf, timingOf, effectsOf), the Timing record at the top of ui/src/stage/tracks.ts and its functions moverOf, draws, drawsToRead, meets and the constants STRIKE and CLOSED, namedBy in ui/src/stage/spans.ts, and the Effect type in ui/src/stage/effects.ts. On the Rust side: rust/crates/beryl_session/src/script/mod.rs (Script, Step, Subject), act.rs (Act), table.rs (Table, the model of the table a script changes, which the web's ui/src/stage/table.ts mirrors) and check.rs (how a script is replayed over a Table step by step).

Why. The web interface works out how each step of a script is timed. The owner decided on 2026-11-14 that the session does it instead and sends the result to both clients. This bead writes the rules in Rust and proves they give the same answer as the web interface's on every recording. Nothing plays the Rust result yet, and nothing under ui/src changes except the three constants named below.

  1. Constants to data. STRIKE.hit and STRIKE.poise (tracks.ts), CLOSED (tracks.ts) and BATCH_EXILE (timing.ts) are numbers in TypeScript. Add them to data/ui-conventions.json: "phases": {"poise": ..., "hit": ...} on the strike verb, "closes" on the vanish case ability finished, and "stagger" on the vanish case exiled. Change tracks.ts and timing.ts to read them from the JSON they already import, with the same values. Run just conventions and check docs/ui-conventions.md is unchanged or only gains these values.
  2. rust/crates/beryl_session/src/script/timing.rs:
    • StepTiming, StepEffect, Curve and Edge are already in this file (the timing types bead). Do not add them to Script yet.
    • Conventions: the verbs, cases and effects of data/ui-conventions.json, embedded with include_str! and parsed once into a std::sync::OnceLock.
    • case_of(act, found: &Table, beside: &[&Act]) -> Option<&'static str>, a port of caseOf, branch for branch, in the same order.
    • timing_of(act, found: &Table, before: Option<&Act>, beside: &[&Act]) -> StepTiming, a port of timingOf, rule for rule, in the same order, each rule keeping the web code's comment. after holds Subjects where the web has names: namedBy turns a Subject into a name, so keep the Subject.
    • effects_of(act, found: &Table) -> Vec<StepEffect>, a port of effectsOf.
    • time_script(script: &Script, before: &Table) -> Vec<StepTiming>: replays the script over a copy of before as check.rs does, calling timing_of and effects_of for each step with the table as that step finds it, and returns one entry per step in playing order. Every ported function's doc comment names the TypeScript function it ports.
  3. The proof, just timing-parity:
    • ui/scripts/timings.mjs (Node, no browser; it imports ui/src/stage/timing.ts directly, as ui/scripts/stage.test.mjs imports the stage): reads recorded fixtures as JSON, replays each view's script over the stage's Table (ui/src/stage/table.ts apply), and prints one JSON line per step: fixture, seat, view number, step number, and the web's timingOf and effectsOf results written in StepTiming's field names, with the curve as its name and each after name as the Subject it came from.
    • beryl_cli step-timings: prints the same lines from time_script for the same recordings. Use the recorder beryl_cli's fixture and specs modules already have.
    • tools/src/beryl_tools/timing_parity.py and the just timing-parity recipe: records every fixture in ui/fixtures.json and every card spec moment from both seats, runs both printers, and compares line by line. Numbers are equal within 0.001. It prints the first 20 differing lines with both values and exits nonzero on any.
    • Register it in tools/src/beryl_tools/checks.py as a fast-check lane that runs when ui/src/stage/timing.ts, tracks.ts, spans.ts, table.ts, rust/crates/beryl_session/src/script/ or data/ui-conventions.json changed, and describe it in docs/checks.md. Measure its wall time five times with the load beside each and put the numbers in a comment on this bead. If it does not fit the fast check's budget, do not cut recordings: say so on the epic, run it over the fixtures only in the fast check, and over everything in slow CI.
  4. ui/AGENTS.md: one paragraph under 'Source' saying that until the web stage plays the session's timing, a change to timing.ts must make the same change in beryl_session/src/script/timing.rs, and that just timing-parity fails otherwise.

Port, run the check, read its differences, fix the port, and repeat until it reports none. A difference is always the port's fault: never change timing.ts to match Rust.

Tests in beryl_session: case_of on one hand-built act for each case named in data/ui-conventions.json's verbs; time_script returns one entry per step for a script of three beats.

Run: just test-rust -p beryl_session; just ui-unit; just timing-parity.

Acceptance criteria

just timing-parity reports zero differences over every fixture and card spec moment from both seats, and is a fast-check lane; the three constants are read from data by both languages; the web interface's behavior is unchanged (just ui-unit and just ui-test verb: pass); Script and the wire format are unchanged.
