Description

Milestone 7b of Project 50k (docs/project-50k.md, "Card pool pipeline": "Oracle exporters derive each card's translation from its effect data"; Acceptance: the card-names allowlist is empty outside the expert system and the per-deck overlay, and no source file is over 800 lines). K16: XMage is a test oracle. Nothing from its code becomes card data or design.

Today

tools/src/beryl_tools/xmage.py is 1,080 lines (the one entry left in data/file-length-allowlist.json) and holds 56 card names (data/card-names-allowlist.json), in the tables at lines 98-223: ABILITIES, MANA_ABILITIES, MANA_CHOICES, CAST_QUESTIONS, OVERLOADS, TRIGGERS_FIRST, FORCED_SEARCHES, TARGETS_IN_CAST, ASKED_FIRST, MAY_CHOOSE, UNLESS_PAYS, CHOICES_AS_TARGETS, SEARCHES, SCRIES, TAKES. Each has a comment saying what difference between Beryl's questions and XMage's it encodes; class Exporter (line 309 to 977) reads them at about 20 sites (grep -n "ABILITIES\|MANA_\|CAST_QUESTIONS\|OVERLOADS\|TRIGGERS_FIRST\|FORCED_SEARCHES\|TARGETS_IN_CAST\|ASKED_FIRST\|MAY_CHOOSE\|UNLESS_PAYS\|CHOICES_AS_TARGETS\|SEARCHES\|SCRIES\|TAKES" tools/src/beryl_tools/xmage.py).

What to build

  1. Replace every name-keyed table with a rule over the dump's card description. Examples of the rule each becomes: a loyalty ability's XMage text starts with its loyalty change ("+1:", "-3:", "0:"); an activated ability's with its cost rendered in XMage's order ("{T}, Sacrifice", "{2}, {T}: Draw a card"), or its keyword ("Cycling", "Crew 5"); a land with one mana ability taps by "{T}: Add {W}" and one with a choice leaves the payment to XMage; a card with overload is cast as "<name> with overload"; an alternative cost is the choice "Cast with <Keyword>", an optional one a yes or no; a resolving ability that scries, searches, or looks-and-takes uses the queue the table's comment names. Where XMage's text for an ability cannot be built from the cost and keyword, fall back to the ability's paragraph of Oracle text from the store (the dump or card_store.py has it), which is what XMage's own rule text starts with for most cards.
  2. Where no rule over data reproduces a table entry, the scenario is reported as unsupported through data/oracle-exporter-gaps.json (read its use in oracles.py and its entries first), with the gap named by mechanism, never by card. Count the scenarios that pass in XMage before and after: none may be lost except those you list on the bead with the mechanism that blocks each. Losing more than five scenarios of the 47 cards' hand-written ones is a sign the dump is missing a fact: add it to the dump (the previous bead's code) rather than accept the gap.
  3. Split the file under 800 lines by responsibility (for example the test-method writer and Java rendering, the position tracking, the translation of answers), each module under 800 lines; delete its entry from data/file-length-allowlist.json and its count from data/card-names-allowlist.json (python -m beryl_tools.checks card-names --shrink lowers counts; an entry at zero is removed). xmage_classes.py and BerylScenarioTest.java stay.
  4. data/oracle-divergences.json is keyed by card and scenario and is data, not code: leave it.

  • Need not read: forge.py, the Rust crates (the dump's shape is in the previous bead's handoff), the UI.
