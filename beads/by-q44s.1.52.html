Close reason

Fullscreen on macOS now a composed window that holds 120 Hz under load; shared rate step-down rule with test; frame log reports chosen rate

Description

Symptom: on the owner's 120 Hz ProMotion Mac, the desktop app's frames were often shown at 60 Hz. In the frame-delivery runs of 2026-11-15 (docs/beryl-3d.md, Measurements), fullscreen under load had 94 late frames, 93 of them held to 60 Hz, while the background window with the same load had none. The client took under 0.1 ms and the encode under 1 ms in every late frame, so the frames were waiting on the window server. Neither the frame log nor those runs say why. The design asked for the display's highest rate but said nothing about what to do when a device cannot hold it.

The owner's decision (C18 in docs/beryl-3d.md, 2026-11-15): run at the highest rate the display and device can hold, but smooth animation is mandatory, so an even lower rate beats an uneven higher one.

Read first: docs/beryl-3d.md C8, C15, C18, 'Hosts' (the desktop host), 'Rendering' (the tier step-down), Measurements. Code: rust/beryl3d/crates/beryl_host/src/macos.rs (the display link), desktop.rs, frames.rs (the frame log), drive.rs; tools/src/beryl_tools/beryl3d for just b3d app and just b3d frames.

Do:

  1. Find out why fullscreen is shown at 60 Hz on a 120 Hz display. Candidates: the display link's preferred frame rate range in fullscreen, the CAMetalLayer's settings (displaySyncEnabled, maximumDrawableCount), wgpu's present mode, and macOS's Game Mode or power policy. Use just b3d app --window fullscreen --load 16 runs and the frame log. Fix it if it can be fixed. If it cannot, make the desktop app start windowed (C15 already allows this) and record the evidence in docs/beryl-3d.md Measurements.
  2. Make the frame log and just b3d frames report the rate the host chose, and count a frame late against that rate. A frame shown at 60 Hz when the host asked for 120 Hz stays a fault ('held to 60 Hz'), not a step down.
  3. Build the rate step-down. When animating frames miss the chosen rate, first drop Enhanced to Baseline (the existing tier step-down; Enhanced is not built yet, so this order is only what the code must keep). If frames still miss, step down to the next rate that divides the display's rate (120 to 60). Step back up only after a sustained run of frames with room to spare, without going back and forth. Put the thresholds in data/beryl3d/space.json or the file the tier thresholds use, not as literals. On macOS the step uses the display link's preferred frame rate range; iOS (CADisplayLink) and Android (Choreographer, Surface.setFrameRate) take the same rule when milestone 4 builds their hosts, so put the rule in a shared place they can call.
  4. Test the step-down rule with a headless test that feeds it a sequence of frame times, including one that would make it go back and forth.

Done when: fullscreen holds 120 Hz in an agent-run just b3d app run under load, or the app starts windowed with the reason recorded; the frame log shows the chosen rate; the step-down rule has its test; the doc says what was found.

Handoff: Found that fullscreen's late frames were not 60 Hz: 75 of the 93 'held to 60 Hz' came 21.3 ms apart. winit's Fullscreen::Borderless makes a fullscreen Space on macOS; there the CADisplayLink's own timestamps skipped 12.5 ms or more (in 4.17 ms steps) about twice a second under load, at every rate down to 30 Hz. Fix: desktop.rs set_fullscreen/is_fullscreen use winit's simple fullscreen on macOS (composed window over the display); it held 120 Hz in two agent runs at load 55 with --load 16 (3 and 1 late of ~1,285). Rate rule: beryl_host/src/rate.rs (RateRule, Thresholds::DATA from frame_rate in data/beryl3d/space.json, generated by beryl_scene/build.rs), wired through FrameLoop::paced / fixed_at in frames.rs; Ticks::set_rate is carried out by the macOS DisplayLink (range min=max=hz) and the windowless Timer; phone spike and winit redraw hosts are fixed-rate. Added settle_frames (120) after a run stepped down on the window's first-second cluster, and lowest_hz (30) instead of a divisor. Anti-oscillation: a failed step up doubles the wait, up to up_frames_most. Frame log: Ticked.hz and .step; Late.hz, Summary.hz/steps; is_late counts against the chosen rate; just b3d frames prints the rate line. Doc: C15, C18, Hosts ('Choosing a frame rate'), Choosing a tier, Measurements table. Reviewer: check the tier step (Step::Baseline) never fires today since tier_can_drop is false everywhere until Enhanced exists.
