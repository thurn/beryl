Close reason

Merge queue in Enact (9a1d506, behind [push] queue), enabled in Beryl (30fc3534); integration test lands 4 of 5 in one push

Description

What we see

enact push (cmd_push) rebases onto origin/staging, runs the fast check and pushes. If another push reached staging first, the remote rejects it and the command rebases and checks again, up to 6 times. Beryl's fast check takes 95 s at the median and 240 s at the 90th percentile. At today's 8 commits per hour the race is rare. At 30 per hour another push lands inside most check windows, so most pushes would run the check two or more times, and the CPU spent on checks would grow faster than the commit rate.

Change

Design and build a merge queue: one integrator per host that lands branches in batches.

  • enact push verifies ownership as now, then adds the branch to a queue and waits for a verdict. Its exit codes and JSON output stay compatible, so agents' instructions do not change.
  • The integrator takes everything queued, rebases the branches in order onto origin/staging in a worktree of its own, runs the fast check once on the combined tree and pushes.
  • A branch that does not rebase cleanly is returned to its agent with the conflict, as exit code 2 is today, and the rest of the batch goes on.
  • When the combined check fails, find the failing branch (by the files the failing checks name, or by halving the batch), land the rest, and return the failing branch with the check's output.
  • Keep the delivery receipts, bead bookkeeping, watch_ci notice and slow-CI start that cmd_push does today.
  • Decide and record: the largest batch, how long the integrator waits to fill one, and what happens to the queue when the integrator dies.

Done when

An integration test queues five branches, one of which fails the check, and sees four land in one check run and one returned. In Beryl, the run log shows fewer fast-check runs than commits over a day. This change is in the Enact repository at ~/enact (scripts/enact.py, tests in tests/test_unit.py and tests/test_integration.py), not in Beryl. Read ~/enact/AGENTS.md first and follow that repository's workflow. The measurements behind this bead are in its parent, by-gdn3.

Handoff: Enact 9a1d506 (staging 095beb1, slow CI passed) adds a merge queue behind [push] queue = true (off by default); Beryl 30fc3534 turns it on. Code: queue_push, run_queue, land, set_aside, settle_landed, queue_tree in ~/enact/scripts/enact.py, wired into cmd_push; design notes in ~/enact/docs/design.md 'Merge queue (2026-11-13)'. Decisions: no daemon, the waiting push holding queue.lock integrates until its own entry has a verdict, then another waiter takes over; if it dies, the OS frees the lock and the next waiter carries on, and receipts tagged with the entry id stop it replaying commits that already landed. Batches hold up to 8 (push.batch). There is no fill wait, because batches form while the previous check runs. The check is killed after 1800 s (push.timeout). A failing batch sets aside the entries whose files the output names (else the later half), lands the rest, then checks those on their own. A branch that merged a diverged master, and --skip-checks, take the old direct path. The integrator tree is <root>/.merge-queue (detached; the sweep keeps it). Test: test_merge_queue_lands_a_batch_with_one_check_and_returns_the_failure (6 pushes: a conflicting pair, one bad; 4 land in one push; 3 checks). Beryl's first push through the queue landed fine. Follow-ups: by-gdn3.11 (ownership-lock timeout throws away a passed check), by-gdn3.12 (worktree reaping kills the push's pipe reader). Not filed: about 48 stale delivery receipts from rejected pushes sit in .git/enact/deliveries, and every push re-scans them. The 'fewer fast-check runs than commits over a day' criterion can only be read from Beryl's runs.jsonl after a day of pushes.
