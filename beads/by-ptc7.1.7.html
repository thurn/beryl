Description

Why

Nine logged bugs were slot order reaching an event, a save or a tie-break. Bitboard::iter is already pub(crate) in the kernel, but State::in_candidate_order returns the same ascending-slot iterator (bitboard::Slots) and is called at 58 places in beryl_rules outside tests, 22 of them with a comment arguing why order cannot matter. Nothing checks those comments. Plan: Designs B3.

What to build

In rust/crates/beryl_kernel/src/{order.rs, bitboard.rs, decision.rs, observation.rs, lib.rs} and every caller:

  • An order-free read stays a fold that takes Fn (Bitboard::any, all, filter, sum, sole, at_least). Add the folds the call sites need (for example a fold into a Bitboard, a maximum, a first member matching by a rules-visible key).
  • Building a decision's candidates is one method that takes the set (Candidates::extend or the name the code suggests): the one place slot order is meant to go, because engine::collapse and the candidate signature make candidate order independent of slots.
  • Anything done to members one at a time, where each step can change the state or emit an event, takes State::in_game_order, State::battlefield(), library_from_top, graveyard or a turn order.
  • State::in_candidate_order and Observation::in_candidate_order become pub(crate). Candidates::objects stays public for search and the session, which read a decision's candidates. SlotId::all and SlotId::pool stay for finding a free token slot (tokens.rs, actions/copy.rs): say so in the contract.
  • Rewrite the 58 rules call sites and the callers in beryl_search (28), beryl_session (20), beryl_cli, beryl_cards and beryl_scenario. A site that turns out to act per member in slot order is a bug of the logged class: fix it with a scenario that shows it under the three slot numberings (beryl_scenario::watch_with) and a docs/bugs.md entry.
  • Rewrite "Sets and orders" in the kernel contract to say what is now enforced.

The in_game_order queue has 128 entries in Small and returns Full; propagate it.

Bars (every bead of this epic)

  • The plan is docs/project-50k-part-2.md. If its design is wrong for the code, build what is right and amend the plan's section in the same push. Never wait for an answer: record the choice in this bead.
  • The absent-cost gate holds with no bump (just count-gate). When you touched the kernel, the rules or the card vocabulary, report the count before and after in the close reason. If it cannot hold after three attempts, stop and say so on the epic: this is the one thing that stops the run.
  • size_of::<State<Small>>() stays within 20,480 bytes. Report the size if you changed it.
  • The frozen saves replay and rollouts_never_change holds (just test-rust).
  • Rules code cites the Comprehensive Rules with a quotation (just citations). A card file cites a rule only for a card-specific ruling.
  • A new card follows the card-writing skill and passes just card check <name> (Beryl, XMage and Forge). A keystone or partner is listed in data/rulings-ledger.json once that file exists, with every ruling a scenario or a reason.
  • No UI work. beryl_cli script-check must pass for a new card from both seats with the verbs and prompt shapes that exist.
  • A rules bug found on the way gets its docs/bugs.md entry, naming the guard that now stops its class.
  • A bead you file is tier:opus for design, keystones and reviews, tier:sonnet for partner cards, sweeps and measurements, and never tier:fable.

Acceptance criteria

State::in_candidate_order is not callable from beryl_rules. Every scenario passes under the three slot numberings. The count is reported; in_game_order on a hot path is avoided or its cost named. Bugs found are in docs/bugs.md.
