Close reason

Enact 77d64c6 passed slow CI and reached master with the ticket store, readiness and atomic batch API. Cold all-ticket graph timing is recorded for the server Warden.

Description

Read the epic by-r61mr first: its description holds the decisions and the code map, and its design field holds the contract this bead builds against. The work is in the Enact repository (~/enact) unless this bead says otherwise, delivered with that repository's own enact worktree create and enact push.

Implement sections 1 to 4 of the contract in the Durable Object, in server/src/: the schema, the ID allocator, alias lookup, the in-memory copy of live tickets loaded when the object wakes, the read routes (/tickets, /tickets/<id>, /graph with its ETag), and POST /batch with every precondition and operation, including the request key that stops a retried create from creating twice and the closing of ancestors whose descendants are all closed.

Readiness is section 4's five rules, computed from memory, with blocked_by saying which ticket and which rule.

Each batch is one SQLite transaction that also updates memory. Keep rows written per operation at or under section 10's figures, and every request under 10 ms of CPU on a store holding 5,000 tickets of which 300 are live.

Acceptance criteria

Tests in the local simulator cover every route, precondition and operation of sections 3 and 4, each clause of the readiness rule (including a finding filed under a milestone after its audit started, and two last tickets under one parent), a batch that fails part-way leaving nothing changed, and a retried create making one ticket. A test seeds 5,000 tickets and asserts graph, list and a batch stay under the CPU limit, and a test asserts each operation's rows written against section 10.
