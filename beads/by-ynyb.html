Enact holds the ownership lock across Beads network I/O

  • Description
  • Comments3
  • Changelog

Description

Symptom: on this Mac, Enact's ownership lock (.git/enact/ownership.lock) is held 100% of the time. 5-minute samples of ownership.lock.holder taken once a second on 2026-11-15 showed 15-16 holds averaging 19 s each, with enact meta up to 41 s, close 28-39 s, start 22-46 s, next up to 104 s. Every enact claim, start, close, meta, push, next and worktree create on this host waits behind it. Claude session transcripts show about 166 "still waiting for the ownership lock" reports (60 s each) and about 20 give-ups after 180 s between 2026-11-13 and 2026-11-15.

What Enact commits cafb1c0 and 440767f already fixed: waiters now queue in arrival order (no more lost handoffs), a Beads sync is skipped when this process wrote nothing and the remote's refs/dolt/data tip is already in Dolt's git cache (checked with git ls-remote, about 0.3 s), and the store's remotes and branch are cached. A sync that does run went from about 6 Dolt launches to 3 and from 5.7 s to 3.4 s when the store was free. The lock stayed 100% busy, so these were not the main cost.

Why holds are still long (measured during that run):

  • Every bd and dolt process opens the embedded store at .beads/embeddeddolt/by and holds its file lock (.dolt/noms/LOCK) exclusively, even for reads. Inside the ownership lock, each bd show, bd list --all, bd update and dolt command waits for every other bd process on the machine: agents' own bd reads, enact brief, and a local Beads web dashboard (scotty, port 3000) that runs bd export --json over all 1,651 beads every 5-20 s while a browser tab is open. Twenty bd show calls a second apart took over 120 s; one took 15 s while an uncontended one takes 0.6 s.
  • Network pushes run under both locks. One dolt push origin main (a git push --force-with-lease of refs/dolt/blobstore to GitHub) sat idle for about 2.5 minutes inside enact start by-bajq.9.7, holding .dolt/noms/LOCK and the ownership lock, so every bd command and every Enact command on the host stopped.
  • bd commits and pushes after every write on its own (commits by "beads" in dolt_log), and the closing Enact sync pulls and pushes again.

What to do (design, tier:opus):

  1. Take network I/O out of the ownership lock. The lock only needs to cover read-check-write on the local store. The closing pull and push could run after the lock is released, as long as ownership is still verified after the merge (remote wins). Look at sync, sync_beads, claim, cmd_start, cmd_close, cmd_meta and finish_delivery in ~/enact/scripts/enact.py, and the remote-wins verification described in ~/enact/docs/design.md under "Ownership and abandoned work".
  2. Bound each Dolt network command with a timeout (the dolt() helper has none), so a stalled git push can't hold both locks for minutes.
  3. Consider running the Beads store as a Dolt sql-server (bd's server mode) on each machine, so reads no longer take an exclusive file lock. Measure bd read latency under the current load before and after. Done when: a 5-minute sample of ownership.lock.holder shows the lock busy well under 100% while viziers run, mean hold under 5 s, and no "gave up waiting for the ownership lock" in a day of transcripts.

2026-11-16 16:55 UTC: Enact 45d5b2b ('perf: push Beads inside the lock only for ownership', slow CI passed, live in ~/enact at about 16:28 UTC) removes the pushes from every sync except those whose check needs the remote's answer: claim (and vizier reservations), start, release, the deferred pusher, enact sync and setup. Every other sync commits and merges, then leaves the push to the background pusher. Measured cause: through a git+ remote, each dolt push or fetch reads all 230 blobs of the remote blobstore (864 MB, including twenty 52 MB parts) from Dolt's git cache, whatever it uploads (20-60 KB). A push also holds the store's file lock for its whole run. A concurrent bd show waited all 4.1 s of a push, but did not wait for a fetch. So moving the push out of the ownership lock alone would not help. The fix has to cut the number of pushes. Before (14:00-16:28 UTC, 504 holds): the lock was busy 82% of the time, waits were 8,600 s per hour, 11 commands gave up, and next's median hold was 4.4 s. After (16:30-16:55 UTC, 151 holds, a busier period by holds per hour): busy 56%, waits 3,750 s per hour, no give-ups, next's median hold 0.8 s, worktree's 4.9 s (17.9 s before), and the mean hold 5.4 s. What is left: the deferred pusher still pushes about 47 times an hour inside the lock, about 9.5 s each, because DEFERRED_SYNC_DELAY is 2 s. Raising the delay, or letting the pusher push without the ownership lock, which it could do safely since it only publishes, is the next step. Not closed: the done criteria (mean hold under 5 s, no give-ups for a day) need a day of data.
