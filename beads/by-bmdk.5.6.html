Description

Read first: epic by-bmdk, sections 'Rules for every bead', 'Contracts' and 'Code map'. Design: docs/manual-multiplayer.md ("the doc"), section 'Library flows' (the paragraph beginning "While a flow's tray is open") and 'Setup and match flow' (the starting steps).

Some steps need a player to choose among cards the host holds: sorting scried cards, keeping or mulliganing, putting cards on the bottom, choosing to play or draw. The host holds the prompt's state and the player's clicks in it are sent as they are made, as engine games handle a prompt. The guest computes nothing.

  • Replace the placeholder TablePrompt in rust/crates/beryl_session/src/protocol/table.rs with the per-seat wire view. TableView.prompt and beryl_session/src/typescript.rs already reference that enum. Keep host prompt state and callbacks in rust/crates/beryl_table_session/src/prompt.rs, which consumes the protocol type. Its view variants are Sort { title, cards, piles: Vec<PileName>, placed } (cards sorted into named piles in order: "top" and "bottom", "top" and "graveyard", or one pile for an order), Choose { title, options: Vec<String> }, Opening { hand, mulligans, to_bottom }. Each seat has at most one open prompt; it is part of that seat's view only.
  • enum Answer: Place { card, pile, index }, Unplace { card }, Pick { option }, Keep, Mulligan, Bottom { card }, Done, Cancel. TableSessions::answer(seat, answer) updates the prompt and re-sends that seat's view; Done turns the prompt into one batch action (or a single action), applies it through the normal path so it is logged, redacted and undoable, and closes the prompt. Cancel closes it and applies nothing (cards looked at stay known).
  • A prompt is opened by a function other beads call: open_prompt(seat, prompt, on_done: fn(&PromptState) -> Action).
  • Command table_answer { answer } (epic Rules, 6); the guest sends it as an act whose action is {"answer": ...}; teach Hosted::act in host.rs to route it.
  • While a Sort is open on cards from a library, the other seat's script lifts those cards (lift span) and ends the span when the prompt closes.
  • Interface: ui/src/table/TablePromptView.tsx draws Sort with the existing ordering tray (ui/src/stage/Tray.tsx; engine scry and surveil use it: find how in ui/src/screens/Scry.tsx and ui/src/stage/tray.ts) and Choose with the existing "choose from a list" shape; each click calls tableAnswer. Opening is drawn by the match-flow bead.

Tests: tests/prompt.rs: a sort over three cards placed, unplaced and finished becomes the expected batch; cancel; the other seat's view never names the cards; a guest's answers over memory::pair. A headless check that opens a sort through a test-only route and sorts two cards. Run just test-rust -p beryl_table_session and the ui checks.

Acceptance criteria

TablePrompt and Answer exist end to end: the host holds prompt state, each answer re-sends the seat's view, Done applies one logged undoable batch, the other seat sees only lifted cards; the tray and list shapes draw them; tests and one headless check pass.

Handoff: TableSessions::open_prompt installs Choose or Opening. open_library_prompt builds Sort from the latest library under the host queue lock. The callback takes &PromptState and returns Result<Action, Refusal> so callers can use flow_result directly. Sort::cards() reads the original top-first packet and Sort::choice() returns the chosen rows. The library-assist dispatcher should open the tray from a client Flow request. The underlying Action::Flow records the peek in the save and the callback supplies the result batch. Cancel appends no entry. The guided-start bead owns the opening-hand screen. Focused Rust suites, TypeScript, UI unit tests, and the headless two-card sort passed. The local Arena recordings were unavailable, so the tray uses the documented Arena layout and Beryl’s shared tray and list components.
