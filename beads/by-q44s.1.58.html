Close reason

Frames on Metal write mapped ring buffers, no blit: footprint while drawing 400 MB -> 257 MB (staging b2df85300)

Description

Symptom: Beryl 3D's footprint while it draws frames is about 400 MB on the Apple M5 Max (release build, --window none --fixture verbs-zones), of which Beryl's own buffers and textures are under 10 MB.

Why (measured in by-q44s.1.55): Apple's Metal driver allocates a fixed pool, counted in the process's physical footprint as 'Owned physical footprint (unmapped) (graphics)', the first time a process encodes each kind of command encoder, and frees it about 1 s after the last encoder of that kind. A bare Swift program shows it: a first render pass costs about 185 MB whatever its size (16x16 or 1920x1080), and a first blit encoder about 112 MB more. While render passes continue at 60 Hz the render pool stays; when blits stop, the blit pool is freed 1 s later even though render passes go on. wgpu turns every queue.write_buffer and queue.write_texture into a copy in a blit encoder, and Renderer::render_view (rust/beryl3d/crates/beryl_render/src/renderer.rs) calls queue.write_buffer every frame for the uniforms and the instance records. So every frame uses a blit encoder and the 112 MB never goes away.

What to do: draw frames with no blit encoder, so the blit pool is held only for the second after an upload (glyph pages, card faces). For example, write the per-frame uniforms and records into buffers the CPU maps (wgpu::Features::MAPPABLE_PRIMARY_BUFFERS on Metal's unified memory, a small ring so the GPU never reads a buffer being written), keeping queue.write_buffer where that feature is missing (OpenGL ES, downlevel limits). Keep the zero-allocations-per-frame gate (just b3d gate) green: map_async boxes its callback, so a design that maps every frame must avoid that or be measured. Measure with 'footprint --pid <pid> --sample 0.25' on a run that keeps drawing (a fixture), not the idle default run, which draws one frame and lets the driver free everything after a second.

Also correct docs/beryl-3d.md 'Measurements': by-q44s.1.16 wrote a startup transient of 344 MB naming by-q44s.1.55. That number is the driver's pools, not a Beryl allocation, and the footprint stays there while frames are drawn. Replace it with the footprint while drawing before and after this change, and the split above, and drop the name by-q44s.1.55.

Acceptance criteria

Footprint sampled while a fixture keeps drawing (release build, --window none) falls by about 100 MB on the M5 Max, measured on five runs; just b3d gate and the beryl_render tests pass under both Limits::Default and Limits::Downlevel; docs/beryl-3d.md 'Measurements' gives the footprint while drawing, explains the driver's pools and no longer names by-q44s.1.55.

Handoff: new rust/beryl3d/crates/beryl_render/src/slots.rs holds the per-frame uniforms and instance records. On Metal (mapped_features: backend Metal + MAPPABLE_PRIMARY_BUFFERS) it is a ring of 3 MAP_WRITE buffer sets: write() waits (poll Wait on the slot's submission) only if the GPU still uses the oldest set, writes via get_mapped_range_mut, unmaps; submitted() re-maps with capture-free callbacks. Elsewhere, and under Limits::Downlevel (to match the GLES floor), one COPY_DST set with queue.write_buffer as before. Renderer::render_view and set_faces use Slots; surface.rs and headless_with request the feature. Decision: Metal only, since on discrete GPUs (Vulkan/DX12) mapped primary buffers are read across the bus. New test render::frames_drawn_back_to_back_keep_their_own_records (8 frames, read after the last). Measured: footprint while replaying verbs-zones (release, --window none, footprint --sample 0.25, 5 runs each, load 24-28): 400 MB (344 graphics) before, 257 MB (199 graphics) after, every run; no late frames either way. docs/beryl-3d.md Measurements updated, by-q44s.1.55 reference dropped. Not measured on phones.
