Description

Read the epic by-r61mr first: its description holds the decisions and the code map, and its design field holds the contract this bead builds against. The work is in the Enact repository (~/enact) unless this bead says otherwise, delivered with that repository's own enact worktree create and enact push.

The contract is already written, in the epic's design field. This bead puts it where code can load it, and decides nothing.

  • Copy the contract into docs/design.md as a section.
  • Write server/contract/schema.sql exactly as section 1 gives it.
  • Write server/contract/api.json: one entry per route in section 3, per batch operation and precondition, per lease operation in section 5 and per feed message in section 6, each with its request and response fields and status codes, plus the exit codes and commands of section 9.
  • Add scripts/tk_stub.py, a stand-in for tk for Enact's tests: it keeps tickets in a local SQLite file made from schema.sql and implements the commands of section 9 that scripts/enact.py will call (graph, show, list, batch, lease, event, events, state), following sections 3 to 5. It need not be fast or complete beyond that.

If something in the contract cannot be written down as it stands, fix the contract in the epic's design field and say what changed in a comment on the epic.

Acceptance criteria

schema.sql loads into SQLite and api.json parses, checked by a test in tests/test_unit.py that also checks every route, operation and command named in the contract appears in api.json. The stand-in passes a test that creates a parent and two children, checks the readiness rule's five clauses, and shows a batch with a failed precondition changing nothing.
