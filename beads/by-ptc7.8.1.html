Description

Why

A CardDef holds one or two faces (rust/crates/beryl_card/src/definition.rs), casting already loops over faces (cast/legal.rs skips faces marked transformed) and the protocol's cast decision carries a face. Nothing says what kind of two-faced card a card is: the rules infer it from Face::transformed, only the test card "Test Stupor" uses a second castable face, and check never looks at the number of faces. The card store records each card's layout. Plan: Designs I, "A shape on the definition".

What to build

  • Shape in beryl_card (the name Layout is taken by the kernel's state layouts): Single, Transforming, Modal, Split { fuse }, Adventure, Prepared, Flip, Meld { with, into }, and whatever the single-faced structures need to be told apart (saga, class, case, leveler and prototype are single-faced: decide whether each is a shape or only vocabulary, and say why in the type's doc comment).
  • CardDef gains shape. rust/crates/beryl_card_build/src/printed.rs writes it from the store's layout beside the faces (faces(record) today appends .transformed() for a transform back face and uses the layout for nothing else), including a flip card's second face, a meld card's partner and result (Meld names two other records), and the defense of a battle if the store has one. complete.rs's rule for a card complete from the store stays single-faced.
  • check.rs refuses a face count the shape does not allow, with a Malformed message that says what the card file must change.
  • The rules read the shape where they branch on the kind of card: cast/legal.rs's face loop, State::copiable and Copiable::turned, the observation's face masking. Nothing infers a shape from Face::transformed, which goes if nothing else needs it.
  • The session's view (rust/crates/beryl_protocol/src/protocol/view.rs, ObjectView): name is the face that is up and facing is up or down. Add what a client needs to show a two-faced card with fields that exist or one new field, and regenerate ui/src/generated/protocol.ts (its header says how). No UI change.
  • The scenario builder (beryl_scenario_types): casting a named face or half (ME.casts_face(card, face) or by the face's name), which the family's cards need.

Jace, Vryn's Prodigy is the one two-faced card in the decks: it must behave as before.

Bars (every bead of this epic)

  • The plan is docs/project-50k-part-2.md. If its design is wrong for the code, build what is right and amend the plan's section in the same push. Never wait for an answer: record the choice in this bead.
  • The absent-cost gate holds with no bump (just count-gate). When you touched the kernel, the rules or the card vocabulary, report the count before and after in the close reason. If it cannot hold after three attempts, stop and say so on the epic: this is the one thing that stops the run.
  • size_of::<State<Small>>() stays within 20,480 bytes. Report the size if you changed it.
  • The frozen saves replay and rollouts_never_change holds (just test-rust).
  • Rules code cites the Comprehensive Rules with a quotation (just citations). A card file cites a rule only for a card-specific ruling.
  • A new card follows the card-writing skill and passes just card check <name> (Beryl, XMage and Forge). A keystone or partner is listed in data/rulings-ledger.json once that file exists, with every ruling a scenario or a reason.
  • No UI work. beryl_cli script-check must pass for a new card from both seats with the verbs and prompt shapes that exist.
  • A rules bug found on the way gets its docs/bugs.md entry, naming the guard that now stops its class.
  • A bead you file is tier:opus for design, keystones and reviews, tier:sonnet for partner cards, sweeps and measurements, and never tier:fable.

Acceptance criteria

Every card definition has a shape generated from the store, check refuses a wrong face count, and no rule infers a shape. Jace, Vryn's Prodigy's scenarios and the frozen saves pass. The count is unchanged.
