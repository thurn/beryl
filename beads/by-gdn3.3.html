Close reason

Description

What we see

With 5 to 10 worktrees active, the Mac's load average sits near 30 and reaches 83, on 18 cores. Yet a 3-hour sample showed it using only 8 to 10 cores on average, and above 14 cores in 3 of 176 minutes. So work arrives in bursts: for seconds at a time many more threads want to run than there are cores, and everything, including the checks that gate a push, slows down together. Twenty agents would make the bursts several times worse.

Why

Each cargo build, test run and check picks its own parallelism from the core count, as if it had the machine to itself. Only browser pages are limited across sessions (ui/scripts/slots.mjs).

Change

Design and build one pool of CPU tokens, sized to the core count, that every heavy command started through by draws from: cargo builds, Rust test runs, oracle runs, browser checks, tournaments and slow CI.

  • Priority order: the fast check of a push, then commands an agent runs by hand, then slow CI, then background work (tournaments, nightly, fuzzing).
  • A command that cannot get tokens waits. A waiting agent costs nothing.
  • Cargo and rustc can share a pool through the GNU make jobserver protocol. Confirm that against cargo's documentation before relying on it, and decide how test binaries (--test-threads) and Node scripts take part.
  • Fold the existing browser page slots into the same pool or state why they stay separate.
  • The check clock (clock.py) slows down when the load average is above the core count. Decide whether time spent waiting for tokens counts against a check's budget, and record the decision here.

Files

tools/src/beryl_tools/system.py, checks.py, clock.py, ui/scripts/slots.mjs, justfile (the low and awake prefixes), docs/checks.md ("Shared machine resources").

Done when

With 10 worktrees building and testing at once, the CPU recorder shows the load average staying near the core count, and the median fast-check time is no worse than it is today with 5. Record the before and after figures in this bead. The measurements behind this bead are in its parent, by-gdn3.

Design decisions (af3431bb):

  • Pool: tools/src/beryl_tools/tokens.py. There is one token per core, and each token is a file in $BERYL_CACHE/cpu-tokens naming its holder's pid and class. The pool's lock file guards every change. Tokens whose holder has exited are taken back, so a step killed at its deadline leaks nothing.
  • Classes: push (by check), then agent (just test-rust, fuzz, exhaust, freeze-saves, any other check run), then ci (by ci). Each class has a ceiling on the tokens it and every lower class hold together: push holds the whole pool, agent+ci at most 3/4, ci at most 1/2. A class takes nothing while a higher class waits, and waiters of the same class split what frees up.
  • A lease is fixed when it starts. Its size goes to CARGO_BUILD_JOBS, NEXTEST_TEST_THREADS, RUST_TEST_THREADS and BERYL_CPU_TOKENS. A child that sees BERYL_CPU_TOKENS runs inside its parent's lease and never waits on it, which prevents deadlock. One lease takes at most 2/3 of the pool, so two heavy lanes of one check split it instead of the second one waiting.
  • Only heavy check steps take tokens (HEAVY_STEPS: clippy, rust tests, app smoke, shots, ui-test, oracle, mobile, script, motion, counts). The other steps are scripts that use one core at most.
  • Jobserver: not used. The jobserver crate that cargo uses does read --jobserver-auth=fifo:PATH from CARGO_MAKEFLAGS/MAKEFLAGS (jobserver 0.1.33 src/unix.rs), but a token there is a byte read from the FIFO. A client killed while holding one (the checks kill steps at their deadlines) loses it for good, and the FIFO cannot order its waiters by priority.
  • No background class: tournaments, the nightly and the justfile's low/system.utility run at utility QoS, which already yields every core to normal-priority work thread by thread. A fixed lease would leave the cores idle for hours on a quiet machine. system.utility and 'by low' set BERYL_CPU_POOL=0, so nightly 'just fuzz' takes no tokens.
  • Browser slots stay separate (ui/scripts/slots.mjs). The step that opens pages holds tokens for its build and Node side. Folding the slots in would mean reimplementing the protocol in Node for page holds of a few seconds each.
  • Clock: a step's wait for tokens counts against the check's deadline and budget, with no special case in clock.py. Push's reserved quarter keeps the wait short. If pushes start timing out on waits, the fix is a larger reserve, not a deadline exception.
  • Before figures, last 24 h of runs.jsonl on jarvis (fast check, step-span estimate): 169 runs, median 134 s, p90 342 s, median load 29. The epic's 3-day figure: median 95 s, p90 240 s. After figures need the pool live under 10 worktrees for a while; I filed that as a follow-up measurement.
