Description

Non-blocking; nothing waits on this. by-w8gv.5.14 made player count, deck size and the token pool parameters of the layout. Small is still two 60-card decks and a pool of 135; Large now holds 256-card decks. So an 80-card Legacy deck is refused by Small (Misfit::DeckTooLarge) and its game plays only in Large, where search has no flat Copy state.

What to decide, when the next project picks its decks: does it want search to run flat on 80-card decks, and by which of two routes.

A. A third layout, flat like Small: 80 + 80 deck slots and a pool of 95 fit the 255 slots of a u8. It needs a slot type of its own (cheapest: Slot generic over its deck size), an impl Layout, a twin of each impl Copy for X<Small>, a third member of every per-layout static (so every card body is compiled a third time: about half again the engine's code and compile time, which milestone 8's scale budgets see), and beryl_search and beryl_session generic over which flat layout a game fits. Small stays bit-for-bit.

B. Re-deal Small itself as 80 + 80 + 95. None of A's costs, but Small's slot numbers move (state hashes and the count gate's corpus change; saves are slot-free and replay) and its pool shrinks from 135 to 95, so more token-heavy games widen into Large.

Default if nobody answers: neither. 80-card games play in Large, and the bead that first needs one in the app starts the session in Large when Small refuses (a few lines in beryl_session's replay.rs and game.rs; today the session reports SessionError::Deck).

The comment "A flat layout for 80-card decks" on by-w8gv.5.14 has the detail. Look at: rust/crates/beryl_kernel/src/ids.rs (SlotId), layout.rs (Small, Large), and the test eighty_card_decks_are_refused_by_small_and_play_in_large in rust/crates/beryl_search/tests/games.rs.

Acceptance criteria

Derek says A, B or neither; if A or B, a bead is filed for it under the next project.

Executor decision (K31: no step waits on Derek, so the bead's own default applies): NEITHER, for now.

Why the default is also the right call today:

  • No Legacy deck is chosen yet. docs/sample-decks/ holds only the WU Control cube lists (40 main + 17-18 side), so there is no 80-card list to size for.
  • A Legacy main deck is almost always exactly 60, which Small's 60 deck slots per player hold. The sideboard is not in the game (CR 100.4a, https://yawgatog.com/resources/magic-rules/#R1004a: 'Sideboard cards are not part of the game'), so best-of-three sideboarding alone never needs more than 60 slots.
  • What does need more: an 80-card companion build (Yorion) or cards fetched from outside the game (Karn, the Great Creator; wishes; a companion). Those are properties of the decks the next project picks, so the decision belongs with that choice, and the second case may want pool or sideboard slots rather than wider decks.
  • A costs about half again the engine's code and compile time against milestone 8's scale budgets; B moves Small's slot numbers (state hashes, count-gate corpus) and shrinks the pool 135 -> 95. Neither is worth paying before a chosen deck needs it.

Fallback when an 80-card game first reaches the app: start the session in Large when Small refuses (beryl_session replay.rs / game.rs; today SessionError::Deck). Verified on origin/staging: Small DECK_SLOTS = 60, Large = 256, and eighty_card_decks_are_refused_by_small_and_play_in_large (beryl_search/tests/games.rs:129) still holds this split.
