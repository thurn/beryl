Description

Seen 2026-11-17: the nightly on jarvis (this Mac) filed by-7ph64 at 13:32 UTC and the nightly on dereks-macbook-pro filed by-xr85w at 13:34 UTC, both for fuzz:games failing at families::replacement seed 243, on staging tips 80c893b35 and d9ca05f50. Two Steward sessions (a Codex session on the MacBook, and the CI steward watch on jarvis) then reproduced the same failure; the watch spent about 10 minutes of the machine on a just fuzz rerun before closing its bead as a duplicate.

Why: tools/src/beryl_tools/nightly_failures.py dedupes by listing open nightly-failure beads in the local Beads database (open_beads, verdicts.Beads.list_issues). Both launchd agents (nightly.agent_plist, FIRST_HOUR..LAST_HOUR) fire at the same local hours, and the first host's bead write is published by a deferred sync (enact sync printed deferred: true), so the second host does not see it two minutes later. Each machine also spends its own 30 min to 2 h nightly on almost the same staging tip.

Options, pick one and record why: (a) run the checks that file beads (fuzz, scale, motion, ui-counts, oracle, iroh) on one host only, keyed on an Enact host setting, and let the other host run only its own cache steps (prune, history); (b) before nightly_failures.file lists open beads, force a synchronous tracker pull, and after filing, publish synchronously; (c) stagger the two hosts' firing hours. (a) also removes the duplicated machine time.

Done: one failure on staging produces one nightly-failure bead across both Macs; tools/tests/test_nightly.py covers the rule.

Acceptance criteria

A nightly failure seen by both Macs files one bead; test in tools/tests/test_nightly.py.
