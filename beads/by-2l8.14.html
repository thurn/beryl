Close reason

bench-count serializes on a VM flock; per-worktree Gungraun home (c8ea844)

Description

by bench-count (tools/src/beryl_tools/bench.py) builds every worktree into the same target dir in the beryl-bench Lima VM (VM_TARGET = $HOME/target), and Gungraun keeps its callgrind outputs and 'old' comparisons under it. Two sessions counting at once overwrite each other's binary and results: on 2026-11-06 a by-2l8.6 run reported another worktree's code (a callgrind profile byte-identical to staging's baseline, 815M where the branch measured 621M). Parallel Enact runs (wardens re-measuring counts, executors optimizing) hit this. A fix: serialize runs with flock on a lock file in the VM around the cargo bench call, or give each worktree its own target dir (slower first build). Workaround used: CARGO_TARGET_DIR=$HOME/target-<bead> via limactl shell.

Acceptance criteria

  • Two just bench-count runs started at once from different worktrees each report their own code's counts (e.g. serialized by a lock, or separate target dirs).\n- docs/benchmarking.md says how concurrent runs behave.

Fix: flock in the VM wraps provisioning+build+count (serializes, keeps the shared warm target dir; separate target dirs would cost a cold VM build per worktree). Also GUNGRAUN_HOME per worktree dir name so Gungraun's 'old' comparison is the worktree's own last run. Verified: two concurrent locked scripts in the VM ran back to back with the waiting message; a killed client's lock was released; just bench-count -p beryl_bench --bench example_counts ran end-to-end with a fresh home. Docs updated in docs/benchmarking.md (The VM).
