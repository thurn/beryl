Cause: after any rules change, the fast check relinked 59 test binaries (39 of them beryl_session integration tests at ~55 MB each, 44 card crates with empty harnesses), and on macOS each newly linked binary waits for the system's executable scan on first launch (cargo nextest list took 74 s wall with ~1 s CPU the first time, 1.3 s the second; single session binaries waited 15-18 s). Windows Defender behaves the same way on Cygnus. Action (b07d1ffc): beryl_session's tests are one binary (tests/main.rs, with a test that fails on an undeclared file), and card crates set test = false / doctest = false. Same probe (one-line beryl_rules change) on this Mac at load 14-23 on 18 cores: tests step 236 -> 98 load-adjusted s (build 88 -> 19 s, 59 -> 21 binaries, 782 tests both times); whole by check 332 -> 155 s. Still over 60 s: the rust lane runs clippy (40 s), tests (98 s) and card-text (14 s) in sequence, and nextest itself takes ~42 s for the tests a rules change can break. Not measured on Cygnus. Closing so the next overrun files a fresh bead from post-change data. Not done: adding a Developer Tools exemption in macOS Privacy & Security (or a Defender exclusion on Cygnus) for the build directory would remove the first-launch scan, but that is a system security setting for the user to change.
