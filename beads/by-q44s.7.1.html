How to write each bead

Whoever works a bead has nothing but the bead, the doc and the code. Write for that reader.

  • Decide everything that can be decided now. A bead never says 'choose', 'pick', 'find out whether' or 'in X or Y'. Where the answer needs a measurement, the bead says what to measure, the threshold, and what to do on each side of it.
  • Name the crate, the file and the function or type for every piece, and which crate each test goes in. Give exact versions for any new dependency.
  • Name the web interface's files that hold the behavior, and say what to take from each. Open each file yourself first and quote the function names: do not name a file you have not read.
  • List the tests by what each one asserts, and give the commands that run them.
  • Write acceptance criteria that a command can show true or false.
  • Say what the bead must not build, when a later bead builds it.
  • Keep a bead to what one session can hold: about 600 lines of new code, or one module.
  • Before filing, check the dependencies: no bead's Run: line uses a command that a bead it does not depend on creates. Run bd dep cycles.
  • The epic's rules 14 to 16 say what a worker does when a bead is wrong and when it is done. Do not repeat them in each bead.

Its phone spike left minimal Swift and Kotlin hosts in rust/beryl3d/crates/beryl_3d/ios and android, five exported C functions, just b3d ios-smoke and just b3d android-smoke, and a report on its bead of what Metal, Vulkan and OpenGL ES each needed.   2. The Swift host, two beads: (a) touches as Pointer inputs with one id per finger, safe-area insets, the display's highest refresh rate through CADisplayLink, the audio session; (b) suspend and resume with the surface lost and recreated, low memory, the share sheet and haptics as Requests.

  4. Text entry on both, one bead: on BeginTextEntry the host shows a native field over the element's rectangle and sends a Text input for each change; on EndTextEntry it removes it. From the Beryl 3D prototype: on a phone, Beryl's own AI search is the only heavy background load. File a bead that plays a game in the iOS Simulator and in the Android emulator with the AI searching on every core (decision C9), and reads the frame log for frames that arrived late while it searched. A simulator says nothing about a phone's speed; it shows whether the search threads' priority starves the frame thread. No bead needs a phone: a run on a real one is listed in the epic's closing note among the things only the owner can start.
