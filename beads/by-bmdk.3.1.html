Description

Read first: epic by-bmdk, sections 'Rules for every bead', 'Contracts' and 'Code map'. Design: docs/manual-multiplayer.md ("the doc"), section 'Views and animation', and 'Hidden information'.

Create the crate rust/crates/beryl_table_session (deps: beryl_table, beryl_link, beryl_session, serde, serde_json) and in it src/view.rs: pub fn view(table: &Table, seat: Seat) -> PlayerView.

  • Start from beryl_table::redact::seen_by(table, seat), so nothing hidden can be read by mistake, and build with the constructors in beryl_session::protocol::neutral (PlayerView::neutral, ObjectView::card, ObjectView::hidden). Never write a PlayerView or ObjectView struct literal here.
  • "You" is seat; "opponent" is the other seat. This file and script.rs are the only places in the whole design that are tied to two seats. On a one-seat table the opponent side is empty.
  • Object slots: the view identifies objects by a slot the stage keys its nodes on. Keep a stable map from the table's ObjectId to a slot in a Slots value the caller owns, so a card keeps its node across views. When the table gives a card a new id (entering a hand, a shuffle) it gets a new slot for a seat that does not know it, and keeps its slot for a seat that does, so the owner sees their drawn card fly and the other seat cannot follow it.
  • Fill: zones in order (libraries as counts plus any known top cards), battlefield rows from beryl_card_store::facts::row unless pinned, tapped, face, counters (+1/+1, -1/-1, loyalty and other names the engine's Counter enum has go in the existing counter list so the stage draws them as it does today; any other name goes in named_counters), shown power and toughness (facts::shown_stats), damage, note, attachments, tokens, ability markers as stack entries naming their source, life, the six mana symbols and other player counters, the active seat and phase (map the eleven manual phases onto the engine's turn structure fields and also set TableView.phase), arrows, and PlayerView.table (TableView): log lines from beryl_table::log::line, the viewer's assists, seats, zones the viewer may act on.
  • Publish an action mapping alongside each viewer's view. Create TableActionRefs::new(table, seat), call expose only for objects or markers actually projected to that viewer and set TableView.object_actions from actions(). Use Subject::Object { slot } for a card and Subject::Ability { id } for a marker. The helper applies the table's access rules, including for anonymous backs in a lent pile. Return the matching map to the host caller so it can replace the previous map when it publishes.
  • Status is Status::Free during a game and Status::Over is never used; the lobby state is carried by a later bead.
  • Rules text, type line and image for a known card come from the store exactly as the engine path fills them: read protocol/build.rs::object_view and beryl_session/src/card_records.rs and call the same helpers, making one pub if needed.

Tests in tests/view.rs: a table with something in every zone gives the expected view for each seat; the doc's draw example (seat 1 sees an unnamed card in seat 0's hand); a random test reusing beryl_table's tests/common/random.rs (move it to a pub mod testing behind a testing cargo feature of beryl_table so this crate can use it): after each of 1,000 actions the JSON of each seat's view contains no name of a card that seat does not know. Run just test-rust -p beryl_table_session.

Acceptance criteria

view() builds a PlayerView for either seat through the neutral constructors only; slots are stable for a seat that knows a card and fresh for one that does not; the redaction random test over views passes; the crate does not depend on the engine except through beryl_session.
