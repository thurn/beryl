Description

Milestone 7b of Project 50k (docs/project-50k.md, "Crates": "Data-only card crates depend on beryl_card alone, so they rebuild only when the vocabulary changes"; "Scenarios compile only for tests and tools"). First bead of lane set-crates; the next moves the card files into set crates.

The problem (found by the M5 Mason audit, by-w8gv.10.1)

A card file outside its scenarios module imports beryl_card alone. Its #[cfg(feature = "scenarios")] pub mod scenarios imports beryl_scenario and beryl_engine (DecisionKind, TurnStep, Zone, Seat, CounterKind), and beryl_scenario depends on the beryl_engine facade (lib.rs:19-21 takes Castings, FaceIx, ManaColor, ObjectAbility, Purpose, CounterKind, CardTable, DecisionKind, Seat, TurnStep, Zone; setup.rs, run.rs, run/, script.rs and exhaust.rs take the whole engine). So with the feature on, every card crate rebuilds on any rules edit. DecisionKind is the one type that lives outside the vocabulary: rust/crates/beryl_kernel/src/decision.rs:103.

What to build

Split the scenario value types (what a card file writes: Scenario, Action, Assertion, Permanent, Pick, P0/P1, and whatever the Scenario::new(...).battlefield(...) builders name) from the runner (setup, run, script, exhaust, the JSON dump), so that a card file's scenarios compile against a crate depending on beryl_card only. If a kernel id proves unavoidable, say why on the bead: the target is beryl_card alone, so a rules or kernel edit rebuilds no card crate even in test builds.

Default design; change it if the code argues otherwise and record why: a new crate beryl_scenario_types holding the value types (or the types moved into beryl_card behind a scenarios feature, if that is smaller); beryl_scenario re-exports them and keeps the runner. DecisionKind, as scenarios use it (the kind of question an Action::answer expects), either moves to beryl_card beside the prompt shapes (beryl_card/src/prompt.rs), re-exported by the kernel so no other caller changes, or the scenario types get their own enum the runner maps: prefer the move if DecisionKind names nothing but vocabulary types. The value types serialize in the dump (beryl_scenario::to_json): keep serde out of what a card crate depends on if the dump can serialize from outside; otherwise it stays behind the feature. Card crates gain no runtime dependency either way.

Then change the 47 card files' scenario modules (rust/crates/beryl_cards/src/<color>/*.rs) and props.rs to import from the new home and nothing from beryl_engine. beryl_cards/src/library/, generate.rs and derive/ (the rules library's scenarios and the generators) stay on the engine: they stay in the registry crate in the next bead.

Files

  • rust/crates/beryl_scenario/src/lib.rs (the types) and its Cargo.toml; beryl_kernel/src/decision.rs; beryl_card/src/prompt.rs, ids.rs.
  • rust/crates/beryl_cards/src/<color>/*.rs scenario modules: a mechanical import change; script it.
  • Need not read: the runner's internals (run.rs, exhaust.rs), beryl_rules, beryl_search, the UI.

Tests: cargo test -p beryl_scenario -p beryl_cards; just test-rust before the push. No behavior changes: every scenario runs as before, and the dump's JSON is byte-identical (diff cargo run -p beryl_cards --features scenarios --bin beryl_scenario -- dump before and after).

Parity at the push (plan K11)

just check passes; the frozen save corpus replays (cargo test -p beryl_session --test corpus); rollouts_never_change holds; slow CI's counts lane (just count-gate, bar 405,276,238 instructions, 1% tolerance, rust/crates/beryl_bench/count-gate.toml) passes with no bump to the bar. Never delete a card implementation. Work the card-names and file-length allowlists down in the files you touch. Record decisions and anything this packet got wrong as comments on the bead; nobody answers questions (K31): proceed on the default given and record it.

Acceptance criteria

No card file under beryl_cards/src/<color>/ imports beryl_engine, beryl_rules or beryl_kernel, in or out of its scenarios module (grep shows none); the crate holding the scenario value types depends on beryl_card alone (cargo tree shows no beryl_kernel, beryl_rules or beryl_engine), or the bead records why a kernel id was unavoidable; beryl_scenario dump output is byte-identical before and after; just test-rust and the parity checks pass.

Decisions: (1) New crate beryl_scenario_types (the default), not a feature of beryl_card: it keeps the vocabulary free of test types. cargo tree shows beryl_card alone; no kernel id was needed. (2) DecisionKind moved to beryl_card/src/decision.rs (a module of its own beside prompt.rs, not inside it), re-exported from beryl_kernel::decision, so no other caller changed; it names no non-vocabulary type. Its doc links to the kernel's Opt became plain code text. (3) serde stays out of the types crate: beryl_scenario/src/json.rs serializes from outside with serde remote definitions (one ...Def mirror per type; the compiler holds enum mirrors exhaustive and struct mirrors to the fields they list. A NEW struct field is not caught: add it to the mirror or the dump omits it). Since Scenario/Action no longer implement Serialize, callers wrap them: beryl_scenario::Json(&scenario) or Json(&action) (two beryl_cards tests and beryl_cli specs/playground.rs changed). (4) Packet gap: it did not name those three Serialize callers. Verified: dump byte-identical (7,812,452 bytes, cmp) before and after; just test-rust, clippy, corpus test and the fast check (incl. oracle, script, ui-test, shots) pass. The fast check reported 81 s against its 60 s budget under load average 50 with a full rebuild (beryl_card changed); it passed and pushed.
