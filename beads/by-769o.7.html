Close reason

Slow CI has an 800 CPU-second budget; over it files one ci-cut bead per lane naming the checks to cut (64a1c556)

Description

What we see

budget.py files one "Audit slow steps" bead per script when a run goes over its budget in load-adjusted seconds. The beads by-vdpy (by ci) and by-vz64 (by check) sit open at P2 with nobody working them: they name no cut, and on a machine that is never quiet the load-adjusted clock mostly measures other work. Slow CI keeps growing with every card and verb.

What to change

Rewrite the slow-CI half of budget.py:

  • The budget is CPU-seconds per slow-CI run (the cpu_seconds field), set from the current total once the timeout removals in this epic land, and never raised. Record the chosen number and how it was picked in this bead.
  • After each slow-CI run, compare the median CPU total of the last N runs (for example 10) with the budget, so one noisy run files nothing.
  • When over budget, file a P1 bead per lane that names exactly which checks to cut, chosen by the value report (the bead this depends on), with each check's runs, catches and CPU seconds. The bead says what to do: delete a check with no catches in 30 days; move a check that has caught something to the nightly. The agent working it makes the cut without asking and records it in the bead. Label these beads so the detector files no duplicate while one is open, and so a new one can be filed once it closes and CI is still over budget.
  • The first run will likely be far over budget. Its beads are the initial sweep: delete every slow-CI check with zero catches in 30 days, except a short list that guards something no other check does (for example the app starting at all), which the bead names.
  • Close by-vdpy and by-vz64 as superseded. Keep the fast check's budget bead as it is unless the same change fits it cheaply.

Rewrite before deleting

Every bead this files asks, for each check it names, before deleting or moving it: could a fast, deterministic test (a Rust unit test, a Node test with no browser, a check against a recorded fixture) keep most of what this end-to-end check protects? If so, the agent writes that test and then deletes the slow check. If not, it deletes the check (no catches) or moves it to the nightly (some catches). The bead records which it chose and why.

Files and tests

tools/src/beryl_tools/budget.py, tools/src/beryl_tools/checks.py (run_all, where the budget is reported), tools/src/beryl_tools/nightly.py (how a check moves to the nightly), tools/src/beryl_tools/verdicts.py (Beads, for filing), tools/tests/, docs/checks.md.

Derek Thurn2026-11-13

Decisions: (1) Budget SLOW_CPU_BUDGET = 800 CPU s. On 2026-11-13 a full run on JARVIS cost ~1,840 CPU s; cutting every zero-catch check (except KEEP) would leave ~520. I did not set the budget at ~520 (the literal 'initial sweep') because at that level the cuts reach ~1,000 Rust unit tests that cost a fraction of a CPU second each and that the fast check also runs; at 800 the greedy cut (lowest value, costliest first) takes ~520 of the costliest zero-catch checks (rust:allocations, rust:doctests, longthink/search integration tests, verb films, script fixtures, shots, some oracle scenarios) in 7 lane beads and stops. A dry run against the real log produced: oracle 56, rust 159, scale 1, script 104, shots 111, ui 1, ui-test 137 checks; none caught a bug, so all say 'delete'. (2) Full-run cost = sum of each check's median CPU s over checks that ran in one of their lane's last 10 runs (check_value.full_run/alive), replacing by-769o.6's median of run totals: slow CI is selective, so run totals are bimodal (rust lane 6 records vs ~935) and their median swung 800->1,900 between consecutive runs. (3) KEEP: app:smoke, mobile:mobile-check, rust:clippy, ui:tsc, and the whole names lane (AGENTS.md rule checks, ~3 CPU s). (4) Windows skips the detector: it has no cpu_seconds. Records are filtered to this host (platform.node()). (5) Dedup is global: while any ci-cut bead is open nothing is filed; after the last closes only runs started after its closed_at count, and 10 are needed, so a cut check is not named again from older runs. (6) The wall SLOW_BUDGET (300 s) is still printed beside slow CI's run time but files nothing. (7) Closed by-vdpy and by-vz64 as superseded.
