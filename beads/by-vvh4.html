New agent worktrees rebuild changed crates with no incremental reuse

Close reason

Done in Enact afa80623 (ad hoc worktrees take slots) and Beryl 137062401 ([worktree] slots = 10), both through slow CI. A test build after a one-function beryl_kernel change took 42 s wall and 59 CPU-seconds in a reused slot, against 575 s and 1,040 CPU-seconds for the first build in a fresh directory, at load 65-80. The by-3sn5 log asks the next run to check fast-check kills in slots.

Description

Symptom

The first Rust build in every new worktree recompiles each changed crate from scratch. Measured on 2026-11-14 at load 40-65 with CARGO_BUILD_JOBS=8, after a one-function change to beryl_kernel (cargo test --workspace --exclude beryl_link_iroh --no-run):

  • in the worktree that built the previous state: 18 CPU-s, 22 s wall
  • in a fresh worktree cloned from the cache (just warm): 421 CPU-s, 164 s wall
  • in an exact APFS clone of the first worktree's target at another path, after warm.rehome_paths: 544 CPU-s, 111 s wall

Cause

rustc keys incremental caches to the working directory, which cargo sets to the checkout's absolute path. With -Zincremental-info, rustc prints "completely ignoring cache because of differing commandline arguments" for a cache built at another path. --remap-path-prefix does not help on stable: the flag itself names the per-worktree path, so it differs too. -Zremap-cwd-prefix and cargo's trim-paths are unstable.

Fingerprints and artifacts are path-independent, so the cache does save third-party and unchanged crates; only the incremental reuse is lost. Every crate on the chain from the changed crate to beryl_cli is rebuilt in full. In the fast check this is the rust:clippy step (median 91 s, p90 250 s over 70 runs on 2026-11-14) and the untimed test build inside rust:tests (median 84 s, p90 255 s).

What already landed

Slow CI reuses one worktree, .worktrees/ci-runner (Enact b10a683 [checks] slow_tree; Beryl c16d98af caches.save_kept). The cache no longer holds incremental caches.

Work

Give agent worktrees reused paths, as slow CI now has. Enact already has [worktree] slots = N (claim_slot in ~/enact/scripts/enact.py), but Beryl does not enable it, and it only applies to bead worktrees, not to enact worktree create <name> from ad hoc sessions. Options:

  1. Enable slots in .enact.toml and extend claim_slot to ad hoc worktrees (the name becomes the branch only). Prefer the free slot whose HEAD is nearest to staging.
  2. Size the pool from the live worktree count (13 on 2026-11-14 at 20:00 UTC) and disk: each slot keeps its own rust/target of up to the 15 GB budget; caches.tidy_target and warm.prune must keep slots within it.
  3. A slot's first build after a long idle still rebuilds what changed on staging since, but with incremental reuse.

Also log the test build's own seconds in runs.jsonl (it is printed as "rust-tests: built in N s" but not recorded), so the effect can be measured from the run log.

Done

In the fast check after a beryl_kernel change in a reused slot, clippy plus the test build take under 60 s at load under 20, and runs.jsonl records the test build time.

Enact afa80623 (perf: ad hoc worktrees reuse slots too) lets enact worktree create <name> without a bead take a slot, found again by its branch enact/<name>, and prefers the free slot parked at the newest staging tip. Beryl 137062401 sets [worktree] slots = 10. caches.tidy_target already runs at every check start, so slot targets stay within the 15 GB budget.

Before (runs.jsonl, fast checks 22:00 UTC 2026-11-14 to 22:00 UTC 2026-11-15): rust:tests was killed at the 180 s limit in 48 of 52 runs and passed in none. rust:clippy was killed in 87 of 157.
