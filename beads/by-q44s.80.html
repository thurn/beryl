Beryl 3D frame and count limits: stop the re-pin churn

Close reason

Native gate runs in its own fast-check lane (bf0c75475); bisect misses map sweep lanes; docs say the change that moves a count moves its limit

Description

Symptom: the Beryl 3D sweep kept failing its gate and frame-counts steps on this Mac on 2026-11-16, and each failure filed a fix bead: gate .47, .51, .62, .63, .65; frame-counts .52, .73, .78, .79. Most of these fixes re-pinned limits in data/beryl3d/gates.json to whatever staging measured, or closed with no change because a later commit had already re-pinned them (.65, .73). .47 found a rebase merge that had counted four limits twice. .78 raised all 14 instruction-count limits to cover the step banner and game log work. Each fix holds only until the next feature lands and pushes a count past its pin, so the run spends a session on bookkeeping every hour or two.

Why it happens, as far as the vizier could tell (check each claim):

  • Limits are pinned to exact measured values with little headroom (.73 found a 20% build-out tolerance on some totals, so the rules differ by kind of count).
  • Beryl 3D's checks run only for changes to Beryl 3D (docs/beryl-3d.md, 'Checks and isolation'), so a change elsewhere can move a count without its author's fast check noticing. The sweep then finds it later and files a bead for someone else.
  • Two branches that each re-pin the same limit conflict, or merge to a wrong value.

Goal: a count that grows because of intended work should be updated by the change that grew it, in the same commit, with the cause recorded. A real regression should still fail. Nobody should need a separate bead to re-pin a limit.

Options to weigh (pick and record the choice here; the gates must serve real performance, so do not loosen a limit that guards a real cost):

  1. Make the fast check run the Beryl 3D count gate for any change that can move its counts, so the author re-pins in the same commit.
  2. Give each kind of count an explicit tolerance band in gates.json (for example a percentage over the pin for totals that grow with build-out, exact for allocations or draw calls), and have the gate say which kind failed.
  3. Have just b3d gate --update write limits in a form that merges cleanly (one line per limit, sorted), and fail the rebase check if a merge changes a limit without a recorded cause.
  4. Have the sweep, when the only failure is a count within a set band of its pin and the commit that moved it is known, name that commit in the bead or re-pin automatically with the measurement recorded.

Read first: rust/beryl3d/AGENTS.md (frame limits), data/beryl3d/gates.json, tools/src/beryl_tools/beryl3d/gate.py, tools/src/beryl_tools/beryl3d/sweep.py, docs/beryl-3d.md ('Checks and isolation', 'Test speed'), docs/checks.md, and the closing notes on the beads listed above.

Done means: the chosen change has landed, docs/beryl-3d.md and rust/beryl3d/AGENTS.md say how limits change, and a feature commit that grows a count either updates the limit itself or fails its own fast check, rather than leaving it to the sweep.

Decision: option 1, applied to the lane the gate already had. Evidence from ~/Library/Caches/beryl/ci/runs: of 327 fast checks that ran beryl3d-tests, only 100 logged a beryl3d-tests:gate result, because gate ran after cargo-test (a lane stops at its first failed step; 168 cargo-test failures) and the 180 s hard limit deferred the rest to the sweep. The gate culprits (afafba2011 etc.) were Beryl 3D commits whose gate never ran; the merge-driver sums (be0772955, 7041e45b6) also landed only because no post-rebase gate ran. Change: gate gets its own lane beryl3d-gate (record, gate). Also fixed bisect miss attribution: it compared sweep lane b3d-gate to fast lane names, so every miss said 'lane did not run'; bisect.misses now takes fast_lane (sweep.fast_lane). Not done: instruction counts (frame-counts) still run only in the VM sweep, since --counts takes minutes, beyond the fast check's limit. Docs now require a change that raises a work-counter limit for work added to every board to run --counts and move instruction limits in the same commit (the .78 case). A per-frame cost the counters cannot see (the .79 flight sampling) still reaches the sweep by design. Rejected options 2 (bands already exist: 1%/20% build-out, exact for work counters), 3 (merge driver exists; a post-rebase gate now catches its wrong sums) and 4 (auto re-pin would loosen limits that guard real cost, e.g. .79's +34%).
