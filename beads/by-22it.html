Derek Thurn2026-11-13

Cause: environment, not the pile viewer. In run 64a1c55607 (load 13.5), five pile checks failed and then passed on the step's rerun. Three of them failed in 0.23 to 1.4 s, faster than a passing boot (1.0 to 1.6 s), so they failed while the page was still loading. The 10-card check sat for 30 s, which is Playwright's default timeout. In the same worktree, the ui-shots step's pages logged Vite hot updates ("[vite] Failed to reload /src/App.tsx, Chrome.tsx, StageBoard.tsx...: Importing a module script failed"), then "Could not connect to the server", and that step hung until it was killed. The Vite dev servers that served_ui starts for checks watched the checkout and pushed hot updates into pages while checks ran. So a file event in the worktree made those pages re-import modules from a server that was not answering. Each pile check passes about 99.8% of the time (484 to 641 runs, 1 to 3 failures each, every failure in a disrupted run), and I found no race in the checks' logic.

Unknown: what wrote into ui/src mid-run. The log kept only summaries for the step that passed on its rerun. Ruled out: the typescript test (it writes only under BERYL_UPDATE_TS), the conventions --check step, and vite build's dist/ (Vite's watcher ignores dist/). Two Vite servers sharing node_modules/.vite also did not reproduce the failure: I ran it with a stale cache and forced re-bundles, and the files are content-hashed and identical. Side finding: every worktree re-bundles at startup, because Vite puts the folder path (root) in the deps cache hash.

Choice: fix the environment and keep the checks (commit 128419f6). served_ui now sets BERYL_UI_FIXED, and vite.config.ts then sets hmr:false and watch:null. Only the interactive "just specs" playground passes hot=True. Verified by hand: with the variable unset, an edit to App.tsx reaches an open page as "[vite] hot updated". With it set, nothing reaches the page.
