Close reason

Worst stress-1024 frame 11.56M -> 9.68M on staging's counter (3.6M under the bead's 13.28M); f04795da6

Description

Symptom: after by-q44s.19 (commit 417c9da07), just b3d gate --counts measures stress-1024's worst frame (frame 30, where Client::handle compiles a script of 40 flights) at 13,282,629 instructions and stress-255's at 3,437,301, against the targets of 4,000,000 and 2,000,000 in docs/beryl-3d.md ('What it is held to').

Where the rest goes (Callgrind self cost in beryl3d-bench, stress-1024, rough):

  • ~3M: the segments themselves. Each step moves about half of its row's ~256 cards, so 40 steps make ~5,000 slides (Motion::step in rust/beryl3d/crates/beryl_scene/src/play/compile.rs: Motion::pose, retarget, add/Track::push).
  • ~2M: per-step work proportional to the whole table, not the dirty row: Zones::of_table (table/place.rs) builds a slot table from the played table's BTreeMap every step; members scans the whole battlefield for the row's cards; Played::leave (rust/crates/beryl_protocol/src/script/table.rs) runs retain over the 1,024-entry battlefield.
  • ~2M: malloc and free, mostly Table::of in beryl_protocol cloning 1,024 ObjectViews (a String and a Vec<CardType> each) at the start of compile and dropping them at the end.
  • ~2M: laying rows out (battlefield_row, lay_row, lands_in_order, piles in table/place.rs and table/rows.rs).
  • ~1.6M: drawing the frame (Table::write, FrameBuilder::finish), which is not compile work.

Possible fixes, cheapest first: (1) let Motion keep each row's member slots by group (it already keeps groups by slot) and look up only those objects, instead of building Zones and scanning the battlefield every step; (2) in beryl_protocol, make Table::leave use position + remove instead of retain; (3) avoid cloning every ObjectView into the played table (for example keep the played table between scripts when the next script starts from the view it ended on, or share unchanged objects). Keep every segment exactly as now.

How to measure quickly: the scratch probe approach used in by-q44s.19 (an example in beryl_inspect that plays the board to frame 30 and calls gate::frame_counted, built in beryl3d-bench and run under valgrind --tool=callgrind --toggle-collect='beryl_inspect::gate::frame_counted') gives one count in ~3 minutes. Remove the example before pushing; it does not pass the lints.

Acceptance criteria

The worst frame of stress-1024 in just b3d gate --counts is lower than 13,282,629 by at least 3,000,000, or the bead records with measured numbers what stops it; gates.json holds the lowered limits; segments are unchanged (just b3d lane passes, and just b3d test reports the same faults as before the change).

Final (f04795da6, rebased four times as staging moved): staging meanwhile started keeping the played table between scripts itself (94b9d3bb7, for ability numbers) and switched to one-run Callgrind counting (1452c9a4e), which moved the baseline to 11,561,495. What landed: play/index.rs keeps the played table's objects by slot and updates only the slots each step names (built only for scripts of 8+ steps, and only when every object equals the before view's, else falls back to Zones::of_table); battlefield rows found by each slot's group number (table/place/indexed.rs); NameIds sorted by name hash; protocol Table::leave uses position+remove; all_members reserves a row on its first card. Same-base measurements, staging -> mine: stress-1024 worst 11,498,087 -> 9,840,539 (final limit 9,679,562 on the last base), stress-255 3,165,356 -> ~2.82M, verbs-zones frame 922 2,337,721 -> 2,282,900, pay-default frame 0 +0.4% (within tolerance). Against the bead's figure 13,282,629 the worst frame is down 3.6M; against staging's own baseline under the new counter it is down ~1.8M. just b3d test: identical outcomes (8,208 tests, same frames and listed faults). The remaining big costs are the Played clone per script (Motion::new clones the carried table) and the per-step Zones::of_table copy for short scripts.
