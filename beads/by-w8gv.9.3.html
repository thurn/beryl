Description

Milestone 5 of Project 50k (plan K5 and K3; epic by-w8gv.9): the rules library and the card port. Line numbers and counts below were read at staging f5034c58; the code as it stands wins over this text, and a deviation is a comment on this bead.

This is the design bead of the milestone. Plan K5: "EffectCtx becomes free functions over Game and Resolution, in modules that mirror the Comprehensive Rules", because "an agent reading 'Scry 2' or a rule number finds the file by name, and each file stays small." Plan, Rules library:

beryl_rules/src/ actions/ CR 701, one file per keyword action (destroy, scry, explore) keywords/ CR 702, one file per keyword ability (flashback, kicker) damage.rs CR 120 counters.rs CR 122 tokens.rs CR 111

"Each module holds the function, the effect-data entry that calls it, its rule citation, its English template and its scenarios. Functions take Game (state, table, event sink). Those that only make sense while something resolves also take Resolution (source, controller, targets, X, the answer record)."

Eleven beads build on what this one decides. Write the decisions as a contract at the top of rust/crates/beryl_rules/src/lib.rs, the way rust/crates/beryl_kernel/src/lib.rs is the kernel's contract, and repeat them in a comment on this bead so enact brief shows them to every dependent.

What exists (after by-w8gv.9's first bead moved it to beryl_rules/src)

  • effect.rs (1,115 lines, 63 pub fns) with effect/ask.rs, effect/continuous.rs and effect/permit.rs: EffectCtx { state, table, sink, entry: StackEntry, ability, answers, record, used, question, mana, offer, full }. The first three are the game. entry is what resolves: source object, controller, card, face, ability, targets, X and what triggered it (TriggerInfo). answers, record, used and question are the answer record: a body that asks returns Err(Pause) and is run again from the top with the answers so far (docs/engine-architecture.md §7.3). mana is the kind a mana ability's activator chose, offer a card the body lets a player cast as it finishes (CR 608.2g), full a capacity that ran out (check, finish).
  • Most methods wrap free functions that already take (s: &mut State<L>, t: &GameTable, sink: &mut Sink<L>): event.rs (move_one, move_batch, draw, gain_life, lose_life, deal_damage, add_counters, remove_counters, set_tapped, create_tokens), layers::refresh, trigger.rs, cast.rs.
  • interpret/mod.rs (resolve, data, mana_ability, intervening_if), interpret/run.rs (Run carries out an Effect by calling EffectCtx methods and keeps the outcome registers behind Objects::Those, Amount::ThatMany, Condition::Did) and interpret/scene.rs (Scene reads Objects, Players, Amount, Condition).
  • bodies.rs: Body<L> = fn(&mut EffectCtx<L>) -> Flow, Bodies { small, large }, Conditions, and the bodies! and conditions! macros. 45 bodies in 32 card files call EffectCtx, and five more in beryl_cards/src/tests/effect_data.rs.
  • beryl_card/src/effect/mod.rs is the vocabulary (Effect, 21 instructions); it stays in beryl_card, which data-only card crates depend on alone (plan, Crates).

Decide, write down, then build

  1. Game: state, table, sink. Say whether the functions that take the triple today convert now or as later beads touch them (default: library functions take &mut Game; the engine's internals convert when a bead touches them, with no mass rewrite here), and how Full travels (today a flag on the context; the discarded-push check holds rules code, so a library function either returns Result<_, Full> or records it on Game in one audited place).
  2. Resolution: source, controller, the targets still legal (CR 608.2b), X, what triggered it, the answer record with the pause protocol, the cast offer and the chosen mana kind. From the M2 Mason audit (comment on by-w8gv.9.1, item 4): Effect::AddMana outside a mana ability reads EffectCtx::mana, which is Colorless unless a mana ability set it, so a spell's "Add {B}{B}{B}" trips a debug assertion and adds colorless mana in release. Decide where the kind comes from when nothing chose it.
  3. The module layout, by rule number: actions/ (CR 701), keywords/ (CR 702), and numbered-rule modules for the rest (zones CR 400, life CR 119, damage CR 120, drawing CR 121, counters CR 122, tokens CR 111, copies CR 707, continuous effects CR 611, and so on). Say where the interpreter's arm for an entry lives, so that "the effect-data entry that calls it" is found from the module. English templates are milestone 8's (K13): name where one will go and write none.
  4. Where a library effect's hand-written scenarios live (K3). The constraints: a scenario names real cards, since XMage and Forge run it; rules code names no card; beryl_scenario depends on the rules. Default: a test-and-tools-only module tree in beryl_cards that mirrors the library's (for example library/actions/scry.rs), whose scenarios use basic lands, the designated props and a card that has the effect. Record the choice: the port beads write one scenario for each entry they add, and a later bead tests that every entry has one.
  5. Custom bodies after the port. They stay in the card file (plan, A card file) and take Game and Resolution. Decide how a card registers one for both layouts without bodies! on every card. One way with no macro: a trait with a method generic over the layout, implemented by a unit type in the card file, from which a const fn takes the Small and Large instances. conditions! goes the same way or is replaced by Condition data.
  6. Build the first slice to prove the design: destroy (CR 701.8), scry (CR 701.22), counters (CR 122), damage (CR 120), life (CR 119) and tokens (CR 111) as free functions in their modules with their citations, called by the interpreter directly. EffectCtx becomes a Game and a Resolution plus its methods, and each method of the slice a one-line delegation: the shim. The 45 bodies compile unchanged and are never rewritten against the free functions; the port turns them into data and the milestone's closing bead deletes the shim.

Not in this bead

The other EffectCtx methods (the lane:library beads), any vocabulary change (lane:vocabulary), any card file.

Tests: cargo test -p beryl_rules, cargo test -p beryl_cards. Dispatch runs 10 to 20 times a game (K1), but scry, counters and tokens are on the counted path: keep the #[inline]s the methods had.

Held by checks (AGENTS.md, Code structure): no card name in generic code; no source file over 800 lines (data/file-length-allowlist.json only shrinks, and a new file starts under the limit); rules code and card bodies ask the state for a player's opponents and never name the other of two; they change the state through a mutator, never the board door; a push whose bound is argued takes Queue::push_bounded and any other propagates Full; a count or position that grows with the layout is never narrowed with as. No procedural macro, and a macro_rules! only where a const fn cannot remove the repetition. beryl_card, beryl_kernel and beryl_rules take no runtime dependency. Rules code cites the Comprehensive Rules with a yawgatog link and a quotation; keep the citations of code you move, and check new ones against the pinned release with just citations. Forge is a test oracle only (K16): no entry, name or design comes from its scripts. beryl_search/src/expert and beryl_search/src/frozen are exempt from the project: edit them only where a call stops compiling, giving the answer the old read gave. Decisions (the contract at the top of rust/crates/beryl_rules/src/lib.rs says the same; read that first).

  1. Game (game.rs) = state, table, sink. A library function that changes the game takes &mut Game and returns Result<T, Full>; one that only reads takes &State and &GameTable as the kernel's queries do (library::top, tokens::predefined). A card body gets game.state() to read and changes the game through the library alone. The engine's triple-taking internals are NOT mass-converted: a bead that touches one converts it, and until then a caller writes Game::new(s, t, sink) at the call (combat.rs, cast.rs, event.rs do).
  2. Resolution (resolution.rs) = the StackEntry (source, controller, card, face, ability, targets, costs paid, X, trigger info), the &'static Ability, legal (the targets legal as the resolution began, CR 608.2b, which the interpreter reads), the answer record (answers, record, used, question), the cast offer and the mana kind. A function takes it beside the game only if it reads the source/controller or asks. Questions are Resolution's methods taking the game: choose_yes_no, choose_up_to, choose_or_done, choose_object, may_choose_object, ask_options, ask_object. Resolution::target/target_object/target_player(&game, place) recheck legality at the call, as the bodies' ctx.target() always did. Mana kind when nothing chose it (M2 audit item 4): in order, the mana ability's activator's choice (carried on the resolution), else the set's one kind, else for a set of several outside a mana ability a question asked as the effect is applied (CR 608.2d). Only the first is built; no card needs the others, and building them is a vocabulary change (ManaSet has no "its one kind", Effect::asks says AddMana never asks), so the first bead that gives a spell AddMana builds the second.
  3. How Full and a pause travel: card::Flow = Result<(), Stop>, Stop::{Pause, Full}, From<Full> for Stop (the unit struct Pause is gone; no card named it). A Game function returns Result<T, Full>; one that may ask returns Result<T, Stop>; ? everywhere. No flag, no default in place of a failed result, no playing on: a push is ? or push_bounded. resolve::run turns it into the stall once (EffectCtx::finish(flow)). Deviation from today, on purpose: a library function out of room ends the resolution at once instead of noting a flag and playing on to the end of the body; the state is abandoned for Large either way (test: an_instruction_out_of_room_stops_the_resolution_at_once). The shim's unit-returning methods keep the flag (EffectCtx::full, check, checked), so no body changes.
  4. Modules, by rule: actions/<name>.rs for CR 701 (built: destroy, scry), keywords/<name>.rs for CR 702 (none yet), and a top-level module named for any other rule's title (built: tokens CR 111, life CR 119, damage CR 120, counters CR 122, library CR 401). Suggested homes for the rest of EffectCtx: actions/{counter, discard, exile, explore, manifest_dread, mill, reveal, sacrifice, search, shuffle, tap}; keywords/{flashback, kicker}; emblems (114), costs (118: unless_pays, pay), drawing (121), zones (400: move_to, move_all, return_to_hand, put_onto_battlefield*), the stack (405: spell_controller, spell_mana_value), linked (607: exile_linked, exiled_with_source), continuous (611: add_effect*, gain_control, with the typed Effect pairs of the M4 audit item 2), coins (705), copies (707). A module holds, in order: the rule's title/number/link as its first line; the pub functions with citations (an action's function has the action's name, actions::scry::scry; a thing's module holds verbs, life::gain); the interpreter's arm for each entry that calls them, pub(crate) fn instruction or <function>_instruction, taking &mut Run and the entry's operands as vocabulary types (Objects, Players, Amount) and returning the Outcome; later the English template (K13, M8) as a const directly above its arm (none written). Run::carry_out in interpret/run.rs is the table: one line per entry naming its arm; an entry whose module is not written still has its arm there. Run's helpers for arms are pub(crate): game(), resolving(), state(), scene(), in_turn_order(), permanents(), next_permanent(), remember(), left_the_battlefield().
  5. Scenarios (K3): not in the library module (a scenario names real cards; rules code names none; beryl_scenario depends on the rules). They go in beryl_cards in a tree mirroring the library (beryl_cards/src/library/actions/scry.rs), using basic lands, the designated props and one card that has the effect. The port bead that adds an entry writes its scenario; a later bead tests every entry has one. Nothing is built for this here: the first port bead creates the tree and joins it to SCENARIOS and the oracle exporters.
  6. Custom bodies: trait beryl_rules::CustomBody { fn resolve<L: Layout>(game: &mut Game<L>, resolution: &mut Resolution<L>) -> Flow } on a unit type in the card file, and body: custom_body::<TheType>(), a const fn that makes both layouts' instances (an associated const holds the Bodies; no macro, no proc macro). Built and used by one test card (tests/cast.rs, DestroyTarget on REMOVAL). Until the shim goes it is adapted to the old Body<L> = fn(&mut EffectCtx<L>). conditions!: an intervening "if" is Condition data; one that data cannot say gets the same trait + const fn when first needed.
  7. The shim: EffectCtx { game, resolution, full }. The third field is the one deviation from "the two of them plus methods": it is the unit-returning methods' old way with Full and goes with the shim. Each lane:library bead moves a method's code into its module's function, the arm into an instruction, and leaves the method a delegation. The closing bead deletes EffectCtx, the flag, bodies! and conditions!.

Counts, just bench-count before (staging 1bd6ff92) -> after: copy 13,481 -> 13,481; next_apply 362,079,176 -> 362,102,204 (+0.006%); policy 1,745,065 -> 1,745,065; rollouts 389,507,068 -> 389,530,096 (+0.006%; just count-gate: +0.05% against the bar of 389,343,295, 1% tolerance, no bump). The 23,028 instructions are in next_apply: resolve::run now builds a Resolution and a Game inside the context and stores legal; I did not chase it further. Tests: beryl_rules 162 (one new), beryl_cards, the corpus replay and rollouts_never_change pass. No card file changed. data/file-length-allowlist.json: effect.rs 1115 -> 1109; cast.rs unchanged at 1739.
