Dump carries each named card's abilities, costs, castings and effect facts; table map on the bead

Description

Milestone 7b of Project 50k (docs/project-50k.md, "Card pool pipeline": "Oracle exporters derive each card's translation from its effect data"; K1: the derived exporters read effect data). First bead of lane exporters. The XMage and Forge exporters keep tables keyed by card name that say how each oracle names an ability, asks about a cost or takes a choice. At 50,000 cards nobody can keep them. This bead puts the facts those tables encode into the scenario dump, read from each card's definition; the next two beads delete the tables.

K16 holds throughout this lane: Forge and XMage are test oracles. Nothing from their scripts or code becomes card data, vocabulary or design; the exporters only translate Beryl's scenarios into each oracle's test language.

Today

  • cargo run -p beryl_cards --features scenarios --bin beryl_scenario -- dump [PATH] (rust/crates/beryl_cards/src/bin/beryl_scenario.rs, 50 lines) writes beryl_scenario::to_json(&CARDS, &cards) (rust/crates/beryl_scenario/src/lib.rs:727): per scenario an Entry { card, scenario, snapshot, trace, failure }. tools/src/beryl_tools/oracles.py:507 (dump_scenarios) runs it. The dump says nothing about what a card's abilities are.
  • The name-keyed tables, each with a comment saying what fact it stands for:
    • tools/src/beryl_tools/xmage.py:98-223: ABILITIES (an activated or loyalty ability by card and index, as the start of its text), MANA_ABILITIES, MANA_CHOICES (sources that make one kind of mana or several), CAST_QUESTIONS (alternative and optional costs asked at casting), OVERLOADS, TRIGGERS_FIRST, FORCED_SEARCHES, TARGETS_IN_CAST, ASKED_FIRST, MAY_CHOOSE, UNLESS_PAYS, CHOICES_AS_TARGETS, SEARCHES, SCRIES, TAKES.
    • tools/src/beryl_tools/forge.py:76-118: COSTS (the casting option's keyword), ABILITIES.
  • A definition is data: rust/crates/beryl_card/src (ability.rs, cost.rs, effect/, trigger.rs, target.rs, and walk.rs, which visits a definition's effect tree). The store has each face's Oracle text (beryl_card_store).

What to build

Add to the dump one description per card that a dumped scenario names (the scenario's own card and every card in its setup), read from the definition and nothing else: per face, each ability's index as scenarios number it (Own i, Granted k), its kind (spell, activated, loyalty, mana, triggered, static), its cost in a form an exporter can render (mana, tap, sacrifice, loyalty change, remove counters, crew, and so on, as cost.rs has them), the mana a mana ability makes (one fixed kind or a choice), each casting option of the face in costs bit order with its kind (alternative or additional) and keyword (overload, evoke, impending, kicker, offspring: whatever the vocabulary calls them), and the effect facts the tables stand for: whether a resolving ability scries, searches a library (whose, and whether "may"), looks at the top N and takes K, asks "may choose" then which, counters "unless its controller pays", chooses objects where an oracle takes targets, and what a target spec accepts (a "spell or permanent" target). Derive each from the effect tree by a walk; do not add a field to the vocabulary to carry one, and do not name a card. Where a table's fact cannot be read from the data, say which and why on the bead (the next beads then report those scenarios through data/oracle-exporter-gaps.json, which exists for the scenarios an exporter cannot script, rather than keep a named entry).

Go through every table above against the list and make sure the dump can replace it; the list here is from reading the tables' comments, not from running them. Keep the description small and stable (sorted keys, no addresses): tools/tests/test_oracles.py, test_xmage.py and test_forge.py use recorded dump entries.

Put the walk in the crate that owns the dump (beryl_scenario, or a module of beryl_cards beside the binary), not in beryl_card. Test it in Rust on a handful of the 47 cards chosen to cover every fact (Strip Mine, Jace the Mind Sculptor, Subtlety, Winds of Abandon, Stock Up, Aang's Iceberg, Trinket Mage, Mana Tithe, Thundertrap Trainer, Floodfarm Verge): the test file may name cards.

This bead changes no exporter behavior: the Python reads past the new field. just oracle gives the same summary before and after.

Acceptance criteria

beryl_scenario dump includes, for every card a dumped scenario names, a description read from its definition alone: each ability's index, kind and cost, mana abilities' output, casting options in bit order with kind and keyword, and the effect facts each name-keyed table in xmage.py and forge.py stands for; the bead maps every one of those tables to the dump field that replaces it, or says why none can; the walk names no card and adds no vocabulary field; Rust tests cover each fact; just oracle's summary is unchanged; the Python lane and the parity checks pass.

Table -> dump field map (dump: each entry has cards: {name: {faces: [{name, transformed?, abilities[], grants[], casting[], additional_cost[]}]}}, the scenario's card, every setup/action card and the tokens they make; per ability: index ("Own i" / "Grant i"), kind (Spell/Activated/Loyalty/Mana/Triggered/Static/Replacement), cost {mana in Scryfall notation, parts[{action, of This|Chosen, counter, zone, other, count|total_power|for_generic, amount, one_of}]}, produces {colors, amount}, conditional, trigger (event), targets[{kind,count,optional,other}], instructions[{kind, may, player, others, objects, count, optional, take, rest, cost}] in written order; May/If/ForEachPlayer/Sequence shape their contents (may, players of the "each") and Unless is an instruction before what it guards. Walk: rust/crates/beryl_scenario/src/facts.rs; tests: beryl_cards/src/tests/facts.rs).

XMage:

  • ABILITIES -> abilities[index] on the face named (back faces by face name). Loyalty: cost.parts[Loyalty].amount -> "+N:". Activated: cost.mana + parts (Tap/Sacrifice/RemoveCounter of This) -> "{W}, {T}, Remove a story counter"; part.for_generic -> "waterbend {N}"; part.total_power -> "Crew N"; Discard of This + Draw -> "Cycling". Same-cost abilities (Currency Converter) differ by instructions[0].kind. "Granted k" (Jace VP's crew): granting face's grants[] ("Grant i"); k counts grants in the order granted, a game fact; with one granting card in the setup it is that card's grants in order.
  • MANA_ABILITIES -> kind Mana with cost Tap of This and produces {colors:[c], amount:n} -> "{T}: Add " + symbol*n.
  • MANA_CHOICES -> a face with several Mana abilities (Tundra, Seachrome, Spara's, Floodfarm whose second is conditional). NOT DATA: Soporific Springs has one {U} ability; XMage's choice comes from the modal card's two faces. The dump says it is faces[1] without transformed (a modal back), which the exporter may key on, else a gap.
  • CAST_QUESTIONS -> casting[bit]: alternative (Impending/Evoke/Overload) -> "Cast with <keyword>"; additional (Kicker/Offspring) -> Yes/No. NOT DATA: Subtlety's "asked only while a blue card in hand could pay" needs the evoke part's filter, which the dump does not render (the part says Exile, Chosen, Hand, count 1); read payability from the scenario (hand contents) or report through oracle-exporter-gaps.json.
  • OVERLOADS -> casting keyword Overload (+ ability, the overloaded spell ability).
  • TRIGGERS_FIRST -> Triggered abilities with trigger and instructions, in index order (Subtlety: Own 0 Enters/PutIntoLibrary, Own 1 Enters/Sacrifice). XMage's wording ("When {this} enters, choose") is XMage's: match by event and order.
  • FORCED_SEARCHES -> Search with player EachPlayer (from the each-player) and count ThoseOf. NOT DATA: "opponent" (only players whose creatures were exiled search) follows from the exile's filter, which is not rendered; treat a Search of every player with a non-fixed count as asked of each, or a gap.
  • TARGETS_IN_CAST -> targets[].kind SpellOrPermanent.
  • ASKED_FIRST -> instruction UntapUpTo (objects "All Battlefield", count 6). The lands filter and XMage's condition for its shortcut are not data.
  • MAY_CHOOSE -> Choose with optional (Elite Spellbinder: one question, setChoice) vs Dig with take MayReveal (Thundertrap: yes/no then addTarget): the instruction kind picks the queue.
  • UNLESS_PAYS -> instruction Unless {player, cost.mana}.
  • CHOICES_AS_TARGETS -> instruction kinds: Search (Trinket Mage, Winds), PutBack/Fateseal (JTMS). The exporter keeps an instruction-kind set, not a card set.
  • SEARCHES -> Search with may.
  • SCRIES -> Scry with count.
  • TAKES -> Dig with count (look) and take n.
  • FORCED_ASKED, FORCED_COSTS, FORCED_CHOICES, CHOICE_KINDS, YES_NO_KINDS: keyed by decision kind or purpose, not card; untouched. Forge:
  • COSTS -> casting[].keyword (Impending/Overload/Evoke/Kicker/Offspring) verbatim.
  • ABILITIES -> loyalty amount ("+1", "-3", "0:"), keyword from cost (Crew/total_power, Cycling, Waterbend/for_generic), else instructions[0].kind (Draw, Destroy, Explore, Choose for "Put a card exiled") via an instruction-kind table.

Decisions: facts ride on each entry (cards), not a top-level map, so entries stay self-contained for the recorded fixtures in tools/tests; +2.8 MB on an 8 MB pretty dump. Filters are not rendered (would need a name table per bitset in the dump crate); named NOT DATA above. beryl_scenario now depends on beryl_card directly (effect types aren't re-exported by beryl_rules::card).
