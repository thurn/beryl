Description

Milestone 5 of Project 50k (plan K5 and K3; epic by-w8gv.9): the rules library and the card port. Line numbers and counts below were read at staging f5034c58; the code as it stands wins over this text, and a deviation is a comment on this bead.

The plan's crate table (docs/project-50k.md, Target architecture, Crates) puts turns, priority, casting, mana, combat, layers, triggers, the interpreter and the rules library in beryl_rules, depending on beryl_kernel and beryl_card, and says: "beryl_engine stays as the facade other crates import until the last caller has moved." The crate does not exist yet: all of it is rust/crates/beryl_engine/src (about 10,900 lines outside src/tests, 7,700 in src/tests). Every later bead of this milestone writes into beryl_rules, so this one lands first and does nothing else.

Scope

  1. Create rust/crates/beryl_rules (edition, license and lints from the workspace; dependencies beryl_card and beryl_kernel only; the coverage feature). git mv every module of beryl_engine/src into it, src/tests included, so history follows: announced, bodies, card, cast, combat, coverage, effect (and effect/), engine, event, face_down, interpret/, layers, mana (and mana/), permission, reference, resolve, rule_change, sba, scratch, start, stops, trigger, turn.
  2. beryl_engine becomes a lib.rs that re-exports beryl_rules under the paths it has today (lib.rs lines 12 to 85 are the list: the card, coverage, effect and event modules, the layout and profile modules that mix kernel and rules items, the kernel modules, and the root re-exports), depends on beryl_rules, and forwards the coverage feature. No other crate's source changes: 56 files of beryl_cards, 85 of beryl_session, 43 of beryl_cli, 24 of beryl_search, 9 of beryl_scenario and 2 of beryl_bench import beryl_engine, and they move in later milestones or never.
  3. bodies! and conditions! (bodies.rs) are #[macro_export] macros that expand to $crate::card::... and $crate::layout::...: after the move $crate is beryl_rules, so those paths must exist there, and beryl_engine re-exports the macros (pub use beryl_rules::{bodies, conditions}). Card files write beryl_engine::bodies.
  4. Tools that name the engine's path: tools/src/beryl_tools/two_player.py, board_door.py, discarded_push.py, card_names.py, scale.py, checks.py (the lanes that map a changed path to a check: rust, script, names, oracle), selection.py and their tests under tools/tests (test_two_player.py, test_board_door.py, test_discarded_push.py, test_card_names.py, test_checks.py, test_file_length.py, test_selection.py, test_warm.py, test_runlog.py, test_prune.py). Each check that holds "rules code" must now hold rust/crates/beryl_rules/src. data/file-length-allowlist.json names cast.rs (1,739), effect.rs (1,115), engine.rs (826) and mana.rs (1,585) under beryl_engine: the entries follow the files with the same counts.
  5. docs/engine-architecture.md §16 (the crate map, which AGENTS.md points at): add the beryl_rules row and correct the beryl_engine row. Nothing else in the docs; the Archivist (by-w8gv.17) rewrites the document at the end of the run.

Gotchas

  • The engine is generic over the layout, so most of it is instantiated in the crates that call it, and the benchmark profile is fat LTO with one codegen unit (rust/Cargo.toml, [profile.search]): the crate boundary should cost nothing. Measure it anyway, and if the count moves, find the function that stopped inlining rather than accept it.
  • beryl_engine's tests are unit tests under src/tests that reach pub(crate) items: they move with the code and stay unit tests of beryl_rules.
  • cargo test -p beryl_engine appears in docs and in other beads; after this bead it is cargo test -p beryl_rules. Leave a line in the handoff.
  • The warm-cache tools (enact worktree, tools/src/beryl_tools/warm.py) copy rust/target: a new crate needs nothing from them, but run just check from a fresh worktree state to be sure.

Need not read: card files, beryl_session, beryl_search, ui/.

Run just bench-count before and after and record both on the bead: the benchmark is the WU Control mirror, so what this milestone moves is on the counted path. No behavior changes: no rules fix, no new card, no new mechanic (K14). A rules bug you do find and fix gets a docs/bugs.md entry (AGENTS.md). A save or a rollout replays the decisions a game asked, in order: never change which questions a resolution asks, their order or their options.

Held by checks (AGENTS.md, Code structure): no card name in generic code; no source file over 800 lines (data/file-length-allowlist.json only shrinks, and a new file starts under the limit); rules code and card bodies ask the state for a player's opponents and never name the other of two; they change the state through a mutator, never the board door; a push whose bound is argued takes Queue::push_bounded and any other propagates Full; a count or position that grows with the layout is never narrowed with as. No procedural macro, and a macro_rules! only where a const fn cannot remove the repetition. beryl_card, beryl_kernel and beryl_rules take no runtime dependency. Rules code cites the Comprehensive Rules with a yawgatog link and a quotation; keep the citations of code you move, and check new ones against the pinned release with just citations. Forge is a test oracle only (K16): no entry, name or design comes from its scripts. beryl_search/src/expert and beryl_search/src/frozen are exempt from the project: edit them only where a call stops compiling, giving the answer the old read gave. Other tracks edit nearby files (presentation by-w8gv.21 in beryl_session and ui/, mobile, the AI ladder): enact push rebases and you fix the conflict.

Decisions: (1) beryl_rules exports only rules items. The kernel's modules are pub(crate) aliases in its lib.rs so moved code keeps its crate::state / crate::ids paths; the facade re-exports the kernel's modules from beryl_kernel itself. The exceptions are the mixed modules the bodies!/conditions! macros and callers need: layout, profile, event (and card, the vocabulary plus Flow/Pause). (2) The rules' tests import the kernel's root names (crate::Choice, crate::State...) as a caller of the facade does; rather than rewrite 15 test files, lib.rs has one #[cfg(test)] pub(crate) use block of those names. The seven tests that imported crate::two_player now import beryl_kernel::two_player, so beryl_rules' lib.rs never names it and needs no exemption from the two-player check. (3) two_player.RULES (which board-door and discarded-push share) and card_names.SCOPE hold beryl_rules/src and still hold beryl_engine/src, so no rule can be written beside the facade unchecked; the facade's lib.rs keeps its two-player exemption for the re-export. (4) tests/banned.rs (determinism: no HashMap, clocks...) scanned beryl_engine and beryl_cards by directory name; it now scans beryl_rules and beryl_cards. (5) git shows beryl_engine/src/lib.rs as modified and beryl_rules/src/lib.rs as added, since the old path still exists; every other file is a rename. (6) Left as the bead says: docs/rules-coverage.md:32 still names beryl_engine/src/card.rs (Archivist).
