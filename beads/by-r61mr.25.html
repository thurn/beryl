Description

Read the epic by-r61mr first: it holds the decisions, the code map and the directory layout this bead assumes. The work is in the Enact repository (~/enact) unless this bead says otherwise, delivered with that repository's own enact worktree create and enact push.

Switch Beryl's fleet to the ticket server. The user decided this happens automatically, with no approval, once three gates pass. Check them first and stop with a comment naming the failed gate if any does not:

  1. The shim's replay test passes on a corpus recorded within the last few days (record a fresh one if the corpus is older).
  2. tk compare shows the production import matches the bead store except for recently changed beads.
  3. The server holds a recent event from each of the three machines.

Then:

  • Set the cutover state to paused. Every shim on every machine now waits, so nothing writes to either store.
  • Run the final tk import and tk compare. If the comparison is not clean, set the state back to before, comment with the differences and stop: nothing has been lost.
  • Set the state to after. Shims now answer from the server and Enact's helper uses the server backend. The pause should last about a minute.
  • Make the bead store read-only and record the date: it is kept for two weeks.
  • Verify from this machine: bd list through the shim, enact next, a claim, a comment, a push through the staging lease, and the dashboard updating live. Watch the first hour's counters against the limits.
  • Add an entry to Beryl's data/efficiency-changes.json for the change, with the lock-wait numbers from the epic as the baseline.
  • Comment on the epic with the pause's length and the verification results.

Acceptance criteria

The cutover state is after; tk compare was clean at the switch; a ticket created through bd create on this machine appears on the dashboard within a second; enact next returns in well under a second; and the epic has the result comment. The bead store is read-only and its date is recorded.

Notes

Follow section 7 of the contract for the pause, the drain wait, the final import and the straggler import one hour later.

Cutover check against JARVIS's bd calls. The bd recorder ran on JARVIS from 2026-11-16 23:30 to 2026-11-17 06:07 UTC and logged 9,126 calls. Every distinct command line was run through the shim's argument parser (Options::try_parse_from in Enact cli/src/shim.rs at 817576a).

  1. On JARVIS, the full exports come from a local 'just status' server ('beryl-status serve', running since 08:46 local time), not from Scotty. It runs a bare 'bd export' about every 4.6 seconds whenever the Dolt files change: 3,935 calls with a median of 1.44 s each. It also runs 'bd history <id> --events --json' 724 times. The shim has no history subcommand, so after cutover those calls fail with 'unsupported arguments'. The bare export parses as Action::Export and is refused, the same way as the recorded 'export --json' shape. The hourly ca.thurn.beryl.status launchd publisher is also installed on JARVIS and makes the same calls. The gate above should require that no 'beryl-status serve' process runs and that the status agent is uninstalled on every host, not only that Scotty is retired.
  2. Agents typed bd commands by hand that the shim rejects after cutover: search (30 calls), version (5), create with a positional title and -l for labels (5), dep cycles (2), children, sync, list --label-any, and comments add -f (1 each). They get 'use tk ...' and can recover. The positional-title create is the most likely to cost a session time.
  3. Volume: if this 6.6-hour rate held for a whole day, JARVIS alone would make about 12,500 reads, 2,600 ticket writes and 900 comments a day. That is 83% and 91% of the contract's fleet-wide normal-day read and comment counts (15,000 and 1,000). Request headroom is large, and writes stay under the model. Enact's Beads.all() ran 1,417 times (about 5,100 a day). After cutover it becomes 'tk graph --all' with an ETag. The changed path is built from memory, but it returns the whole archive, and the local cold build measured 16 ms against the 10 ms free-plan CPU limit, so the production CPU check should include this rate.

No concern found for: claim conflicts (the shim reproduces bd's message), 'create --id' duplicates (verdicts.py uses the native path with request_key, and the legacy path ignores the failure), SIGPIPE exits from 'bd show', and calls from cache worktrees under ~/Library/Caches/beryl (not tested against the shim's config lookup).
