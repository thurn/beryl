Description

File the task beads for milestone 5 of this epic (parity), against the code that exists now.

For the web interface's side of the same features, read ui/src and the open beads that are changing it.

Then file children of this milestone epic so that every exit check is covered:

  • Each bead is one session's work and is a context packet: the doc sections to read, the files and functions to change, the helpers to reuse, the tests to write and the command that runs them. Look at milestone 1's beads for the level of detail.
  • Size beads by code, not by topic. Give two to four beads that touch the same code and have the same tier one lane:<name> label, and label tiers as AGENTS.md's Enact section says. Never label an epic.
  • Add dependencies only where one bead needs another's result.
  • File one Warden (role:warden, P1) per area, depending on that area's beads, saying what to look hardest at.
  • Where the doc and the code now disagree, correct the doc in a change of its own.
  • Update the epic's 'Code map' with the modules this milestone will touch.
  • Follow the epic's 'Rules for planners' and the tracks below. They decide the shape; you decide the detail.

Run enact sync when the beads are filed.

Tracks

  • the parity list (item 1), first;
  • one bead for each line of the list that is not complete (item 2), side by side;
  • the tools (item 3), one bead each, side by side;
  • UI Conventions (item 4) and Windows (item 6);
  • the manual QA pass and the write-up (items 5 and 7), last.

How to write each bead

Whoever works a bead has nothing but the bead, the doc and the code. Write for that reader.

  • Decide everything that can be decided now. A bead never says 'choose', 'pick', 'find out whether' or 'in X or Y'. Where the answer needs a measurement, the bead says what to measure, the threshold, and what to do on each side of it.
  • Name the crate, the file and the function or type for every piece, and which crate each test goes in. Give exact versions for any new dependency.
  • Name the web interface's files that hold the behavior, and say what to take from each. Open each file yourself first and quote the function names: do not name a file you have not read.
  • List the tests by what each one asserts, and give the commands that run them.
  • Write acceptance criteria that a command can show true or false.
  • Say what the bead must not build, when a later bead builds it.
  • Keep a bead to what one session can hold: about 600 lines of new code, or one module.
  • Before filing, check the dependencies: no bead's Run: line uses a command that a bead it does not depend on creates. Run bd dep cycles.
  • The epic's rules 14 to 16 say what a worker does when a bead is wrong and when it is done. Do not repeat them in each bead.

What this milestone's beads must cover

Each numbered item is at least one bead. The indented lines are what that bead must say; add the function names you find when you read the code. The web interface's files named below come from a listing of ui/src on 2026-11-14 and from reading the headers of the stage's files; that code changes every day, so open each file before you quote it, and replace a name that has moved. Where an item says 'one bead each', file that many.

What exists when you start: Beryl 3D plays whole games on the Mac. This milestone finds and closes every remaining difference from the web interface. It ends with a write-up of the switch, not the switch.

  1. The parity list, one bead (doc 'The parity list'): data/beryl3d/parity.json listing the screens and the tools by hand (described in rust/beryl3d/AGENTS.md); in the tools package, just b3d parity, which prints the list in the doc's format from ui/fixtures.json, the card specs, ui/shapes.json, data/ui-conventions.json, data/beryl3d/timeline-parity.json, data/beryl3d/parity.json and the result of just b3d test; a step of the sweep that fails when a screen in ui/src/screens or a skill is missing from data/beryl3d/parity.json.

  3.   8. One Warden for the parity list and the tools.
