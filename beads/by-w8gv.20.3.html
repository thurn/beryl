Close reason

Inferred verdicts recorded in ci-check beads, quarantine and pending list, ci-report --quarantined/--pending, by verdict (3d0f935f)

Description

Infer a verdict for every failure, rerun failures once, and quarantine repeat flakes (plan K18 and K21). Builds on the run log bead.

  • Rerun: when a lane fails, rerun only its failed checks once (ui-test takes title filters, shots takes names, nextest takes a filter expression, oracle takes card names). If they pass, the lane passes, the first failures are logged with verdict flaky and a flaky: line names them.
  • Stale test or caught a bug: when a check that failed next passes, classify the paths that changed between the two trees. Only the check's own side (ui/scripts, ui/fixtures.json, ui/shots.json, Rust under tests/ or src/tests or inside #[cfg(test)], a card file's scenarios, data/oracle-divergences.json) is stale; only product code is catch; both is mixed. Keep the per-lane path rules in one table.
  • Mixed prints one line asking for by verdict <check> stale|catch and never blocks. The same command corrects any inferred verdict.
  • This covers a slow-CI failure a Steward fixes: failure at one commit, pass at a later one.
  • Quarantine is derived from the log, not a committed list: two flaky verdicts in seven days on this host. A quarantined check still runs and is logged, cannot fail a run, and files no bead. just ci-report --quarantined lists them.
  • Tests in tools/tests for the classifier and the quarantine window.

Acceptance criteria

A flaky, a stale and a caught failure each get the right verdict in a pytest; a rerun that passes passes the lane; two flakes in seven days stop a check failing a run.

Notes

2026-11-10, added scope agreed with the presentation track (by-w8gv.21, plan K30): a pending list, built on the same mechanism as quarantine. A check named on it runs and is logged with outcome pending-fail or pending-pass but cannot fail a run. Entries are boards in beryl_cli's boards.rs tagged with the bead id of the banked UI report; the list lives beside the verdict table's path rules and each entry names its board and bead. just ci-report --pending lists them, with any that now pass, so the stage's beads can claim them (remove the entry, making the check a normal one). The weekly prune ignores pending checks. by-w8gv.21.2 uses this if it has landed and otherwise keeps its own list, so do not hold either bead for the other. 2026-11-10, added scope from the user ("could this be recorded in beads as well, at least for failures, for long term analysis?"): every failure that reaches a verdict is also recorded in beads, which are in git, shared by every machine and survive a cache wipe. Shape: one bead per check that has ever failed, created closed so nothing schedules it, titled with the check id, labeled ci-check and ci-lane:<lane> (not lane:, which Enact reads as a work lane). Each resolved failure is one comment on it (bd comments add; comments are rows of their own, so two sessions recording at once do not conflict as edits to one notes field would): a single JSON line with time, host, failing commit, script (check or ci), verdict, the commit or tree that fixed it, seconds, and for a slow-CI failure its Steward bead id. Only failures with a verdict are written: one line per flaky, stale, catch or miss, never one per red run while an author iterates, and never a pass (passes and timings stay in runs.jsonl). by verdict rewrites the comment it corrects. Quarantine and the pruning rule read verdict history from these beads, so they are the same on every host; runs.jsonl supplies run counts and seconds. just ci-report joins the two, and bd sql over the comments is the long-term query. A bd write that fails never fails a check; enact push and enact sync publish as usual. 2026-11-10: the rerun itself moved to by-w8gv.20.7 so that protection does not wait for the run log. This bead now takes its flaky: results as given: it logs them with verdict flaky, records them in the ci-check beads and adds quarantine. Everything else here is unchanged.
