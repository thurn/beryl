Close reason

Published the viewer-scoped action contract and tested reference resolution against the live table log.

Description

The M2 view bead by-bmdk.3.1 explicitly maps beryl_table::ObjectId(u32) to beryl_session::protocol::ObjectId(u16) with viewer-specific stability. But its public view contains only the stage slot. By-bmdk.3.5 sends Action JSON with beryl_table/src/action.rs Selection and SeenObject host ids, and by-bmdk.3.11 has the client turn taps and other gestures on stage slots into those actions. A tap can name a different card as soon as the first slot and host id diverge. Slot reuse also means translating a delayed request using only the current slot table can hit a new occupant in the same zone.

Define one explicit action reference boundary for the upcoming beryl_table_session view and command signatures. Carry a viewer-scoped actionable handle and expected zone/generation (or a view revision tied to the slot mapping) where needed, then translate centrally before calling Log::apply and its existing permissions checks. Keep host log actions and save format using host ids. Give the UI an explicit typed reference where it has enough permission to act. Do not make the UI infer a host id or expose a private id correspondence. Coordinate with the marker identities and visibility projection gate beads. Touch beryl_session/src/protocol/table.rs and protocol generation, and document the contract for by-bmdk.3.1, .3.5 and .3.11 before callers implement it.

Acceptance criteria

After drawing or shuffling, a seat can tap, move and target the current visible card through the public table command. A reference from before the replacement or from another viewer is refused and cannot act on a new occupant. Cover two equal stack markers and a lent opposing pile. Client code uses no cast from a stage slot to a host object id.
