Close reason

Agent cargo builds start on free tokens (no 10 s hold-out); median edit-to-output 2.8 s at load 20

Description

Symptom: after a one-line edit in beryl_scene, just b3d tree verbs-zones --at 1500ms (target 3 s, docs/beryl-3d.md 'Edit-to-output time') took 11-13 s in three of six runs at load 8-16 on 2026-11-16, after e07e319fe removed the same wait from the b3d command itself. The incremental cargo build held its lease 1.6-1.9 s but waited 8.3-11.6 s for it ($BERYL_CACHE/cpu-tokens/leases.jsonl, class agent, command 'cargo build', wanted 12).

Why: the cargo shim (tools/shims/cargo, tools/src/beryl_tools/cargo_pool.py) asks tokens.Pool.acquire for largest(pool) = 12 tokens. When fewer are free and a lower class (ci, sweep) holds elastic tokens, acquire holds out for up to RECLAIM_SECONDS (10 s, tokens.py) to get all 12. Over milestone 3 (2026-11-15 21:00 to 2026-11-16 20:30) agent 'cargo build' leases waited 44,918 s in total against 75,214 s held, p90 wait 24 s.

Proposed change: do not hold out for reclaim when the build will be short. Either take what is free at once and let the lease grow (cargo reads no grant file, so give the shim a jobserver-style top-up, or simply skip the hold-out for class agent), or skip the hold-out when the target directory's last build of the same package set finished in under a few seconds. Keep pushes' behaviour unchanged.

Expected gain: edit-to-output back under 3 s at the machine's usual load, and roughly 10 s off every agent build that currently waits.

Acceptance criteria

Six one-line edits in beryl_scene, each followed by just b3d tree verbs-zones --at 1500ms, at load 15 or more: every 'cargo build' lease in leases.jsonl waited under 1 s and the median command time is under 3 s. tools tests cover the new rule (tools/tests/test_tokens.py or test_cargo_pool.py). Entry in data/efficiency-changes.json.

Handoff: tools/src/beryl_tools/cargo_pool.py: compile-only commands (SHRINKS) of a class below push (STARTS_SHORT = agent, ci, sweep) call Pool.acquire(hold_out=False), so they start at once on free tokens; while short of want, for the first RECLAIM_SECONDS they keep a waiter file (cargo_pool.wait_beside, written only when lower classes hold elastic tokens) so ci/sweep still give back, and the jobserver top-up takes those tokens. tokens.py: Pool.acquire gains hold_out (default True, pushes/queue unchanged); Pool.waiter(klass) names the per-thread wait file that grant counts as its own; _THREADS renamed THREADS so cargo_pool can take it (tokens.py stays under 800 lines, 797 now). Tests: test_cargo_pool.py test_an_agent_build_starts_on_free_tokens_while_ci_gives_back, test_a_push_build_still_waits_for_lower_classes. Measured at load 20-21, six one-line edits in beryl_scene/notice.rs then just b3d tree verbs-zones --at 1500ms: every agent cargo build lease waited_s 0.0, times 4.03 4.33 2.79 2.37 2.80 2.77 s, median 2.8 s. Deviation: chose 'skip hold-out for classes below push' plus a time-boxed waiter file over the 'last build was short' heuristic, so long agent builds still reclaim from ci/sweep.
