Close reason

Time split per window (window_time), command kinds table (other 1.3%), compile vs run; pushed ccc617ba

Description

Split each bead window's wall-clock time so that every second falls in exactly one category and the categories sum to the window's length.

Design sections: "Time accounting" with "Command kinds".

What to build

  • The six categories of the design, with its order of precedence where more than one could apply: waiting on a person, queued for cores, tool by kind, model, waiting on background work, idle. Agent minutes are queued for cores, tool, model and waiting on background work; waiting on a person and idle are reported beside them. A subagent's time adds nothing to the window: it is a breakdown of the parent's Agent call. "Queued for cores" is filled by the CPU bead: leave the column and the join point, at zero.
  • Parallel tool calls: overlapping seconds divided equally among the calls running at that instant.
  • data/efficiency-command-kinds.json: the ordered table of patterns, with its entry in data/AGENTS.md. Match after removing leading cd <path> && and environment assignments. A first pass over the real transcripts found these buckets by tool time, which the table must name: orchestration wait (enact next, enact wait), small shell reads (grep, sed, ls and similar), Rust tests, enact push, slow CI wait (enact ci --wait), browser checks (just ui-test, ui-shots, specs, motion), cargo build/check/clippy, just check, just card, just b3d, just oracle, git, bd. In that pass a naive pattern put 61 hours into a wrong bucket because the word enact appears in worktree paths; the stripping rule exists to prevent that.
  • Compile against run: read cargo's Finished ... in <N>s line from the tool result while ingesting (store the seconds, not the text).
  • Chained heavy commands get the first heavy command's kind and a chained flag.
  • coverage lists the most expensive commands of kind "other".

Waiting on a person: the AskUserQuestion tool, and a turn's end followed by a user message a person typed. A turn's end followed by a task notification or a message from another session is waiting on background work.

Shared context

  • The design is docs/efficiency-dashboard.md. Read the sections named above before anything else; the rest can wait. The decisions taken with the user are in the epic, bd show by-ig5e.
  • The dashboard's code is the separate Python project in efficiency/ (package beryl_efficiency, standard library only, pyre strict, black). It imports nothing from tools/ and nothing imports it. Read efficiency/AGENTS.md first once it exists.
  • Tests use small synthetic sources built in the test itself or kept under efficiency/tests/. The repository is public: never commit a real transcript, session record or command line from this machine.
  • Real data exists only on the main Mac (host jarvis). Where the acceptance criteria name a check against real data, run it there; if this session is on another machine, record that the check was not run in a comment on this bead and close on the tests.
  • Collection must stay free for agents: no hook, wrapper or prompt text may be added to any session, and ingest must never run inside another command.

Acceptance criteria

Tests: categories sum to the window length for every fixture window, including one with three overlapping tool calls; a question to the user counts as waiting on a person and not as a tool; a turn's end followed by a scheduled wake-up is idle and outside agent minutes; a subagent's time is not added to its parent's window; a command prefixed with cd /x/.worktrees/enact-thing && is classified by what follows; a cargo Finished line splits a test command into compile and run; the data file is validated (unique kinds, patterns compile). On the main Mac, commands of kind other are under 5% of all tool time over the last 7 days, shown by just efficiency coverage.
