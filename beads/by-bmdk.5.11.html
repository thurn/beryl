Description

Read first: epic by-bmdk, sections 'Rules for every bead', 'Contracts' and 'Code map'. Design: docs/manual-multiplayer.md ("the doc"), section 'Assists' (the shared rules and the three forms). Reference image docs/ui_mockups/manual_combat_proposal.png (intent only).

Interface code goes in ui/src/table/, registered with TableClient (ui/src/table/client.ts). Headless checks start a table with ui/scripts/table.mjs and go in ui/scripts/kept-table-<topic>.mjs; run one with just ui-test <title>.

Host: rust/crates/beryl_table_session/src/assists.rs. Interface: ui/src/table/ProposalPanel.tsx, Labels.tsx.

  • After every applied action the host recomputes, for each seat: the upkeep proposal (beryl_table::assist::upkeep::proposal, shown only to the seat whose turn is beginning), the combat proposal (assist::combat::proposal, shown to each seat that has the assist on), and the nudge labels (assist::nudges::labels). A proposal whose cause is gone is withdrawn. Put them in that seat's TableView.proposals and labels, through the redaction function for their text. A seat with an assist off gets nothing from it.
  • A proposal keeps a stable id while its cause persists, and remembers per seat which lines that seat switched off (table_lobby-style command table_proposal { id, line, on }, or an Answer; choose one and say which on the bead). Recomputing keeps a line's switch when the same line is still present.
  • Applying: table_proposal { id, apply: true } sends the batch of the lines still on (apply_proposal) through the normal action path, as the acting seat, to both players' cards. It is one log entry either player may undo.
  • A label is applied by a click on it: it sends the label's action.
  • Scripts: reuse proposal_marks and script_with_proposal_marks in rust/crates/beryl_table_session/src/script.rs. Compute marks from each seat's redacted proposal, view and slots. Pass old and new marks and use no log entry for a panel-only update. The adapter already omits private cards from these marks.
  • Interface: the proposal panel lists each change as a line with a switch, ending with whose card it is ("yours" or "theirs"), and one "Apply" button. Build it from the existing list and button shapes; it sits where it covers no card (the generic overlap audit must pass on a crowded board). Labels are small tags on the card or life total.
  • Nothing changes without a click. With every assist off, no proposal, label or "Assists" menu row ever appears: write that as a test over a whole scripted game.
  • data/ui-conventions.json: no-equivalent, "Proposal panel" and "Assist label".

Tests: tests/assists.rs: visibility per seat and per switch; withdrawal; switched-off lines survive a recompute; apply and undo by the other seat; the all-off game. Checks (kept-table-assists.mjs): the panel for the turn-upkeep proposal on a solo table; apply with one line off. A fixture or kept moment with a pending proposal on a crowded board.

Acceptance criteria

The host computes proposals and labels per seat after every action, withdraws stale ones, keeps per-seat line switches, and applies a proposal as one undoable batch; the panel and labels draw them; with all assists off nothing appears in a whole scripted game; a pending proposal is under the generic audits.
