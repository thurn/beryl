Derek Thurn2026-11-14

Investigation. Reproduced with the report's fixture.json played live (ui/scripts/perf.mjs against vite preview builds of e0ee030c, whose stage code matches 5c3aed1c), with the combat part alone (views 55-61 and 39-47: tap, attack, strike on the opponent, life count), and with the seeded fixtures combat-declare, combat-blockers, combat-double-block, verbs-combat and verbs-combat-theirs.

journal.jsonl shows the AI was not searching during the player's combat (turn 10, 22:46:06), so it was not competing for the CPU.

Headless WebKit and Chromium on this Mac drop few frames on either build (p95 19 ms in WebKit, 16.7 ms in Chromium; 0-2.5% dropped, which is noise), even with Chromium's CPU throttled 4x. So the real app's lag (WKWebView, Retina, under load) does not reproduce as dropped frames headless.

The cause was found from Chromium traces instead (perf.mjs --trace, counting Paint events). Over one 2.4 s combat there were 272 paints. 72 were svg.life-orb-art: both orbs, every frame for the ~600 ms of the strike and life count, which are the verbs with WebKit's longest late frames (strike/count 120-250 ms late per run). 64 were svg.step-icon. CSS knockouts (perf.mjs --css) showed filters and shadows were half of Chromium's GPU time and two thirds of its raster time in combat; the WebGL light canvases were about a quarter of GPU time.

CAUSE 1: the stage writes each effect's progress (--impact, --loss, --settle and the rest) on the node the effect is on (stage/dom.ts effect()). Custom properties inherit, so the card or orb inside the node was restyled and its filtered art repainted every frame. A MutationObserver showed div.hud.life getting --impact and --loss every frame.

CAUSE 2: the phase tracker icons transition fill and opacity for 120 ms with no layer of their own and stacked drop-shadow filters, two icons per step change.

There is also a first-use hitch: the first light in the under layer (combat lines, on the first attack of a game) creates a WebGL context, and the next frame runs ~75 ms in headless WebKit. That is one frame per game, so I left it alone.

Fix and results (commit b8dff8b1, "perf: stop combat repainting life orbs and step icons").

Changes:

  • ui/src/stage/effects.css (the effect styles, moved out of stage.css, which was at the 800-line limit): the card inside a stage node and the orb inside a [data-life] element reset every effect progress number (--beam --blanch --cover --dim --dissolve --flash --gain --glow --impact --loss --settle --trail) to initial, so their style no longer changes while an effect plays. Only the effect's own element and .life-change see the numbers. --pulse still inherits.
  • ui/src/design/components/phase-tracker.css: .step-icon fades only opacity, with will-change: opacity; its fill changes at once.
  • ui/scripts/verbs.mjs: for every effect, a new check that the effect's own element reads its progress and that no other child of the node inherits it. It fails on staging before the fix (for example "passes its glow down to what it is drawn on") and passes after.

Rejected approach: @property inherits:false with --x: inherit on each reader. WebKit did not always restyle the reader when the node's value changed: verb:lift read the life-change drift as 0 in 3 of 5 runs.

Measurements, old build vs new (medians of 3 interleaved runs):

  • Chromium raster ms: bug combat 78->34 and 67->21; combat-declare 339->198; combat-blockers 106->58; verbs-combat 241->123; verbs-combat-theirs 305->162.
  • Chromium GPU ms: down 13-39% on the same fixtures.
  • Chromium paints over one combat: 272->77. Life orb repaints went 72->0 and step icon repaints 64->8.
  • p95 frame: under 1.5 frames on both builds and both engines (WebKit 19 ms, Chromium 16.7 ms).
  • Dropped share, WebKit: bug combat 1.97->1.77%, bug combat1 1.40->1.23%, combat-blockers 3.13->2.53%, combat-declare 0.63->1.03%, verbs-combat 0.80->0.40%, verbs-combat-theirs 1.10->0.57%.
  • Dropped share, Chromium: ~0% on both builds.
  • The verbs that had the long frames (WebKit, old build): strike and count (the blow on the player and the life count, 120-250 ms late per run), tap, and set.

Checks: just motion passes; verb:strike passes; npm test passes 218/218; typecheck is clean. verb:fly (yours/phone, theirs/desktop) and verb:mark (all four) fail identically on unmodified staging e0ee030c; they predate this change.

NOT MET: the acceptance asks for the dropped share cut by at least half versus 5c3aed1c. Headless WebKit and Chromium drop only 0-3% of frames on the old build too, which is within noise, so the halving cannot be judged there. The player's lag happens in the real WKWebView window (Retina, under load), which agents cannot open.

NEXT: play a combat in the app (just dev, by the user) to judge it. If it still lags, the remaining measured costs are:

  1. The two full-stage WebGL light canvases (stage/glow.ts) are repainted every frame while combat lines or wedges are lit. They are created with antialias:true at up to 2x density, and cost about a quarter of Chromium's GPU time in combat. Turning off MSAA (the shapes are soft distance fields) or drawing at 1x density are candidates.
  2. A ~75 ms hitch on the first frame after the under-layer painter is created, which happens at the first attack of a game.

Third pass: cause found from the app's own frame log (8088e535). Real-app data, desktop WKWebView, builds f4968bff and later, 2026-11-14 18:31-20:10:

  • 18 of the 21 journal 'frames:' warnings (>=3 and >=10% dropped) overlap an AI search (beryl.jsonl 'ai' entries carry the search's ms). The combat ones too: streak/tap 6/41 during 'Cast Counterspell' (1.8 s search), tap/streak/vanish 13/122 during 'Jace +1' and another search.
  • In the 20:04-20:06 game's ui.json (all frame runs, not only warnings): runs overlapping a search dropped 43/454 = 9.5%; runs with no search 23/698 = 3.3%, of which 13 were one 'dwell' run, so ~1.6% otherwise. Combat verbs with no search: streak 1/47, tap 1/86. So the lag is not one animation: the AI's long search (pimc72-hidden-30m-anchor, 30M steps, one thread per core = 18) competes with the webview for the cores, as by-jx3h's worker also found.

Measured with a scratch program (not committed): a user-interactive thread waking every 16.7 ms with a little work, under load ~40, while the deep searcher plays the WU mirror. Late >8 ms: no search 0.3-1.8%; 18 threads 4-9%; 12 threads 2.4-4%; 6 threads 0.3-0.8% (as no search). p99 6.6 -> 12.5-17 ms with 18 threads. Search in a separate process: same as in-process (p99 13 vs 12.5), so a helper process would not help. 6 threads all the time costs 1.5-2.1x search time (25 decisions: 50-57 s at 18 threads, 78-122 s at 6), too slow.

Fix (78a36d1c, 'perf: fewer search threads while the stage animates'): beryl_search::pace. The UI calls the new stage_animating command (ui/src/ipc.ts stageAnimating, from pageStage in stage/playback.ts on the stage's first step and on idle; native app only). While animating, long-search workers with index >= cores/3 (6 of 18) wait; a waiting worker returns its half-grown tree to a shared list for a running worker; worker 0 never waits. Trees grow independently, so moves do not change. With the real code, interleaved rounds: p99 no search 8.6-10.9 ms, unpaced 18 threads 12.5-23.5 ms, paced 8.4-10.8 ms.

Acceptance: headless ui-perf cannot show this (no search runs in fixtures; prior passes measured 0-3% there). The real-app criterion is judged by the frame log: after this lands, runs overlapping a search should drop about as few frames as runs without one (~1-3%). Tests: pace::tests (items finish under holding), beryl_search + beryl_session 412 pass, ui unit 293 pass, typecheck and clippy clean. just motion unaffected (no UI motion change).
