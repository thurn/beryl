Close reason

Session streams a view per step change and agent decision (thinking/playing statuses), halts the human under smart stops at their main and the opponent's end step; staging 6a41182

Description

Today beryl_session emits a PlayerView only at the human's decisions: game.rs advance plays every agent decision in one blocking loop and session.rs run publishes once the human must decide. So the UI is silent for seconds while the AI thinks, then jumps (owner: "If I drag a plains out to play it, it freezes the UI for around 5 seconds, and then suddenly it's my second turn and the opponent has played a land"; "the opponent countered my card with mana drain, there is no indication"; "Clicking start shows no game in progress").

Change the session and protocol (rust/crates/beryl_session/src/{game,session,protocol}.rs, beryl_app stays a thin wrapper) so that:

  • A view is emitted as soon as a game starts, before any agent decides, and after every agent action and every step change, each carrying the events since the previous view. A non-deciding status says who is acting (e.g. the opponent is thinking / acting), so the UI can show it.
  • Under smart stops the session halts the human at their own first main phase (precombat main) and at the opponent's end step even when the engine offers them no decision: a session-level pause (a synthetic decision or status the UI answers with End turn / Continue), recorded in the replay so replays and fixtures stay deterministic. The engine's Stops::Smart and the AI's search profiles must not change (MCTS uses Stops::Smart; the state holds one profile for both seats).
  • IPC never blocks; events must not be lost or duplicated across views; the fixture recorder (beryl_cli record-fixture) captures the streamed views so the UI can replay them.
  • Regenerate ui/src/generated/protocol.ts and keep ui/src/ipc.ts and the UI compiling (minimal UI changes only: the playback, indicator and log are a separate bead).

Rules-engine code you touch keeps its Comprehensive Rules citations (yawgatog links).

Context

Part of the run epic by-l1w, whose description holds the owner's full report (verbatim) and the decisions made in pre-flight; read it first. Agents never open a window: verify through just ui-shots (fixture states in ui/fixtures.json / ui/shots.json, recorded with beryl_cli record-fixture), just ui-test (plays the game screen through a fixture) and just test-rust, and look at the screenshots you capture (Read the PNGs) before pushing. Never commit screenshots. Fix poor aesthetic choices you meet in the code you touch.

Acceptance criteria

  • Rust tests in beryl_session show: a view before the agent's first decision; one view per agent action and step change, events partitioned without loss; the halt at the human's precombat main and the opponent's end step under smart stops with no legal action; no halts under exact stops beyond what the engine offers; replays of halted games reproduce.
  • The AI's behavior is unchanged: existing search/agent tests pass untouched.
  • protocol.ts regenerated; just check passes.

Done as designed, with these shapes for the next beads:

  • Engine: new opt-in beryl_engine::next_in_step(s,t,x,a, seen:(turn,step)) -> Option<Step>, which is next() but returns None once the turn reaches a step other than seen (after layers refresh). next() is unchanged (const-generic STEPS=false). Profiles, Stops::Smart and agents are untouched: only the session's own calls use it; halts look ahead on a state copy with a separate non-recording Scratch.
  • Protocol: Status gains thinking (the agent is about to decide; next view follows once it has) and playing (a step began; next view follows at once). Views come at every step begin, before every agent decision, at human decisions and at the end; each engine event is in exactly one view (tested against a plain engine replay). The untap step has no view of its own (it ends inside begin_step, CR 502.4); its events arrive with upkeep's view.
  • Halts: a Status::deciding view whose DecisionView.halt=true, kind priority, one candidate (pass, index 0), passTo as next_stop says. Answered with choose(id, 0). Under smart stops only, at the human's precombat main and the opponent's end step, unless the engine gives the human a decision in that step before any agent decision. Replay entry Entry::Halt records each answer; from_replay rebuilds the stream position exactly and returns the view live play emitted at the record's end (human decision/halt, agent thinking, or over).
  • Game API: next_view() -> Option<PlayerView> drains views to the human's next decision; choose(answer) only applies. answer_by_stand_in() -> bool.
  • Fixture recorder: records every streamed view; Until 'first <kind> decision' now skips halts; new 'first halt for seat <n> [from turn <t>]' for the UI bead's halt shot.
  • UI (minimal): fixture transport releases views after choose up to the next one awaiting the player; Game.tsx treats thinking/playing as waiting (pill 'Opponent is thinking'), keeps planned picks across them, and only shows the game-over overlay for over/stopped. shots.json at= indices remapped to the same states (greedy-turn-9 6->48, 11->93; first-target 3->4). Fixtures are ~10x bigger (largest 10 MB); ui-shots still ~21 s.
  • Thinking views often follow a playing view with no events in between (step began, then the agent decides at once): the UI bead should pace such empty views quickly.
