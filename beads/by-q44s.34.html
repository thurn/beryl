Close reason

gates.json merge driver sums both branches' limit changes; b3d target clone restores source times

Description

What happened: by-q44s.3.19 (point arrows) was rebased five times in about three hours because the M2 verb beads (streak, flip/showcase/lift, mark, tap/set, effects) all landed on staging meanwhile, and each one raises the same verbs-zones limits in data/beryl3d/gates.json (total_records, worst_frame_records, worst_frame_draw_calls, worst_frame_upload_bytes, handle_allocations). Every rebase in enact push stopped on a gates.json conflict. Each time the fix was the same: take staging's numbers, add this branch's own increase (for 3.19 always +1669 total_records and +3 handle_allocations), and confirm with just b3d gate, which in a new worktree under load 40 took 10 to 30 minutes because it builds from scratch and queues on the shared b3d target lock. Most of the bead's wall time went here, not into the feature.

Why: gates.json holds absolute totals, so two beads that each add work to the same board always edit the same lines. The work each adds is independent, but git can only see a text conflict.

Build: a way for a branch's limit changes to be reapplied onto staging's gates.json without a person doing arithmetic. Suggested shape, in tools/src/beryl_tools/beryl3d (C17 keeps it there): a git merge driver for data/beryl3d/gates.json, registered by the repo's .gitattributes and set up by just b3d (or by enact worktree create), that for each numeric key computes ours = base + (branch - base_of_branch) when only one side moved it, and theirs + (ours - base) when both did. It must keep the rules in rust/beryl3d/AGENTS.md ('Data files'): limits only rise with work, a count below its limit fails, and the commit body gives old and new numbers. The fast check's gate run still proves the result, so a wrong sum fails the push rather than landing. Also look at why a fresh worktree's first just b3d gate rebuilt the whole beryl3d workspace instead of copying the shared target from $BERYL_CACHE.

Files: data/beryl3d/gates.json, tools/src/beryl_tools/beryl3d/cli.py (gate, SHARED_BUILD), rust/beryl3d/AGENTS.md (gates.json section), .gitattributes.

Acceptance criteria

Two branches cut from one staging commit, each raising verbs-zones total_records by a different amount, rebase onto each other with no gates.json conflict and with the sum of both increases; a test in tools covers the driver on a three-way example; rust/beryl3d/AGENTS.md says how it works; just b3d gate in a new worktree reuses the shared target (or the bead records why it cannot).
