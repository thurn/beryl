Description

Milestone 7b of Project 50k (docs/project-50k.md, Acceptance, "Scale rehearsal"): "A scratch workspace of 50,000 implemented definitions, cloned from the real ones, meets these budgets on the development machine": cold cargo check 60 s, release build 180 s, rebuild after one edit 2 s, largest compiler process 4 GiB. "App startup and the UI bundle do not grow with the card store. A budget that cannot be met after three attempts is recorded with its measured value and cause, and a follow-up bead is filed." This bead runs after the whole set-crates lane: card files live in rust/cards/<group>/<set>/ in set crates with build scripts and a generated registry, characteristics and headers come from the store, Subtype comes from the catalogs, and store-only creatures have no file. Read those beads' handoffs and the scale numbers they recorded.

Today

tools/src/beryl_tools/scale.py (456 lines; just scale --cards N --crates K) generates a scratch workspace under $BERYL_CACHE/scale: N clones of the real card files with unique names, split over K library crates shard0… that it writes itself (shard_lib, shard_manifest, main_rs), each with a hand-built module list and a names module, and a binary that references every card. Its docstring says "Budgets are not asserted yet (milestone 7 adds --assert…)". The earlier beads only kept it running.

Measured at the M5 gate (staging 8e6fc07c, --cards 5000 --crates 5, loaded machine, CPU seconds): cold check 14.2 s, release 9.0 s, one-card rebuild 1.3 s, peak 0.64 GiB: 2.8 ms a card for check, against the plan's 0.9 ms, because card() now checks each definition as it compiles (by-w8gv.9.13). At 50,000 that is about 142 CPU-seconds, so the 60 s budget needs the set crates to build at least three wide. The harness then cloned 36 of the 47 files.

What to build

  1. The rehearsal builds what the tree builds. The scratch workspace uses the real structure: set crates made by the same build helper and build.rs as rust/cards/*, the same generated registry, store records for the clones (a scratch store beside the workspace), generated characteristics and headers, and the shipped proportion of crate sizes (data/set-groups.json: groups of 500 to 1,500 cards, so 50,000 cards is 35 to 100 crates; default --crates to what the grouping gives and say so in the report). Delete the harness's own shard writers once the real ones serve. Every card file is cloneable now that no card reaches another's file: report the pool size and why any file is left out.
  2. --assert. With it, just scale exits non-zero when a budget is missed, printing each measure, its budget and its margin; the budgets are a table in scale.py with the plan's four values. State precisely what each measure is and keep it honest: the budgets are wall-clock seconds on this machine with all its cores, load-adjusted as the checks' clocks are (checks.Clock), not CPU-seconds; the one-edit rebuild is cargo check after editing one card file, including the build script and the registry; the release build is the registry and every set crate; the memory is the largest single rustc process. Report CPU-seconds beside each, since they are what scales with machines.
  3. Meet the budgets at 50,000, attempt by attempt, each recorded on the bead with its numbers and cause: (1) measure as built; (2) the cheapest structural change the profile points to (cargo build --timings; crate count and width; what the build scripts cost per crate, since a script that rereads a 22 MB store for every crate is a likely hot spot; what card()'s compile-time checks cost per definition and whether they can run in a test or the build script instead of in every cargo check; codegen units and debug info for the release profile of data-only crates); (3) one more. After three attempts, a budget still missed is recorded on the milestone epic (by-w8gv.13) with its measured value and cause, a follow-up bead is filed under by-w8gv.13 with tier:opus, and --assert holds that measure to the recorded value plus 10% so it cannot get worse unnoticed, with a comment naming the follow-up. Changes that speed the real tree up land in the real tree, not only in the scratch workspace.
  4. Where it runs. A 50,000-card rehearsal takes minutes and holds the machine, so it is not in just check or just ci. Add it to the nightly (tools/src/beryl_tools/nightly.py, a step like fuzz_step) with --assert, at utility QoS like the tournaments (taskpolicy -c utility; see the justfile's low), logged in the run log. The Python lane keeps a small test of the harness (--cards 60 --crates 2, no assert on time) if one exists today; do not add a timing assertion to any check (tests never depend on machine speed).
  5. The rest of the acceptance line. Record on by-w8gv.13: the four measures at 50,000 with their budgets; the store's size and record count; app start-up (just smoke's time to the UI's report) and the UI bundle's size (ui/dist after npm run build) now and at the commit before M7a's first bead landed (git log --diff-filter=A -- data/card-store.tsv finds it), to show neither grows with the store; and the per-card script-check cost the harness already prints. Update docs/project-50k.md's "Measurements" with the same numbers in a few lines, and scale.py's docstring.

Cause: each set crate's SCENARIOS (and CARDS, STORE_CARDS) table was a const of per-card const scenario arrays, and Rust evaluates a const again in every crate that uses it, so the registry evaluated all 50,000 clones' scenarios in CTFE, single-threaded; the harness's own registry bin did it once more because its SCENARIOS type named total(SET_SCENARIOS) (a harness bug, fixed to mirror beryl_cards' slices). Attempt 2: the generated set-crate tables become statics (beryl_card_build generate.rs, real tree), so each crate evaluates its own scenarios once, in parallel, and the registry only reads them.
