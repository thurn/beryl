rust tests via nextest + parallel allocations (19.6-21.5 s -> 6.0 s warm), cargo test fallback, tournaments/play under nice -n 10, AGENTS.md tournament cost note; a7f2db1

Description

Part of Milestone 1 (epic by-b0q). Filed by the Sage audit of M1b (by-b0q.4.2).

Measured problem

  • The fast check (just check, budget 60 s) ran over budget in 6 of 19 M1b sessions that ran the rust lane: 62, 66, 75, 88, 132 and 144 s. The worst two ran while MCTS tournaments in the same session or a parallel one held all 18 cores (a 100-game MCTS pairing is about 18,000 CPU-seconds).
  • The rust lane's tests step (cargo test --locked --workspace -q, tools/src/beryl_tools/checks.py rust_lane) runs its test binaries one after another: 19.4 s warm on a quiet machine, 31 s in a fresh worktree under load ~27. The slowest binaries are beryl_engine unit tests (5.1 s, one test), beryl_search games (3.8 s), greedy (1.9 s), mcts (1.8 s), expert (1.3 s).
  • cargo nextest run --locked --workspace -E 'not binary(allocations)' runs the same 186 tests in 5.7 s warm and quiet (nextest is installed at ~/.cargo/bin). The two allocations targets (beryl_search, beryl_bench) are harness = false and nextest cannot list them.
  • just tournament and just play run at normal priority, so a tournament starves every other session's checks on the machine.

Proposed change

  1. The rust lane's tests step (fast check and slow CI) runs cargo nextest run --locked --workspace over the harnessed tests and the two harness-less allocations targets with cargo test --locked --test allocations for their packages, in parallel or one after the other, whichever is faster; fall back to plain cargo test when cargo-nextest is missing, so other machines keep working. Nextest's own config, if needed, goes in rust/.config/nextest.toml.
  2. just tournament and just play run their binary under nice -n 10 (macOS honours it), so checks and interactive work in other sessions keep their CPU.
  3. One AGENTS.md sentence under Testing your work: what a tournament costs (about 180 CPU-seconds per game involving an MCTS agent at --iterations 300 --trees 4, so a 100-game pairing holds the whole machine for about 20 minutes and a full round robin over 2 hours), and that Wardens rerun only gated pairings, never reported-only ones.

Expected gain: about 12-14 s off every rust-lane run of the fast check and slow CI on a quiet machine, more under load, and fewer over-budget fast checks while tournaments run.

Acceptance criteria

  • The rust lane's tests step uses cargo nextest when installed and still runs every test, including both allocations targets (a deliberately failing allocations assertion fails the lane).
  • Without cargo-nextest on PATH the lane falls back to cargo test and passes.
  • The tests step takes at most 10 s warm on a quiet machine (measured, reported on the bead with before/after).
  • just tournament and just play run under nice -n 10.
  • AGENTS.md states the tournament cost and that Wardens rerun only gated pairings.
  • just check and just ci pass.

Done in 33df127. The tests step is now a Python step (checks.py rust-tests): it builds with cargo test --no-run, then runs cargo nextest (-E 'not binary(allocations)', quiet status levels) at the same time as cargo test --workspace --test allocations. If cargo-nextest is not on PATH it runs plain cargo test. I used --workspace for the allocations run, not -p beryl_search -p beryl_bench, because -p resolves features differently and triggered a 10 s rebuild. Timings, warm, load 8-15 (the machine was never fully quiet): before, cargo test 19.6/19.7/21.5 s; after, 6.0/6.0/6.1 s. Local just ci: rust tests 14 s alongside all other lanes (the audit saw 40 s); the whole run passed in 54 s. Verified: planting a failing assertion in beryl_search's allocations test makes 'by ci rust' fail (tests exit 101). With cargo-nextest off PATH the lane passes on cargo test in 20.5 s. just tournament mcts-hidden runs at niceness 10 or more (15 when started from a zsh background job). Inline review (a cold subagent) confirmed no problems. Its one nit: the main dispatch raises KeyError on an unknown step name. I left it, since only the lanes call it.
