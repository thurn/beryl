English templates for every vocabulary entry; render/render_face/render_ability in beryl_card::render; beryl_scenario render prints any card

Description

Milestone 8 of Project 50k (run epic by-w8gv; plan docs/project-50k.md, "Authoring tools", decisions K13). Read the plan's sections named here and enact brief on this bead before starting. This milestone starts once M7b (by-w8gv.13) closes: read its beads' handoffs for the set crates, the generated registry and characteristics, and the card store as they landed.

K13: "A definition renders back to Oracle-style text, which is compared with Scryfall's." Why: "A cheap model's typical error is a plausible definition that differs from the card. Rendering makes that error mechanical to find." Scope from the M8 epic: "English templates on each vocabulary entry; a renderer from definition to Oracle-style text … the same templates give the UI rules text for abilities." This bead is the templates and the renderer; a later bead in the render lane adds the normalized diff against Scryfall, and another uses the renderer for the UI.

Today

The vocabulary is rust/crates/beryl_card/src (no runtime dependencies): Effect (about 50 variants, effect/mod.rs) with Amount, Condition, Objects, Players, Recipients and the terms in effect/; Ability/AbilityKind/Behavior (ability.rs), Cost/CostPart/CostAction/CastingOption (cost.rs), triggers (trigger.rs), continuous effects, replacements and layers (continuous.rs), Filter (filter.rs), targets (target.rs), keywords and characteristics (characteristics.rs, generated printed:: constants). Every card in rust/cards/ is effect data: none uses a Rust body (custom_body), though the vocabulary allows one. Nothing renders text today: the session finds an ability's paragraph in the printed text by counting abilities of its kind (beryl_session/src/protocol/outcome.rs ability_ref, build.rs paragraphs_before), and cost text for the UI comes from cost_text (beryl_session/src/protocol/candidates.rs ~line 357), which you can reuse or replace.

What to build

  1. A template per entry. Each vocabulary variant gets its English wording, in Oracle's style (CR 201.4 for self-reference: "this creature", "this spell"; modern Oracle templating: "target creature", "each opponent", "Draw two cards.", "+1/+1 counter"). Write the templates as exhaustive matches in a renderer module of beryl_card (for example render/ with one file per part: effects, costs, triggers, statics, filters), so adding a vocabulary variant without a template fails to compile. The vocabulary's doc comments and their CR quotations are the source for each wording; Oracle text of the 47 implemented cards (the card store, just card brief <name>) shows the target style. Not Forge's or XMage's text generators (K16; XMage's is MIT but write ours from the rules).
  2. The renderer. render(def: &CardDef) -> String (and per face, per ability: render_ability(&Ability) -> String, which the UI bead uses) gives Oracle-style rules text: keyword lines first as Oracle orders them, then abilities in definition order, activated abilities as "cost: effect", loyalty abilities as "+1: …", triggered as "When/Whenever/At …, …", modal spells with "Choose one —" and "•" lines, each paragraph on its own line. A Rust body renders as a marked placeholder ([custom ability]), so a reader can tell it was not rendered. It runs at build time or in tools only: it allocates Strings, so it lives behind a module the engine and the rollout never call (a std feature or just not reachable from beryl_rules; check cargo tree, and keep the kernel, rules and card crates free of runtime dependencies).
  3. A way to print it. A subcommand prints each implemented card's rendered text by name (for example beryl_scenario render <name> beside dump, or a beryl_cli subcommand), so the next bead and just card can call it. Snapshot tests are a change detector (K24, K20): instead test a handful of templates (one per part) against hand-written expectations taken from the cards' Oracle text.

Do not chase a match rate here: the next bead measures it. Do not change any definition.

Files

beryl_card/src (new render module; read effect/, ability.rs, cost.rs, trigger.rs, continuous.rs, filter.rs, target.rs, characteristics.rs), beryl_cards/src/bin/beryl_scenario.rs or beryl_cli for the printer, beryl_session/src/protocol/candidates.rs (cost_text) to reuse. Need not read: beryl_rules beyond what a variant means, beryl_search, the UI, the exporters.

Tests: cargo test -p beryl_card, clippy pedantic; the printer on all 47 cards without a panic.

Parity at the push (plan K11)

just check passes; the frozen save corpus replays (cargo test -p beryl_session --test corpus); rollouts_never_change holds (rust/crates/beryl_bench/src/rollout.rs); slow CI's counts lane (just count-gate, bar 405,276,238 instructions, 1% tolerance, rust/crates/beryl_bench/count-gate.toml) passes with no bump to the bar. Never delete a card implementation. Work the card-names and file-length allowlists (data/card-names-allowlist.json, data/file-length-allowlist.json) down in the files you touch; no new source file over 800 lines. K16: Beryl stays Apache-2.0, and no definition, vocabulary entry, template or brief is derived from a Forge script or from Forge's code. Record decisions and anything this packet got wrong as comments on the bead; nobody answers questions (K31): proceed on the default given and record it.

Acceptance criteria

Every vocabulary variant has an English template in an exhaustive match in beryl_card, so a new variant without one does not compile; render(def) and render_ability(ability) give Oracle-style text for every implemented card without a panic, and a Rust body renders as a marked placeholder; a subcommand prints a card's rendered text by name; the kernel, rules and card crates gain no runtime dependency and the rollout never calls the renderer; a few hand-written template tests pass; parity checks pass.

Derek Thurn2026-11-13

Decisions and packet corrections: (1) The packet cites CR 201.4 for self-reference; in the pinned 2026-11-06 rules that is 201.5 (201.4 is choosing a card name). Cited 201.5. (2) The vocabulary has no modal entry (no modes in Effect; ModeIx is unused), so there is no 'Choose one —' template to write. (3) render is a plain pub module of beryl_card, not behind a feature: beryl_card already uses std (RuleChange::words returns String), it adds no dependency, and only beryl_scenario render and tests call it (grep). (4) Keyword-part abilities (impending's static and countdown, offspring's copy, evoke's sacrifice: any ability whose condition holds Paid(Impending|Offspring|Evoke)) are not printed; the casting option's keyword line stands for them. Reminder text is never rendered. Delayed abilities print inside the Delay that makes them; an Overload option's alternate spell ability is skipped. (5) Two mana abilities with the same cost and amount and no restriction print as one line ('{T}: Add {W} or {U}.'), and two triggers of the object sharing one effect and in_paragraph_before print as 'Whenever this permanent enters or attacks, ...'. (6) Keyword bit sets got a NAMED list from their macro, so a new keyword/type/color/supertype is named the moment it is added (the exhaustive-match guarantee for bitsets).
