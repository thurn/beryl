Description

Shapes, purposes and today's code

Check each against the design's table.

  • Yes or no: pay or not so an effect does not happen (with what paying would tap: unless_paid, preview.rs about 236); pay life for a land; discard a basic land instead; an explored card to the graveyard; "you may move that card"; top or bottom; a fateseal; a cast offer. Today: choices.ts Ask, FloatPrompt.tsx. A yes or no that only opens a choice is not here: it is folded into that choice's shape.
  • A number: X, with what each value costs (Payment::cost, priced, preview.rs about 313), and how many targets where the pick shape did not fold it.
  • A mode: play or draw; keep or mulligan; and the chooser a click on a card at priority opens when the card has several ways to be used (faces, casting options, abilities: ui/src/game/ModeChooser.tsx, CastStep.tsx, AbilityChooser.tsx, casting.ts; protocol candidates' casting_options); a payment plan among plans with different consequences. The priority prompt's click on such a card now opens this prompt in the session, and its reply stops saying "the old UI's chooser".
  • A catalog choice (a color, a type, a card name): no card asks one yet. Typed state, tested from a decision built in the test.
  • Dividing: combat damage among blockers (DamageDivision, lethal picks and Done), with DecisionView::damage_default replaced by a suggested mark and the field deleted (the old UI reads the mark: Board.tsx); and dividing an amount, which no card asks yet, tested from a built decision.

  • A confirm answers the engine's run of picks through the session's own choose path, recorded in the choice log exactly as the old UI's planned picks are today (continuation answers), so a save made through clicks and one made through the old UI replay alike. And one test per shape plays a card's scenario or a scripted board through clicks alone and reaches the same final state as the picks the old UI plans for that choice.

DECISIONS AND DEVIATIONS (by-w8gv.11.10)

  1. Where the code is. rust/crates/beryl_session/src/prompt/: yes_no.rs, number.rs, mode.rs, catalog.rs, divide.rs (one module per shape, each open / click / show), pick/damage.rs (a division of combat damage, a pick), ahead.rs (answers played ahead on a copy of the game under Stops::Forced: forced, answer, castable; pick/untap.rs now uses it). held.rs's Shaped has eight variants and Held::open routes every shape but pay and declare, which stay a UI's until by-w8gv.11.11.
  2. The choice among a card's ways (mode act) is held by the session over the priority, as part of the priority's own state (pick/priority.rs, Priority.acting). One prompt lies over the other and they count their revisions as one: the click that opens it replies with the act prompt at revision n+1, its buttons are Option { index } for each way (index among the priority's candidates, labelled with the candidate's label) and decline "Cancel", which goes back to the priority's prompt at the next revision. A way's button answers the priority decision with that candidate (not a continuation). While it is open it takes every click; a view drawn again and current_game show it. Clicked::Opens is gone. The design had "closing it without choosing returns to the priority prompt" without saying how: it is ButtonId::Decline.
  3. Yes or no: buttons are Option { index } for the yes and the no, in the table's words. Which is put forward: neither where the record names two places (two places for one card: fateseal, top-or-bottom, and explore too, which the old UI puts "Graveyard" forward for); for pay-life the yes only when paying lets the player cast more of their hand than not paying, each answer played ahead on a copy and counted by the engine's refusal (the old UI's untappedLandWanted compares mana values from card data); elsewhere the yes.
  4. Marks beyond the design's summary: suggested on the permanents the engine's default payment would tap, for the yes of an unless-pays and for the value set of an X (the old UI lights both). They come from the candidates' payments, which preview.rs already computes.
  5. An X's confirm is recorded as a continuation of the cast's pick (Run::continuing, honoured by Game::choose only while casting), as the old UI's cast step records it, so one undo takes back the cast with its X (tests/modes.rs an_x_is_set_and_then_paid). No other shape's confirm continues: a target picked on the board is its own answer today.
  6. Combat damage is held here, as this bead's description says, though the design's summary and by-w8gv.11.9's handoff left it to by-w8gv.11.11. It stays Pick / combat-damage (the engine is untouched). The player toggles the blockers that die; what each set of picks leaves (which blockers the damage still reaches, whether the division may end, which the session would take next) comes from playing every run of picks ahead on a copy as the prompt opens, keyed by the kinds picked so that interchangeable blockers are one kind and either twin can be clicked. Marks: selected on the picked, suggested on the blocker beryl_engine::preferred_damage takes next, eligible on the others still reached. One button, confirm "Done", enabled once the engine offers an end. The run is the picks in whatever order the engine offers them (held.rs named and alike now match Opt::Lethal) and the end only where the engine asks it: a lone Done is never asked (engine.rs forced), and left in the run it could answer the next attacker's division. The picks after the first are continuations, so one undo takes back one attacker's division. DecisionView::damage_default is deleted; the old UI finds the suggested pick from the mark (ui/src/game/decisions.ts suggestedDamage, used by Board.tsx and PhoneBoard.tsx) and still sends one pick at a time. The suggested mark's meaning in data/ui-conventions.json and verb.rs says so.
  7. Divide: what there is to give out is read from the shares the first recipient is offered (the most it may take leaves each other the least), so a prompt taken up mid-run shows what is left, not the record's count. The last recipient's number is not in the run: what is left is its one answer, which the engine does not ask. Recipients are objects only: Decision.about is a set of objects, so a player as a recipient needs a new form when a card first asks.
  8. Catalog: the session names a color's entries (CR 105.1's five, by Opt::Number index). Creature types and card names have no catalog in the session yet and list by the candidate's label (its number): the names come with the first card that asks. Confirm is Arena's "Submit n" from the table; the design's "Arena takes a color at a click" is noted in wording.rs and not followed, per the design's "Click Entry; Confirm".
  9. A plain may (Purpose::May) is reached by no card's scenario (tests/asks.rs REACHED has none), so its snapshot is from a decision built in the test, like catalog and divide. For those, Held, Clicked and Run are now public with Held::opening (a prompt held apart from a game); Run::new and its steps stay crate-private. tests/common/play.rs has position and asked for building one.
  10. Not here: "how many targets" as a number: by-w8gv.11.8 folded every count into the target pick. A payment plan among plans: the design's table has it as Pay / mana / Plan, so it is by-w8gv.11.11's with the pay shape, though this bead's list names it under modes.
  11. The old UI is untouched but for reading the suggested mark. It never calls click, so the act prompt's new reply changes nothing there.
