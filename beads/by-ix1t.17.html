Close reason

Staged 8bc489cc and slow CI passed. Verified Idle priority and explicit execution-speed throttling opt-out on the Windows ladder child.

Description

On Cygnus, the 3M ladder match in by-ix1t.9 slowed to roughly four cores despite 20 ready worker threads, full process affinity, and little other CPU load. Windows was managing the CLI process's power throttling automatically. Setting ProcessPowerThrottling on the live beryl_cli.exe process with Version=1, ControlMask=PROCESS_POWER_THROTTLING_EXECUTION_SPEED and StateMask=0 brought its CPU use from about 350% to 1990% while its priority class stayed Idle. The worker kept the same games, seeds, and step budget.

Fix the Windows launch path used by just ladder so the actual search process opts out of automatic execution speed throttling while keeping Idle priority. Start from the ladder recipe in justfile and tools/src/beryl_tools/system.py::low. The recipe launches cargo, which in turn launches beryl_cli, so verify the setting on the actual CLI process. Scope the setting to ladder work if changing all low-priority recipes would disturb their scheduling.

Microsoft API reference: https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-setprocessinformation

Acceptance criteria

On Cygnus, verify that a child beryl_cli.exe started by the ladder recipe has Idle priority and explicitly disables execution speed throttling. Keep the existing ladder result and reproducibility checks passing. Use the process settings for verification instead of a machine-speed threshold.
