Description

What we see

Beryl stalls at about 4-5 concurrent agent sessions on the Mac (18 cores). The machine feels saturated and staging receives about 8 commits per hour. The goal is 10-20 concurrent Enact agents on the same machine, each on its own task.

Merge conflicts are not the limit: each card is one file and the card lists are generated. The limit is the CPU spent verifying each commit, plus contention when that work arrives in bursts.

This bead is the design, revised on 2026-11-13 against the 3-hour CPU sample below. Each numbered change has a child bead, listed here in the suggested order of work:

  • by-gdn3.1: change 9, record CPU per session.
  • by-gdn3.2: change 4, end a worktree's processes when it is removed.
  • by-gdn3.3: change 5, the machine-wide CPU scheduler (after by-gdn3.1).
  • by-gdn3.4: change 6, cheap source checks before a push.
  • by-gdn3.5: change 8, keep VS Code out of agent worktrees.
  • by-gdn3.6: change 7, change-aware slow CI.
  • by-gdn3.7: change 2, reusable worktree slots, measured first.
  • by-gdn3.8: change 1, the merge queue.
  • by-gdn3.9: change 3, slow CI at a fixed share (after by-gdn3.3).

The four Enact changes (.2, .7, .8, .9) are made in the Enact repository at ~/enact, not in Beryl.

Measurements (2026-11-12)

From $BERYL_CACHE/ci/runs.jsonl and git log origin/staging, last 3 days:

  • 593 commits to staging, about 8 per hour around the clock.
  • Load average while checks ran: median 30, 90th percentile 48.
  • Slow CI (by ci): 248 runs, median 333 s wall, about 11 checks running at once. It accounts for 261 of the 337 logged check-hours. The ui-test lane alone is 135 hours and rust:beryl_cli is 40.
  • Fast check (by check): 433 runs, median 95 s wall, 90th percentile 240 s.
  • 180 fast-check runs failed (42%). 80 of them failed repo:file-length, 19 python:pyre and 16 repo:markdown.
  • 73 slow-CI runs failed (29%). The failure rate does not rise with load, so these are real failures, not load flakes.

From a 12-minute sample of every process's CPU time (20:19-20:30, load median 32), attributed by process ancestry and working directory:

  • The machine used about 10 of 18 cores. top reported 42-57% idle in the same period. The sampler misses about a fifth of the work (short-lived processes), so the true figure is nearer 12 cores. The load average therefore overstates how busy the machine is, probably because work arrives in bursts. That cause is not confirmed.
  • Slow CI 2.6 cores (25%), fast checks 1.5 (14%), headless WebKit pages with no traceable parent 1.5 (14%, mostly check work), VS Code 1.0 (10%), commands the agents ran themselves 0.9 (9%), an orphaned fuzz run 0.7 (7%), desktop 0.7 (7%), everything else 1.3 (14%).
  • So checks are over half of the CPU in use. The three or four active agents together used under one core for their own builds and browser runs.

From a 3-hour run of the same sampler (20:19-23:18 on 2026-11-12, 22 commits to staging, between 5 and 10 worktrees active in each half hour until 22:50):

  • The machine used 8.2 of 18 cores on average (45%), with a median load average of 22 and a maximum of 83. In the busiest two hours it used about 10 cores at a load average near 30, which matches the 12-minute sample.
  • Per minute, CPU use had a median of 8.5 cores and a 90th percentile of 12.5. Only 3 of 176 minutes were above 14 cores. Allowing for the fifth the sampler misses, the machine was at or near full for a few minutes in three hours and had spare cores the rest of the time.
  • So the machine is not short of CPU averaged over a minute. The load average of 30 to 80 says many more threads want to run than there are cores for seconds at a time. The slowness people see is this short-burst contention, which the per-minute figures cannot show, plus the time checks take.
  • Shares over the 3 hours: slow CI 1.7 cores (21%), headless WebKit pages with no traceable parent 1.3 (16%), commands the agents ran themselves 1.15 (14%), fast checks 1.0 (12%), VS Code 0.8 (9%), desktop 0.7 (9%), and 1.2 cores (15%) of processes the sampler could not name or attribute.
  • Compared with the 12-minute sample, slow CI is smaller (1.7 cores, not 2.6) and the agents' own commands are larger (1.15, not 0.9). One session ran 0.46 cores of tests by itself. Checks plus the WebKit pages are still about half.
  • The unattributed 1.2 cores included one minute at 6.7 cores (21:15). What ran then is not known, because the sampler does not record process names.

Proposed changes to Enact

  1. Merge queue in place of optimistic pushes. Today enact push (cmd_push in ~/enact/scripts/enact.py) rebases, runs the fast check, pushes, and on a rejected push repeats all three, up to 6 times. At 30 pushes per hour with 95-240 s checks, most pushes would lose that race at least once. Instead, one integrator process per host takes queued branches, rebases a batch in order, runs the fast check once on the combined tree and pushes. When the batch fails, it finds the failing branch, pushes the rest and returns the failing branch to its agent with the check output. enact push becomes "enqueue and wait for the verdict", with the same exit codes as now.
  2. Reusable worktree slots. enact worktree create makes a new directory each time and enact push deletes it. A comment in tools/src/beryl_tools/warm.py says each new worktree rebuilds the workspace crates under new hashes, because the path changed. Keep a fixed pool of slot directories (for example .worktrees/slot-01 to slot-20), hand out a free one reset to origin/staging, and return it on push instead of deleting it. The saving is not measured yet: measure one bead's build time in a new worktree against a reused path before building this.
  3. Slow CI at a fixed cost. Slow CI already tests the tip of staging whenever it is free, about 2.4 commits per run. Keep that, and cap its share of the machine through the scheduler in change 5 so that a higher commit rate produces larger batches, not more CPU.
  4. Reap a worktree's processes when it is removed. A fuzz run (cargo test --release -p beryl_search --test games) started in the worktree of bead by-w8gv.13.6 ran for four and a half hours on a full core after the bead closed and the worktree was deleted. remove_worktree should end every process whose working directory or executable is inside the worktree.

Proposed changes to Beryl

  1. Machine-wide CPU scheduler. Today only browser pages have slots (ui/scripts/slots.mjs). Extend the same idea to every heavy command that by starts: cargo builds, test runs, oracle runs, tournaments and slow CI draw tokens from one pool sized to the core count. Push checks go first, then commands an agent runs by hand, then slow CI, then background work. An agent waiting for a token costs nothing, whereas 20 unthrottled agents would oversubscribe the machine several times over. Cargo can share a pool through the jobserver protocol; confirm that before relying on it.
  2. Cheap source checks at commit time. file-length, pyre and Markdown formatting cause over half of the fast-check failures, and each failure costs a rebase and a full push cycle. Run the repo and names lanes (about 3 s each) and the changed-file formatters from a commit hook, or as the first step of enact push before the rebase.
  3. Change-aware slow CI. Slow CI runs every lane on every run. The fast check already chooses browser checks from the nightly coverage data (selection.py). Use the same choice in by ci, so a commit that only adds card files does not rerun every verb:* browser check, and run the full sweep once an hour and nightly. ui-test is 52% of slow CI's check time, so this is the largest single saving.
  4. Keep editors out of agent worktrees. VS Code held one core for the whole sample, more than all the agents' own commands together. The cause was not checked. If it is file watching or rust-analyzer indexing .worktrees and rust/target, exclude both in the workspace settings.
  5. Record CPU per session. The per-process sampler used for the numbers above is a throwaway script. Move it into tools/ as a by command that appends to $BERYL_CACHE, so the effect of each change here can be read from data.

Decision: slow CI stays on this Mac

Derek decided on 2026-11-12 that slow CI keeps running locally. An earlier draft proposed moving its heavy lanes (app, shots, ui-test, oracle, counts, mobile) to Cygnus or a second Mac; that is dropped. Slow CI's cost therefore has to come down on this machine, which makes change 7 (change-aware slow CI) and change 3 (a capped share of the machine) the ones that decide whether 20 agents fit.

Suggested order

9 and 4 first, because they are small and make everything else measurable. Then 5, which the 3-hour sample moved up: the problem it showed is bursts, and the scheduler is the only change that smooths them. Then 6 and 8, which are cheap. Then 7, then 1. Do 2 only if its measurement shows a real saving.

Expected result

About 10 agents on this Mac after changes 1, 5, 6 and 7. The 3-hour sample supports this: about 7 commits per hour used 8 to 10 cores, so doubling the commit rate fits only if the cost of checks per commit roughly halves, which is what changes 1, 6 and 7 are for. Whether 20 fit depends on how far change 7 cuts slow CI, which used 1.7 cores on average over 3 hours and 5 or more in its busiest minutes. These are estimates from the measurements above, not results.

Still unmeasured

  • What the unattributed 1.2 cores are. Change 9 must record process names so the next sample can say.
  • CPU use at a finer grain than a minute, to confirm the short bursts directly.
  • The build time a reused worktree path saves (change 2).
  • The merge-conflict rate at 20 agents. The likely hot spots are the allowlists under data/, docs/bugs.md and data/ui-conventions.json.
  • Limits outside the machine: 20 sessions need 20 independent ready beads at all times, and enough model rate limit.
