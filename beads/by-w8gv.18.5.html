Close reason

UI asks for card records over IPC and bundles none; data/cards.json deleted; token records by maker

Description

The UI gets card data over IPC on demand; its bundle holds none, and data/cards.json is deleted (plan: docs/project-50k.md, audit "The UI bundles cards.json into its JavaScript: 65 KB today, about 42 MB at 50,000 cards"; Acceptance, "App startup and the UI bundle do not grow with the card store").

Read first: the card store's Rust bead's handoff (the card_records command, its response's shape, what a fixture records); ui/src/cards.ts (133 lines, all of it); ui/src/ipc.ts (581 lines: fixtureTransport at 76, liveTransport at 266, browserFixture at 342, rawTransport at 419, onGameUpdate at 539, artAvailable and cardImageUrl at 547 on); AGENTS.md, UI. Need not read: Board.tsx and the other callers beyond their one line each.

Today

cards.ts imports ../../data/cards.json and builds a map by card, face and token name. Its lookups are synchronous (cardEntry, faceEntry, landFace, tokenFace, useCardArt, useCardBack) and are called from 15 files, several of them pure functions that decide layout or legality from a card's text: game/choices.ts, layout.ts, tablePick.ts, untapChoice.ts, faces.ts, Board.tsx (which the presentation track deletes at its cut-over), CastStep.tsx, AbilityChooser.tsx, Piles.tsx, screens/Game.tsx, mobile/PhoneBoard.tsx, components/Card.tsx, screens/Testing.tsx.

Do

  • Keep those lookups synchronous over a cache, and guarantee the cache instead: a game update reaches its listeners only after the record of every card name it shows is cached (objects' names, and any name its events, candidates and prompt carry: read ui/src/generated/protocol.ts for where names appear). Updates stay in order. When nothing is missing, deliver exactly as today, in the same tick: the stage's stepped clock (ui/src/stage, npm test, just ui-test verb:) and every fixture's timing must not change. One batched request per update, with requests in flight shared.
  • A typed wrapper for the command in ipc.ts, and each transport answers it: Tauri by invoke; live (?live=) and relayed spec frames (?relay) through their server, which answers already; the fixture transport by name from the records its fixture recorded (the replay-in-order rule cannot fit a request that varies); the plain browser with nothing.
  • Screens that show cards outside a game load what they show first: screens/Testing.tsx's CardImage lists every card with a spec, so give it a hook that asks for its names.
  • The card back's image comes with the records or is a constant; useCardBack keeps its behavior where art does not load.
  • A name with no record behaves as a name missing from cards.json does today.
  • ui/scripts/interactions.mjs reads data/cards.json at lines 664 and 9033: read the page's cache or the store instead. Drop ui/vite.config.ts's allowance for importing from the repository root (line 16) if nothing else uses it.
  • Delete data/cards.json and what still writes it (the --output path the pipeline bead kept in tools/src/beryl_tools/cards.py and its test). Before deleting, grep the repository for cards.json: nothing may still read it. Fix the comments that name it (rust/crates/beryl_session/src/protocol/view.rs line 191, which regenerates ui/src/generated/protocol.ts; rust/crates/beryl_app/src/art.rs's header; ui/src/game/faces.ts) and AGENTS.md's data/ paragraph, which should describe the store and how the app serves it.
  • A guard: a test under ui/scripts/*.test.mjs fails if any file under ui/src imports from data/.

No visible change is intended: no new loading state, label or motion. If one proves unavoidable, follow AGENTS.md's UI section (Arena or the nearest existing behavior, a bead labelled human) rather than inventing a look.

Verify

npm run typecheck and npm test in ui/; npm run build, recording the JavaScript's size before and after in the handoff (it should fall by about the 65 KB of card data); just ui-test; just ui-shots; just specs --drive for one card with a token and one with two faces; just smoke.

Parity and policy

This is the data track: it edits no engine-track file (nothing under rust/crates/beryl_engine, beryl_kernel, beryl_card or a card file), and nothing here creates a Rust file per card (K2: an unimplemented card is a record in the store). Parity (plan K11) at the push: just check passes; the frozen save corpus replays (cargo test -p beryl_session --test corpus); rollouts_never_change holds; slow CI's counts lane (just count-gate, bar 405,276,238 instructions, 1% tolerance, rust/crates/beryl_bench/count-gate.toml) passes with no bump to the bar. Nothing waits on the user (K31): proceed on a default and file a non-blocking bead labelled human, parented to by-w8gv.18, where his judgement is wanted. Record decisions and deviations as comments on this bead.

Acceptance criteria

Nothing under ui/src imports from data/, and a test fails if one does; data/cards.json is deleted and nothing in the repository reads it; a game update reaches its listeners only after its cards' records are cached, in order, and in the same tick when none is missing; fixture pages render their cards with no server; the built JavaScript's size before and after is in the handoff; npm run typecheck, npm test, just ui-test, just ui-shots, just smoke and just check pass.
