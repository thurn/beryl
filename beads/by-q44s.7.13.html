Description

Read first: docs/beryl-3d.md 'Threads' (decision C9: search threads use every core one scheduling class below the frame thread), 'Performance gates' ('Measurements') and 'Hosts'; beryl_3d/src/session.rs (the session thread puts itself in the utility class, and the game's and search's threads inherit it), beryl_host/src/threads.rs (interactive_thread, utility_thread, the iOS and Android branches), beryl_3d/src/frame_log.rs (each frame line's searching flag, Summary, Late), just b3d frames (how an agent reads a frame log), and the phone smoke commands in tools/src/beryl_tools/beryl3d/phone.py with the live-game and stand-in options the host beads added.

Why. On a phone, Beryl's own AI search is the only heavy background load. The prototype showed that what matters is whether the search threads' priority lets the frame thread run when it must. A simulator or emulator says nothing about a phone's speed, but it does show whether the frame thread is starved while the AI searches on every core.

Build: just b3d phone-search (with --help and two examples, rule 19), in tools/src/beryl_tools/beryl3d/phone.py. It plays one live game against expert in the iOS Simulator and then in the Android emulator (Vulkan, then with --gles if given), with the human's seat played by the stand-in agent greedy so the game needs no person, for 5 minutes or until the game ends, then pulls the frame log and prints, for each platform: frames drawn, frames drawn while searching was true, late frames while searching and while not, the worst gap while searching, and the load average of the Mac (rule 10). It writes the frame logs into a folder named for the run.

The rule for the result, since the machines are software-rendered and loaded:

  • If late frames while searching are more than twice the share of late frames while not searching (for example 20% against 8%), the search is starving the frame thread on that platform. Then read beryl_host/src/threads.rs's branch for that platform: confirm with a log line in debug builds that the frame thread's class is set (iOS QOS_CLASS_USER_INTERACTIVE, Android setpriority to -10 or the platform's display priority) and that the session thread's is the utility class before the game starts. Fix a class that is not applied in this bead. If both are applied as the doc says and the starvation remains, file a bead under milestone 4 with the numbers and close this one.
  • Otherwise, report the numbers and close.

Report on this bead, and summarize on the epic: the table of numbers for each platform, the adapter, the load, and which rule applied. Do not gate anything on the numbers and do not add this command to the sweep: it is a measurement.

Run: just b3d phone-search; just b3d phone-search --gles.

Acceptance criteria

just b3d phone-search and just b3d phone-search --gles run a live game in the simulator and the emulator and print frames, frames while searching, late frames while searching and not, the worst gap and the load; a comment on this bead and a summary on the epic give the numbers and which rule applied, with a fix or a filed bead when the search starved the frame thread.
