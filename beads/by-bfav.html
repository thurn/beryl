Description

Found while moving card files into set crates (by-w8gv.13.4); not fixed there.

beryl_session/tests/sessions.rs a_game_resumed_from_its_save_plays_on_as_if_it_never_stopped holds only for the decks seed 3 happens to deal. beryl_cards::decks::fuzz_deck used to shuffle the nonbasic cards in CARDS order; when that order changed (card files now list by crate, set and file), seed 3 gave other decks and the test failed at the last view compared (view 30 of 31): the random opponent, who had mulliganed to no cards (mulligans: 7), had played a land in the session that was saved after 15 answers and resumed (lands_played: 1, one permanent on the battlefield) and had not in the same game played straight through by Game::new (lands_played: 0). saves.rs an_answer_no_candidate_does_stops_the_replay_naming_the_step failed with the same decks only because the human played no card in 30 answers (a test precondition, no bug).

fuzz_deck now sorts by name before shuffling, so both tests pass again, by the luck of the decks.

Reproduce: delete the two sort_unstable_by_key lines in rust/crates/beryl_cards/src/decks.rs fuzz_deck and run cargo nextest run -p beryl_session a_game_resumed_from_its_save. Cause not established. First guess: Game::from_replay (beryl_session/src/game/replaying.rs) replays the recorded choices without drawing from the opponent agent's random stream, so after a resume the 'random' agent's next draw is not the one the uninterrupted game makes. If that is intended (a resumed game need only be a legal continuation), the test's claim should be narrowed to the human's views; if not, the agent's stream position belongs in the save.

Acceptance criteria

The resumed game matches the uninterrupted one for every fuzz seed tried (say 0..20), or the test and its doc comment say what a resume does guarantee; cargo test -p beryl_session passes.
