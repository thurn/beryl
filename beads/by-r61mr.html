Description

Current run scope

Land the complete ticket implementation for Beryl and Enact and verify it in local simulators and isolated fixtures. Keep Beads authoritative for both live projects. The user will run the Windows check (by-r61mr.38). Production deployment, live imports, fleet cutover, and legacy retirement move to follow-up epic by-vaexw. The production steps and gates below describe that follow-up.

The full contract (schema, API, readiness rule, leases, feed, cutover, tokens, the tk command line and the budget) is in this epic's design field: bd show by-r61mr --json, key design. It is settled; child tickets build against it and do not redesign it.

What is wrong today

Beryl's tasks are kept in beads (bd, an embedded Dolt database in .beads/, 2.7 GB on disk, 4,644 beads of which 212 are open). Enact serializes every bd call and every Dolt sync behind a per-clone file lock, the "ownership lock" (ownership_lock in ~/enact/scripts/enact.py). Sessions spend most of their coordination time waiting for it.

Measured on this Mac on 2026-11-16, from .git/enact/lock-waits.jsonl:

  • In 16 hours there were 3,345 lock acquisitions. Sessions waited 1,173 minutes in total for the lock: a median of 4.7 s, 64 s at the 90th percentile, 395 s at worst, and 34 waiters gave up.
  • A plain bd list --status open --limit 3 took 36 s of wall time for 0.3 s of CPU, all of it waiting on Dolt's lock.
  • A full sync holds the lock for 10 to 25 s, mostly pushing Dolt data to GitHub.
  • The status site (status/) is rebuilt from bd export and pushed to GitHub Pages at most once every ten minutes, so it is never current.

What this epic builds

A ticket system hosted on Cloudflare's free plan that replaces beads for Beryl and for Enact's own tasks, becomes Enact's whole coordination service, and serves the status dashboard live. Nothing in it may cost money: if any part turns out not to fit the free plan, stop and record why in this epic rather than paying or working around it.

The free plan's limits, checked on 2026-11-16, are 100,000 requests per day, 100,000 SQLite rows written per day, 5 million rows read per day, 5 GB of storage and 10 ms of CPU per request. Exceeding a daily limit makes those operations fail until 00:00 UTC. Beryl's load is well inside them, on one condition: nothing polls. Anything that waits (enact next --wait, the dashboard) holds a WebSocket, where 20 incoming messages are billed as one request.

Decisions (from the design interview with the user, 2026-11-16)

  1. One authority. A single SQLite-backed Durable Object per project, behind a Worker, holds every ticket. Clients call it over HTTPS. There is no local mirror, no daemon and no D1 database.
  2. All of Enact's coordination moves to the server. That is tickets, atomic claims, and expiring leases that replace the staging lock (refs/enact/staging-lock) and the Justiciar refs (refs/enact/justiciars/). Sessions and slow-CI results are posted as events so the dashboard can show them. Enact keeps git for code only. The ownership lock, the sync pusher and all Dolt code are deleted. Note what this does not fix: the staging lease is still held while a merge-queue batch runs its fast check. Taking and renewing it becomes one request instead of several git round trips, and waiters queue fairly, but the check takes as long as before.
  3. Ticket IDs. A new root ID is 4 lower-case base32 characters, the first a letter, from an alphabet without i, l, o and u (about 700,000 roots), allocated by the server, for example k7mq. A child appends a dot and a number: k7mq.3 is the third child of an epic and k7mq.3.12 a ticket under that milestone. IDs carry no project prefix; the project comes from the repository's Enact config. A migrated bead keeps its root and numbers with the prefix dropped (by-q44s.7.24 becomes q44s.7.24), and the prefixed form is accepted as an alias forever, because commits, docs and transcripts cite it.
  4. The ticket model is bd's, limited to what is in use: the statuses, priorities P0 to P4, labels, dependency types, parents, assignees, comments and a changelog. Keeping it the same is what makes the shim in decision 6 exact.
  5. Everything migrates: all 4,644 beads with their dependencies, labels, comments and changelog. The closed beads are imported over the days before the cutover so that the final import is only open and recently changed tickets, which keeps each day under the rows-written limit. Rehearsal imports count against the same limit, so rehearse against wrangler's local simulator.
  6. Cutover through a bd-compatible shim. bd is called from enact.py (the subcommands create, show, list, ready, update, close, dep, label, comments, epic, defer, init, dolt), from the skill and role prompts that running sessions follow, and from Beryl's tools (tools/src/beryl_tools/{bugs,nightly,flaky,verdicts,cpu,app}.py, status/src/beryl_status/, efficiency/src/beryl_efficiency/, the justfile). The shim is a bd stand-in that turns those subcommands, flags and JSON outputs into server calls. The cutover pauses writes for about a minute, imports the delta and swaps the bd on PATH on all three machines. Running sessions carry on without noticing. Afterwards the callers move to the native CLI one at a time and the shim is deleted.
  7. The cutover is automatic. The run cuts over by itself once three gates pass: the shim gives identical results on the compatibility corpus of recorded bd calls; a rehearsal import matches the bead store ticket for ticket; and all three machines reach the server with their tokens. It posts the result on the dashboard. The frozen bead store is kept for two weeks, then .beads/ is removed. There is no dual-write period and no reverse sync: a problem after the cutover is fixed forward.
  8. Access is deliberately simple, because the stakes are low and the tickets are already public. Anyone can read. Writes, claims and leases need a static bearer token, one for each of the three machines (this Mac, the second Mac, and Cygnus, the Windows PC), stored outside any repository. Build nothing beyond that.
  9. The dashboard is HTML rendered by the Worker from the ticket store, cached per ticket version. Cirrus's CSS and cirrus.js are served as static assets, and its Python components are ported to TypeScript. The code that swaps changed content into an open page stays; the poll of version.json that drives it is replaced by a WebSocket naming the tickets that changed, so an open page is current within about a second. The dashboard stays read-only and keeps the priorities in status/AGENTS.md: measured performance first, then cirrus.
  10. All of it lives in the Enact repository (~/enact): the Worker, the CLI, the shim and the dashboard, with cirrus moved over from Beryl's status/. One deployment serves every project under a path per project. Beryl's status/ directory, its launchd publisher and the GitHub Pages site are removed once the new dashboard is live.
  11. The CLI is a compiled Rust binary, and the shim is the same binary under the name bd. Each machine builds it from source and rebuilds it when its sources change. enact.py stays stdlib Python for now and runs the binary for every ticket, claim and lease operation, so there is one client. Enact's scheduler stays in Python: a command reads the live graph in one request (usually answered "unchanged") and writes with one atomic batch that carries preconditions, so no command needs a lock.
  12. "Ticket" replaces "bead" in the new CLI, server and dashboard from the start. After the shim is deleted, one mechanical lane renames the word in the AGENTS.md files, the Enact skills and role prompts, and tool output. Not before, so that running sessions' prompts stay valid.
  13. The work runs on the second Mac, because this Mac's CPU is fully used by Beryl 3D work. Start /enact-plan there. The first ticket sets up wrangler (run through npx) and checks wrangler whoami; if no login is saved, the user runs wrangler login once on that machine. Until the first deploy, everything runs against wrangler's local simulator, so no ticket waits on the login. This is the only step that can need the user.
  14. A copy outside Cloudflare. One machine pulls a full export every day and pushes it to a git branch of the project's repository.
  15. No review gate epics. Enact files an epic such as "M3 review gate" after every milestone to hold its Mason and Sage audits, because beads only lets an epic block an epic and hides a blocked epic's children. The ticket server removes the limit instead:
    • Any ticket may depend on any ticket. A dependency on a ticket that has children is satisfied only when it and all its descendants are closed, including children filed later.
    • A ticket inherits the blockers of its ancestors, and stays visible in listings with the reason it is not ready.
    • A ticket flagged last is ready only when every other descendant of its parent that is not itself last is closed. Audits and the Archivist are last tickets under the milestone or epic they cover. Findings an auditor files go under the same milestone, so whatever depends on the milestone waits for them.
    • A parent closes on the server when its last open descendant closes. Gate epics already in the bead store migrate as ordinary tickets.
  16. The whole fleet switches at once. The server holds a cutover state: before, paused or after. The shim is installed as bd on every machine days ahead. In before it runs the real bd; in paused it waits; in after it answers from the server. The cutover is a change of that one value, so no machine is ever on a different store from the others, and no session needs access to another machine.
  17. Machines register their own tokens. There is no SSH between the machines and the Enact repository is public. Each machine generates its token on first use and pushes only its hash to a ref in the project's GitHub repository, which it can already push to. The server accepts a token whose hash is on that ref.

Defaults chosen without asking, to change if they prove wrong:

  • When the server cannot be reached or a daily limit is hit, a command retries with backoff for a few minutes and then fails with a distinct exit code. Nothing is queued locally, because a claim cannot be made offline.
  • The server counts its own requests and rows written per day, and the dashboard shows them against the limits.
  • The production dashboard and API use https://tickets.thurn.workers.dev/ in Cloudflare account 0cc730645e29feff389c14f36cb9cf4c. The existing tickets Worker is a placeholder; deploy the new server to that Worker, not to a new service or subdomain.
  • Beryl migrates first; Enact's own beads (prefix en) follow with the same importer.

Targets

  • A ticket command takes under 100 ms at the median and under 500 ms at the 99th percentile, measured on a loaded machine.
  • Total time sessions spend waiting on coordination, other than the staging lease during a check, falls from about 1,200 minutes a day to under 10.
  • A change to a ticket shows on an open dashboard page within one second.
  • A normal day uses under a third of every free-plan limit (the contract's budget table estimates 31,500 requests and 29,000 rows written).

Shape of the graph

The children are flat under this epic, with no milestone epics and so no gate epics. Dependencies are only where one ticket needs another's result, and lanes are used only where work is truly sequential, because the user asked for as much parallelism as the work allows and accepts merge conflicts.

  • Ready at once: the contract, the recording of real bd calls, and the project set-up.
  • After the contract and set-up: the store, the CLI, Enact's port (against a stand-in for tk generated from the contract) and cirrus's move, together.
  • Then, together: claims and leases, the change feed, the importer, the dashboard's pages, the per-machine install, Enact's leases, and gate-free plans; then the shim, token registration and live updates.
  • Four Wardens review the risky areas (server races, data fidelity, the dashboard, Enact on the server), and the deploy and cutover wait for them.
  • After the cutover, the callers move off bd in parallel, then the shim and the beads backend are deleted, then "bead" is renamed.

There is one Mason audit at the end, no Sage, and one Archivist. Every ticket carries tier:opus (design, review, anything that can lose data) or tier:sonnet (mechanical); never tier:fable. Tickets filed later under this epic follow the same policy.

Design

Contract

This is the settled design every child ticket builds against. A ticket that finds it wrong changes it here, in the same session, and comments on the epic with what changed and why; it does not work around it.

1. Storage

One Durable Object per project, named by the project key (by, en). Its SQLite database is server/contract/schema.sql:

CREATE TABLE meta (key TEXT PRIMARY KEY, value TEXT NOT NULL) WITHOUT ROWID;
-- keys: seq (global change counter), cutover (before|paused|after),
-- cutover_at, daily_usage ({day, requests, rows_written}),
-- token_hashes (hash to machine), token_fetched_at

CREATE TABLE tickets (
  id          TEXT PRIMARY KEY,          -- 'q44s.7.24', no project prefix
  parent      TEXT,                      -- id with the last dotted part removed
  next_child  INTEGER NOT NULL DEFAULT 1,-- next number handed to a child
  title       TEXT NOT NULL,
  body        TEXT NOT NULL DEFAULT '',
  acceptance  TEXT NOT NULL DEFAULT '',
  design      TEXT NOT NULL DEFAULT '',
  notes       TEXT NOT NULL DEFAULT '',
  type        TEXT NOT NULL DEFAULT 'task',   -- task|epic|bug|feature|chore|decision|spike|story|milestone
  status      TEXT NOT NULL DEFAULT 'open',   -- open|in_progress|blocked|deferred|closed
  priority    INTEGER NOT NULL DEFAULT 2,     -- 0..4
  assignee    TEXT,
  last        INTEGER NOT NULL DEFAULT 0,     -- 1: runs after its siblings (section 4)
  labels      TEXT NOT NULL DEFAULT '[]',     -- JSON array of strings
  metadata    TEXT NOT NULL DEFAULT '{}',     -- JSON object (Enact's enact_* keys)
  defer_until TEXT,
  close_reason TEXT,
  created_at  TEXT NOT NULL, created_by TEXT NOT NULL,
  updated_at  TEXT NOT NULL, closed_at TEXT,
  version     INTEGER NOT NULL                -- value of seq at the last change
) WITHOUT ROWID;
CREATE INDEX tickets_live ON tickets(status) WHERE status != 'closed';
CREATE INDEX tickets_parent ON tickets(parent) WHERE parent IS NOT NULL;

CREATE TABLE edges (                       -- src depends on dst
  src TEXT NOT NULL, dst TEXT NOT NULL,
  kind TEXT NOT NULL DEFAULT 'blocks',     -- blocks|conditional-blocks|waits-for|related|discovered-from
  PRIMARY KEY (src, dst)
) WITHOUT ROWID;
CREATE INDEX edges_dst ON edges(dst);

CREATE TABLE comments (
  ticket TEXT NOT NULL, n INTEGER NOT NULL,
  author TEXT NOT NULL, at TEXT NOT NULL, text TEXT NOT NULL,
  PRIMARY KEY (ticket, n)
) WITHOUT ROWID;

CREATE TABLE history (                     -- the changelog
  ticket TEXT NOT NULL, seq INTEGER NOT NULL,
  actor TEXT NOT NULL, at TEXT NOT NULL,
  change TEXT NOT NULL,                    -- JSON: {field: [old, new], ...}
  PRIMARY KEY (ticket, seq)
) WITHOUT ROWID;

CREATE TABLE leases (
  name TEXT PRIMARY KEY, holder TEXT NOT NULL, machine TEXT NOT NULL,
  expires_at TEXT NOT NULL, payload TEXT NOT NULL DEFAULT '{}',
  waiters TEXT NOT NULL DEFAULT '[]'       -- JSON array of {holder, since}, arrival order
) WITHOUT ROWID;

CREATE TABLE events (
  seq INTEGER PRIMARY KEY, at TEXT NOT NULL,
  kind TEXT NOT NULL,                      -- session|ci|machine|cutover|usage
  machine TEXT NOT NULL, actor TEXT NOT NULL, data TEXT NOT NULL  -- JSON
);
CREATE INDEX events_kind ON events(kind, seq);

CREATE TABLE aliases (alias TEXT PRIMARY KEY, id TEXT NOT NULL) WITHOUT ROWID;
CREATE INDEX aliases_id ON aliases(id);
  • Labels and metadata are JSON in the ticket's row, not tables. Filtering by label scans the live tickets, of which there are a few hundred.
  • When the object wakes it loads every ticket whose status is not closed, and the edges among them, into memory. graph, ready and readiness are answered from memory; writes go to SQLite and memory in one transaction.
  • An imported bead's whole changelog is one history row (seq 0, change a JSON array of the old events). This keeps a full import near 40,000 rows written, inside one day's limit; the importer ticket measures the real figure.
  • Events older than 30 days are deleted by a daily alarm.

2. IDs

  • Alphabet: 0123456789abcdefghjkmnpqrstvwxyz (base32 without i l o u).
  • A new root is 4 characters, the first one a letter, chosen at random and retried on collision with a ticket or an alias.
  • A child's ID is <parent>.<next_child>, taking and incrementing the parent's next_child in the same transaction. Depth is not limited. A ticket keeps its ID when an update changes its parent. Readiness uses the stored parent.
  • Every lookup strips a leading <project>- and then consults aliases. The importer sets each parent's next_child to one past its highest child. Imported roots keep whatever characters they have.

3. HTTP API

All routes are under /<project>/api. Reads need no token. Writes need Authorization: Bearer <token> and take the session's name from X-Actor and the machine's from the token's registration.

RouteDoes
GET /state{cutover, cutover_at, seq, day, requests, rows_written, limits}
GET /tickets/<id>?comments=1&history=1One ticket with its edges in both directions, children, ready and blocked_by
GET /tickets?status=&type=&parent=&ancestor=&label=&assignee=&ready=1&all=1&limit=A list; closed tickets only with all=1 or status=closed
GET /graph?all=1Live tickets by default, or all tickets with all=1. Includes ready, edges within the selected graph, and seq. Omits body, design and notes. Matching the projection's ETag returns 304.
POST /batchThe only way to write tickets (below)
POST /leases/<name>`{op: acquire\renew\release, holder, ttl_s, payload}`
GET /leasesEvery lease with its holder, expiry and waiters
POST /events{kind, data}
GET /events?kind=&since=&limit=Events after since
GET /feedWebSocket (section 6)
POST /importUp to 200 tickets with edges, comments and history; idempotent
GET /export?after=<id>JSON lines of whole tickets sorted by ID, paged

The import body is {tickets: [...]}. Each element has the ticket fields plus its outgoing edges, comments, history and optional aliases arrays. Export uses the same flat objects, up to 200 per page and an empty page at the end. The server assigns the version of changed ticket fields and preserves the higher child allocation counter. It skips snapshots older than the stored ticket by updated_at. Import returns {seq, imported, rows_written}, where imported counts changed tickets and rows_written counts their data and the shared sequence write.

POST /batch takes {if: [...], ops: [...]} and applies all of it in one transaction or none of it.

  • Preconditions in if: {id, version}, {id, assignee} (null for unassigned), {id, status}, {seq} (nothing at all has changed since).
  • Operations in ops: create (fields; parent; deps; returns the new ID, which later operations in the batch may name as $0, $1), update (set fields, add_labels, remove_labels, set_meta, unset_meta), claim (sets assignee to the actor and status to in_progress; fails if assigned to anyone else), close (reason), reopen, defer (until), comment (text), dep_add, dep_remove (on, kind).
  • Result: {seq, results: [...]}, or status 409 with {failed: <index of the precondition or operation>, current: <ticket>}.
  • Closing a ticket also closes each ancestor whose descendants are now all closed, in the same transaction, and reports them in the result.
  • A close with include_ready: true also returns ready, the IDs ready after that close. The scheduler uses them to choose a lane continuation from the graph it already has, conditional on the close's result sequence.

Enact uses the all=1 projection to keep closed worker assignments visible for archiving and to track their commits through slow CI. Cache each graph projection separately by URL, project and query. tk graph --if-none-match returns {"unchanged": true} on HTTP 304. For wait change --since SEQ, use that sequence in the first feed message so a change between the previous read and subscription wakes the caller.

Status codes: 200; 304; 400 malformed; 401 missing or unknown token; 404 no such ticket; 409 precondition failed or claim or lease lost; 429 with {limit: requests|rows_written} when the object's own count says the write would pass 90 percent of a daily limit.

There are no endpoints written specially for Enact. Its scheduler stays in Python: enact next is one GET /graph (usually a 304 against the copy the helper cached on disk) and one POST /batch whose preconditions make the reservation atomic. enact start and enact close are one batch each, the close with --continue reading the reply's graph delta to pick the lane's next ticket and claiming it in a second batch. So an Enact command makes at most two requests (three for a lane continuation), and none under a lock.

4. Readiness

A ticket is ready when all of these hold:

  1. Its status is open, and defer_until is absent or in the past.
  2. Every edges row from it of kind blocks, conditional-blocks or waits-for points at a ticket that is closed and, if that ticket has children, has no live descendant.
  3. The same holds for every ancestor's blocking edges.
  4. If last is 1: every other descendant of its parent whose last is 0 is closed.
  5. It has no live child. A ticket with children is a container and closes by itself.

GET /tickets/<id> reports blocked_by as the list of ticket IDs that make it not ready, with which rule each came from, so a listing can always say why. Nothing is hidden from listings for being blocked.

Each live graph ticket includes blocked_by for rules 2–5 so a scheduler can see blockers involving closed tickets omitted from the live graph. The graph includes the full readiness result in ready. When an eligible ticket's defer time passes, the graph's ETag changes without a new write. The graph's numeric seq remains the batch precondition.

5. Leases

A lease is a named, expiring claim. Names in use: staging (the merge queue's lock, ttl_s 180, renewed every 60 s while a batch is checked), justiciar/<machine>, and vizier/<epic>/<vizier> (the liveness leases that are files under the clone's state directory today).

  • acquire: succeeds if there is no row, the row has expired, or the caller already holds it. Otherwise the caller is appended to waiters if absent and gets 409 with the holder, expiry and its position. An expired lease goes to the first waiter that asks; a waiter that has not asked for 60 s is dropped.
  • renew and release succeed only for the holder; anyone else gets 409, which is how a holder learns it lost the lease (LeaseLost in Enact).
  • A waiter does not poll: it holds the feed and asks again when told the lease changed or reached its expiry.

6. The feed

GET /feed upgrades to a WebSocket, accepted with the hibernation API so an idle connection costs nothing.

  • Server to client, after each committed change: {seq, tickets: [ids], leases: [names], events: [kinds], cutover}. Changes within 100 ms are sent as one message.
  • Client to server, once after connecting: {since: <seq>}. If the server's seq differs, it replies with one message listing everything changed since, or {resync: true} if that is more than 500 tickets.
  • A lease's expiry is announced by an alarm set for the earliest expiry.
  • tk wait and the dashboard are the only clients. The dashboard fetches the HTML fragments for the tickets named and swaps them in.

7. Cutover state and the shim

  • The shim caches GET /state in a file for 5 seconds for calls that only read. A call that writes always fetches it first.
  • before: run the real bd. If the server cannot be reached, also run the real bd.
  • paused: on first seeing it, publish the machine's bead store (enact sync with ENACT_SYNC_NOW) and post a machine event {drained: true}; then wait on the feed for the state to change.
  • after: answer from the server. The transition from paused preserves cutover_at from the start of the pause. Returning to before clears it.
  • The cutover session sets paused, waits until every machine that posted a machine event in the previous 10 minutes has posted drained (at most 5 minutes, else it sets before again and stops), pulls the bead store, runs the final import and comparison, and sets after.
  • One hour later it pulls the bead store's remote once more and imports any bead changed after cutover_at, to catch a write that was in flight on a machine that was asleep during the pause.

8. Tokens

  • tk register writes 32 random bytes, hex encoded, to ~/.config/enact/token (%APPDATA%\enact\token on Windows), and pushes the ref refs/enact/tokens/<machine>/<sha256 of the token> to the project's GitHub remote, pointing at the repository's first commit. It deletes the machine's older refs.
  • On a write whose token hash is not in meta.token_hashes, the server calls GitHub's public git/matching-refs/enact/tokens for the project's repository, at most once a minute, replaces the stored set with the ref names, and decides. The repository for each project is a Worker variable.

Spelling rule (decided with the user on 2026-11-17). Where a tk command means the same as a bd command, it uses bd's name, flags, short flags and positional arguments, as above. Agents and prompts already know bd's spelling, so callers move to tk mostly by renaming the program. tk adds commands and flags only for what bd never did (leases, events, waiting, the cutover state, conditional writes) and leaves out bd features with no server counterpart (Dolt, sync, memories, mail). It keeps its own JSON output and exit codes; the shim still translates output into bd's JSON shapes.

Without --json a command prints a short human-readable form; with it, the server's JSON. Exit codes: 0 done; 1 bad usage, not found or a malformed request; 3 a precondition failed or a claim or lease belongs to someone else (the code Enact already uses for a lost race); 4 the server could not be reached within --retry-for; 5 a daily limit was hit and did not clear within --retry-for; 6 tk wait timed out. Retries back off from 0.2 s to 10 s. Only reads and operations with preconditions are retried without asking the server whether the first attempt landed; a create carries a client-chosen request key that the server remembers for a day, so a retry never creates twice.

Invoked as bd, the binary is the shim (section 7).

10. Budget

SQLite reports the rows and index entries written. A changed batch writes the shared meta.seq row once. Excluding that row:

  • A keyed root create writes 4 rows (ticket, live index, history and request key). A child writes 2 more (parent index and the parent's allocation counter). A newly added dependency writes 2. An unkeyed or closed creation omits its request-key or live-index row, respectively. A keyed retry writes zero.
  • A ticket update writes 2 rows for the ticket and history. An insert or update of a live status adds 1, and a new parent adds 1. In the simulator a close writes 2 rows per closed ticket, including any closed ancestors.
  • A comment writes 1 row. Removing a dependency writes 1. Comments and dependency changes advance graph seq; they have their own tables and leave the ticket's field version unchanged. The allocation counter also leaves the parent's field version unchanged.
  • An event writes 2 rows and a lease operation writes 1, before shared bookkeeping.
