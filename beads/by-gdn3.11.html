Push loses a passed fast check when the ownership lock is busy

  • Close reason
  • Description
  • Comments1
  • Changelog

Close reason

Passed-check pushes and queue landings wait out the ownership lock; lock holder recorded and logged

Description

What we see

On 2026-11-13 a Beryl enact push passed its fast check, then failed with ownership operation busy; retry (exit 3): ownership_lock in ~/enact/scripts/enact.py gives up after 180 s, and another session held the lock that long. The check's work was thrown away and the push had to run again.

The merge queue (land in enact.py) takes the same lock before it pushes a checked batch. If it times out there, the Fail escapes run_queue, the integrator's own push fails, and the next integrator rebuilds and re-checks the whole batch.

Change

  1. Record who holds ownership.lock (pid, command, start time) next to the lock, and log it when a waiter times out, so the long holder can be found.
  2. In land, keep waiting for the ownership lock after a passing check instead of failing: losing a checked batch costs far more than waiting. Same for the direct path in cmd_push after its check passes.
  3. Find what held the lock for over 3 minutes (likely a Dolt sync or compaction under load) and file it if it needs its own fix.

Done when

A unit or integration test shows a push whose check passed waiting out a held ownership lock and landing, and a timed-out waiter's log names the holder. Change is in ~/enact (tests in tests/test_unit.py, tests/test_integration.py); read ~/enact/AGENTS.md first.
