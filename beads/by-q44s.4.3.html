Description

Symptom: the worst frame of most gated boards is far over the 2 million instruction target that docs/beryl-3d.md ('Threads', 'Measurements') gives every frame, and has kept rising. On staging e07e319fe, data/beryl3d/gates.json holds worst_frame_instructions at 4,816,173 for verbs-zones, 3,267,119 for stress-255, 9,283,180 for stress-1024 and 2,638,123 for stress-verbs. On a 2015-class CPU, 9.3M instructions is roughly half a frame before the renderer has encoded anything.

Why: the worst frame is always the frame whose Client::handle receives a view with a script. play::compile (rust/beryl3d/crates/beryl_scene/src/play/compile.rs, compile) plays every step of the script at once through Motion::step (src/play/step.rs), re-placing the groups each step changes (src/play/step/placement.rs, src/table/place.rs). just b3d gate --board verbs-zones shows frame 980 placing 738 objects over 34 steps in that one call. Six beads (by-q44s.22, .3.57, .3.61 to .3.65) cut the cost per step; by-q44s.3.65 measured about 160 instructions per placement and concluded that 2M cannot be reached by placing fewer cards. The cost grows with the script's length, and the design compiles the whole script in one frame.

Current design: Show::push (src/play/mod.rs) compiles a script the moment it arrives, against the view the table will show when its turn comes, and the whole result (Compiled: tracks, finals, effects, sounds) exists before the next frame.

Proposed design: compile a script resumably. Laying the script out in time (beat::lay_out over its StepTimings) is cheap and stays whole, so every step's start and end are known at once. The per-step part (Motion::step, the effects and the sounds of each step) runs in order, up to a fixed number of steps per frame, and must reach each step before the frame in which that step begins. A beat's steps start together, so the frame that receives the script compiles at least its first beat; later beats start at least one beat's duration later (hundreds of milliseconds, so tens of frames), which leaves room to spread them. Sketch:

pub(crate) struct Compiling<'a> { motion: Motion<'a>, next: usize, compiled: Compiled } impl Compiling<'_> { /// Compiles steps until through (the last step that begins by until) or budget steps, whichever is later. fn advance(&mut self, until: u64, budget: usize) -> bool /* done */; }

Default for where the later steps run: inside Client::frame, before the frame is assembled, with every buffer the script needs reserved when the script arrives in handle (its step count and object count are known then), so that Client::frame still allocates nothing (rule 3, the allocation gate). Record the choice on this bead if the code makes another place simpler. finals (the resting places once the script ends) is known only when the last step is compiled; anything that reads it earlier (src/table/scene.rs, src/play/scroll.rs, the rest-placement check) must wait for completion or use the view's own placement (Table::placement), which the debug assertion in Motion::step already proves equal.

What it removes: the per-frame cost that grows with the script's length, and the series of per-step micro-optimisation beads aimed at a target that design cannot reach.

Behavior that must not change: every pose at every time (the interface tests and just b3d timeline-parity give identical output), the rest-placement and step-time checks, and frame_allocations = 0.

Files: rust/beryl3d/crates/beryl_scene/src/play/compile.rs, play/mod.rs, play/playing.rs, play/step.rs, client/mod.rs; tests in rust/beryl3d/crates/beryl_scene/tests/all and beryl_inspect/tests/all/frame_allocation.rs; limits in data/beryl3d/gates.json; docs/beryl-3d.md 'Threads' and 'Measurements'.

Acceptance criteria

  1. A beryl_scene test plays a script of at least 30 steps in 4 or more beats and asserts that the frame receiving it compiles only the steps that begin by the next frame (a work counter, Work::steps, of the receiving frame is at most the first beat's step count plus the per-frame budget), while every pose at a series of times equals the whole-compile result.
  2. just b3d gate --counts --board verbs-zones --board stress-255 --board stress-1024 --board stress-verbs shows each worst frame lower than its limit on staging e07e319fe, and the limits are lowered with --counts --update in the same change; old and new numbers are in the commit body.
  3. just b3d test, just b3d timeline-parity --fixtures and just b3d gate pass with no entry raised, and frame_allocations stays 0.

Scope: did the first coherent part and filed the rest as by-q44s.4.10. The full design runs into four problems that each need their own work. (1) Motion<'a> borrows the views and the Table, so keeping it across frames needs Rc'd updates plus self_cell, or slot-indexed NameIds/Index. (2) Motion::step allocates, so it cannot run inside Client::frame; it needs a new Client::prepare entry point that hosts call before frame. (3) Many Show paths read or mutate the whole Compiled at script start: relay, hand_over, hand_over_tray, place_let_go, affect/announce, coming_counts/coming_notices in handle, finals in scene.rs every frame, and wake. (4) Exactness: a later step's retarget changes the landing pose of an earlier flight still on its way, so per-beat 'compile before it begins' is not enough. The horizon rule (compile every step that begins before the latest active segment ends) fixes this, and the draw test fails without it. Also found: a Track holds 16 segments, so a script with ~20+ draws drops library cards' earliest segments even in the whole compile; tests keep under that. stress-verbs is one unstaggered beat of 106 steps and cannot gain; the stress-255/1024 beats are staggered (30 ms) and should drop to ~14 of 40 steps in the receiving frame.
