Description

The scale rehearsal's one-edit rebuild (just scale --assert, tools/src/beryl_tools/scale.py, budget 2 s on the reference machine) is borderline after by-w8gv.13.14 (staging e28db8c6): at a load of about 20 it takes 1.55 to 1.8 s on the clock to its last unit, and the harness divides by this machine's speed factor 0.82, so --assert gave a median of 2.2 s at load 19. What remains is the edited set crate's own incremental recheck, about 0.9 s for 1,350 cards (rustc -Z time-passes: parsing the crate's files 0.29 s, resolution 0.10 s, writing metadata 0.29 s for a 20.6 MB rmeta, saving incremental state 0.17 s), plus about 0.4 s in which Cargo checks the times of every card file before any unit starts. The recheck grows with the crate's size, which data/set-groups.json fixes at 500 to 1,500 cards per crate (plan decision K8, docs/project-50k.md). Measure the rebuild with smaller crates: just scale --no-scripts --crates 74 (half the size) and --crates 111, against the default 37, interleaving edits between workspaces at the same load as by-w8gv.13.14 did (two BERYL_CACHE roots; time cargo check -p beryl_cards --features scenarios --timings after appending to one clone). Also record the cold check, release build and peak memory, which more crates may raise. If a smaller group size keeps the other three budgets and gives the rebuild real margin, change the grouping rule in data/set-groups.json's generator (tools/src/beryl_tools/set_groups.py, just card crates) and record the decision under K8; otherwise record the numbers on this bead and close it.

Acceptance criteria

The bead records the rebuild, cold check, release build and peak memory at 37, 74 and 111 crates from interleaved runs. Either the grouping rule changes with K8 updated and just scale --assert passing, or the bead closes with the numbers and why the rule stays.

Numbers (50,000 clones, three scratch workspaces in separate BERYL_CACHE roots, just scale --no-scripts --crates N run one after another at load 21-34):

  • 37 crates: cold check 47.7 s adj (486 CPU-s), release 14.5 s (164 CPU-s), rebuild median 1.8 s (5.2, 1.8, 1.7), peak 1.11 GiB.
  • 74 crates: cold 57.7 s (496 CPU-s), release 26.7 s (212 CPU-s), rebuild 1.6 s (3.9, 1.6, 1.5), peak 1.12 GiB.
  • 111 crates: cold 49.6 s (486 CPU-s), release 39.2 s (220 CPU-s), rebuild 2.6 s (2.6, 3.7, 2.5), peak 1.13 GiB. Interleaved one-edit rebuilds (one warm-up edit each, then 8 rounds, order alternating 37/74/111, load 13-20): adjusted medians 3.23 / 2.78 / 2.99 s, wall medians 2.68 / 2.38 / 2.52 s, CPU medians 3.00 / 2.46 / 2.37 s, peak 0.51 / 0.44 / 0.44 GiB. Over budget at every size under this load. cargo --timings, 3 interleaved rounds at load ~11, wall 1.83-2.06 / 1.79-1.91 / 1.80-2.03 s: units start 0.37-0.48 s in all; set build script 0.2-0.35; set crate check 0.87-0.99 / 0.43-0.50 / 0.33-0.37; beryl_card_names build script 0.26-0.41 then its check 0.62-0.73, ending at 1.4-1.6 s; registry 0.09-0.15 after both. So at 74 and 111 crates the names crate is the longest path and the set crate's halving barely shows. Experiment: names crate pinned to its generated names.rs (no watch on rust/cards) in all three workspaces, 8 more interleaved rounds — load had risen to 30-42 with syspolicyd scanning, so walls are noise (2-20 s), but the set crate check medians were 3.12 / 0.93 / 0.61 s, and the names crate left the path entirely. Decision: K8's rule (500-1,500 cards) stays. Halving it saves 0.1-0.3 s while beryl_card_names reruns on every card edit (it watches ../../cards; Cargo reruns on any newer mtime under it). Follow-up by-w8gv.13.16 fixes that, then re-measures 37 vs 74 and may halve the rule. Also filed by-w8gv.13.17 after the user said this machine is always heavily loaded and plans must not assume a quiet one (scale --assert, just bench's quiet refusal, docs/benchmarking.md).
