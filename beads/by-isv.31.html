Close reason

Test and CLI paths found at run time; regression test for a moved target (59ec509)

Description

Seen in by-isv.16 on staging fabd4d6: in a fresh worktree whose rust/target was cloned from the warm cache (tools/src/beryl_tools/warm.py), just check failed four tests in rust/crates/beryl_cli/tests/longthink.rs (a_game_that_crashes_twice_is_skipped, no_arguments_start_or_resume_the_latest_run, one_runner_per_run, stops_cost_nothing_but_time) at longthink.rs:42 with NotFound spawning BIN. BIN is env!("CARGO_BIN_EXE_beryl_cli"), an absolute path baked in at compile time. Cargo fingerprints workspace members by workspace-relative path, so the cached test binary, compiled in another (since deleted) worktree, counts as fresh and points at that worktree's target/debug/beryl_cli. cargo nextest run -p beryl_cli (different feature set, so a separate artifact) passed; touching tests/longthink.rs forced a rebuild and just check passed. Any fresh worktree can hit this, including enact push's fast check. Fix: find the binary at run time (e.g. next to std::env::current_exe(): target/debug/deps/.. -> target/debug/beryl_cli), or otherwise make the cache-cloned test binary safe; check other tests using CARGO_BIN_EXE_ for the same pattern.

Acceptance criteria

A test (or by check step) that copies or clones rust/target to a different checkout path still passes the longthink integration tests without a rebuild; no test in the workspace bakes in an absolute CARGO_BIN_EXE_ path that a cloned target can make stale.
