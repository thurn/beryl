Close reason

APNAP timestamps for permanents entering together, with the controller's order asked only when it may change layer results; landed 45907726

Description

Why

by-bajq.2.3 built dependencies (CR 613.8) and timestamp renumbering but not CR 613.7m: objects that enter the battlefield at the same time still take timestamps in the order the kernel moves them (State::take_timestamp in beryl_kernel/src/timestamps.rs, called per object from zone.rs's move). CR 613.7m: "If two or more objects would receive a timestamp simultaneously, such as by entering a zone simultaneously or becoming attached simultaneously, their relative timestamps are determined in APNAP order (see rule 101.4). Objects controlled by the active player ... have an earlier relative timestamp in the order of that player's choice, followed by each other player in turn order." Worldgorger Dragon returning several permanents at once (this epic) is the first card where this matters, for two returned permanents whose effects share a layer and do not depend on each other (two SetTypes or two SetColors).

What to build

  1. Objects entering together take timestamps in APNAP order of their controllers (State::players_in_turn_order or equivalent, never two-player assumptions).
  2. Within one player's group, order by a decision of that player only when two of the objects have static abilities with effects in one layer that layers/dependency.rs's prefilter (may_depend's reads and LayerChange::writes) says could interact, or that both write the same characteristic; otherwise use State::in_game_order, so no game asks a question that cannot change anything. Use an existing prompt shape (an ordering pick, as trigger order uses).
  3. A rules test in beryl_rules/src/tests/land_types.rs (or a new file) with two test permanents entering together whose order changes the outcome, and one where it does not and no decision is asked.

Files

beryl_kernel/src/{timestamps.rs, zone.rs, mutate.rs}, beryl_rules/src/event.rs (batched moves), beryl_rules/src/layers/dependency.rs, beryl_rules/src/tests/.

Bars

The epic's bars: count gate with no bump, State<Small> within 20,480 bytes, frozen saves and rollouts_never_change, citations.

Acceptance criteria

Objects entering together get APNAP-ordered timestamps; a decision is asked only when two of them have effects in one layer that may interact; tests show both cases; count gate holds.
