Description

Why

Shahrazad has the players play a whole game, using their libraries as their decks, while the main game waits. State<Small> is a flat Copy value and cannot hold another state. Decision P14 of the plan puts subgames in the Large layout only. Plan: Designs G, "Subgames"; CR 730.

What to build

  • State<Large> gains outer: Option<Box<State<Large>>> (beryl_kernel/src/state.rs, layout.rs). State<Small> gains nothing: use the layout's associated types so the field is zero-sized there, and assert State<Small>'s size.
  • Starting a subgame (a kernel mutator, used by the rules): box the main state into outer of a fresh state dealt from each player's main-game library, over the same slots. A card's slot is the same in both games; a slot that is not a library card of the main game is Nowhere in the subgame; a subgame token may use a pool slot the main game also uses, since they are different states. Format supplies life, hand size and the mulligan. The starting player is chosen at random (CR 730.1c or the rule that says so in the pinned release: cite it).
  • In Small, starting a subgame returns Full, which is how the session and the search widen a game today (beryl_session/src/game/boards.rs, beryl_search's Widen).
  • The engine (beryl_rules/src/engine.rs): next and apply act on the innermost game. When it ends, the engine takes outer back, puts every card of the subgame into its owner's main-game library and shuffles (CR 730.5; the cards never left those slots' library zone in the main state, so this is the shuffle), and resumes the main game's paused resolution with the subgame's result as the answer to the question it stopped at. An Outcome::Stalled in a subgame stalls the whole game.
  • clone_state, the state hash (hash_game), Relayout, fits and the invariants cover outer. Determinization (chance.rs) redeals the hidden cards of both games. Observation shows the innermost game; a viewer learns nothing new about the outer one.
  • The turn and decision limits (Limits) count across a subgame, so a rollout that enters one still ends.
  • Saves: a checkpoint inside a subgame holds both states.
  • Tests with a test card: start a subgame, play it to a win, a draw and a concession; a subgame inside a subgame; a save cut off inside one and resumed.

Shahrazad itself is the next bead.

Bars (every bead of this epic)

  • The plan is docs/project-50k-part-2.md. If its design is wrong for the code, build what is right and amend the plan's section in the same push. Never wait for an answer: record the choice in this bead.
  • The absent-cost gate holds with no bump (just count-gate). When you touched the kernel, the rules or the card vocabulary, report the count before and after in the close reason. If it cannot hold after three attempts, stop and say so on the epic: this is the one thing that stops the run.
  • size_of::<State<Small>>() stays within 20,480 bytes. Report the size if you changed it.
  • The frozen saves replay and rollouts_never_change holds (just test-rust).
  • Rules code cites the Comprehensive Rules with a quotation (just citations). A card file cites a rule only for a card-specific ruling.
  • A new card follows the card-writing skill and passes just card check <name> (Beryl, XMage and Forge). A keystone or partner is listed in data/rulings-ledger.json once that file exists, with every ruling a scenario or a reason.
  • No UI work. beryl_cli script-check must pass for a new card from both seats with the verbs and prompt shapes that exist.
  • A rules bug found on the way gets its docs/bugs.md entry, naming the guard that now stops its class.
  • A bead you file is tier:opus for design, keystones and reviews, tier:sonnet for partner cards, sweeps and measurements, and never tier:fable.

Acceptance criteria

A test card starts a subgame in Large, the engine plays it and resumes the main game with its result, and a save taken inside it replays. State<Small>'s size is unchanged and the count holds; the close reason gives both.
