Mason audit of Beryl 3D milestone 1 (by-q44s.2.1): measured why the beryl3d lane is over its budget, and moved this bead under the M1 gate epic (by-q44s.2) so that milestone 2 waits for it.

Numbers. Over the last 71 fast checks that ran the lane (runs.jsonl), the lane took a median of 109 s and a 90th percentile of 180 s (the step hang limit) at loads of 20 to 80. Step medians: cargo-test 95 s, gate 18.5 s, clippy 16 s, fmt 3 s, the three source lints 0.1 s each. A cold just b3d cargo-test in a fresh worktree at load 22 to 46 took 176 s on the clock: 21 s cloning the cached target, 17 s rebuilding the recordings pack (the record program plays the engine), and 6.3 s running the 212 tests. Everything else, about 130 s, was compiling and linking.

Where the time goes, in order of what I expect to save most:

  1. Three builds of the same crates. clippy builds with check metadata, cargo-test with the test profile (opt-level 1) and gate with dev (opt-level 2 for beryl_scene and beryl_inspect). An edit to beryl_scene recompiles it and everything above it three times. Run the gate's work counters and allocation gate as tests of the test build (or build gate with the test profile), so the lane compiles twice at most.
  2. 48 test binaries. beryl_scene has 12 integration test files, beryl_inspect 9, beryl_3d 6, beryl_render 4, beryl_assets 3, beryl_host 3, plus each crate's unit tests and bench. Each integration file is a binary of its own that links the crate and its dependencies; beryl_3d's six each link wgpu and the engine through beryl_session. Make each crate's integration tests one binary (tests/all/main.rs with one module per file).
  3. The recordings pack is rebuilt whenever its key changes; check which sources the key hashes and that a change confined to rust/beryl3d does not change it.

by-q44s.1.54 will add just b3d test (target under 10 s) to the same lane, so this has to land first or that step will not fit either. Measure the lane after a one-line edit to beryl_scene, median of five runs with the load beside each, before and after.

Most of the cold cost is the main-workspace crates (beryl_session, beryl_cli, beryl_cards) changing on staging after $BERYL_CACHE/b3d/target was saved. The sweep saves that directory only at the end of a whole sweep, and at 18:36Z it was 3.5 h old. by-q44s.2.6 moves the save earlier. Taking the engine out of the test build (beryl_scene's dev-dependency on beryl_session, beryl_assets on beryl_session and beryl_cards) would remove that cost for every crate but beryl_3d and beryl_record.

Measured (JARVIS, one-line edit to beryl_scene/src/lib.rs, then each step on the clock). Before, load 48: clippy 35 s, cargo-test 75 s, gate 51 s. After, median of five at load 31-60: clippy 10 s, cargo-test 40 s, gate 3 s. A warm just b3d lane with no edit: 15 load-adjusted s (25 s on the clock) at load 40, budget 60.

Causes and actions (both 'make it cheaper', no check moved or deleted):

  1. record and gate were built with cargo run -p beryl_record / -p beryl_inspect in the dev profile. Cargo resolves features per named package, so each compiled beryl_scene, beryl_inspect and (record) the engine in a flavor of its own, beside the tests' test-profile build. Now SHARED_BUILD in tools/src/beryl_tools/beryl3d/cli.py builds every target nextest needs plus the programs in the test profile; record, gate and gpu.send_pack run target/debug/<program> from it, and nextest compiles nothing after it. Narrower test-profile builds (-p beryl_record) were tried and recompile the whole engine, so the whole-workspace build is the only flavor that can be shared. Trade-off: just b3d record (and b3d commands when the pack is missing) now build all test targets too, but no longer a dev-profile engine that nothing else builds.
  2. 37 integration test binaries became one per crate (tests/all/main.rs); the four files with a #[global_allocator] stay separate. pack.rs's child-process test now passes its module path in the --exact name. Mason item 3 (pack key) needed nothing: pack/sources.rs already excludes Beryl 3D's own crates, so a client-only change keeps the pack.
