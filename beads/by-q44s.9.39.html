Description

Question: why did Opus agents, Wardens and the milestone 3 gate (Mason, Sage) report Beryl 3D's text, icons, prompts and furniture as working, when the owner's first look at the desktop app found these within minutes?

  • text missing letters ("You won the __ip"), no inline mana symbols, no loyalty, no icons (the menu gear);
  • the play/draw prompt drawn greyed out;
  • the life total drawn over "on the play";
  • playable-card outlines shifted right of their cards;
  • life orbs that look nothing like the web's. The bugs themselves are filed as P0 beads under by-q44s.9 (by-q44s.9.35 to 9.38; see this bead's related links).

Investigate, with evidence from the closed beads' comments, their sessions' transcripts (just efficiency can find the sessions) and the tools' code:

  1. What each closing session ran to check its work (by-q44s.5.6, 5.7, 5.16, 5.20, 5.24, 3.20 and the Wardens 5.39 to 5.41), and whether any of it showed the real window's output.
  2. Whether the headless host, just b3d png, tree, check and test use the same display scale, glyph path and atlas as the desktop host (rust/beryl3d/crates/beryl_host/src/headless.rs vs desktop.rs). A tree that lists a text element with the right string says nothing about whether its glyphs drew.
  3. Whether agents looked at pictures at all, and if they did, whether the pictures could have shown the fault (resolution, scale, the film's own bitmap font in beryl_pictures/src/font.rs).
  4. Why the generic checks (overlap, off-screen, reachability) did not catch the life total over "on the play" or the outlines off their cards.
  5. Whether anything compared Beryl 3D with the web interface at the same moment (decision C5 forbids whole-picture comparison; what took its place?).

Deliverable: a comment on this bead with the findings, then file a bead (under by-q44s.9 or by-q44s.10) for each gap, each naming the tool change that closes it, such as: running the interface tests at scale 2; a check that every glyph and icon a text element asks for has an atlas cell and drew non-empty pixels; a check that a mark's rectangle matches its card's; a parity check of a few furniture pixels against the web. Prefer checks that run on every push. Add a docs/bugs.md entry for the class of bug if the root cause is in engine-adjacent code, and update the Wardens' and the card-writing / b3d skills' instructions where they let a session declare a look done without seeing it.

Acceptance criteria

Findings (from the closed beads' comments, the tools' code and fresh runs on staging 5971ecfc7):

  1. What closing sessions ran. 5.6: unit tests, the gate, and one just b3d png pay-default --at prompt:2 at scale 1, which showed "Pay (1)(W)". Its handoff says "desktop host still requests no glyphs (only headless does)", and no bead was filed for that. 5.7: unit tests, the gate and a shader test; no picture. Its handoff says the headless host asks for icons(1.0). 5.16: prompts tests and parity counts; no picture. 5.20: tests and one png of pay-default at scale 1, where it noticed Mana Crypt drawn over the stop icons and closed anyway because every check passed. 5.24: just b3d tree screen/start and b3d test; no picture. 3.20: verbs_mark tests and frame_allocation; no picture. The Wardens 5.39 to 5.41 reviewed code and ran the interface tests; their comments mention no picture. None of this ran the real window or scale 2.
  2. Same scale and path? No. The test driver sends Input::Surface { scale: 1.0 } whatever the options say (beryl_scene/src/driver/mod.rs begin). Headless::new asks for prepare_latin(1.0) and icons(1.0), and its --scale only makes the target larger, so png --scale 2 stretches a scale-1 frame. It also draws wrongly: just b3d png screen/start --at end --scale 2 loses the whole opponent list, because the clip stays in scale-1 pixels. The windowless app that agents can run is hardcoded to scale 1 (beryl_3d/src/app.rs WindowlessOptions { scale: 1.0 }). The desktop host uses Glyphs::start(window.scale_factor()) and the client's glyph keys at scale 2. just b3d test runs only scale-1 windows. Confirmed by the owner's screenshot: the live app draws "You won the ip" (the "fl" ligature is missing), while just b3d png opening-play --at prompt:1 draws "You won the flip" correctly.
  3. Pictures. Two of the nine sessions looked at one picture each, at scale 1, of a different moment from the ones the owner reported. Scale-1 pictures could not have shown the missing ligature, symbols or gear. They could have shown the disabled-looking Play button and the plain orb: both are visible in today's scale-1 png of opening-play (the Play button is a dark orange with grey text, unlike Start's bright orange with white text), and 5.20 saw its orb picture without comparing it with the web's. beryl_pictures/src/font.rs is only the film's label font and has no part in this.
  4. Generic checks. overlap judges only interactive elements, so text over text and floats such as the life total are never compared. Marks are glow quads in the 3D scene that no check relates to their card. missing_glyphs is counted only in the app's frame log summary, and nothing fails on it. (The headless opening-play and opening-keep recordings show no "on the play" text, so the life-total overlap could not be reproduced at scale 1. by-q44s.9.36 owns that.)
  5. Comparison with the web. Nothing compared them at the same moment. C5 forbids whole-picture comparison, and only the parity list, which counts which items exist, took its place. Nothing compared how they look.

Gaps filed (P1, under by-q44s.9): 9.43 headless tools and windowless app at scale 2, with scale 2 in b3d test; 9.44 a check that every glyph and icon drew (after 9.43); 9.45 a check that marks sit on their cards and 9.46 an overlap check that covers text and floats (lane b3d-checks, after 9.43); 9.47 just b3d compare beside the web, plus a furniture parity check of draw properties against the web's tokens.

Instructions changed in this bead: the b3d skill gains "What these tools cannot show" (scale 1 only, a tree line isn't proof that glyphs drew, a look is done only after reading a png beside the web's at the same moment, with both paths on the bead). rust/beryl3d/AGENTS.md "Seeing and checking" carries the same rule for executors and Wardens. Enact's warden.md is outside this repository; Wardens read rust/beryl3d/AGENTS.md, so the rule is there. No docs/bugs.md entry: the faults are in the client's glyph and layout code, not the rules engine, and their root causes belong to 9.35 to 9.38.
