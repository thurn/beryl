Mason audit of milestone 1's core, read on origin/staging at fb79cc146.

Answers to the bead's questions:

  1. Do Client::handle and Client::frame alone reach the core? Yes in production code. beryl_3d (src/app.rs:266, src/ffi/mod.rs:145), beryl_inspect (src/gate.rs:121) and the driver (beryl_scene/src/driver/mod.rs:797) all build a Client and feed it through handle and frame. Only tests build Show or FrameBuilder directly (beryl_inspect/tests/recorded.rs, beryl_render/tests/, beryl_scene/tests/). Client also has test hooks that change state, record and plant (client.rs), which are not behind the driver feature; harmless, not filed.
  2. Does scene-purity forbid what 'Determinism' lists? It did not: it matched only fully spelled paths, so use std::{fs, time::Instant}, use std::collections::* then HashSet, a static AtomicU32 or a new rand dependency passed. Fixed in bbc704dd2 (tools/src/beryl_tools/beryl3d/purity.py): it follows braced groups across lines, bans the names however imported, and holds beryl_scene's dependencies to a list. Today's sources pass. What it cannot see, the frame gate's run-twice rule covers: parley and fontique keep per-process-seeded hashbrown maps (as the doc says), and beryl_protocol pulls in uuid and getrandom, which beryl_scene never calls.
  3. Can the 15 remaining verbs, the flat layer and the phone hosts be added without changing Input, Frame, Draw or Resolved? Input (input.rs) already has keys with Back, text, lifecycle, safe area, touch ids and the tier, which is what the phone hosts need; milestone 3's contract adds Input::Settings and Input::Agents, a planned contract change. Draw has room: materials streak, icon and particle are reserved with their fields in the doc's table, and the flags have spare clip and mesh values. Resolved covers the roles and state bits widgets need, but has no value field for a text field's contents or a slider's position (comment on by-q44s.5). Frame changes in by-q44s.3.2 (sounds becomes Vec<Sound>, shake), which that contract bead plans. The verbs themselves need StepIn/StepOut instead of today's one-Segment verbs::segment and the matches!(verb, Verb::Fly | Verb::Appear) in play/compile.rs step; by-q44s.3.2 does that.
  4. Does only beryl_render name a wgpu type? Yes. Only beryl_render's manifest depends on wgpu and naga (beryl_host and beryl_3d depend on beryl_render); the other mentions are comments and a log file name (beryl_3d/src/ffi/mod.rs:81). beryl_render's public API (src/lib.rs) exports no wgpu type; pipeline::bind_group_layout takes a wgpu::Device but its module is private.
  5. Does every material read only the fields the doc's table gives it? Yes for the five built (shader.wgsl shade_table, shade_card, shade_contact_shadow, shade_glow, shade_panel, shade_glyph): table reads tint; card reads layer, uv[0] as the back's layer, tint and params.y (whiten; dissolve is milestone 2's); contact shadow params.x; glow the atlas rectangle, page and params.x; panel uv as the border color and params; glyph rectangle and page. Two notes, not violations: the vertex shader computes an atlas coordinate from uv for every non-card material, panel included (unused there), and every fragment samples the picture array before the material switch, so the table and panels pay a texture sample (comment on by-q44s.3).
  6. Does code outside the session's timing module choose how a step is timed? Yes, in both clients. The web stage: ui/src/stage/tracks.ts REGROUP (170 ms for a hand's other cards), WAITS (tap waits until TURNED), STRIKE reading strike's phases from data/ui-conventions.json, and an unused CLOSED; timing.ts RELEASE reads fly's values for the pointer's let-go, which is pointer motion, not a step. Beryl 3D: play/compile.rs step moves what makes room over the whole step (verbs::slide over own, easing chosen in verbs/mod.rs), which differs from the web's 170 ms; and milestone 2's beads plan to add a regroup time to space.json (by-q44s.3.16) and read strike's phases from ui-conventions.json in the build script (by-q44s.3.15). Filed by-q44s.2.3. The other case names that grep finds in ui/src and tools are ordinary words (draw, tap, counter, mana, end) used for other things. Step timing now lives in rust/crates/beryl_protocol/src/script/timing.rs, not beryl_session; the epic's text said beryl_session and is corrected.
  7. Does beryl_inspect depend on any GPU crate? No. cargo tree -p beryl_inspect shows no wgpu, winit, naga, beryl_render or beryl_host, and no engine or card crate (beryl_protocol does pull in beryl_kernel). The scene-purity check enforces it on the manifest.

Isolation (C17):

  • A Beryl 3D-only change runs beryl3d, repo and names, plus the main python lane when it touches tools/src/beryl_tools/beryl3d (e.g. 00fbcd52f, 4be300484 in runs.jsonl). The doc claimed otherwise; corrected in bbc704dd2. Beryl 3D's Python tests (tools/tests/test_beryl3d*.py, about 2 s) therefore run in every main python lane, the one direction where a main change runs a Beryl 3D test. Kept: too cheap to be worth a lane.
  • No main-only change ran beryl3d in the fast check or in slow CI over the last 150 staging commits; the b3d and b3d-sweep records against main commits are the sweep running on the staging tip, as designed. Some Beryl 3D commits show only repo and names under their final hash: their beryl3d run is logged under the pre-rebase hash, and the rebase's narrowed rerun skipped it.
  • Main lock file: only d4ef99b28 (beryl_art, a listed exception). data/ui-conventions.json: one prose path fix (ac574fe54) plus the lane:timing changes. count-gate.toml: untouched. Engine VM: untouched; counts run in beryl3d-bench.
  • Can milestones 2 and 3 add checks and commands without editing outside Beryl 3D's paths? Yes: just b3d *args passes everything to the tools package (justfile:61), lane steps are appended in beryl3d/lane.py and sweep steps in beryl3d/sweep.py. The edits outside are the listed exceptions (ui/scripts/timeline.mjs, beryl_shell, design tokens) plus by-q44s.2.3 (session timing) and by-q44s.2.5 (constructors in beryl_protocol).

  • Rule 3 (no allocation in frame): held by the allocation gate; Frame::sounds is Vec::new() and would allocate on its first sound, which by-q44s.3.2 fixes.
  • Rule 6 (values are data): broken. The whole desktop layout is literals in beryl_scene/src/table/mod.rs DESKTOP; space.json has only fly's arc, catch_up and frame_rate. Filed by-q44s.2.4. tokens.rs and layout/mod.rs DOCK_RIGHT/DOCK_BOTTOM are literals the design tokens bead (by-q44s.5.3) takes over.
  • Rule 7b: broken in both clients (question 6); by-q44s.2.3.
  • Rule 11 (unsafe), 12 (wgpu), 17 (paths): held, with the python-lane exception now in the doc.
  • Rule 7a (fast interface tests): beryl_inspect/tests/recorded.rs verbs_zones_passes_every_check_on_every_tick checks every tick inside cargo-test; it is one recording and cheap, not filed.

CI budget and load-sensitivity: the beryl3d lane takes a median of 109 s and a 90th percentile of 180 s (the step hang limit) against the 60 s target; the 212 tests run in 6.3 s and the rest is compiling under three profiles and linking 48 test binaries. by-wzq9 (filed by CI) covered it; I added the analysis and moved it under this gate.
