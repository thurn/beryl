Description

Symptom: in the desktop app, prompts look disabled. The play-or-draw prompt's buttons are drawn greyed out, as if they can't be pressed, though they work.

Compare with the web interface's buttons (ui/src/design tokens, the shared design tokens file from by-q44s.5.3) and with Arena's play/draw prompt (arena-video skill). Find why the button is drawn in its disabled or dimmed style: a wrong state, a wrong token, a dim effect left on the layer, or the Enhanced tier's shading (by-q44s.11, which recently landed bloom) darkening the flat layer. The tiers must differ only in shading of the 3D scene (decision C8).

Files: rust/beryl3d/crates/beryl_scene/src/widgets/button.rs, beryl_scene/src/prompts/ (the yes/no prompt, by-q44s.5.16), beryl_scene/src/client/screen.rs, beryl_render/src/shader.wgsl, beryl_render/src/enhanced/.

Reported by the owner on 2026-11-16 from the desktop app (just b3d app, a real window on a Retina Mac). Every interface test and Warden passed on this code, so the headless tools do not see it. Reproduce in the real window path first: just b3d live against a running debug build (live tree, live png), not only just b3d png / tree, which use the headless host. A likely difference is the display scale: the desktop host (rust/beryl3d/crates/beryl_host/src/desktop.rs, Glyphs::start(window.scale_factor()), glyphs.rescale, Translator::new(size, window.scale_factor())) runs at scale 2 on a Retina display, while the headless host and the test matrix may run at scale 1. Confirm or rule this out.

Rules: the epic by-q44s ('Rules for every bead'), rust/beryl3d/AGENTS.md, docs/beryl-3d.md. A UI bug fix adds the broken state to a check that runs on every push (root AGENTS.md, 'Checks'), so the fix includes a test that fails before it at the scale and host the owner used.

Acceptance criteria

The play/draw prompt's buttons draw in their enabled style in the desktop app, matching the web's buttons; a test fails without the fix.

Handoff: Cause: screens::game::game (beryl_scene/src/screens/game.rs) made the prompt the first child of the 'game' holder and the opening screen a later child. The flat layer draws in tree order, so the opening's full-window scrim (screens::backdrop, color BACKDROP) was painted over the prompt bar, which dimmed Play/Draw and Keep/Mulligan. The display scale is not involved: the headless host at scale 1 draws the same dimmed picture (b3d png opening-play --at prompt:1 before the fix), so I did not need the live window path. Fix: the opening now comes before the prompt in game and game_phone. The opening has no Tab stops, so Tab still reaches the prompt first. On the phone the game-over scrim also moves before the furniture, matching the desktop order, because it dimmed the Menu button. Check: StateBits::PAINTED (frame.rs) is set by layout/write.rs on any flat-layer element drawn on a panel; hit::painted_over finds a later painted element over a point; checks::reachable now fails when one covers an interactive element's centre (the scrim lets presses through, so the hit test alone missed it). It failed on opening-play and opening-keep before the fix, and these run in the fast check's interface lane. docs/beryl-3d.md 'Reachable' updated. Compared pictures: Beryl 3D /Users/dthurn/Library/Caches/beryl/b3d/out/opening-play-you-1600x900-prompt_1-41712.png against web /Users/dthurn/Library/Caches/beryl/ui-shots/slot-09/opening-play.png. Play is amber with white type and Draw is near black with white type in both. A remaining, already-documented difference is that the web puts the buttons in the window's middle and Beryl 3D puts them in the prompt bar (opening.rs 'Not built yet'). Phone suite (not in the lane): 67 failing tests on staging, 92 now. All 25 new failures are the new rule finding prompt choice buttons drawn under the phase pill or a lands label, filed as by-q44s.9.49. Desktop suite: 8280 tests, 0 failed. Reviewer: check that game_over::scrim staying after the prompt on the desktop is right (the prompt is normally closed by game over).
