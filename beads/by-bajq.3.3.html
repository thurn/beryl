Description

Why

Painter's Servant chooses a color as it enters, Pithing Needle a card name, Cavern of Souls a creature type. "As this enters, choose" is a replacement effect of the permanent's own entering (CR 614.1c), the choice is not a target, and the permanent's abilities read it for as long as it stays.

What to build

Plan: Designs 6, "A chosen value"; decision R12.

  • A rewrite of the entering proposal: choose a value of a kind. The question is asked through choices in the Catalog shape (beryl_card/src/prompt.rs), with a Purpose for each kind.
  • Candidates. A color: the five. A creature type: the creature types the game's table numbers, and "another". A card name: every name in the game's table, and "another card". Every name outside both decklists has the same consequences, so one candidate stands for them all (D6). Tokens' names are candidates only where a card has that name.
  • Storage. Memo::Chosen of the permanent (beryl_kernel/src/memos.rs): a name as the game's card index or "another", a color, a subtype's game number or "another". It is public, ends with the object as every memo does, and is part of State::signature.
  • Reading. Filter::ChosenName, Filter::ChosenColor and their kin are read for the permanent with the ability; a Colors or subtype operand may be "the chosen one".
  • Saves and views. The save description of a catalog answer names the value, not an index (beryl_session::save). The view shows the chosen value on the permanent.
  • A copy of the permanent does not copy the choice (CR 707.2), and a permanent that becomes a copy keeps its own memo.

Build the five colors as one shared list of Catalog candidates. by-bajq.3.9 asks for a color as an ability resolves and may run at the same time as this bead: whichever of the two lands second uses the other's list and adds no second one.

No card lands here: prove it with a test definition that chooses each kind.

Derek Thurn2026-11-14

Scope decision: this bead builds the choice (Rewrite::Choose(ChosenKind) on Replaced::ThisEnters, asked through the sink's record of answers as the permanent's entering proposal is replaced, and through Pending::EnterChoosing for a land played), the candidates (five colors as one shared list, Colors::EACH; the creature types the game numbers + another; the distinct names of the game's non-token cards + another), the storage (Memo::Chosen, public, in State::signature), queries (State::chosen and MemosOf::chosen), saves (Act::Chosen names the value) and the view (ObjectView.chosen). It does NOT add Filter::ChosenName/ChosenColor: a filter is evaluated with a player and X only (63 call sites of Evaluate), never with the source permanent, so a chosen-value filter needs a source threaded through every evaluation. The first readers (by-bajq.7.3 Pithing Needle reads the maker of a rule change; by-bajq.5.1 Painter's Servant reads the source of a layer effect) each have the permanent at hand and build their operand there on top of State::chosen. Comments left on both beads. Resolutions run on the scratch copy in a game whose table has Capability::ChoosesAsEnters, so an inline source answers the choice; other games are unchanged.

Handoff: commit 8786e72a on staging.

  • Vocabulary: Replacement::choose_as_enters(ChosenKind {Color, CreatureType, CardName}) = Rewrite::Choose on Replaced::ThisEnters; ChosenKind::purpose/of_purpose; Colors::EACH + Colors::NAMES is the one shared five-color list (by-bajq.3.9 should use it and choices::catalog). Renders 'As this <noun> enters, choose a color.'
  • Kernel: chosen.rs has ChosenValue<L> {Color(Colors), CreatureType(Option<u8 game subtype number>), Name(Option<L::Card>)}, candidate numbers (ChosenValue::candidates/of_number/number, ANOTHER=255) and name(t). Memo::Chosen (memo entry still 3 bytes, store 100 bytes), State::chosen(slot), MemosOf::chosen. GameTable::names() (distinct non-token card names), SubtypeNumbers::creature_types(), Capability::ChoosesAsEnters (capabilities now u16), GameTable::can_either. Pending::EnterChoosing {slot, kind, pay_life} is the LAST variant on purpose, so the other variants' hashed discriminants don't shift (an insert mid-enum changed the attachments family corpus pin). Sink::chosen holds a batch's values until it has moved.
  • Rules: replace::entering asks via replace::answer (renamed from choose; it takes &State + &mut Sink) and pushes into sink.chosen; event::move_batch_to remembers them after the batch moves, before layers/triggers (remember_chosen, cold). A stopped run clears sink.chosen (resolve::run_answered, paused_step::run). A played land asks Pending::EnterChoosing (after EnterPayingLife if both) and its answer is put in sink.asking's record for entering to read. resolve uses replace::resolution_may_ask = t.can_either(Dredge, ChoosesAsEnters), so every resolution in such a game runs on the scratch copy and an inline source answers. rules/chosen.rs builds the catalog Decision (DecisionKind::ChooseObject, one Opt::Number per value); choices::catalog asks one in a resolution.
  • Session: save Act::Chosen{value: name}; catalog candidates labeled by name (candidates::catalog_label); prompt/catalog.rs uses labels (COLORS constant gone); ObjectView.chosen (protocol.ts regenerated). The UI does not render ObjectView.chosen yet.
  • Not built (by decision, see the earlier comment): Filter::ChosenName/ChosenColor. Filters have no source permanent; by-bajq.7.3 and 5.1 were told to read State::chosen from their own context.
  • Tests: beryl_rules tests/chosen.rs (color on a spell, creature type on a land, name candidates without tokens, signature), tests/replay.rs values_chosen_as_permanents_enter_replay_to_the_same_state, beryl_session tests/chosen_values.rs (saved by name, found in a table that numbers cards otherwise).
