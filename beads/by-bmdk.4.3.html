Close reason

Solo and hosted table actions share an atomic, per-seat publication path. Staging 9229a3e8.

Description

A linked action must pass the same per-seat reference and projection checks as a solo action. Today TableSessions::act in rust/crates/beryl_table_session/src/sessions.rs owns that transaction privately, uses a hard-coded SOLO seat, and redacts/advances Slots before commit and then calls view, which redacts/advances again. The milestone 3 host bead currently sketches direct beryl_table::apply. That would bypass the Log, authenticated TableActionRefs and capacity preflight. Also, view and script pass a seat, slots, references and views as independent values, so their API permits pairing one seat's snapshot with another's references or transition.

Extract the existing solo publication path in beryl_table_session, with a per-seat publication value that owns the view, slots and action refs, and a transition using matching before/after state. Keep the authenticated seat the only source of the actor; use TableActionRefs::apply_checked/Log for client actions, and keep raw host-generated actions behind the same checked publication path. Prepare each active seat's projection against the staged result before commit. Reuse the prepared result for the wire/app update. Solo must use the extracted path now; leave a concrete seam by-bmdk.5.1 can call for two seats. Keep constructors in beryl_session and keep player views/redacted animation inputs viewer-specific.

Acceptance criteria

A deterministic two-seat adapter test publishes for both seats, rotates both mappings on commit, rejects a reference from the other seat, and replays both scripts without disclosing hidden names. A projection error for either seat leaves the table, log and both published snapshots unchanged. Existing solo integration tests pass. No new transport is required.
