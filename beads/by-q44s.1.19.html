Description

Review the work counters, data/beryl3d/gates.json, the allocation gate, beryl_inspect/benches/frame_counts.rs, the gates' tooling in tools/src/beryl_tools/beryl3d, the frame log and the drive scripts, and the phone spike, against docs/beryl-3d.md 'Performance gates' and docs/benchmarking.md. Fix what you find.

Look hardest at: counts that differ between two runs (run each gate three times); a worst-frame selection that can change when unrelated code changes; a limit set with slack above its measurement; a stress board that is cheaper than a real board of its size because its cards are identical or stacked into piles; gates that only run in the sweep when the lane could run them in a second; limits a change could raise without saying why; a GPU count that would reward a design a real phone GPU would punish (blending over opaque, a discard in the opaque pass); a frame timing taken back to back instead of paced; a measurement whose run needed a person; the phone spike's hosts holding any logic beyond passing a surface and calling beryl3d_frame; anything installed in the engine's virtual machine, beryl-bench.

Acceptance criteria

Derek Thurn2026-11-15

Warden review findings (fixed in the worktree, not yet pushed):

  1. Scrolled-out row cards were drawn during every script (Table::write, beryl_scene/src/table/scene.rs). A moving card's visibility came from pose opacity alone, so cards a battlefield row had scrolled out of view, which rest at the row's end above the last card shown, covered that card while any script played. On the stress boards this drew all 256 / 1,025 cards in flight frames instead of 142, inflating records, upload bytes and handle-allocation limits. Fix: a moving card is drawn only if it is in view before or after the script (Table::object_at). Test: beryl_inspect gate::a_flight_draws_only_the_cards_the_rows_show.
  2. Fading cards were drawn in the opaque pass with alpha below 255. The design (docs/beryl-3d.md, 'Opaque first, nearest first') draws partly transparent cards with the blended records; in the opaque pass they darken from black and hide what is under them, and the fragment count treats them as opaque. Fix: tint alpha < 255 goes to Band::TableMarks. Test: beryl_scene play::a_fading_card_is_drawn_with_the_blended_records. No gated board fades a card, so no gate covers this; the scene test does.
  3. Slack in limits: handle_allocations was 11,508 / 862 on verbs-zones / pay-default but measured 7,676 / 702. The native gate passed silently under its limits. Since its counts are exact, gate.py now fails on a count under its limit too, pointing at --update. Limits lowered.
  4. The iOS spike's display link asked for 60 up to the display's top rate while Phone counts against a fixed 60 Hz; on ProMotion, uneven rates would go unreported (against C18). Now fixed at 60 Hz. Left alone, with reasons: stress boards draw every card from face layer 0 (CardRecords::none): the CPU and fragment counts do not depend on texture contents, only frame_times would be slightly optimistic, and it is not gated. The Android host's Choreographer ticks at the display's rate, which may be above the 60 Hz Phone counts against on 90/120 Hz phones: needs Surface.setFrameRate (API 30), which belongs to milestone 4's phone hosts with the rate rule. Rate rule (beryl_host/src/rate.rs), frame loop pacing, drive scripts, frame_times pacing, the counting allocator and the frame_counts bench reviewed: no issues. Tier step (Step::Baseline) is unreachable until Enhanced exists, as the 1.52 handoff says; its test covers it. Nothing is installed in beryl-bench: the gates use beryl3d-bench only. shader_cost runs in the lane; only the driver fragment count (needs Vulkan pipeline statistics) is sweep-only, rightly.
