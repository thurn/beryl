Handoff: rust/beryl3d/crates/beryl_scene/src/table/stack.rs: stack_pose keeps the leaning cascade while each item's left strip (step*scale*lean) is at least audit::TARGET_POINTS. Otherwise in_rows lays the items in rows: pitch = target * stack.spare (new space.json value, 1.25) across within a row and up between rows. Rows are right-aligned at the top item's column and run left no further than reach*lean. Items shrink to fit under stack.top, and if they would drop below SMALLEST_IN_ROWS (0.5) of full size the rows get longer instead. Ordinary recordings are unchanged: in all 8220 interface tests, only stress-stack's faults moved. stress-stack reachable faults went from 27/26/26/25 to 4/3/3/0 at 1440x900, 1600x900, 1920x1080 and 2560x1080. The faults left are opponent creature-row permanents under the stack's column (#43/#45/#47/#49). The old cascade already covered 2/1/1/0 of these. With 50 items the stack needs about that much area, so the remaining faults belong with the crowded-row beads (by-q44s.3.43/.45). I tried a slanted variant of the rows and it covered more permanents, so I rejected it. New test: table.rs every_item_of_a_stack_of_any_size_can_be_pressed, which fails on the old layout at 8 items in 1440x900. Gates: native segments 50->43, total 800->688, blended 0.1019->0.1017; --gpu fragments 1.101213->1.099233 screens (llvmpipe, deterministic). I did not rerun the instruction counts; the sweep owns those. The doc (The table, stack paragraph) notes that the web interface has no row layout.
