Close reason

Player count, deck size and the token pool are the layout's (SlotId numbering, Layout::Deck and PerPlayer); Large holds 256-card decks and relayout goes by place; a misfit is a typed refusal; counts 403,934,912 -> 404,063,827

Description

Milestone 3 (plan "State"): "Player count, deck size, slot count and card-index width are parameters of the layout. Small stays two players within 20 KiB." Today DECK_SLOTS is 60 and is also the library and graveyard capacity, which blocks legal 80-card Legacy decks; the token slots start at 2 * DECK_SLOTS; and the players, their knowledge and their zones are arrays of 2.

Read first

docs/project-50k.md: Decisions K6, K7, K11 and K12, and "Crates", "State" and "Kernel rules" under Target architecture. rust/crates/beryl_kernel/src/lib.rs: its rustdoc is the kernel's API contract (who writes, mutator and getter naming, events, the board door, the legacy accessor, sets and orders); follow it, and change it in the same push when the code proves it wrong. enact brief shows the handoffs of the beads this one depends on.

Also read the handoffs of the by-w8gv.5.4 (zones), by-w8gv.5.8 (stack and pending) and by-w8gv.5.13 (player API) beads: after them these arrays and constants are the kernel's private business, which is what makes this bead local.

Scope

  • The constants (beryl_kernel, from state.rs:19-40): SLOTS = Slot::COUNT (255), DECK_SLOTS = 60, TOKEN_SLOTS = 2 * DECK_SLOTS, BATTLEFIELD = 128, deck_slot(player, i), token_slots(), Layout::TOKEN_POOL. Uses outside state.rs when this was decomposed: table.rs (TableError::DeckTooLarge, the per-game deck lists), observation.rs (determinize), zone.rs, invariants.rs, start.rs, effect.rs, event.rs, and outside the engine beryl_session/src/checkpoint.rs, beryl_scenario/src/setup.rs, beryl_search (expert/, frozen/, tests) and beryl_cli/src/blunders.rs.
  • The per-player arrays: State::players: [Player; 2], State::knowledge: [Bitboard; 2], Zones::members: [[Bitboard; Zone::OWNED]; 2], Zones::library and graveyard: [Queue<Slot, DECK_SLOTS>; 2], Resolving::knowledge, GameTable::decks: [Vec<CardIx>; 2].
  • Make them parameters of Layout (layout.rs). An associated const cannot size an array in a generic struct on stable Rust; Layout already solves that for queues and tables with associated types (Queue<T, N>, Table<T, N>), so a per-player container and a deck-sized queue can be associated types the same way. Small's must be the arrays they are today.
  • Small: two players, 60 deck slots, 255 slots, unchanged. Slot numbers, bitboard words and sizes must not move: saves, rollouts_never_change and the count gate all see them.
  • Large (the layout beryl_session plays in; search relayouts to Small): its queues are Vecs already. Give it deck capacity for at least 100 cards and say in its rustdoc what bounds it. Relayout between layouts with different deck capacity maps a deck slot by (player, index within the deck) and a token slot by its index among tokens, not by raw slot number (relayout.rs:30, slot); a game that does not fit the target layout is a typed error, not a panic.
  • GameTable::new refuses a deck over DECK_SLOTS. The table is not generic over the layout: move the refusal to where a State of a layout is made (start.rs), with a typed error.
  • A flat layout for 80-card decks that search can run on (160 deck slots and 95 token slots fit the 255 of a u8 slot) is then a new impl Layout. Do not add it: say in a comment on the bead what it would take, and file a bead under by-w8gv labelled human (non-blocking) asking whether the next project wants it.

Constraints

  • No third player. Player count is a parameter both layouts set to 2; the test of the parameter is that no code outside the layouts assumes it.
  • relayout.rs is being edited by the prompts milestone (by-w8gv.11): keep the diff there to slots and containers.
  • Every State access in the rollout goes through these types. Run just bench-count before and after and record both; Small's generated code should be identical.
  • Card-index width is the next bead's.

Parity and checks

Parity (plan K11) at the push: just check passes; the frozen save corpus replays (cargo test -p beryl_session --test corpus); rollouts_never_change holds (cargo test -p beryl_bench rollouts_never_change); slow CI's counts lane (just count-gate, bar 405,276,238 instructions, 1% tolerance, rust/crates/beryl_bench/count-gate.toml) passes with no bump to the bar. No behavior changes: no rules fix, no new card, no new mechanic. Work the card-names and file-length allowlists down as files are touched (data/card-names-allowlist.json, data/file-length-allowlist.json; an entry moves with its file and its count only falls; a new file is under 800 lines). Rules code cites the Comprehensive Rules (AGENTS.md); keep the citations of code you move.

Decisions and deviations (staging base 27577e82).

  1. The numbering is the slot type's. The bead says "parameters of Layout"; an associated const on Layout cannot be reached from a slot alone, and every conversion between layouts (relayout.rs's slot and bits, LargeSlot::from, the session protocol's SlotId::num at about 50 sites) is written over the slot types. So SlotId carries PLAYERS, DECK_SLOTS and POOL (the first pool slot), with deck(player, i), pool(), place(), at(place) and to::<T>(); Layout carries the containers: type Deck<T> (a queue as long as a deck: Small's is Fixed<T, 60>, Large's Vec) and type PerPlayer<T> (both layouts: PerSeat<T> = [T; Seat::BOTH.len()]), beside TOKEN_POOL. Two layouts that deal their slots differently have different slot types, so a number of one cannot be read as a number of the other. The kernel contract has a new "Layouts" section saying this.
  2. Large's slot numbers moved: 256 slots a deck and a pool of 512 (was 60, 60 and 904). P1's cards are 256.. and tokens 512.. there. Relayout maps by place (SlotId::to), monotonically, so a Choice over objects names the same object in every layout (asserted over all 255 Small slots).
  3. Protocol ids moved with it. The session shows a Small board's objects by slot number and keeps its decisions in Large, which only agreed because the numbers were equal. SlotId::num is now "the number among LargeSlots", so an object keeps its id when its game is widened, and no session code changed but two from_index calls (now SlotId::from_num). The visible effect: in the UI protocol the second player's cards are 256.. (were 60..) and tokens 512.. (were 120..). Saves name objects by card and zone and replay unchanged (corpus passes). I updated the literal ids in ui/shots.json (three shots: retaken and looked at) and in beryl_session's script_spans.rs and script_build.rs tests.
  4. State::new returns Result<State, Misfit> (75 callers: tests unwrap, tools and the session pass the error on). State::deal::<L> is the generic deal; State::new is deal in Small. TableError::DeckTooLarge is gone: GameTable takes decks of any size.
  5. State::try_relayout::<M> is the typed refusal: State::fits::<M> checks every object has a slot in M, every list fits the room M's field type gives it (read from the type, Queue::CAPACITY, so no capacity is written twice) and every recorded index is one M can name; then the existing infallible Relayout runs. I did not make the Relayout trait fallible: that rewrites all 25 impls in relayout.rs, which the bead asks me to keep to slots and containers (its diff is the two helpers, objects by place and the per-player containers). Misfit: DeckTooLarge, PoolTooSmall, ListTooLong, IndexTooWide.
  6. Seat::BOTH still walks the players inside the kernel: Seat is a two-variant enum (settled at the M2 gate), so a third player needs a third seat before any layout could have one. passes < 2 and PlayerSet::seats read SlotId::PLAYERS. Profile's stops and GameTable's decks, which are not generic over the layout, are PerSeat<T>.
  7. The session still deals in Small, so it still refuses a deck over 60 (now as Misfit's text in SessionError::Deck). Starting a session in Large when Small refuses is not in this bead.

Counts (just bench-count, rollouts corpus): 403,934,912 before -> 404,063,827 after (+128,915, +0.03%); next_apply 375,903,752 -> 376,032,675; copy and policy unchanged. Per-symbol diff of the two callgrind profiles: every beryl_engine and beryl_kernel symbol is +0; the whole difference is beryl_search's rollout Policy (may_draw +1.58M inclusive, best_target, decide and block down by about as much), source I did not touch: inlining drift. Bar 405,276,238.

Not converted: beryl_cards' one per-controller array (Winds of Abandon) now uses PerPlayer<L, _>; arrays of two outside the kernel and engine (session, search, CLI, scenarios) are as by-w8gv.5.13 listed them.

A flat layout for 80-card decks (not added): what it would take.

The numbers work: 2 x 80 deck slots + 95 pool slots = the 255 a u8 slot numbers, and State grows by 80 bytes (four deck queues of 80, not 60), still inside 20 KiB.

  1. A slot type. A numbering is its slot type's (SlotId::PLAYERS, DECK_SLOTS), so Slot stays 60 a deck and the flat layout needs its own. Cheapest: make Slot generic over its deck size (struct Slot<const DECK: usize = 60>), which gives Slot<80> its inherent const fns and impls for nothing; every use of bare Slot keeps meaning Small's.
  2. impl Layout: Slot = Slot<80>, Index = u8, Queue = Fixed, Table = [T; N], Deck<T> = Fixed<T, 80>, PerPlayer = PerSeat, TOKEN_POOL = bits 160..255, clone_state = *state. Relayout to and from Large, SlotId::num and State::try_relayout already work for any numbering: nothing in relayout.rs or the session's protocol changes.
  3. The impl Copy for X<Small> {} lines (State, Zones, Player, Pending, Resolving, Decision, Candidates, StackEntry and the rest, about 15) each need a twin: Copy cannot be implemented for "every flat layout" at once.
  4. Layout::of and PerLayout hold one value per layout (the card bodies and conditions tables). A third layout is a third member of every such static and a third monomorphization of every card body and rules function: about half again the engine's code size and compile time, which the scale budgets of milestone 8 see.
  5. beryl_search and beryl_session name Small: the agents, Widening, the session's Boards and Snapshot. They would become generic over "the flat layout this game fits" or get a third arm.
  6. A count-gate benchmark of its own; Small's is untouched.

The alternative is to re-deal Small itself as 80 + 80 + 95. It costs none of 3 to 6, but Small is then not bit-for-bit what it was (slot numbers move, so state hashes and the count gate's corpus do; saves are slot-free and replay), and the pool shrinks from 135 to 95, so more games widen into Large.

Until one of these exists, an 80-card game plays in Large from its deal (State::<Large>::deal; the 80-card test in beryl_search/tests/games.rs), where agents play it as they play any game that outgrew Small (Agent<Large>), without Small's flat copies. The session still deals in Small and so still refuses a deck over 60 (SessionError::Deck, as before this bead): starting a session in Large when Small refuses is a few lines in beryl_session's replay.rs and game.rs (Boards::new takes a State<Small>), left for the bead that first needs an 80-card game in the app.
