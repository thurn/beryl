Close reason

--drive/--load/--slow-gpu, wait distribution in the frame log, three measured runs in comments and the doc; staging ee6f9df33

Description

Read first: docs/beryl-3d.md decisions C15 and C16, 'The agent interface' ('Driving the running app' and the action lines under 'Times, moments, locators and actions'), 'Threads' and 'Measurements'. Read the prototype's --sweep in src/main.rs and its late-frame line in src/window.rs.

Finding why the prototype's window dropped frames took the project's owner running it, moving the pointer and pasting terminal output back, several rounds. This bead makes every such measurement a run an agent starts and reads.

In rust/beryl3d/crates/beryl_3d and beryl_host:

  • --drive <script>: the host plays a file of the doc's action lines on the display's clock, each line optionally beginning at <duration>, through the same Inputs a person's events make, and then exits. Scripts live in rust/beryl3d/drive. Write hover-hand, which moves the pointer across the hand while a recording plays: the case the owner kept reproducing by hand.
  • --load <threads>[:<class>]: starts that many busy threads in a scheduling class (default, utility or interactive; default when none is given), so a run can reproduce a loaded machine on purpose.
  • --slow-gpu <duration>: holds each finished frame back before it is shown.
  • The run's summary gains the distribution of waits for a drawable (median, 95th percentile, worst), and just b3d frames prints it.

Tests: a drive script played twice through the windowless host gives equal frames; the load threads report the class they were given; just b3d frames reads a log a test wrote.

Then measure, and put the summaries in a comment on this bead and on the epic: hover-hand over verbs-zones for 20 seconds with --window background, at --load 0 and at --load 16, and once more at --load 16 with --window fullscreen --for 20s, which takes the screen for those 20 seconds.

Run: just b3d app --drive hover-hand --fixture verbs-zones --for 5s; just b3d app --drive hover-hand --fixture verbs-zones --load 16 --window background --for 20s; just b3d frames.

Acceptance criteria

A drive script plays the same twice; the three measured runs' summaries are in a comment, each with its window mode, display rate and load; just b3d frames prints the newest run's summary and worst frames; every run this bead made ended by itself.

Frame delivery measured by an agent, 2026-11-15, Apple M5 Max, 120 Hz display. Each run: just b3d app --drive hover-hand --fixture verbs-zones --for 20s with the options below; every run ended by itself. Waits are for a drawable.

  1. --window background --load 0 (load average 56.3 52.6 52.6) 1246 frames in 19.7 s on the 120 Hz display; late 8 (3 held to 60 Hz, 5 missed 60 Hz); worst gap 154.3 ms; wait median 0.1 ms, 95th 0.6 ms, worst 153.9 ms, 827.0 ms in all; 1 frame found no drawable.
  2. --window background --load 16 (16 busy threads, default class; load average 50.7 51.6 52.2) 1302 frames in 19.8 s on the 120 Hz display; late 0; worst gap 8.6 ms; wait median 0.1 ms, 95th 0.1 ms, worst 1.8 ms, 70.8 ms in all; 1 frame found no drawable.
  3. --window fullscreen --load 16 (load average 54.4 52.4 52.5) 1126 frames in 19.7 s on the 120 Hz display; late 94 (93 held to 60 Hz, 1 missed 60 Hz); worst gap 46.4 ms; wait median 0.1 ms, 95th 8.0 ms, worst 45.9 ms, 1385.5 ms in all; 0 frames found no drawable.

In every late frame the client took under 0.1 ms and the encode under 1 ms: the late frames are waits on the window server. The background run with no added load had one 154 ms wait, so one run does not show the added threads matter. Fullscreen was often shown at 60 Hz (93 of 94 late frames held to 60 Hz). The numbers are also in docs/beryl-3d.md, Measurements.
