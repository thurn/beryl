Description

Read first: docs/beryl-3d.md 'Hosts' (the C functions, the iOS and Android hosts, losing the surface) and 'Migration and compatibility' (Platforms and versions). Read tools/src/beryl_tools/mobile.py and android.py and the ios-smoke and android-smoke recipes for how this machine builds, installs and launches the Tauri phone apps in a headless simulator and emulator, and reuse their helpers. Read the cross-target bead's closing comment for what each target needed.

Why this bead exists. Performance on old phones is the first requirement, and without this bead nothing would draw on a phone's graphics path until milestone 4. This is a spike: the smallest hosts that put milestone 1's table on a phone screen, so that problems with wgpu on Metal for iOS, on Vulkan and on OpenGL ES 3.0 for Android, with the surface's lifetime or with the build are found now. Milestone 4 builds the real hosts on what this leaves. Add no touch input, no text entry, no audio and no phone layout.

  • beryl_3d: build as a static library for iOS and a shared library for Android as well as an executable, and export five of the doc's C functions: beryl3d_new, beryl3d_surface, beryl3d_surface_lost, beryl3d_lifecycle and beryl3d_frame. beryl3d_new takes a fixture name and replays it, as the desktop app's --fixture does. Write the C header by hand, in rust/beryl3d/crates/beryl_3d/include/beryl3d.h. The unsafe this needs is allowed in beryl_3d on exactly these functions, each with a comment saying which pointer it trusts and why. The epic's rule 11 allows it.
  • rust/beryl3d/crates/beryl_3d/ios: a Swift app with one view backed by a CAMetalLayer and a CADisplayLink that calls beryl3d_frame. Deployment target iOS 15. A bundle identifier different from the Tauri app's, so both can be installed.
  • rust/beryl3d/crates/beryl_3d/android: a Kotlin app with one SurfaceView and a Choreographer frame callback, calling the same functions through JNI. Minimum API level 24. An application id different from the Tauri app's.
  • just b3d ios-smoke and just b3d android-smoke, in the tools package, each with --help: build, install into the headless simulator or emulator, launch replaying verbs-zones, wait until the app logs that it presented its first frame and then that the fixture's last script ended, save a PNG of the screen as ios-smoke does, and exit. android-smoke --gles runs the emulator with Vulkan unavailable, so wgpu falls back to OpenGL ES 3.0; find the emulator flag or AVD setting that does this and record it on this bead.
  • Do not add these to the lane or to the sweep. Milestone 4 does that.
  • One run on the user's iPhone. He agreed on 2026-11-14 to one install of this spike for a frame log, which counts as his asking under AGENTS.md's rule for just ios-device --user-asked. Add just b3d ios-device --user-asked, modelled on ios-device in tools/src/beryl_tools/mobile.py. Run it once: install, replay verbs-zones and then stress-255, and pull the app's frame log off the phone as just mobile-bugs --device pulls bug reports. If no paired iPhone is reachable when you run it, say so in your comment and close the bead without it: do not wait and do not ask. Give the install and each replay ten minutes. A signing, trust or unlock prompt that nobody answers counts as not reachable: stop the command and say so. His iPhone is a current model, so its log shows what a fast phone does, not the floor.

Report in a comment on this bead and summarize on the epic: for iOS on Metal, Android on Vulkan and Android on OpenGL ES, whether the fixture drew to its end, the backend and adapter wgpu chose (log adapter.get_info()), the frame log's late frames, anything in the renderer that had to change for the backend, and the size of the library. A simulator and an emulator say nothing about a real phone's speed: report what broke, not frame times. From the iPhone run, report the frame log whole: the refresh rate, how many frames each fixture drew and how many arrived late.

If a path cannot be made to work within this bead, do not work around it by changing the renderer's design. Record exactly what failed (the error, the wgpu call), file a bead under milestone 1, and close this bead with the other paths working.

Derek Thurn2026-11-15

Report: the table on phones' graphics paths (verbs-zones, debug library, headless).

iOS Simulator, Metal: just b3d ios-smoke passed. The fixture drew to its end: 684 frames in 20.8 s, none late (worst gap 16.7 ms). Adapter: "Apple iOS simulator GPU (Metal)". Nothing in the renderer had to change for Metal. The screenshot is in the simulator's portrait framebuffer, so the landscape app appears turned 90 degrees.

Android emulator, Vulkan: just b3d android-smoke passed. 207 to 372 frames in 21 s, 158 to 175 late. Adapter: "llvmpipe (LLVM 21.1.4, 128 bits) (Vulkan)": the headless emulator's Vulkan is software, so its late frames say nothing about a phone. Two changes were needed: (1) wgpu refused an Android window with no display handle, so the surface passes RawDisplayHandle::Android; (2) the emulator's Vulkan driver (vulkan.ranchu.so) crashed with SIGSEGV in vk_common_SetDebugUtilsObjectNameEXT during request_device, when wgpu named objects, which a debug build does for every object. The phone instance removes wgpu::InstanceFlags::DEBUG and keeps validation.

Android emulator, OpenGL ES 3.0: just b3d android-smoke --gles passed. 223 frames in 21.3 s, 179 late. Adapter: "Android Emulator OpenGL ES Translator (ANGLE (Google, Vulkan 1.3.0 (SwiftShader Device ...)), SwiftShader driver-5.0.0)) (Gl)", which is software too. The emulator option that hides Vulkan is -feature -Vulkan (with -no-snapshot, so each boot takes its options). One change was needed: with every backend enabled, wgpu made a Vulkan surface on the window as well, and Android's Vulkan loader connects the window to the EGL API when it makes one, so Surface::configure failed with "Invalid surface" (EGL: "Error in create_window_surface: BadAlloc"). The renderer now picks one backend before any surface exists: Vulkan when enumerate_adapters finds a Vulkan adapter, else GL.

All paths: the phone device is made with downlevel_webgl2_defaults (the floor's limits), and the renderer drew every frame within them.

Library sizes: iOS Simulator static library (debug) 485 MB; iOS device static library (release, thin LTO) 105.5 MB; Android shared library (debug) 99.2 MB, which needs only libandroid, libdl, libm and libc and loads at API 24 (no libc++_shared.so, since nothing calls ctt's encoders yet). The debug APK is 100 MB.

iPhone run: not done. The iPhone 16 paired with this Mac was listed as available, and just b3d ios-device --user-asked built, signed and reached the install, but devicectl stopped with "The developer disk image could not be mounted ... kAMDMobileImageMounterDeviceLocked: The device is locked." Per the bead, a locked phone counts as not reachable, so there is no frame log from it, and the one allowed install is still unused. The command is ready: run just b3d ios-device --user-asked with the phone unlocked. It replays verbs-zones and then stress-255, and copies each frame log off the phone into $BERYL_CACHE/b3d/phone/<run>-iphone.

Commands run: just b3d ios-smoke; just b3d android-smoke; just b3d android-smoke --gles; just b3d ios-device --user-asked (stopped at the locked phone).

Seen in passing: cargo clippy --target aarch64-linux-android flags clippy::missing_const_for_thread_local in beryl_assets/src/prepare.rs:73, on Android only. No lane runs clippy for Android yet.
