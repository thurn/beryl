Sessions, PlayerView protocol (ts-rs), replays, IPC, record-fixture and a fixture shot (651e442)

Description

Part of Milestone 1 (epic by-b0q): a rules-exact engine, game UI and AI opponents for a mirror match of the 40-card WU Control main deck in docs/sample-decks/2026-10-17-PrinceJools-wu-control.txt (29 distinct cards). Read the epic's description (plan, card table) and design field (decisions) first; docs/engine-architecture.md is the design. Rules code cites the Comprehensive Rules with yawgatog links and quotations (AGENTS.md).

Architecture section 19.2, design decisions 12 to 14.

  • beryl_session (new crate): a GameSession on its own thread running next/apply, with an Agent or the human in each seat. When the human decides, it emits a PlayerView: a reduced owned view of the human's Observation with what the UI draws (zones, visible identities, derived P/T, counters, tapped, attachments, the stack with targets, life, turn and step, priority), the pending decision with candidates described by public slot or option label, and the engine events since the last view for animation. It then waits for choose(session, decision_seq, index).
  • The human's profile: smart stops by default, the exact profile by setting.
  • Replay files (seed, decklists, choice log) in the app's data directory; a replay reproduces the game.
  • An agent registry in beryl_search (names to constructors) that later beads extend; random for now.
  • TypeScript types generated with ts-rs into ui/src/generated/, checked in, with a test that fails when they are stale.
  • beryl_app: commands to list agents, start a game against one, choose, and change the profile; events carrying PlayerViews. Keep it thin.
  • ui/src/ipc.ts: typed wrappers for the commands and events, and the fixture transport replaying recorded streams.
  • beryl_cli (new crate): record-fixture plays a seeded game between named agents and writes the stream the fixture transport replays, stopping at a named condition (for example "first scry decision for seat 0"). just ui-shots runs it from a committed list of fixture definitions, so fixtures are generated, never committed.

Acceptance criteria

  • A session test plays a full game with a scripted human seat against random through the session API, and its replay file reproduces it.
  • A test shows no PlayerView carries an opponent's hidden identity.
  • The ts-rs staleness test, typecheck and just smoke pass.
  • just ui-shots renders one recorded fixture through the fixture transport.

Delivered: beryl_session (Game = synchronous core; GameSession = Game on a thread, choose validated synchronously against the open (seq, len), stops changes taken only while the human decides so the log places them exactly), PlayerView built from the human's Observation of the engine's view() position (paused bodies replayed), ReplayFile (seed, decks, initial stops, log of every seat's Choice plus Stops entries; Game::from_replay resumes). Engine: Observation::derived/stack/triggers (public). Agent registry beryl_search::AGENTS (random). ts-rs 12 into ui/src/generated/protocol.ts (one file, prettier-ignored); staleness test tests/typescript.rs, BERYL_UPDATE_TS=1 rewrites. App: list_agents, start_game (WU mirror, human seat 0, replay in app_data_dir/replays), choose, set_stops; event game-update {session, view}. beryl_cli record-fixture <defs> <out> [name..]; conditions 'first <kind> decision for seat <n>' | 'game over'; decks wu-control | fuzz:<seed>. ui/fixtures.json + shot game-first-target. Deviations: (1) Stops live in State's one Profile, so the human's setting also applies to the agent's seat. (2) Events of a paused body are not in the view (the engine truncates them) and arrive when it completes, while the paused view already shows its effects. (3) Game.tsx is a plain list rendering of PlayerView, a stopgap for the game-screen beads. (4) No 'scry' decision kind exists; scry asks chooseUpTo, so a scry fixture is 'first chooseUpTo decision for seat 0'.
