Description

Audit the architecture of milestone 1 of epic by-bmdk (docs/manual-multiplayer.md). Scope: rust/crates/beryl_table, beryl_link, beryl_link_iroh, the card store's search and facts, the view type additions in beryl_session, the stage pointer hooks, ui/src/table/ and data/table-commands.json.

Questions to answer: Is Change really the only way the table changes, and is it enough for the adapter to animate from? Do the crate boundaries in the epic's Contracts hold (no table or link code depending on the engine or the session)? Are the view additions shaped so the adapter in milestone 2 can fill them without another change to shared types? Is the pointer API one a second client can use without the engine prompt code knowing?

Also check each rule under 'Rules for every bead' in the epic against the code, and that the epic's 'Contracts' section still describes what exists; correct the section where the code is right and the text is stale.

File each important finding as a child of this gate epic with tier:opus or tier:sonnet, the files to change and a test that would show it fixed. Fix small ones yourself.

Handoff: Audited origin/staging at 6770658e using the M1 children and Warden commits. The M2 adapter, table command and pointer plans were checked against that revision. Updated the parent epic's Contracts to reflect the actual crate dependencies, save and entry bookkeeping, numbered seats, neutral view constructors, wire and stage interfaces. The seven findings are children of by-bmdk.2, which blocks M2. There were no small source changes to land.

  1. Change and animation. apply/mod.rs plans gameplay changes against the table and Change::perform applies them. The performer also advances next_id; commit sets entry_number. Batch uses a staged copy and history applies inverses or RestoreTable. Public fields and Change::perform make the invariant a live caller convention rather than an enforced type boundary. The adapter should use Log::apply, and keep separate editable setup state and seat projections if more callers need to construct tables. A larger state encapsulation refactor can wait. The raw change list records actual state mutations, but apply/mod.rs flattens batches, apply/library.rs writes Learn only when knowledge changed, and redact.rs strips private hand-entry links. The adapter needs seat-specific animation facts, not another copy of action semantics. by-bmdk.2.3 handles that contract. by-bmdk.2.7 exposes per-seat history and undo using log.rs and undo.rs as the authority. Passing tests include failed batch rollback, save replay, targeted undo, shuffle and knowledge restoration.
  2. Crate boundaries. The Cargo.toml files for beryl_table, beryl_card_store, beryl_link and beryl_link_iroh keep engine, cards and session dependencies outside their dependency paths. beryl_link/src/host.rs takes numeric seats and opaque payloads through Hosted. The neutral constructors in beryl_session depend in the opposite direction from the planned adapter. The log's display formatter says “you” but table state and permissions use seats. Reviewed search.rs and facts.rs: one name index serves all three lookups, and printed facts are already independent of the engine. The Warden's face-vs-record bug is handled by printed-face helpers and tests. No new store abstraction is needed for M2.
  3. View and replay. protocol/neutral.rs supplies complete starting values, protocol/build.rs omits PlayerView.table on engine views, and protocol/typescript.rs emits the additive types. M2 still needs shared protocol work. by-bmdk.2.4 covers lossless manual numbers, replay and manual banners. by-bmdk.2.5 covers ordered hand, exile and sideboard state. by-bmdk.2.6 covers marker controller and stable ability number after reset. by-bmdk.2.9 supplies a typed action-reference boundary between stage slots and the table's host ids. Save/load, redaction and the engine fixture payloads must continue to work. The later host-held prompt payload and deck token suggestions are already in the planned scope of by-bmdk.5.6 and by-bmdk.3.21. Host/guest blocked-undo metadata and final fingerprint inputs are noted on by-bmdk.5.1 for its wire integration.
  4. Pointer. stage/pointer.ts exposes named gestures and makes no calls into the engine. The ownership hook is incomplete at composition: playback.ts always creates Prompts, Chrome.tsx and the boards subscribe through it, and holdable and the listener have separate lifetimes. Primary life-total presses also never reach a listener today. by-bmdk.2.8 covers the shared lifecycle and a typed player click before the table screen starts wiring callers.
