Run the step's own command, just b3d gate --gpu, in your worktree, or replay it at that commit with just b3d sweep --step gpu --commit 361fdaf61dd6. A replay runs in a tree of its own and does not wait for a sweep that is running.

Fix the break in Beryl 3D's code, not by reverting the commit that exposed it (docs/beryl-3d.md, 'Checks and isolation'); whoever is working on Beryl 3D takes this bead first.

Handoff: cause was a token-pool self-deadlock, not Beryl 3D code. vm_host.join (tools/src/beryl_tools/vm_host.py) took a CPU lease for the VM's 8 cores, held until process exit; as a sweep step it got all 3 sweep-class tokens, then the same process ran cargo via the shim (source.send_pack -> shared_build), which waited forever for a 4th sweep token. Both gpu and frame-counts hit it (both call vm start then send_pack). Fix: join writes lease.env() into os.environ so later child commands inherit the lease. Test: test_commands_started_after_joining_run_inside_the_machines_lease in tools/tests/test_vm_host.py; the autouse fixture now clears tokens.HELD_ENV. Verified: BERYL_CPU_CLASS=sweep just b3d gate --gpu passed in 157 s (3 build-out WARNs: stress-stack, verbs-zones, pay-default slightly over their fragment limits, within the 1.75 target). A replay as agent class could not reproduce the hang (the agent ceiling has room above the VM lease). I killed the running sweep's deadlocked gate --counts (pid 8702), which would have hit its hang limit anyway; its bisect at older commits will still hang until it picks up staging 18e7d37e2.
