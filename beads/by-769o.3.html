Close reason

Real-time browser waits now use HANG_MS (120 s); LONGEST is stage-time only (d7513b8f)

Description

What we see

Browser checks use timers in two different ways:

  • Hang guards. ui/scripts/hang.mjs fails a check after CHECK_SECONDS (60 load-adjusted seconds), where the slowest check that ever passed took 17 s. This catches a page whose main thread never yields (by-b8wh). That is the intended use of a timeout and stays.
  • Waits that act as gates. Some page.waitForFunction and retry-loop timeouts are close to how long the wait takes on a busy machine, for example shapes.mjs (15 s around line 293), moments.mjs (LONGEST, 30 s) and film.mjs. On a loaded machine these can fail a check that would have passed, which is nondeterminism.

What to change

Go through the timers in ui/scripts/ and, for each:

  • Keep it if it is a hang guard: well above the slowest pass seen in the run log, and only reached when something is stuck. Make its failure message say the check appears hung.
  • Otherwise, wait on a deterministic signal the page already exposes (for example settled or owed from window.berylStage), drive Playwright's paused clock instead of waiting on real time, or raise the limit to hang guard level. Do not keep any timer that a slow but healthy run can reach.

List the timers changed and kept in this bead.

Files and tests

ui/scripts/hang.mjs, kept-harness.mjs, shapes.mjs, verbs.mjs, moments.mjs, film.mjs, capture.mjs, kept-crowded.mjs, kept-piles.mjs, kept-screens.mjs, slots.mjs. Check with cd ui && npm run typecheck, npm test, and just ui-test <title> for a few affected checks.
