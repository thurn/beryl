Description

A tool that shows where agent sessions' time, the machine's CPU and LLM tokens go, per bead, so that development can be made faster and cheaper on evidence. It is a command, just efficiency, that agents can read, and a local web page that draws the same results for a person. The design is docs/efficiency-dashboard.md, written on 2026-11-15 after a design interview. Every bead is written against it.

Why

1,828 commits landed in the project's first week. A first pass over the 1,111 Claude transcripts on the main Mac found 19.3 billion cache-read tokens against 60 million output tokens (about 227,000 tokens of context per request), and 389 hours of sessions waiting for tools: 78 h of orchestrators waiting for workers, 46 h in 41,000 small shell reads, 34 h in Rust tests, 30 h in enact push, 27 h in browser checks, 19 h waiting for slow CI. The user's goals are to run more sessions in parallel on a machine that is CPU-bound, to spend less on CI and compilation, and to write thousands of cards on small models.

What is built

  • A standalone Python project, efficiency/, standard library only, with its own check lane, that reads existing logs into one SQLite store in the cache.
  • Per bead, epic and cohort: agent minutes by what the session was doing, core minutes, dollars by class, by source and by purpose, rework, lead time.
  • Machine: saturation, time queued for cores, a parallel capacity estimate.
  • CI: cost, catches, stale and flaky failures and misses by script, check lane, family and check; CPU by kind of process (compile, test, the Java oracles, browser); the fast check per push; the cost of a slow-CI failure.
  • Efficiency changes marked on trends with before and after medians.
  • Findings: ranked opportunities with estimated savings.
  • A page served on localhost, rendered by Python from the same query results the command prints, quiet by default with detail on drill-down.

Decisions taken with the user (2026-11-15)

  • Unit of output: the closed bead. Cards are a cohort (beads whose commits add a card file), with cost per card.
  • Token unit: API-price dollars from a price table in data/; raw counts by class one level down.
  • Coverage: this Mac, Claude and Codex sessions. Every row carries host and provider, and beads that ran elsewhere show as "no data". Export and import between machines is the last executor bead.
  • UI: a standalone page with its own isolated check lane, served by a small local server, rendered by Python. Not a route in ui/, not a static file.
  • CPU history: no new sampler. The dashboard reads the existing always-on sampler (just cpu install, landed in 31af1902b). The one addition is a line per CPU lease.
  • Optimizations: listed in data/efficiency-changes.json, each with the metric it was meant to move; the entry is added in the commit that makes the change.
  • Findings are ranked and shown; they never file beads.
  • Rework is a separate figure beside direct cost, counted only where traceable (Steward beads through enact_ci_range, later fix commits to card files).
  • First screen: four per-bead medians with trends, one bar for where agent time went, one for where dollars went, then the epics.
  • CI must be shown richly: which checks catch real bugs, which are flaky, and how much CPU goes to Java for the oracle scenarios.
  • Collection must cost agents nothing noticeable, and everything on the page must be available from the command.

Defaults recorded without asking

  • Time waiting on the user and idle time are reported beside agent minutes, not in them.
  • An orchestrator session's cost goes to its epic as "orchestration", not to its beads.
  • Findings are grouped by unit (dollars, agent hours, core hours); no unit is converted into another.
  • The store keeps commands and paths but no message text or tool output, and stays in the cache. Tests use synthetic sources because the repository is public.
  • The check lane has no browser step; just efficiency shot renders a page to a PNG for development only.
  • Review: one Warden at the end, which also runs the design's Manual QA on real data, and one Archivist. No Mason and no Sage.
  • Models by name: tier:opus for everything except the Codex parser, export and import, and the Archivist, which are tier:sonnet. Nothing is tier:fable. A bead filed later follows the same policy.

Order

.1 (skeleton) then .2 (Claude ingest) then the lane accounting (.3 time, .4 tokens) then .5 (queries). After .5, the page (.13), CPU (.7), rework (.10) and Codex (.6) can proceed side by side; CI (.8, .9) follows CPU and rework; changes and findings (.11, .12) follow those; the page's other views (.14) and export (.15) come last, then the Warden and the Archivist. Edges are on the beads that need a result.

Whole-run acceptance

  • Every item of "Manual QA" in the design passes on the main Mac, or is recorded on the Warden bead with its cause.
  • For every bead in the store, time categories sum to window lengths and each dollar split sums to the bead's dollars.
  • just efficiency ci --since 7d agrees with just ci-value --days 7 on runs, CPU seconds and catches.
  • The sampler and all ingests together use under 1% of the machine's CPU over a day, and nothing was added to any agent session.
  • A change under efficiency/ runs only its own check lane and the repository-wide formatting checks.
  • Everything the page shows can be printed by a just efficiency command with the same numbers.

Code map

  • efficiency/ (created by .1): src/beryl_efficiency/, tests/, AGENTS.md. Command: just efficiency <query>. Tests: the efficiency check lane (black, pyre, pytest).
  • Data files: data/efficiency-prices.json, data/efficiency-command-kinds.json, data/efficiency-changes.json, each described in data/AGENTS.md.
  • Check lanes: tools/src/beryl_tools/checks.py (fast_lanes), slow_ci.py (lane_reason, lanes_for), lanes.py; the precedent for an isolated lane is tools/src/beryl_tools/beryl3d/paths.py. Reference: docs/checks.md.
  • Sources read, never imported: tools/src/beryl_tools/runlog.py (run log), cpu.py (sampler rows), tokens.py (CPU token pool; gains the lease line), verdicts.py and check_value.py (verdicts and check value).
  • Outside the repository: ~/.claude/projects/ (Claude transcripts), the Claude desktop app's claude-code-sessions/ records, ~/.codex/sessions/ (Codex logs), $BERYL_CACHE/ci/runs.jsonl, $BERYL_CACHE/cpu/samples.jsonl, $BERYL_CACHE/efficiency/store.sqlite (the store).
  • Enact metadata on beads: enact_session, enact_worktree, enact_commits, enact_vizier, enact_ci_range, enact_spawn_host, enact_spawn_provider.

Acceptance criteria

Every item of Manual QA in docs/efficiency-dashboard.md passes on the main Mac or is recorded on the Warden bead with its cause; time and dollar splits sum to their totals; CI figures agree with just ci-value; collection costs under 1% of the machine's CPU; the efficiency check lane is isolated; everything on the page is printable by the command.
