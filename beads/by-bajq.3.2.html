Description

The problem

When two replacement effects apply to one event and they differ, the affected player or the affected object's controller chooses which applies first (CR 616.1). An optional one ("you may") is a choice even alone. The event may be in the middle of a resolution, where choices can pause and replay, or in the draw step, combat damage or a state-based action, where nothing can pause: next has changed the state by the time the question comes up.

What to build

Plan: Designs 3, "Asking in the middle of a step".

  1. The flag. The state knows whether a replacement choice is possible now: an optional replacement is live, or two live replacements of one kind are not the same data. Keep it current where replacements start and end and where the layers fold the masks.
  2. The transaction. While the flag is set, next runs each advance as a resolution is run today (architecture §7.3): on the scratch copy with a record of answers; if a question has no answer, the copy is discarded and the question is stored with the record; apply appends the answer and the advance runs again. With the flag clear, and in a rollout, whose answers come inline, nothing changes. Read engine.rs, engine/questions.rs and resolve.rs first: reuse the record and the pause that exist.
  3. The decision. DecisionKind has the next replacement to apply; give it its Purpose, its save description (beryl_session::save, the exhaustive matches) and its candidates: one for each set of replacements that are the same data. The player is the affected player or the affected object's controller, or its owner if it has none.
  4. The replay differential test (beryl_rules/src/tests/replay.rs) is extended to steps run this way: inline answers and replayed answers reach the same state hash.
  5. A search profile may fix the order by rule (Profile), as it fixes trigger order.

Card

Life from the Loam: "Return up to three target land cards from your graveyard to your hand. Dredge 3." Dredge (CR 702.52) is an optional replacement of its owner's draw that works from the graveyard: mill three, then return this card to hand, only if the library has at least three cards. It needs targets in a graveyard, "up to three".

Scenarios: dredge in the draw step (the choice comes in a step, not a resolution); two dredge cards in the graveyard; too few cards in the library; decline.

Decisions and deviations (recorded without asking):

  • The flag is computed, not stored: replace::may_ask, read as a step's turn-based actions or a resolution begin (dredge card in a graveyard with enough library). Cheaper than keeping it current and never stale. Gap: a dredge card that reaches a graveyard inside the same run is not offered there; filed by-bajq.3.16.
  • No new DecisionKind: the choice is Purpose::Replace asked as ChooseUpTo (Opt::Object per dredge card, Opt::Done = draw). Avoids touching every exhaustive DecisionKind match, frozen code included. Save kinds unchanged.
  • The pause point is a step's turn-based actions (Pending::StepActions), not the whole end of a step: the step begins on the state itself so the session shows it begin. An earlier version paused the whole step end; beryl_session's streaming test caught it (docs/bugs.md).
  • Two differing move replacements are still not a choice (no card puts an object anywhere but exile); the debug_assert stays. Combat damage meets no replacement until by-bajq.3.9; its damage step's turn-based actions already run through the same pause.
  • No Profile rule: rollouts answer inline through their policy, which scores a dredge card by value against 0 for declining, so they dredge.
  • The replay test covers the draw step (step pauses) and resolutions with dredge, not combat damage (nothing to choose there yet).
