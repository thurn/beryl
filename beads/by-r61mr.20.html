Description

Read the epic by-r61mr first: it holds the decisions, the code map and the directory layout this bead assumes. The work is in the Enact repository (~/enact) unless this bead says otherwise, delivered with that repository's own enact worktree create and enact push.

Every plan with milestones today gets a "review gate" epic per milestone ("M3 review gate") holding its Mason and Sage audits, because beads only lets an epic block an epic and hides a blocked epic's children. The ticket server has no such limit (the epic's decision 15), so with the server backend:

  • An audit is a ticket under the milestone it audits, flagged last, so it becomes ready when the milestone's other work is closed. Findings the auditor files go under the same milestone. The next milestone depends on the milestone itself, so it waits for the audit and its findings with no extra epic.
  • The Archivist ticket is a last child of the run epic, replacing the helper's special hold.
  • Parents close on the server when their last descendant closes, replacing the helper's closing of eligible epics in enact next.

Change the "Audit gates" and "Final documentation" sections of skills/enact-plan/SKILL.md, the roles skills/enact/roles/mason.md, sage.md and archivist.md, skills/enact-sweep/SKILL.md where it mentions gates, and the helper code that creates or closes gates. Existing gate epics imported from beads keep working as ordinary tickets and are not rewritten. The beads backend keeps today's behaviour until it is deleted.

Acceptance criteria

An integration test files a two-milestone plan on the server backend with no gate epics and shows: the audit becomes ready only after the milestone's other tickets close, a finding filed by the audit keeps the second milestone's tickets not ready, they become ready when it closes, and the Archivist is ready last. The skill text no longer tells a planner to create gate epics on the server backend.
