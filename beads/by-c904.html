Key oracle outcomes on the exports, not the exporter source

Description

What someone sees: after almost any card commit, slow CI's oracle lane on this Mac plays every scenario (about 1,700 card scenarios and 200 generated ones, 150-700 s), and the fast check's oracle lane defers most of the generated scenarios to slow CI.

Why: the outcomes cache in tools/src/beryl_tools/oracle_memory.py (commit fc50cb18) keys each scenario on its dump entry plus a hash of the oracles' side. That side is the oracle pins plus the source of the exporters and harnesses (SIDE_GLOBS: xmage*.py, forge.py, card_facts.py, tools/oracles/**, data/card-store.tsv). Card commits nearly always edit those files to teach the exporters the new card: 6 of the 12 commits before 1023c46f did. Each edit changes the side hash, so every remembered outcome stops matching. Separately, oracle_selection.HARNESS makes slow CI play every card whenever one of those files changes, which is why "Generated" played in 83 of about 130 slow-CI runs on 2026-11-13/14.

Measured 2026-11-15: in a worktree at 1023c46f (Mindslaver, which edited card_facts.py, forge.py, xmage.py and xmage_trace.py), just oracle --new --no-sim played all 100 generated scenarios (138 s), although slow CI had recorded passes for the tree before it. A second run on the same tree played none, so the key itself is stable.

Fix: key each outcome on what the oracle actually runs. For XMage, that is the exported test method's Java source (xmage.export_all -> xmage_java) and the classes it needs. For Forge, it is the scenario's exported JSON (forge.export). Add the pins and the generic harness files (tools/oracles/*.java). An exporter edit for one card then changes only the exports of the scenarios that use that card. Then replace the HARNESS full sweep in oracle_selection.choose with "play every scenario whose export key has not passed". Keep the nightly's full sweep as the backstop. check_xmage and check_forge in oracles.py export internally, so the export step has to move before the selection. oracles.py is close to the 800-line limit (about 780 lines).

Done when: (1) after a commit that adds one card's facts to card_facts.py, by oracle --select plays only the scenarios whose exports changed (measure the count against 1,900); (2) the fast check of such a commit plays the changed generated scenarios inside its budget; (3) the outcomes-cache tests in tools/tests/test_oracle_memory.py cover the new key.
