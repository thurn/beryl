Close reason

Beryl 3D sweep beads now carry enact_host/enact_ci_host of the failing machine (f49cbf1d1)

Description

The Beryl 3D sweep's file() (tools/src/beryl_tools/beryl3d/sweep.py) files a failed step as a role:executor bead under by-q44s with no host metadata, so any vizier on the run may take it. On 2026-11-16 Cygnus (win32) filed by-q44s.48 for b3d-cargo-test:cargo-test. A Mac worker took it, could not reproduce it or reach Cygnus's lane log, and the Justiciar then held the whole run overnight. The cause was MSVC's missing mspdbcore.dll on Cygnus, which only Cygnus could have seen.

The main nightly already records its machine (nightly_failures.py sets enact_ci_host from nightly_failures.host()). But Enact routes on enact_ci_host only for role:steward beads (targeted_here and steward_targeted_here in ~/enact/scripts/enact.py). An executor bead needs enact_host, which only that machine's vizier picks up. When no vizier on the run serves that host, Enact marks the bead stranded, and the Justiciar moves it out of the epic, still open (~/enact/skills/enact/roles/justiciar.md, 'A requirement nobody here can meet').

Change: add enact_host (and enact_ci_host, to match the nightly) set to nightly_failures.host() in the --metadata of the bd create call in file(). Also show the host in DryRun's 'would file' line. Say in the module or function docstring why the bead is pinned. A repeat failure only comments on the existing bead and needs no change. Check whether any other tool under tools/src/beryl_tools files role:executor beads from a sweep or nightly without a host, and fix those the same way.

Acceptance criteria

A bead filed by the Beryl 3D sweep carries enact_host and enact_ci_host naming the machine that ran it (ENACT_HOST, else the short hostname), as tests/test_beryl3d_sweep.py shows with a fake store. The dry run prints the host. Other sweep or nightly filers that create role:executor beads also set enact_host, or the bead's handoff names none.
