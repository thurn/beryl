Close reason

Per-step hang limits (4x slowest pass, 900-2400 s) replace the run deadline; no rerun after kills; slow_timeout 3600 (252c4129)

Description

What we see

by ci kills any step still running when the run reaches its hard deadline (checks.HANG_DEADLINE = 600 s, or CHECK_DEADLINE_S), and the lane fails. Enact kills the whole run at slow_timeout (1000 s in .enact.toml), which checks.Steps anticipates through bisect.time_left. On 2026-11-13 these limits failed every slow-CI run for three hours although nothing had hung: the steps were slow (CPU token waits, cold builds on one or two cargo jobs), not stuck. Bisect does not search timeouts, so no culprit was named.

Policy

Timeouts stay, as a safety net for real problems such as a hang or a deadlock. They are never a gate meaning "CI took too long". So:

  • A slow run never fails for being slow. Going over the budget files a bead (budget.py already does this for the run as a whole).
  • A step fails on a timer only when the timer means it is stuck: the limit sits far above anything a healthy run takes on a loaded machine (several times the slowest passing run of that step in the run log), and time spent waiting for CPU tokens or file locks does not count.

What to change

  • Replace the single run deadline with a hang limit per step, set from the run log (for example 4x the step's slowest pass in 30 days, with a floor), so a step that hits it is very likely hung. Record the chosen rule and why in this bead.
  • When a step hits its hang limit, the failure message says the step appears hung, prints what it was doing if that is cheap to capture (for example the last output lines and the process tree), and is distinct from a test failure in the run log so that bisect and verdicts can treat it as such.
  • Raise Enact's slow_timeout in .enact.toml so it sits above the largest step hang limit and never fires first.
  • Keep the rerun-after-deadline in checks.run_all only if it still serves a purpose under the new limits; otherwise remove it.

Files and tests

tools/src/beryl_tools/checks.py (HANG_DEADLINE, Steps, run_all), tools/src/beryl_tools/bisect.py (time_left, ENACT_TIMEOUT), tools/src/beryl_tools/budget.py, tools/src/beryl_tools/runlog.py, .enact.toml, tools/tests/test_checks.py, tools/tests/test_bisect.py, docs/checks.md.

Derek Thurn2026-11-13

Rule chosen for the hang limit (tools/src/beryl_tools/hang.py): 4x the step's slowest pass on this machine in the last 30 days, floor 900 s, cap 2400 s, 1800 s with no pass on record. Why: the bead asked for several times the slowest pass. The floor sits above the slowest cold clippy pass seen in the Enact CI logs (555 s, which also included token waits), because a step whose warm passes take seconds can still rebuild cold. The cap keeps every limit under Enact's slow_timeout. Step times are stored per step and per day in $BERYL_CACHE/ci/step-times.json, because runs.jsonl records checks rather than steps, and reading its 430 MB at every run start would be slow. The limit counts adjusted seconds from the process start, after the token lease. Removed: the rerun-after-deadline in run_all, and Run.timed_out. Kills are now marked on the records as they are written, timeout=hang|wall|stopped, so the marks also reach the log on disk. slow_timeout went from 1000 s to 3600 s. Deviation from the bead: bisect gets its own SEARCH = 600 s wall limit, because the larger slow_timeout would otherwise let one search run for about 50 minutes. Bisect probes run under that wall limit only, not under the per-step hang limits, because they use a WallClock.
