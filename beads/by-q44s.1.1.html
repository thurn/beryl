Description

Read first: docs/beryl-3d.md 'Checks and isolation' and decision C17; the epic's rules 17 to 19. Then tools/src/beryl_tools/checks.py (fast_lanes), slow_ci.py (QUIET, PLACED, whole_reason, lane_reason, choose, fingerprints), rust_tests.py (affected_packages), selection.py (choice, the line that tests p.startswith("rust/")), cli.py, and docs/checks.md.

Why first. Every other bead of this epic pushes files under rust/beryl3d or data/beryl3d. Today a path under rust/ that is in no package of the main workspace makes affected_packages return the whole workspace, and any path under rust/ selects the browser lanes, the oracle lane and ui-smoke. This bead makes those paths select one lane and nothing else, before any such file exists. It changes tools only.

  1. Make room. checks.py is exactly 800 lines, the file-length limit, and data/file-length-allowlist.json is empty. In a commit of its own, move its lane constructors (repo_lane to card_oracle_lane) into a new module lanes.py and import them back, changing nothing else.
  2. The package tools/src/beryl_tools/beryl3d/ (a package, not a module: slow_ci's fingerprints hash only the top-level modules, so no later edit here reruns another lane):
    • paths.py: OWN, the pattern ^(rust/beryl3d|data/beryl3d)/; split(changed), which returns Beryl 3D's paths and the rest; the workspace's directory; the cache directory $BERYL_CACHE/b3d; EPIC = "by-q44s".
    • cli.py: the b3d command and its table of subcommands. just b3d with no argument prints each subcommand with one line. just b3d <command> --help prints its options and two examples. An unknown command exits 2 and names the nearest. In this bead the table holds one subcommand, lane, which runs the lane's steps.
    • lane.py: lane() -> Lane, named beryl3d, with a list of steps that later beads append to. It has no steps yet and passes.
  3. The one wiring into the main tools:
    • the justfile: one recipe, b3d *args; the main cli.py: one registration;
    • checks.fast_lanes: every lane but repo and names is chosen from the rest only, and the beryl3d lane is added when there is a Beryl 3D path;
    • slow_ci.choose: lane_reason and rust_packages are given the rest only. Slow CI has no beryl3d lane;
    • selection.choice ignores Beryl 3D's paths;
    • file_length.SCOPE gains rust/beryl3d/crates. A change to tools/src/beryl_tools/beryl3d still runs the python lane, as any tools change does. Say so in docs/checks.md.
  4. The isolation tests, in the tools' tests beside the other lane tests:
    • for [rust/beryl3d/crates/beryl_scene/src/lib.rs, data/beryl3d/gates.json, rust/beryl3d/crates/beryl_3d/ios/App.swift], fast_lanes returns exactly repo, names and beryl3d, and slow_ci.choose plans no lane but repo and names;
    • for [rust/crates/beryl_session/src/lib.rs], for [ui/src/stage/beat.ts] and for [data/ui-conventions.json], neither returns beryl3d;
    • adding a Beryl 3D path to a list of main paths changes neither the main lanes chosen nor the packages the rust lane tests.
  5. docs/checks.md: a short 'Beryl 3D' section saying what the lane is and pointing to the doc's 'Checks and isolation'.

Run: just b3d; just b3d lane; just check.

Acceptance criteria

The isolation tests pass; just b3d lists its subcommands and just b3d lane passes; a commit that only adds a file under rust/beryl3d runs the lanes repo, names and beryl3d in the fast check, and slow CI plans no other lane for it (paste both plans in a comment); checks.py is under 800 lines; no lane's choice for a change without Beryl 3D paths differs from before (the existing lane tests pass unchanged).

Deviations and decisions:

  • lanes.py also holds Lane, Step, BY and SMOKE_TITLES, not only the constructors. Importing them from checks.py would form an import cycle that breaks python -m beryl_tools.checks <step> (checks runs as main and is imported a second time). checks.py re-exports every name, so callers and tests are unchanged. checks.py is now 640 lines.
  • The bead names selection.choice; the function is selection.choose, which now drops Beryl 3D's paths first.
  • slow_ci.Plan.packages also splits: it computes the rust lane's packages from the diff on its own, and a Beryl 3D path there would have made the rust lane test the whole workspace.
  • fast_lanes(None) (no branch base, every lane) includes beryl3d, since nothing says what changed.
  • The names lane is chosen from every path (a Beryl 3D .rs file still gets its citations checked); every other lane from the rest.
  • EPIC is a constant in beryl3d/paths.py as the bead asks, although AGENTS.md discourages bead ids in code: the sweep needs it to file under the epic.
  • just b3d runs with @ so output starts with the reproducing command (rule 19).
