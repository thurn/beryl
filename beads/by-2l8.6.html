Description

Part of the long-think epic. Every rung's cost is rollouts, so a faster rollout speeds the whole ladder. A 12 s sample of the cube rollout benchmark's whole rollouts on staging (2026-11-05, ~9,900 self samples; rollouts ~0.575 ms, ~1,740 a core-second, busy machine):

PartSelf time
Candidate list: engine::decision, collapse, cast_options, Situation::of, candidates~30%
Mana solver: mana::source, Units::groups, Funds::of, plans, walk, complete, pays~29%
Events and triggers: move_batch_to, match_event, Filter::matches, fires~10%
next~6%
Legend rule: sba::legendary, unresolved_legends, legend_group~6%
layers::refresh~5%
Rollout policy~2%

_platform_memmove (~6%) is inside Situation::of, Funds::of, refresh and plans: large structs copied by value.

Leads, largest first:

  1. Lazy candidates for rollouts. ~60% of a rollout lists every castable, payable option, and the rollout policy then takes the most valuable one. Let the policy ask for options in its own value order and check payment only until one works (or cache a decision's candidates while nothing they depend on changed). Estimated 1.5-2x on rollouts.
  2. The legend rule is still ~6% after 690ac90 and 95d9fcc: the mirror has many legendary permanents. Index them so the check is O(changed).
  3. The memmoves: pass the big structs by reference, or build them in place.

Every change must leave every move unchanged (same rollouts, same answers), so that a running long-think ladder can adopt the faster binary in place (by-2l8.3) instead of starting over. Follow docs/benchmarking.md: counts first, then ABBA on a quiet machine.

Acceptance criteria

  • just bench-count: the rollouts subject runs at most 2/3 of the instructions of the commit this bead starts from (1.5x). just bench ABBA timing is reported when the machine is quiet; it is not a gate. If the three leads are done and the gain is under 1.5x, record the measured gain and the new profile in the close reason and close.
  • Behavior unchanged: a test compares every corpus rollout's answers and result with the starting commit's, and just oracle and just test-rust pass.
  • A fresh profile in the commit body names what is now the largest cost.

Delivered on staging 0e536f8 (14 commits). Instruction counts, rollout_counts 'rollouts' subject: start 6361f24 816,298,580 -> 538,981,590 (1.51x); after rebasing onto aeab4fc (expert/greedy retune changed the rollouts) base 744,027,792 -> 489,320,976 (1.52x). next_apply (default entry point, cross-check): 781,154,307 -> 525,435,081 on the old base. Behavior: rollouts_never_change pins every corpus rollout's answers (decisions and inline) and ending; re-pinned on aeab4fc from the base's own engine and search code, and the perf code reproduces it exactly. just test-rust and just oracle pass. ABBA timing not run: machine not quiet (Chrome, ArqAgent, WindowServer busy). Leads: (1) lazy candidates turned out not to pay: 20.5k of 31.4k computed priority decisions are forced passes, which must check every option anyway, so instead the listing got cheaper checks: mana before targets, a timing prefilter before collapse, a per-face facts table (mana source kind, activated-ability mask, static rules), Funds as units with exclusions taken back out, early exit once a spec has enough targets, in-place decisions, and skipping the SBA check right after a pass that only hands priority over (still counted). (2) Legend rule: card/face equality before names, one pass with the other state-based checks. (3) memmoves: smaller mana Groups, Funds without the 128-entry source array, layer list built only when an effect applies. Fresh profile: engine::decision (priority listing) 18.6%, mana::source 8.8%, layers::refresh 6.7%, next 6.6%, Filter::matches_x 6.1%. No State layout change, so saved states and the in-place adoption by by-2l8.3 are unaffected. Surprise: just bench-count shares one VM target dir across sessions; a concurrent run overwrote my binary once (filed follow-up).
