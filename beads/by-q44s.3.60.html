Close reason

Mana artifacts stand in the lands row in Beryl 3D and on the web, from ObjectView.mana_ability; shape-pay-theirs and shape-mode/opponent parity entries removed, shape-mode/you 4 to 2

Description

The web interface puts every mana source in the back row's lands part: a land, or a noncreature artifact whose card says '{T}: Add' a mana, such as Mana Crypt or a Treasure (isManaSource and battlefieldRow in ui/src/game/battlefield.ts, which read the card's oracle text through cardEntry). Beryl 3D's row_of (rust/beryl3d/crates/beryl_scene/src/table/place.rs) puts only lands there, so a mana rock stands in the other permanents' row. When one leaves, the other permanents to its right slide over in Beryl 3D and the beat waits for them, while on the web nothing moves. Recordings that differ only for this: shape-mode/you, shape-mode/opponent, shape-pay-theirs/you, shape-pay-theirs/opponent (data/beryl3d/timeline-parity.json).

Placement has no card text today: Zones (table/place.rs) reads only ObjectView. Either have the session say on ObjectView that a permanent is a mana source (beryl_protocol's protocol/view.rs, with the web reading the same field instead of its regex), or give placement the card records Beryl 3D already receives (faces.rs). Pick the one that keeps placement a pure function of the view and record why.

Acceptance criteria

A noncreature artifact with a {T}: Add mana ability rests in its side's lands row in Beryl 3D, with a test in rust/beryl3d/crates/beryl_scene/tests/all/under.rs or beside it. just b3d timeline-parity --update lowers the four shape-mode and shape-pay-theirs entries, and just b3d test and just b3d gate pass.

Derek Thurn2026-11-16

Decision: the session now sets ObjectView.mana_ability (true when the face up's definition has an AbilityKind::Mana ability; false when face down or unknown), and both clients stand a noncreature artifact with it in the lands row. I chose this over giving placement the card records from faces.rs because it keeps placement a pure function of the view, as place.rs's module doc requires, and it gives the web and Beryl 3D one answer: the web drops its oracle-text regex (MANA_ABILITY in ui/src/game/battlefield.ts). The manual table needs no change, because beryl_table_session always pins each battlefield object's row. Note that lands also report mana_ability=true (an Island's definition lists its mana ability). Row choice still keys lands on their type, so this changes nothing for them.

Derek Thurn2026-11-16

Handoff: ObjectView.mana_ability (beryl_protocol view.rs) is set by beryl_session protocol/build.rs has_mana_ability: the face up's definition has an AbilityKind::Mana ability. Lands report true too (an Island's definition lists one). The web's battlefieldRow (ui/src/game/battlefield.ts) and Beryl 3D's row_of (beryl_scene table/place.rs) stand a noncreature artifact with it in the lands row. Beryl 3D's lands_in_order (table/place/row.rs) now stands lands before mana artifacts within the untapped and the tapped groups, as the web's sideGroups does. Without that, a bounced Mana Crypt left of an Island made the Island slide and the beat wait. Tests: beryl_session tests/object_states.rs a_view_says_which_permanents_have_a_mana_ability, and beryl_scene tests/all/under.rs an_artifact_with_a_mana_ability_stands_among_the_lands_after_them. timeline-parity: shape-pay-theirs (both seats) and shape-mode/opponent are gone. shape-mode/you is down from 4 to 2: what remains is the web's own 'lift tray' step, which comes from a prompt and is milestone 3 work. gates.json: verbs-zones and pay-default now have a Mana Crypt in the lands row, so segments, records and placed went up and allocations went down (numbers in the commit body). just b3d test passed before the rebase, and gate and parity passed after it.
