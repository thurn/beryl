Close reason

lock test retries by count until a forked child's flock copy is gone

Description

rust/crates/beryl_cli/src/longthink/files.rs, test a_second_lock_names_the_first_holder, failed 2 of 7 'just test-rust' loops on 2026-11-10 while ui-test ran beside it (load 25-60): at line 330, after drop(held), holder() still returned Some("<own pid>\na note\n"), i.e. the flock on the lock file outlived the Lock. Likely cause (not proven): another test in the same binary spawns a subprocess; between fork and exec the child holds the parent's open file descriptions, so a flock taken on the lock file stays held until the child execs or exits. Rust sets CLOEXEC, which closes the fd only at exec, not at fork. Under load the fork-to-exec window grows. Fix options: take the lock on an fd the test owns alone (unlikely to help with fork), make the test tolerate the window by polling holder() until None within a bounded number of retries (no wall-clock sleeps: retry count only), or serialize this test against subprocess-spawning tests. longthink is retired (AGENTS.md), so deleting this test is acceptable if it guards nothing live: check whether lock()/holder() are still used outside longthink first.

Acceptance criteria

The test passes 20 loops of 'cargo test -p beryl_cli --bin beryl_cli longthink::files' while 'just test-rust' runs beside it, or it is deleted with a commit body saying why it guards nothing live.
