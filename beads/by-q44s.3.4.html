Close reason

ui/scripts/timeline.mjs prints the web stage's per-step timeline; checked on verbs-zones, pay-default and a Counterspell spec moment

Description

Read first: docs/beryl-3d.md 'Timeline parity' and 'Timing a script'; the epic by-q44s ('Rules for every bead', decisions C1 and C17). Code to read: ui/src/stage/stage.ts (ScriptStage, and follow, which calls a function with an Edge as each step begins and ends), ui/src/stage/beat.ts (Edge, laid), ui/src/stage/clock.ts (Clock), ui/src/stage/prompt.ts (Prompts, which makes the steps a client plays for itself while a prompt is open), ui/src/stage/playback.ts (createBoardStage) and feed.ts for how views reach a stage, ui/scripts/stage.test.mjs and stage-table.mjs (stage(), recorder(): a stage built in Node over a surface that only records), ui/scripts/stage-audit.mjs (a follower that collects every step), and ui/scripts/fixture-views.mjs (how a recorded fixture's JSON is read).

Add one file, ui/scripts/timeline.mjs, and nothing else under ui/. It is the web interface's half of the check that holds the two clients to the same timeline; the check itself is Beryl 3D's (by-q44s.3.6) and never runs for a change to ui/.

Usage: node scripts/timeline.mjs <directory>. The directory holds one file for each recording and seat, <name>.<seat>.json, where a / in a recording's name is written __ and the content is the array of fixture messages that beryl_cli's fixture recorder writes (the format fixture-views.mjs reads). The script plays every file in name order in one process and prints one line of JSON for each step to standard output.

How it plays a recording: through ScriptStage on a Clock it steps itself, with a surface that only records and the desktop layout (ui/src/stage/desktop.ts desktop), and with Prompts attached so that the stage plays its own steps for each prompt. It gives the first view at stage time 0 and each later view 400 milliseconds of stage time after the stage has played out the view before; views the game plays on through (those that neither ask the viewer something nor end the game) are given together. This is the clock Beryl 3D's test driver uses (rust/beryl3d/crates/beryl_scene/src/driver/mod.rs, REPLY_DELAY and plays_on in driver/recording.rs), and the two must agree, because a step that ends a span waits for how long the span has stood.

Each line has these keys in this order: "recording", "seat", "view" (the view's number in the recording, from 1), "beat" and "step" (from 0), "verb", "case" (null when the timing has none), "start" and "end" (milliseconds from the start of the step's script, rounded to 3 decimal places), "effects" (one string for each effect of the step's timing, in order: <name>@start or <name>@end, with +<into> appended to 3 decimal places when the effect has into, as in "impact@start+0.376"), and "own": true on a step the stage made itself, which no other line has. Lines are in the order the steps begin, a recording at a time.

Do not build: any comparison, any Beryl 3D code, or a test file under ui/.

Check it by hand on three recordings: the recorded fixture files of verbs-zones and pay-default that the web's own checks play (ui/AGENTS.md says how fixtures.json is recorded and where the files are written), and one card spec moment's (the specs skill). Copy each into a directory under the names above and count the lines.

Run: just ui-typecheck; just ui-unit; node ui/scripts/timeline.mjs <directory>.

Acceptance criteria

For verbs-zones the script prints one line for each step of each script the recording holds (the count equals the sum of beats[].length over its views' scripts) and every line parses as JSON with the keys in the stated order; playing the same directory twice prints identical bytes; pay-default prints at least one line with "own": true; a comment on the bead gives the three counts and the seconds the script took for each.

Handoff: one file, ui/scripts/timeline.mjs. Notes for by-q44s.3.6 (the comparison):

  • Own steps need the own-timing table. The script reads it from a recording's stage_timings response, which beryl_cli's record-fixture writes for the human seat only. Spec moments and the opponent-seat recordings (fixture::record_from, specs::trace, i.e. Beryl 3D's recordings pack) have none, so the script throws on the first own step of such a recording. 3.6 should insert FixtureMessage::response(ipc::STAGE_TIMINGS, &own_timings()) into each file it writes, as record_all does.
  • Files may be { messages } or a bare array. Seat is just the filename's second-to-last dot part (you/opponent).
  • beat/step of a sent step are its place in the session's script (the k-th sent step in timing order); an own step's are its place in the script the stage played it in (Prompts' marks script, or the session's script with paid/lowered steps inserted).
  • start/end are relative to the script's start, taken as the smallest span.turn among its told steps (the first beat's first step's turn).
  • The desktop layout's import graph reaches Vite-only code, so the script registers node:module hooks (extensionless resolution, TS-compile every src .ts, .tsx served as literal exported consts only, freeze.ts stubbed). If the stage starts importing something else from a component or a browser-reading module, the script fails at link or load time by name; add the module to BROWSER or move the constant.
