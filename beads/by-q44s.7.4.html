Close reason

Phone frame rate follows the rate rule; due() skips ticks on fixed-rate displays; tests and both smokes pass; staging e30485c95

Description

Read first: docs/beryl-3d.md 'Hosts' ('Choosing a frame rate', decision C18) and 'Drawing only when something changes'; beryl_host/src/rate.rs (RateRule, Paced, Step, Thresholds::DATA), beryl_host/src/frames.rs (FrameLoop::paced, fixed_at, Ticks::set_rate, set_running, next_wake), beryl_host/src/macos.rs (how the macOS display link carries out a step), beryl_host/src/phone.rs (Phone, Platform, the fixed_at(60.0) and the display_hz: 60.0 it assumes), and the C functions bead's (by-q44s.7.3) handoff (BerylConfig::display_hz, BerylWake::hz, Phone::hz).

Why. The spike's phone host counts frames against 60 Hz and never steps, so a 120 Hz iPhone is logged against the wrong rate and a phone that cannot hold its rate never steps down. Milestone 4's hosts carry out the rule's steps by changing CADisplayLink.preferredFrameRateRange and Surface.setFrameRate; this bead makes the Rust side choose the rate and say it.

Build, in beryl_host/src/phone.rs (and its test file):

  • Phone::new takes the display's highest rate (display_hz: f32) from BerylConfig. Phone::surface's first call builds the frame loop with FrameLoop::new(client, Platform::default()).paced(display_hz, false) instead of fixed_at(60.0), and passes display_hz to Opened.
  • Platform implements Ticks::set_rate by storing the rate; Phone::hz() returns it. The hosts read it from BerylWake::hz after every frame and apply it when it differs from what they last applied.
  • Some platforms cannot change their rate (Android below API 30 has no Surface.setFrameRate, and a display may ignore the request). So Phone::frame skips a tick when less than the chosen interval minus half the display's interval has passed since the last tick it drew: with the display at 120 Hz and the rule at 60 Hz, every other tick draws. A skipped tick returns Wake::Now with the same hz and does not count as a frame for the rule. Put the decision in a pure function fn due(last_drawn: Option<u64>, now: u64, hz: f32, display_hz: f32) -> bool in phone.rs.
  • Platform::set_running(false) is how the frame loop says it is idle; Phone::frame already returns Wake::Never or Wake::At then. No change there, but the doc must say the hosts now pause their ticks on those wakes (the host beads do it).

Tests, in beryl_host/tests/phone.rs (new): due at 120 Hz display and 60 Hz rule draws every other tick, at 60/60 draws every tick, at 120/40 draws every third tick, and a first tick always draws; and a FrameLoop paced at 120 Hz, fed 200 settled animating frames whose gap is three 120 Hz intervals, steps to 60 Hz and Platform's stored rate becomes 60 (use the same fake clock the tests of rate.rs use).

In beryl_3d: app::phone_feed and phone_live_feed take the display's rate for the frame log's Run::display_hz (today 0.0 until opened), so a phone's frame log names the rate the frames were counted against. Correct docs/beryl-3d.md 'Hosts' ('Who steps') to say that the phone hosts now step, and how a platform that cannot change its rate is handled.

Not in this bead: any Swift or Kotlin change (the host beads apply hz and pause ticks).

Run: cd rust/beryl3d && cargo test -p beryl_host --test phone && cargo test -p beryl_host -p beryl_3d; just b3d ios-smoke; just b3d android-smoke.

Acceptance criteria

cargo test -p beryl_host --test phone passes, covering due at 120/60, 60/60 and 120/40 and a paced loop stepping from 120 to 60 Hz; Phone::hz() returns the rule's rate and BerylWake::hz carries it; a phone frame log's display_hz is the configured rate; just b3d ios-smoke and just b3d android-smoke pass; the doc's 'Who steps' describes the phones.

Handoff: staging e30485c95. beryl_host/src/phone.rs: Phone paces FrameLoop with paced(display_hz, false) (display_hz sanitized to 60 if not finite or < 1); pub struct Platform stores set_rate and hz() reads it; Phone::hz() is the rule's rate (display_hz before the first surface); pub fn due(last_drawn, now, hz, display_hz) gates Phone::frame, and a skipped tick still drains the inbox and returns the loop's next wake. phone is now a pub module (beryl_host::phone::{due, Platform, Wakeup}); FrameLoop::ticks_ref added. beryl_3d app.rs: phone_feed/phone_live_feed take display_hz for Run::display_hz. Tests: beryl_host tests/all/phone.rs (due at 120/60, 60/60, 120/40, first tick; a paced 120 Hz loop steps to 60), beryl_3d tests/all/ffi.rs asserts the log's display_hz (header.c now passes 120). Deviation: the test file is tests/all/phone.rs per rust/beryl3d/AGENTS.md (cargo test -p beryl_host --test all phone). Smokes: ios-smoke passed at 60 Hz with none late; android-smoke passed and the rule stepped the software emulator from 60 to 30 Hz at 6 s, drawing every other tick. Note for the host beads: Android's Display.Mode.refreshRate reads 60.000004 on the emulator, so the rates the rule chooses carry that float noise; harmless, but a host comparing rates should allow a tolerance.
