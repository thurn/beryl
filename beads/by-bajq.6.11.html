Close reason

Repeated copy exceptions that change nothing are collapsed; Stage self-copy stays at one exception in Small (614e240b7)

Description

Thespian's Stage reads: '{2}, {T}: This land becomes a copy of target land, except it has this ability.' Nothing stops it targeting itself. Each time it does, it takes its own copiable values, which already carry the 'has this ability' exception, and adds the exception again (become_copy_instruction in rust/crates/beryl_rules/src/continuous.rs, Copiable::with_addition in rust/crates/beryl_kernel/src/copiable.rs). Two Stages copying each other do the same. The list of exceptions (Layout::Additions, rust/crates/beryl_kernel/src/layout.rs) holds 3 in Small and 8 in Large. The fourth activation moves the game to Large, and the ninth fills Large's list too. Large has no larger layout to fall back on, so the game ends Stalled(Capacity). A rollout policy or the fuzzer can play this line: it is legal, if pointless, and costs only {2} a turn. By CR 113.2c ('If an object has multiple instances of the same ability, each instance functions independently') the copy really does have the ability once for each repeat, so simply dropping the duplicate is not exact in general. It is exact for an activated ability whose instances can't be told apart, and for exceptions that only set values (CopyChange::PowerToughness, Colors, AddSubtype) when they repeat the last entry. Choose a bounded representation, for example a repeat count on an Addition, or collapsing repeats that can't be told apart, and record the rule that justifies it. Found while working by-bajq.6.10, which raised Small's list from 2 to 3 entries.

Acceptance criteria

A scenario or kernel test activates Thespian's Stage targeting itself at least 10 times and the game neither stalls nor leaves Small without need; the result's abilities match CR 113.2c / 707.9a as recorded in the code; State<Small> within 20,480 bytes; just count-gate holds with no bump.

From the copies Warden (by-bajq.6.6): a related silent cap. State::copy_grants (beryl_kernel/src/definition.rs) zips the activated abilities a copy's exceptions give into a 4-slot array, so a fifth is dropped without a Full. With Thespian's Stage copying itself repeatedly, the repeats past four vanish from layer 1 rather than moving the game to Large. Whatever bounded representation this bead picks should also make that array's limit explicit (propagate Full or collapse repeats before it).

Handoff: Copiable::with_addition_read (rust/crates/beryl_kernel/src/copiable.rs) now skips an exception the values already carry when Copiable::repeats says a second copy changes nothing: CopyChange::Has only for an ability whose instances can't be told apart (free fn interchangeable: Activated or Mana kind, CR 113.2c/113.3b; it must return false for any future per-instance activation limit such as 'only once each turn'), wherever the first copy sits among the exceptions; AddSubtype always; PowerToughness and Colors only when the earlier copy is the last exception (CR 707.9b), and for Colors only with the same ReadColors. The anywhere-rule for Has covers two Stages copying each other ([A,B] stays two). Chose collapsing over a repeat count: no State size change, no count-gate cost (-0.81% vs bar). Test: beryl_cards tests::copies::a_stage_that_copies_itself_ten_times_keeps_one_copy_exception (fails without the fix). The two-Stage case has no test, because scenarios pick permanents by name and both are named Thespian's Stage. Re-pinned the copies family corpus hash in beryl_bench family tests: the turn numbers are unchanged, only the Stage's state bytes differ. Seen but not mine: on staging, beryl_cards every_ability_and_casting_option_is_exercised_by_a_scenario and derive::every_ability_of_a_generated_card... fail for Glasspool Mimic / Glasspool Shore (since 6b2f90bf4 'feat: Glasspool Mimic').
