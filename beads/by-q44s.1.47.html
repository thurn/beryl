Close reason

Fixtures record from both seats (130/140; tables and props one seat) via Sessions::with_across and fixture::record_from

Description

Read first: rust/crates/beryl_cli/src/fixture.rs (record, record_game, Definition::seat, Until::seat), rust/beryl3d/crates/beryl_inspect/src/recorder.rs (Cli::record) and docs/beryl-3d.md 'Recordings'.

The recordings pack (beryl_inspect::recordings) holds every card spec moment from both seats, but each fixture in ui/fixtures.json only from the seat its until stop is seen from. The doc's checks run over 'every fixture ... from both seats'. beryl_cli::fixture::record has no way to seat the viewer across the table: the session sends views to the human's seat only, and the stop condition is read from that seat.

Add to beryl_cli's library a function that records a fixture's game as the other seat sees it: the same game, the same stand-in answers and the same stop, with the views sent to the other seat (a spec moment's View::Theirs does this for spec boards; copy how specs/start.rs seats the viewer). This is a change to a main-workspace crate for Beryl 3D's sake, so say so in the commit body and list it in the doc's 'Checks and isolation' exceptions. Do not change what any beryl_cli subcommand prints or writes.

Then in recorder.rs record each fixture from both seats, and remove the sentence in docs/beryl-3d.md 'Recordings' that says a fixture is recorded from its own seat only. A table fixture (manual table) may stay one seat if its session has no second viewer; say so in the doc.

Run: just test-rust -p beryl_cli; just b3d cargo-test -p beryl_inspect; then build the pack once by hand and report how many fixtures now have two seats.

Acceptance criteria

Every fixture in ui/fixtures.json that is a game is in the recordings pack from both seats; beryl_cli's subcommands behave as before; the doc says what was built.

Handoff: Pushed 7a262bac1. beryl_session: Sessions::with_across(emit) makes each game draw the other seat's view of every update (Game::watch_across/publish_across, reusing Game::opponent_view as fuzz.rs does) and send it just before the human's view; the game itself is unchanged. Do not combine it with start_review, which draws that seat's views itself. beryl_cli fixture.rs: Definition::seats() (manual tables and prop fixtures give one seat only), record_from(def, source, seat), and record_game(def, across). From across the table the recording stops on the human's views but records only the other seat's views, and it pushes no CHOOSE or CLICK responses, because that seat never decides. Session setup moved into listen() to keep record_game under clippy's line limit. clicks::next_view is now generic. recorder.rs records one job per (fixture, seat). Pack built by hand: 1,710 recordings; 130 of 140 fixtures have two seats; the 6 table-* fixtures and shape-catalog(-theirs) and shape-divide(-theirs) (props) have one; nothing failed and every recording plays. Test: fixture::tests::a_recording_from_across_the_table_shows_the_same_updates. Note: the beryl_scene/stress.rs build break I met was already fixed on staging, so I dropped my own fix for it.
