Beryl 3D builds catch up to staging separately in every worktree

  • Description
  • Comments1
  • Changelog

Description

Symptom

The Beryl 3D record step (the shared test-profile build every Beryl 3D fast-check lane starts with, cli.SHARED_BUILD) uses 130-500 CPU-seconds in most pushes, and 50-160 s of wall time on its 2-4 token lease. Measured on 2026-11-17 in a scratch worktree:

  • After a one-function edit to beryl_scene, the shared build took 24 CPU-seconds (12 s wall).
  • After an added function in beryl_kernel, 21 CPU-seconds of cargo time, 40 s wall.
  • Moving the same target from staging as of 75 minutes earlier to the tip (26 commits, 87 Rust files) took 300 CPU-seconds (157 s wall at load 25). By crate: beryl_scene 72 s and its tests 24 s, beryl_search 40 s, beryl_cli 33 s, beryl_session 32 s, beryl_inspect 23 + 13 s, beryl_scenario 20 s, beryl_3d 15 s.
  • A fresh worktree that cloned $BERYL_CACHE/b3d/target (saved by the Beryl 3D sweep about 75 minutes earlier) took 426 CPU-seconds and 397 s for its first just b3d record.

So the cost of a push's build is mostly the distance between the commit its target last built and staging's tip, not the push's own change. About 200 of 327 staging commits in a day touch rust/beryl3d (1,285 file changes in beryl_scene alone), so every target falls behind within minutes. Each slot, each agent worktree and each sweep catches up on its own: with about 15 Beryl 3D pushes an hour, that is roughly 3,000 CPU-seconds an hour, on the push's critical path.

Why the obvious fixes don't work yet

  • Cloning a fresher cache into a slot throws away the slot's rustc incremental caches: target_cache.save_target drops incremental/ because rustc keys them to the absolute path of the checkout. A clone then compiles the changed crates from scratch (beryl_scene is 52,000 lines).
  • claim_slot in Enact already takes the free slot parked at the newest staging commit, but the parked commit says nothing about when the slot last built Beryl 3D.

Options to measure

  1. Make incremental caches portable across checkouts: build with --remap-path-prefix=<checkout>=/beryl (in RUSTFLAGS set by the cargo shim, tools/shims/cargo and cargo_pool.py, for both workspaces) and test whether rustc then reuses incremental/ in a clone. If it does, keep incremental in save_target, and have the fast check (or every passing push-class shared build) save its target so the cache stays minutes behind staging. Note the effect on debugger paths and panic messages.
  2. Stamp each target with the commit it last built (target/.built-at), and in cli.warm_target replace a slot's target with the cache when the cache's stamp is closer to HEAD (fewer changed files under rust/ per git diff --name-only).
  3. Split beryl_scene so that a change to one part does not recompile 52,000 lines and every crate above it.

Done

A Beryl 3D push's record step uses under 100 CPU-seconds at the median over a day (runs.jsonl, script check, the largest cpu_seconds among the *:record steps of one run), against 130-500 now.

Files: tools/src/beryl_tools/beryl3d/cli.py (warm_target, build, SHARED_BUILD), tools/src/beryl_tools/beryl3d/target_cache.py, tools/src/beryl_tools/warm.py, tools/src/beryl_tools/rehome.py, tools/src/beryl_tools/caches.py (save_kept, incremental_folders), tools/src/beryl_tools/cargo_pool.py, ~/enact/scripts/enact.py (claim_slot).

Run of 2026-11-17 04:10-06:10 UTC (CI structure). Options 1 and 2 above don't work on this toolchain. cargo trim-paths is still unstable in cargo 1.98.1 (tested), -Zremap-cwd-prefix needs nightly, and --remap-path-prefix puts each tree's path into the flag itself, so incremental caches can't move between directories. Cloning a fresher target therefore still throws away incremental state.

Landed instead: fast checks run in fixed-path trees that stay near staging. Enact ed0d3a6 adds [push] check_trees = N: enact push runs the fast check in the first free of .worktrees/check-1..check-N (most recently used first, pushed head detached, build directories kept), and falls back to the pushing tree when all are busy. Beryl c34fb0454 sets check_trees = 3, and runlog.place reads ENACT_BRANCH so a run's place is still its branch. Every push is staging's tip plus one change, so a check tree rebuilds only the commits since its last push. This works for both rust/target (clippy, tests) and rust/beryl3d/target (record).

First numbers (05:00-05:30 UTC): the first runs in check-1 were cold (record killed at 180 s; 417 and 199 CPU-s while warming). The first warm Beryl 3D push took 24 CPU-s for record, against a 134 median before. Pushes from worktrees created before the change still check in their own tree on their first attempt, because Enact reads .enact.toml before rebasing. Only check-1 was used in the first half hour. Leave this open until a day of data meets the done criterion (median record under 100 CPU-s).
