Run enact sync when the beads are filed.

Tracks

Milestone 6 runs beside milestones 3 to 5. It needs milestone 2's effects and nothing later. Everything is in beryl_render and the gates, except choosing the tier:

  • the tier input and the check that the tiers are equal (item 1), first and alone: every other bead depends on it;
  • the shadow map, lighting, bloom with multisampling, and particles (items 2 to 5), four tracks side by side, each a pipeline or shading function of its own;
  • choosing the tier (item 6), in the host;
  • the Enhanced tier's limits (item 7), last.

How to write each bead

Whoever works a bead has nothing but the bead, the doc and the code. Write for that reader.

  • Decide everything that can be decided now. A bead never says 'choose', 'pick', 'find out whether' or 'in X or Y'. Where the answer needs a measurement, the bead says what to measure, the threshold, and what to do on each side of it.
  • Name the crate, the file and the function or type for every piece, and which crate each test goes in. Give exact versions for any new dependency.
  • Name the web interface's files that hold the behavior, and say what to take from each. Open each file yourself first and quote the function names: do not name a file you have not read.
  • List the tests by what each one asserts, and give the commands that run them.
  • Write acceptance criteria that a command can show true or false.
  • Say what the bead must not build, when a later bead builds it.
  • Keep a bead to what one session can hold: about 600 lines of new code, or one module.
  • Before filing, check the dependencies: no bead's Run: line uses a command that a bead it does not depend on creates. Run bd dep cycles.
  • The epic's rules 14 to 16 say what a worker does when a bead is wrong and when it is done. Do not repeat them in each bead.

What this milestone's beads must cover

Each numbered item is at least one bead. The indented lines are what that bead must say; add the function names you find when you read the code. The web interface's files named below come from a listing of ui/src on 2026-11-14 and from reading the headers of the stage's files; that code changes every day, so open each file before you quote it, and replace a name that has moved. Where an item says 'one bead each', file that many.

What exists when you start: the Baseline tier with every verb and effect of milestone 2. Parity is milestone 5's, and is not needed here. Nothing in this milestone may change where anything is, how large it is or when it moves.

  1. The tier input and the tier-equality check, one bead. File first. Input::Tier makes the client leave out the records a tier does not draw. A check plays every gated fixture in both tiers and requires identical resolved elements and identical draw records wherever a record is in both. It is a step of the beryl3d lane.
  2. The shadow map, one bead: a depth-only pass from one key light, sampled in the main pass; the Baseline shadow quads left out of Enhanced. Pixel tests: a lifted card's shadow falls on the table and on a card below it.
  3. Per-pixel lighting with the sheen, one bead: shade_card and shade_table variants for the Enhanced pipeline. The Baseline shaders do not change; a test compares their source's hash before and after.
  4. Bloom and four-sample multisampling, one bead: a half-resolution blur of the glow and streak records; the Enhanced target multisampled with a depth buffer.
  5. Particles, one bead: the looks of vanish (ash for dissolve, a vortex for blanch) as instanced quads with motion seeded by the object's id and the step's index; a limit of 2,000 in the gates; the same seed gives the same particles.
  6. Choosing the tier, one bead: the startup measurement on stress-255 during the loading screen, the step down when 3 of 60 animating frames arrive more than half an interval late, the setting (Automatic, Baseline, Enhanced), the log line. Tests use --slow-gpu: Automatic steps down within 120 frames and nothing moves; Enhanced stays.
  7. The Enhanced tier's limits in data/beryl3d/gates.json and the count gates, with the Baseline tier's limits unchanged and every interface check still passing.
  8. One Warden. It looks hardest at anything that differs between the tiers besides shading.

Acceptance criteria

Every exit check of the milestone is covered by a bead that names its files, helpers and tests; lanes and tiers follow AGENTS.md; each area has a Warden; the beads are published.
