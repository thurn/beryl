Description

tools/src/beryl_tools/bench.py runs every worktree's just bench-count / just count-gate in the beryl-bench Lima VM with CARGO_TARGET_DIR=$HOME/target, one target dir shared by all worktrees (GUNGRAUN_HOME is already per worktree). Cargo names path-package artifacts by a hash of the path relative to the workspace root, so every worktree builds the same libberyl_engine-<hash>.rlib, and freshness is mtime-based. When worktree B builds between two runs of worktree A, A's next run sees its own sources older than the artifact, calls beryl_engine "Fresh", and links B's code.

Seen in by-cbf.1 (2026-11-06): after another worktree's run, just bench-count failed with no Layout in the root of beryl_engine although the worktree's lib.rs exports it, and cargo bench -v in the VM printed Fresh beryl_engine; touching every .rs file fixed it. When both trees' APIs agree, nothing fails: the counts (and the count gate in slow CI's throwaway worktrees) silently measure another tree's engine.

Fix: give each worktree its own target dir in the VM (e.g. $HOME/target/<worktree name>, as GUNGRAUN_HOME does), keeping a warm one for count-gate, or otherwise make a run always build its own sources. Mind VM disk: prune target dirs of worktrees that no longer exist.

Acceptance criteria

  • Two worktrees with different beryl_engine sources, run alternately with bench-count and count-gate, each build and count their own code (a test or a scripted check shows it).
  • A warm count-gate run still takes about the same time as today.

Done in 25deacd. Each worktree gets $HOME/targets/<worktree> in the VM; count-gate keeps $HOME/targets/count-gate warm for CI's throwaway worktrees. A per-profile owner stamp (.beryl-checkout.<profile>) triggers 'cargo clean --workspace --profile <p>' when another checkout last built the dir, so deps stay warm and only workspace crates rebuild. New worktree dirs start as a copy of the gate's warm dir. Each run prunes target dirs and Gungraun homes of worktrees no longer in 'git worktree list'. Surprise: 'cargo clean --workspace' without --profile only cleans dev, so a first version silently skipped the clean. VM check: worktree B with an extra engine fn built between two runs of A; A stayed Fresh on its own rlib (no probe symbol), B's had it. count-gate alternating A,B,A,A: 31/31/30 s on owner change (CI today: 33 s, it rebuilds the workspace from a fresh checkout too), 14 s warm. Moved the legacy $HOME/target to $HOME/targets/count-gate by hand so the gate stays warm.
