Sweep replaced builds out of reused worktree targets

  • Close reason

Close reason

Landed in 1150ec5da; slow CI passed. Per-worktree Beryl 3D target: fresh worktree 19 GB -> 10 GB after one sweep with no recompiles; slot-08 estimated 52 GB -> about 12-19 GB once its builds mark what they use.

Description

Symptom: free disk fell from about 600 GB to 305 GB between 2026-11-01 and 2026-11-15. On 2026-11-15 each Enact worktree slot held 15-57 GB, most of it rust/beryl3d/target (slot-08: 47 GB of Beryl 3D build output against 7 GB of rust/target/debug).

Why: Enact reuses its ten slots for days and keeps their build directories. Whenever a change on staging alters a crate's dependency versions, features or profile, cargo builds that crate and every crate above it under a new hash, beside the old build. slot-08 held 28 builds of beryl_scene from that one day, 8,105 fingerprint units in 2,368 distinct kinds, and 475 incremental caches in slot-01. Nothing deleted the replaced builds. warm.prune evicts by last access time, but APFS records only the first read after a write, so a unit every build reads looked as old as one replaced hours ago. Its file-count trigger (caches.tidy_target, from a2003d820) also skipped targets under 50,000 deps files, and slot-01 was 26 GB at 42,872.

Design chosen: mark and sweep, in tools/src/beryl_tools/target_sweep.py. Every 6 hours, from caches.tidy_target (which runs before every just b3d cargo command and every fast check, with the target's cargo lock held), the sweep:

  • deletes each unit (its deps/, build/ and .fingerprint/ entries) that no build read since the last mark while a newer build of the same unit was read or written. "Same unit" means the same crate, fingerprint kind (lib, test-lib, each integration test, build script) and fingerprint JSON features, profile, target, compile_kind and rustflags. That keeps clippy's check builds apart from test builds. Cargo reads a unit's fingerprint file whenever a build includes it, fresh or not, so a live unit always shows a read.
  • deletes an incremental cache left unwritten since the mark while another cache of its crate was written.
  • moves what it deletes into a .swept-* folder by rename and deletes that in a detached utility-priority process, so the lock is held for seconds.
  • marks every fingerprint unread again (warm.mark_unread) and touches .beryl-marked. A unit none of whose builds was used since the mark keeps every build, so a slot that sat idle loses nothing. Clones write a fresh mark (warm.mark), so a new worktree's first sweep can't take what its first build skipped.

Rejected:

  • One shared CARGO_TARGET_DIR for all slots. Cargo holds an exclusive lock on the profile directory for a whole build, so ten slots building at load 30-40 would run one at a time. Slots at different commits would also overwrite each other's fingerprints and rebuild constantly.
  • A smaller debug profile. Beryl 3D's dev profile already uses debug = "line-tables-only" with unpacked split debug info, and the bulk is rlibs and rmeta of replaced builds, not debug info.
  • Deleting a slot's target when Enact frees it. That throws away the incremental caches that slots exist to keep (18 against 421-544 CPU-seconds after a one-function change).

Measurements (load 28-55):

  • Fresh worktree, cloned from $BERYL_CACHE/b3d/target, after the shared test build and clippy: 19 GB and 30,946 deps files before the sweep, 10 GB and 14,472 after. The sweep took 6.7 s at load 55. Afterwards the test build compiled nothing (cargo: Finished in 0.78 s) and clippy checked nothing (1.05 s), so build time is unchanged.
  • Estimated for the long-lived slots, counting every build that is not the newest of its unit kind, once their next builds have marked what they use: slot-08 52.5 GB, of which 33.1 GB are replaced builds and up to 7.6 GB more are replaced incremental caches; slot-01 and slot-06 about 25 GB, of which 4.5-4.8 GB are replaced builds and up to 11 GB replaced incremental caches.
  • The first version grouped units by crate name only. It cut the fresh worktree to 6.9 GB, but a cargo build -p would then have swept the test and clippy builds of the same crates, so it was narrowed.

Related: by-keqt2 (wait or prune before a build when free disk is low) stays open. This change caps what each slot keeps, so a snapshot-pinned disk fills more slowly, but it does not guard a build against ENOSPC. The run log ($BERYL_CACHE/ci/runs.jsonl, 1.1 GB after five days, about 220 MB a day) feeds the history reads in runlog.read_log (selection, budget, bisect, deadline, check_value), so rotating it means teaching read_log to read rotated files. It is left out of this change.
