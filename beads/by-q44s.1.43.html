Description

Read first: docs/beryl-3d.md 'Threads', 'Hosts', 'The agent interface' ('Driving the running app') and decisions C15 and C16. Read rust/crates/beryl_app/src/lib.rs and games.rs for how the Tauri shell starts Sessions, forwards updates and resumes the newest unfinished game, and tools/src/beryl_tools/app.py for how just smoke launches an app with no window and waits for it to report.

In rust/beryl3d/crates/beryl_3d, the binary beryl3d:

  • It starts Sessions with an emitter that sends each GameUpdate down a channel to the frame thread and wakes the host's event loop. It resumes the newest unfinished game as the Tauri shell does.
  • The frame thread never calls a function of Sessions. Each frame it drains Client::next_command into a channel. A thread of the app's takes each SessionCommand, calls the function of Sessions it names, and sends the result back as an Input::Reply.
  • Scheduling classes are set, never inherited: the session thread and the search threads are put in the utility class. Find how beryl_search's pool starts its threads and set the class there through a hook the app passes, or start the game from a utility-class thread as the prototype does. Say which in a comment on this bead.
  • Options: --fixture <recording> (a debug build replays a recording from beryl_inspect, an optional dependency behind a tools feature that release builds leave off), --pause-at <moment>, --for <duration> and --window none|background|foreground| fullscreen. none uses the windowless host.
  • The frame log. Every run writes its own file, $BERYL_CACHE/b3d/frames/<start time>-<process id>.jsonl. Its first line describes the run: the checkout it was started from, the window mode, the display's rate, the GPU adapter and the load average. Then one JSON line for each late frame: the time since the last frame, the wait for a drawable, the client's time, encode and submit, GPU time where there is one, the verbs playing and whether the AI was searching. Frames held to 60 Hz on a faster display are counted apart from frames that missed 60 Hz. At exit the app prints the summary and the file's path.

In the tools package:

  • just b3d app <options>. An agent's run gets --window none unless it names a window, and a run that an agent starts with a window must give --for. A person's run gets fullscreen.
  • just b3d smoke: starts the app with --window none --fixture verbs-zones, waits until it reports its first presented frame, and exits. It is a step of the sweep.
  • just b3d frames [path]: a frame log's summary and its 10 worst frames. With no path it reads the newest log whose first line names this checkout.

Tests in beryl_3d/tests: the frame log's writer and reader agree; with a stand-in for Sessions whose calls take 200 ms, the frame thread keeps producing frames at every tick; --fixture verbs-zones --window none --for 3s exits with status 0 and a summary; a release build has no --fixture option.

Run: just b3d smoke; just b3d app --fixture verbs-zones --for 3s; just b3d frames; just b3d cargo-test -p beryl_3d.

What the prototype found (rust/prototypes/beryl3d, 2026-11-14; read its code for a working example, then build it properly):

  • A macOS thread inherits its creator's scheduling class, and neither the session nor beryl_search sets one. A game started from the user-interactive frame thread ran its search level with drawing, and the prototype then saw stalls of 50 to 230 ms at load 20. It now starts the game from a utility-class thread (rust/prototypes/beryl3d/src/game.rs).
  • In the owner's runs at load 42 to 51, the late frames that remained had waited 17 to 90 ms for a drawable with the GPU done in about 1 ms: the window server under load, not the app. That is why the log records the wait for a drawable apart from the app's own work.

Acceptance criteria

just b3d smoke passes; just b3d app --fixture verbs-zones --window background --for 10s, run by this bead's own session, writes a frame log whose summary shows every frame drawn on a tick; a run with --pause-at 1500ms --window background --for 5s draws no frame after the pause; no call into Sessions is made on the frame thread; no criterion here needs a person.

Decisions: (1) Scheduling classes: no hook in beryl_search. The app's session thread calls beryl_host::utility_thread() before it builds Sessions and resumes/starts a game, so the game thread and every search thread inherit the utility class (as the prototype did). The frame thread is set interactive by both hosts; the frame log's writer thread is utility too. (2) The frame thread does no file I/O: FrameLog counts frames itself and sends late-frame and summary lines to a writer thread. (3) --fixture replays on the frame thread from beryl_scene::driver::Responses with the driver's clock (views 400 ms after rest); it never touches Sessions. --pause-at is behind the tools feature too, since named moments need the recordings pack. (4) Every agent run of just b3d app must give --for, not only windowed ones: a windowless run had nothing to end it (doc sentence updated). (5) The app is built with cargo's test profile (opt-level 1, shares deps with cargo-test) with --features tools; release builds leave tools off. The test 'a release build has no --fixture option' checks Options::parse with tools=false. (6) The stand-in session test holds each call until the test releases it (longer than any frame) instead of sleeping 200 ms, so it cannot pass or fail on machine speed. (7) Beryl 3D keeps replays in its own data folder (~/Library/Application Support/beryl3d) so it and the web app never resume each other's game; with nothing to resume it starts a game against the first offered agent. (8) GPU time is null in every log line: no host measures it yet. Acceptance runs (load ~45): background --for 10s: 684 frames on a 120 Hz display, 5 late (4 held to 60 Hz, 1 missed); --pause-at 1500ms background --for 5s: 0 frames after the pause; just b3d smoke passed in 2.4 s. verbs-zones logs tap, streak, vanish, point as not built.
