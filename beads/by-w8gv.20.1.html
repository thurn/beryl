Close reason

Run log in $BERYL_CACHE/ci/runs.jsonl for every check of by check/ci, and just ci-report (a08bf9d2)

Description

Log every run of every check (plan K18; docs/project-50k.md, Target architecture, Checks).

  • A new module in tools/src/beryl_tools appends one JSON line per check per run to paths.cache_root()/ci/runs.jsonl, under a file lock (worktrees and slow CI write at once). Never in the tree.
  • Fields: time (UTC), host, commit, tree (a tree hash of the working tree as checked, so an unchanged rerun is recognizable before any commit), script (check or ci), lane, check, outcome (pass, fail, skip), seconds, load average, chosen (all, for now).
  • Check ids are stable across runs: rust:<binary>::<test path>, ui-test:<title>, shots:<name>, oracle:<card>/<scenario>/<engine>. A step with nothing finer (fmt, clippy, tsc, smoke, count-gate, mobile-check) is one check, <lane>:<step>.
  • Sources: cargo-nextest's machine-readable output in checks.py rust_tests_step; ui/scripts/interactions.mjs check() (line 149) writes a results file with each title, outcome and seconds, as does shots.mjs per shot; the oracle report oracles.py already writes.
  • just ci-report [--days 30] [--json]: per check, runs, failures, verdict counts (empty until the verdict bead) and total seconds, costliest first, with a per-lane total.
  • A run that cannot write the log still passes: logging never fails a check.

Acceptance criteria

After just check and just ci, runs.jsonl holds one record per check with the fields above; just ci-report prints per-check and per-lane totals; pytest covers the writer and the report.
