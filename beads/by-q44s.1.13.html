Close reason

GPU gate (just b3d gate --gpu): driver fragment count in beryl3d-bench and naga shader cost, staging c94d5e46f

Description

Read first: docs/beryl-3d.md 'Performance gates' ('What is counted', 'What counts do not show') and decision C13. GPU time cannot be counted, so this bead counts GPU work, and it must never push the design toward a better count at a real device's expense. Read the spike bead's comment on the epic: it says whether the software Vulkan driver in beryl3d-bench gives a fragment count that is repeatable and leaves out depth-rejected fragments.

  • Fragments shaded per frame. If the spike found the driver's count usable: build beryl_render in beryl3d-bench, create the renderer on the software driver, and draw each gated board's ranked worst frames with a pipeline statistics query around each pass (wgpu's Features::PIPELINE_STATISTICS_QUERY, fragment shader invocations), divided by the target's pixels. If it did not: compute the count in test code as the doc says, by drawing the opaque records nearest first into a depth buffer of your own, counting the pixels that pass, and adding the blended records' pixels. Say which in the commit body.
  • Cost per fragment. A test in beryl_render parses the shader source with naga (the release wgpu 30.0.2 depends on, as a dev-dependency), finds each function named shade_ and a material, and counts its ImageSample expressions and all its expressions (function.expressions.len()), adding the fragment entry point's own two counts to each. No Baseline material may have more than one ImageSample. Arm's offline shader compiler is not used: its installer needs a person.
  • data/beryl3d/gates.json: tiers.baseline.fragments per board (the target is 1.75 screens), and under materials.<name> a limit on texture samples and on expressions, each set from the first measurement.
  • just b3d gate --gpu runs both and fails over a limit. It is a step of the sweep.
  • Measure a typical recorded board both ways, all blended back to front and opaque with depth, and put the two fragment counts in the doc's Baseline table in place of the estimates.

Run: just b3d gate --gpu.

What the prototype found (rust/prototypes/beryl3d, 2026-11-14; read its code for a working example, then build it properly):

  • GPU timestamps do not work on this Mac: wgpu 30 reports TIMESTAMP_QUERY on Metal, but a render pass's end timestamp comes back 0.2 to 0.3 ms before its start.
  • The prototype's opaque records cover 1.7 screens (live), 3.0 (stress-255) and 9.2 (stress-1024) before the depth test; on Apple's GPU the frame as built finished 1.2 to 1.6 times faster than the same frame all blended with no depth buffer.

Acceptance criteria

Fragment counts for both stress boards are identical over three runs and have limits; each material has a counted number of texture samples and expressions with a limit, and a planted second textureSample in shade_card fails the gate; the doc's Baseline table holds measured numbers.
