Close reason

Card faces and tokens start from printed:: constants generated from the card store; typed values refused by the build; generated headers with just card header and a names-lane check; staging d9e02968

Description

Milestone 7b of Project 50k (docs/project-50k.md K2: "Printed characteristics are generated from Scryfall for the whole pool into the card store. A card gets a Rust file, under a generated header, when it gets written abilities", because "Nobody types a cost or type line"; "A card file" shows the target shape). Lane set-crates, after the card files moved to rust/cards/<group>/<set>/ with a build script per set crate and the shared build helper (previous bead; read its handoff).

Today

Every card file types its printed characteristics and its header by hand, for example Counterspell's:

//! Counterspell. {U}{U} Instant. "Counter target spell." pub static CARD: CardDef = card(names::COUNTERSPELL, &[Face::EMPTY .cost(mana("{U}{U}")).types(Types::INSTANT).colors(Colors::BLUE) .abilities(&[…])]);

Tokens are typed the same way (HUMAN in Adeline's file; the shared tokens). The store (data/card-store.tsv; format in the docstring of tools/src/beryl_tools/card_store.py; Rust reader beryl_card_store) has, per face: name, mana_cost, type_line, oracle_text, colors, color_indicator, power, toughness, loyalty, defense, and token: records for every token a pool card makes.

What to build

  1. Generated characteristics. For every card with a file, and every token a card file defines, the set crate's build script (through the shared helper) reads the store record and generates a const per face holding its cost, supertypes, types, subtypes, colors (from the color indicator where there is one), power and toughness, and loyalty: a Face with no abilities, or whatever fits the const fn builders of beryl_card/src/definition.rs. The card file starts from it and adds only abilities and what the rules need beyond print. Keywords stay with the abilities unless the helper can place them from the store's keyword list. Adeline's printed * power is 0 in her definition beside her characteristic-defining ability, so * generates 0 and the comment in her file moves to the generator. A card file no longer contains .cost(…), .types(…), .subtypes(…), .colors(…), .power_toughness(…) or .loyalty(…) for a printed value, and a check (a test of the helper or a step in the names lane) refuses one that does. Unprinted costs stay typed (mana("{1}{U}") for a kicker). The helper parses the store line itself with the standard library: the store is one JSON object per line found by binary search, and beryl_card_store/src/lib.rs already reads it with no dependency, so share or move that parser rather than write a second. Emit cargo:rerun-if-changed for the store.
  2. Parity first. Before deleting the typed values, generate and assert, for all 47 cards and every token, that the generated values equal the typed ones. List every difference on the bead and settle each: a generator rule (such as *), or a latent card bug, which gets a docs/bugs.md entry. Then delete the typed values in the same push.
  3. Generated header. Each card file begins with a generated //! header between two marker lines: name and mana cost, type line and P/T or loyalty, and the Oracle text, per face. One command rewrites it from the store (just card header <name>, and --all; document it in the justfile). The names lane of just check (tools/src/beryl_tools/checks.py, names_lane) fails when a changed card file's header is stale, and slow CI checks every file. Hand-written commentary lives below the markers and is never touched. Wrap as rustfmt leaves it (100 columns).
  4. A subtype the engine's Subtype enum lacks cannot occur among the 47 today; the generator fails the build naming the card and the subtype. The next bead in the lane generates Subtype from the catalogs.

The scale harness clones card files, and after this bead a clone needs a store record for its unique name. Keep just scale --cards 200 --crates 2 working by the smallest means (the helper accepts a second file of records, which the harness writes); the scale bead finishes it.

Files

  • rust/crates/beryl_card_build (the helper from the previous bead) and each set crate's build.rs.
  • rust/crates/beryl_card/src/definition.rs (card, the Face builders), characteristics.rs (Types, Subtypes, Colors, Supertypes), mana.rs (mana("…") parses Scryfall's notation at compile time), check.rs (card() checks a definition as it compiles).
  • All 47 card files and the token definitions: mechanical once the shape is fixed. Do three by hand, then script the rest.
  • tools/src/beryl_tools/card.py, checks.py (names_lane), card_store.py.
  • Need not read: beryl_rules, beryl_kernel, beryl_search, the UI, the exporters.

Tests: just test-rust; just oracle on five cards of different kinds (a planeswalker, a land, a creature that makes a token, a spell with an alternative cost, an artifact); just check.

Parity at the push (plan K11)

just check passes; the frozen save corpus replays (cargo test -p beryl_session --test corpus); rollouts_never_change holds; slow CI's counts lane (just count-gate, bar 405,276,238 instructions, 1% tolerance, rust/crates/beryl_bench/count-gate.toml) passes with no bump to the bar. Never delete a card implementation. Work the card-names and file-length allowlists down in the files you touch. Record decisions and anything this packet got wrong as comments on the bead; nobody answers questions (K31): proceed on the default given and record it.

Acceptance criteria

No card file or token definition types a printed cost, supertype, type, subtype, color, power, toughness or loyalty: each comes from a constant the build generates from the card's store record, and a check refuses a file that types one; the bead lists every difference found between the typed and generated values for the 47 cards and their tokens and how each was settled; every card file starts with the generated header, one command rewrites it, and just check fails on a stale header (shown by a test); just scale --cards 200 --crates 2 still runs; just test-rust, just oracle on five cards of different kinds and the parity checks pass.

Decisions: (1) The packet said beryl_card_store reads the store 'with no dependency'; it uses serde. beryl_card_build now depends on beryl_card_store (a build dependency of the card crates, not a runtime one) and reads records through its binary search, sharing the parser as asked; names are still listed by beryl_card_build's own scan. (2) Shape: each set crate's generated cards.rs has 'pub mod printed' with a Face const per face of its cards (printed::COUNTERSPELL, printed::SOPORIFIC_SPRINGS) and 'printed::token::<CONST>' for each token its files name; a token resolves to the printing its card's record links, else every store printing of that name, which must agree (the shared crate's Treasure; beryl_card_shared got a build.rs). Tokens live in a submodule because a token can share its card's name (Thundertrap Trainer's offspring). (3) A back face's name and a transforming back face's flag are generated too (layout 'transform'). Keywords stay in files. (4) Subtype check: the generator reads beryl_card's 'pub enum Subtype' variants from characteristics.rs and fails naming the face and subtype; the next bead replaces this with the catalogs. (5) The typed-characteristic refusal is in the build helper: a card or shared file containing .cost( .supertypes( .types( .subtypes( .colors( .power_toughness( .loyalty( .named( fails its crate's build. (6) Scale harness: no second record file was needed; a shard's 'printed' module re-exports each clone's faces from its original's set crate, since a clone's faces are its original's.
