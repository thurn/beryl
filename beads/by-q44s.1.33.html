Close reason

Frame ordering, draw calls, load and clip overflow fault on staging at c60c33ce4

Description

Read first: docs/beryl-3d.md 'The frame' (the rules for building a frame) and 'Rendering' ('The Baseline tier'). The contract bead left FrameBuilder::finish returning records in the order they were pushed.

In rust/beryl3d/crates/beryl_scene, src/frame/order.rs:

  • finish puts the draw list in drawing order: the opaque records first, cards nearest the camera first and the table last; then the seven blended bands in the doc's order, farthest first within a band, and the flat layer's band in the order of its tree. It sets Frame::opaque.
  • It counts the load as it goes: one draw call for each run of consecutive records with the same mesh, texture array and clip; instances; upload bytes (80 a record); and the screen area of the opaque and of the blended records, each divided by the screen's area. The builder is given the projection for this.
  • clip(rect) gives entries 1 to 15 of Frame::clips. A sixteenth sets a flag on the frame that the checks report as a fault.
  • The arrays are sized at startup for the engine's largest board (1,024 objects), with the sizes as named constants and the reason beside each. Ordering allocates nothing: the sort keys live in a scratch array the builder owns.

Tests in beryl_scene/tests: the order and the draw-call count of a hand-built list holding every band; finish on 600 synthetic cards allocates nothing after the first call (a counting global allocator in the test binary); the areas of two quads of known size; a sixteenth clip sets the flag.

Run: just b3d cargo-test -p beryl_scene.

What the prototype found (rust/prototypes/beryl3d, 2026-11-14; read its code for a working example, then build it properly):

  • The table and the shadows can be the card mesh scaled, so every opaque record is one draw call and every blended record another: the prototype draws two calls a frame on every board.
  • Zero allocations held on every board by using scratch arrays sized at startup and a small Copy record per object instead of cloning ObjectView, whose vectors would allocate. See core/mod.rs and core/play.rs.
  • The prototype's worst frame walked all 1,100 object slots. Walk live objects only.

Acceptance criteria

The tests pass; finish allocates nothing after the first frame; no code outside src/frame sorts records or counts load.
