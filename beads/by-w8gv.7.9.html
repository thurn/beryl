Description

Milestone 4 of Project 50k (plan K4, epic by-w8gv.7). An object holds the three common kinds of counter in fields and one (kind, count) pair for every other kind, so a second long-tail kind on one permanent replaces the first, and the kinds are a hand-written enum in which Story and Chorus exist for one card each. This bead generates the kinds from one list and gives each its own count.

Read first

  • docs/project-50k.md: decisions K4, K6, K11, and "State" and "Kernel rules" under Target architecture.
  • rust/crates/beryl_kernel/src/lib.rs: the kernel's contract. Its "Stores" section (written by by-w8gv.7.2) is the design this bead follows: kinds, shapes, capacities and byte allotments, expiry, indexing, capability bits, and what a store implements once. The same numbers are in a comment on by-w8gv.7.2, and enact brief shows that bead's handoff. Where the code proves the contract wrong, change its text in the same push and say so on the bead.
  • rust/crates/beryl_kernel/src/legacy.rs: the table of what M4 deletes. Delete each Legacy method this bead replaces; the struct itself goes in by-w8gv.7.10.

Need not read: cast.rs, mana.rs, combat.rs, the Effects store's internals, ui/ beyond the generated protocol file.

Where it is (staging 08d1a377)

  • vocabulary: CounterKind in rust/crates/beryl_card/src/ids.rs: PlusOne, MinusOne, Loyalty, Time, Story, Chorus. data/card-names-allowlist.json lists CounterKind::Story and CounterKind::Chorus as one-card mechanics.
  • kernel: Counters in object.rs (plus_one, minus_one, loyalty, other_kind, other; is_long_tail, long_tail, get, get_mut); the counter mutators in mutate.rs (put_counters, take_counters, Arrival::counters, each asserting the kind is not long-tail); Legacy::add_counters, remove_counters and set_counters; Board's counter setter (board.rs); the zone move, which resets counters (CR 122.2).
  • engine: arrive, add_counters and remove_counters in event.rs, each of which splits on Counters::is_long_tail; layers.rs (counters_matter, StaticCondition::HasCounter(kind), the impending condition's time counters, and the 7c loop over +1/+1 and -1/-1); sba.rs (a planeswalker with no loyalty, CR 704.5i).
  • the names, written by hand more than once: CounterName in beryl_session/src/checkpoint.rs (the save's names: "+1/+1", "-1/-1", "loyalty", "time", "story", "chorus"), counter_name in beryl_session/src/protocol/candidates.rs, and whatever protocol/names.rs, beryl_cli/src/transcript.rs and beryl_scenario hold (grep -rln 'CounterKind' rust/crates).

Scope

  1. One list. The kinds and each kind's name in the rules (CR 122.1: "Counters with the same name or description are interchangeable") come from one list, from which the vocabulary's type and every name table above derive. Adding a kind is one entry and no engine edit. Story and Chorus are entries like any other, and leave the card-names mechanics list. The list holds the kinds the pool's cards use, in a form the card pool pipeline can later fill: a macro_rules! list in beryl_card, or a data file with a generator beside the one that writes beryl_cards' names.rs. No procedural macro (AGENTS.md).
  2. Each kind its own count. An object can hold any number of kinds at once. The kinds the rules themselves read may stay fields of the object: +1/+1 and -1/-1 (CR 704.5q, 613.4c) and loyalty (CR 306.5b, 704.5i). Every other kind is a row of a keyed table (object, kind, count), as the contract shapes it: 255 objects cannot each carry a field for every kind. other_kind, other, is_long_tail's callers outside the kernel, and the three Legacy counter methods go: the engine calls one add_counters and one remove_counters whatever the kind.
  3. A keyed row ends when its object changes zones (CR 122.2) and when its count reaches 0. With no card in the game that uses a keyed kind, the zone move pays one AND (a GameTable capability bit).
  4. The save format's counter names do not change (the frozen corpus replays), and neither does ui/src/generated/protocol.ts unless a type moved: a test fails when it is stale, and its header says how to regenerate it.

Gotchas

  • get_mut makes kind the object's long-tail kind even when asked only to read toward a removal; event.rs's remove_counters reads first for that reason. The keyed table removes the trap: delete the comment with it.
  • signature (zone.rs) compares whole Objects: two permanents that differ only in a keyed counter are not interchangeable.
  • Counters matter to the layers only for some kinds on some cards (layers::counters_matter): the mutators take that answer from the rules today, and still do.
  • Scenarios: staff_of_the_storyteller.rs (story), malcolm_alluring_scoundrel.rs (chorus), overlord_of_the_mistmoors.rs (time), and the planeswalkers (loyalty): cargo test -p beryl_cards, cargo test -p beryl_session, and just oracle on the card files you touch.

Acceptance criteria

Counter kinds and their rules names come from one list: CounterKind and every name table (the checkpoint's, the protocol's, the transcript's, the scenarios') derive from it, and a test shows every kind's name round-trips through the save's counter name. Counters::other_kind and other and Legacy::add_counters, remove_counters and set_counters are gone: a kind without rules of its own is a row of a keyed table sized as the contract says, an object can hold two such kinds at once (a kernel test), and a row ends with its object's zone change. CounterKind::Story and CounterKind::Chorus are off the card-names mechanics list. The engine has one path for adding and one for removing counters of any kind. The save's counter names and the corpus are unchanged. just bench-count before and after and the state size are recorded on the bead; parity holds with no bump to the count gate.

Numbers and decisions (by-w8gv.7.9).

COUNT (just count-gate, rollouts subject, bar 389,343,295, no bump): before 389,728,983 (+0.10% against the bar); first cut 390,288,734; as pushed 389,975,802 (+0.06% against before, +0.16% against the bar). The benchmark's deck holds Staff of the Storyteller, so story counters are live on the counted path. By profile the table's own cost in the first cut was 364k instructions: State::signature's comparison (about 210k), the last-known snapshot walking every kind (43k), the ability offer's read of the count (47k) and the remove path's three scans (26k); the first, second and fourth were trimmed.

SIZE: size_of::<State<Small>>() 20,080 -> 20,176 (+96 of the +104 allotted; the table is 97 bytes, a row 3). Object stays 24.

DECISIONS:

  • The list is beryl_card's counter_kinds!, a macro_rules list that hands its entries to a macro named by the caller. CounterKind (ALL, name, named) and the protocol's Counter mirror are written from it; the save's CounterName is now a newtype of CounterKind serialized by CounterKind::name; the candidates' wording, the transcript, the scenario snapshot and the blunder boards read name()/ALL.
  • Deviation from the bead text: no GameTable capability bit for the table's kinds. The contract's indexing rule (by-w8gv.7.2) holds: the zone move and every read pay the bit test of the keyed slots the other stores already pay, so a game with no such card pays nothing new.
  • The table has no kinds mask: every read is of one object.
  • State::add_counters returns Result<Event, Full>, and State::arrive and Board::set_counters Result<(), Full>: the first counter of a table kind on an object needs a row.
  • Last-known information (interpret/scene.rs Known) holds CountersHeld, one byte per kind of the list (6 now). It grows with the list; at hundreds of kinds a later bead may want the effect's own kinds only.
  • corpus_never_changes moved (15_570_083_640_149_560_188 -> 8_946_941_424_377_973_772): an object no longer hashes its one long-tail pair. Checked by hashing as the old representation did (each object's first row, kept at zero, in place of the pair): the corpus gives the old pin. rollouts_never_change is untouched.
  • Legacy has no method left; the empty struct and legacy_mut stay for by-w8gv.7.10 behind an expect(dead_code).
  • Not derived from the list, on purpose: the oracles' own names (tools forge.py COUNTERS, xmage.py), the UI's badge kinds (ui Card.tsx CounterMark, by wire name) and the fixture conditions' Mark (beryl_cli fixture/condition.rs). A new kind shows in the UI only once it has a badge.
  • No docs/bugs.md entry: no card of the pool could put a second long-tail kind on one permanent, so the old limit was never reached.
