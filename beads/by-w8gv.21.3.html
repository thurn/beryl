Description

Prove a stage clock that a test can step, before the animation mechanism is chosen (plan K25; agreed with the CI track, K21).

The stage (K25) runs script steps in order and ends each step when its animation ends. The browser harness will pause its fake clock by default (by-w8gv.20.2): ui/scripts/interactions.mjs check() installs Playwright's page.clock and advances it with clock.runFor. That clock drives timers and requestAnimationFrame; as far as is known it does not drive CSS transitions or the Web Animations API. A stage that ends a step on one of those would hang under a paused clock and race under a running one.

Write a small probe (a scratch page and a Playwright script; not shipped, not committed) and measure in Playwright's WebKit, which is what the Tauri window is:

  1. Which of these a paused page.clock can step to completion deterministically, with the step's end observable as a promise: the motion package's animate() on motion values (what ui/src/game/CardLayer.tsx uses today), a Web Animations animation whose currentTime the stage sets from its own clock, a CSS transition.
  2. The frame cost of each for 80 card nodes animating transform and opacity at once.
  3. Whether the same mechanism can be sampled at exact stage times for the motion oracle (K27: path and peak size measured in stepped stage time, never wall time).

Record on this bead: the numbers, the mechanism chosen and why, and the shape of the clock interface the stage should expose to tests. The decompose bead (by-w8gv.21.4) builds on it. No product code changes.

Acceptance criteria

This bead records, from a probe run in Playwright's WebKit: which mechanisms a paused page.clock steps to completion, the frame cost of each for 80 nodes, the mechanism chosen, and the clock interface the stage exposes to tests. Nothing is committed.

Findings: a stage clock a test can step

Probe: a scratch page of 80 card-like nodes (126x176, gradient, shadow, text) moving transform (translate, scale, rotate) and opacity together, driven from Playwright 1.64 WebKit 27.2 (build 2370), headless, 1600x900, DPR 1, motion 14.9. One 600 ms linear step unless said. The machine was busy throughout (load average 24 to 38 on 18 cores), so the wall-time numbers are ceilings, not floors; the stepped results do not depend on load. Nothing is committed; the page and scripts are outside the repo at ~/Library/Application Support/Claude/side-session-notes/local_a260f7a2-8f12-475b-9514-e77d65ec1dc4/by-w8gv.21.3-stage-clock-probe/ (node probe.mjs [paused|seek|chain|cost|step|spring], layers.mjs, held.mjs).

1. What a paused page.clock steps

Playwright's clock fakes Date, performance.now, timers and requestAnimationFrame (a frame every 16 ms of page time). It does not touch document.timeline: with the clock paused, performance.now moved 0 ms in 200 ms of wall time and document.timeline.currentTime moved 203 ms.

So the bead's guess needs one correction: a native Web Animation or CSS transition does not hang under a paused clock. It ignores the clock and finishes on wall time, which is the race.

motion's animate() on motion values does step, and its promise does resolve, but its samples are not repeatable: it reads performance.now() when it starts, so it carries the phase between the instant the harness paused and the fake frame grid (0 to 16 ms, different every run). A clock that only sums frame deltas has no phase.

Also seen: a paused Web Animation seeked to its end never resolves its own finished, and cancelling one rejects finished with AbortError. The stage must resolve its own promise from its clock, never forward the browser's.

The cost that matters is not script (0.1 to 0.6 ms a frame) but repaint. A node with a Web Animation or transition on it gets its own compositing layer; a node whose inline transform is rewritten each frame is repainted unless it has will-change. With will-change every mechanism holds 60 fps at 80 nodes. Today's cards already carry it (.card-el in ui/src/screens/screens.css, for the same reason); the stage's nodes must keep it. At 800 nodes everything was at the mercy of the machine's load (in 2 s: plain direct writes 8 frames, layered direct writes 30 to 45, seeked Web Animations 67 to 95, each with one 300 to 640 ms stall at the start); read nothing finer from it.

Paint time itself cannot be read from script in WebKit; the frame interval is the proxy.

3. Sampling at exact stage times

With the stage clock in manual mode (no rAF, the page clock paused and never moved, or live: the same rows either way) and stepped to 0, 100, 250, 333.25, 599, 600, 700 ms in ticks of 16 ms or in one jump:

  • direct writes, seeked Web Animations and seeked CSS transitions: computed transform and opacity match the linear expectation to 0.0005 (the rounding of the readback), identical across tick sizes and clocks. done is false at 599 and true at 600.
  • motion with manual timing: rounds elapsed time to whole milliseconds (333.25 reads as 333: x 222.000 for 222.167) and reports the end one tick late (not done at 600, done at 700).
  • On ease-out (cubic-bezier(0, 0, 0.58, 1)) all four agree to three decimals: x 151.255, 273.857, 362.614 at 150, 300, 450 ms.
  • motion's spring({ keyframes: [0, 1], stiffness: 210, damping: 28 }) (CardLayer's SPRING) is a pure function of time: .next(t).value gives the same values in any order, and it settles at 600 ms. WebKit supports linear() easing, were a spring ever needed inside a Web Animation.

Sequencing decides whether stage time is exact. Two steps, 600 ms then 400 ms back, sampled at 800 ms (expected x 200): started inside the clock's tick at the first step's exact end, x is 200 for ticks of 16, 100 and 1000 ms; chained on the first step's promise, the second started only when the caller next yielded (at 800), so x was 400.

Wall cost of stepping one second of stage time: 63 calls of page.clock.runFor(16) took 444 ms (and one runFor(1008) took 436 ms: about 7 ms a fake frame); one page.evaluate that advances the stage clock 63 ticks and samples computed style at each took 43 ms (54 ms on seeked Web Animations); 63 separate evaluates took 171 ms. For the CI track: a verb check that steps the stage clock directly costs about a tenth of one that steps Playwright's.

Mechanism chosen

The stage computes each node's pose from its own clock and writes style.transform and style.opacity itself, on nodes that carry will-change: transform, opacity. No browser-timed animation runs on the stage: no CSS transition, no el.animate left to play, no motion animate(). motion stays as a curve library only (spring, cubicBezier, mix), all pure.

Why this one:

  • Time has one owner. It is the only family where nothing can run ahead of, or behind, the stage's clock, so it is the same code path live, under Playwright's paused clock and under a manual clock.
  • The pose is data. A step is a function from stage time to poses, so the oracle (K27) can read path and peak size from the stage's model at any time without a layout read, arrows and combat lines can follow a moving card from the same numbers (the rule invariants about arrows and moving objects become checks on data), and retargeting a card mid-flight starts from a known pose.
  • Cost is not a reason against it: 0.07 ms of script a tick for 80 nodes, 60 fps once the nodes are layered.

Rejected:

  • Web Animations seeked from the stage clock: equally exact, and the cheapest script (0.01 ms). But the pose then lives in the browser (every reader pays a style resolution, 0.33 ms a tick), fill animations pile up and must be committed and cancelled per step, cancelling rejects finished, and a spring must be baked into linear(). It is the fallback if direct writes ever show a problem on a real phone: the clock interface below does not change, only the writer.
  • CSS transitions: created as a side effect of a style change and steppable only by fishing out getAnimations().
  • motion's frame loop on manual timing: a global switch over an internal API (frameSteps), whole-millisecond time, end one tick late, the dearest script.
  • Playing natively live and seeking only in tests: the tests would measure a mechanism that does not ship.

One limit to know: all main-thread-clocked motion, direct or seeked, stalls when the main thread stalls (a large React commit in the chrome). Only an animation left to the compositor does not, and that is the one that cannot be clocked. K25 already made that trade.

The clock interface the stage should expose

interface StageClock {
  /** Stage milliseconds. Moves only inside advance(). */
  readonly now: number;
  /** Runs everything due in (now, now + ms]: applies each running track at its time, ends
   * steps at their exact end and starts the next step at that same time with the remainder,
   * then writes styles once. Synchronous. */
  advance(ms: number): void;
  /** Stop following requestAnimationFrame: from here only advance() moves time. */
  hold(): void;
  /** Follow requestAnimationFrame again. */
  release(): void;
}

interface Stage {
  readonly clock: StageClock;
  /** Resolves when the queued script has played out. Settled inside the tick. */
  idle(): Promise<void>;
  /** hold(), then advance to the end of the queued script; returns the stage ms it took.
   * Throws past `limit`, or when the script is waiting on the player. */
  settle(limit?: number): number;
  /** The step playing now: its index in the script, its verb, its start and end in stage ms. */
  readonly step: { index: number; verb: string; from: number; to: number } | null;
  /** An object's pose at clock.now, from the model: no layout read. */
  pose(object: ObjectId): Pose | null;
}

Rules that the probe showed are needed:

  1. Live, one requestAnimationFrame loop calls advance(timestamp - lastTimestamp). Because it only sums frame deltas, Playwright's paused clock drives it with no change to check(): runFor(304) is exactly 304 ms of stage time. Nothing on the stage reads performance.now() or Date.now().
  2. Starts and ends are stage times. A step's end starts the next step inside the same advance(), carrying the remainder, so the script's timeline is a pure function of the script: pose(t) is the same whether t is reached in 16 ms ticks or one jump. Promises are for observers (tests, the session's "script done" signal), never for sequencing.
  3. A wait that is not motion (a spell's dwell on the stack) is a step with a duration on the same clock. No setTimeout on the stage.
  4. Tests reach the stage through a hook on window in fixture and spec builds. The motion oracle runs in one page.evaluate: hold(), then advance(dt) and read pose() in a loop, at whatever dt matches the Arena recording's frame times.
  5. Reduced motion is durations of zero: a step then ends in the tick that starts it.
  6. Outside the clock, and so outside what a verb may depend on: React chrome and its motion components, and CSS hover transitions. Sound cues fire from steps at stage times.
