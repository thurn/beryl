Close reason

Slow CI picks lanes by per-lane base and tools fingerprint, full sweep hourly; replay saves about 20 percent; coverage follow-up by-gdn3.13

Description

What we see

Slow CI (by ci) is the largest single user of the Mac's CPU: 21% of what was used in a 3-hour sample, 5 or more cores in its busiest minutes, and 261 of the 337 check-hours logged in three days. Its ui-test lane is 52% of that time and rust:beryl_cli is 15%. It must stay on this Mac (see the decision in by-gdn3), so its cost has to come down here.

Why

Slow CI runs every lane and every check on every run, whatever changed. A commit that adds one card file reruns every verb:* browser check.

Change

Make by ci choose what to run from what changed since the last commit slow CI passed, the way the fast check already does.

  • Reuse the nightly coverage data and selection.py, which already choose ui-test and shots checks for the fast check. Extend the same idea to Rust test binaries where a crate's dependencies show a change cannot reach it.
  • Run everything when the tools, the harnesses or the coverage data itself changed, or when the coverage data is stale.
  • Run the full sweep on a schedule as well, hourly while staging is moving and in the nightly run, so a wrong selection is caught within the hour. bisect.py already finds the commit that broke a check.
  • Log why each check ran or was left out, as the fast check's chosen and cut fields do.

Files

tools/src/beryl_tools/checks.py, selection.py, coverage.py, oracle_selection.py (an existing example of selection in slow CI), slow_only.py, nightly.py, tools/tests/test_selection.py, docs/checks.md.

Done when

Over a day of normal work, the run log shows slow CI's check-seconds per run at half or less of today's median (3,692 s), with no failure that the hourly full sweep caught and the selected run missed. Record both figures in this bead. The measurements behind this bead are in its parent, by-gdn3.

Note from a cross-check on 2026-11-13. Selecting Rust test binaries by crate dependency will not narrow a card-only change: every set crate feeds beryl_cards, and beryl_session, beryl_search and beryl_cli all depend on it, so one new card file still selects all of their tests. A card-only change (a diff that touches only files under rust/cards/) needs its own rule: run the changed card's scenarios, its Oracle text diff and its oracles, as the fast check already does (by-w8gv.20.12), plus the tests that are a property of every card. by-w8gv.16.4 makes the fuzz decks stable when a card is added, which is what makes skipping the session and search tests safe for such a change.

Design as built (deviations from the plan): (1) Base is per lane, not origin/master: the commit at which the lane last passed on this machine ($BERYL_CACHE/ci/lane-passes.json), else the merge base with origin/master. Diffing from master alone gave 4% saving in a replay of the last 3 days (272 slow-CI runs), because master lags while staging is red and diffs span hundreds of paths. (2) tools/src changes are judged by a per-lane fingerprint (step commands + source of the tools modules the steps run or import + reruns/verdicts/slow_only + uv.lock/pyproject), not 'tools changed => everything': checks.py alone imports 65 of 79 modules, so path rules made nearly every run full. (3) Full sweep hourly (FULL_EVERY) or $BERYL_CI_FULL; not added to the nightly, since the hourly sweep already runs whenever staging moves. Replay estimate on 3 days of runs (lane-level and Rust packages only; browser selection not replayable): median check-seconds per run 3761 -> 2925 (78%), total 80%; 46 of 272 runs were hourly full sweeps. Browser lanes: ~77% of their seconds stay, because diffs often touch ui/src lines the nightly coverage cannot map, and slow CI then runs every check. So the 50% target is likely NOT met by this change alone; the day's real figures are not measured yet (needs a day of runs). Follow-up filed for fresher coverage.
