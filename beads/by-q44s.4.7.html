Close reason

tree median 3.0 s over 20 runs (png 4.5 s): pool floor for b3d rebuilds, one-token programs unpooled, dev LTO off

Description

Symptom: after a one-line edit to beryl_scene, just b3d tree verbs-zones --at 1500ms now takes 6.0 s (median of five runs: 6.0, 8.9, 5.4, 4.0, 17.7 s at load 16-18) against its 3 s target. just b3d png takes 7.3 s (6.2, 6.3, 7.3, 119.2, 21.2 s) against 6 s. On 2026-11-15 tree took 2.5 s. The first command in a fresh worktree took 92 s. The numbers are in docs/beryl-3d.md 'Edit-to-output time' (commit c31a92001).

Why, as far as measured: beryl_scene grew from about 11,000 to about 48,000 lines during milestones 2 and 3, and every edit recompiles it at opt-level 2 and then beryl_inspect. The 119 s and 21 s outliers look like waits for CPU tokens or a rebuild, not compilation; check them.

Proposed change: run cargo build --timings for one edit to split the time into beryl_scene, beryl_inspect, the link and any token wait. Then take the cheapest lever that reaches 3 s, for example: split beryl_scene into crates so an edit to one module recompiles a smaller unit; build beryl_scene at opt-level 1 in the profile just b3d tree uses, if interface-test speed allows; or have tree skip token queueing for a single-crate rebuild (e07e319fe already made tree take one token). Record the choice and the new runs in the doc.

Files: rust/beryl3d/Cargo.toml (profiles), rust/beryl3d/crates/beryl_scene, rust/beryl3d/crates/beryl_inspect, tools/src/beryl_tools/beryl3d/cli.py, docs/beryl-3d.md 'Edit-to-output time'.

Acceptance criteria

just b3d tree after a one-line beryl_scene edit has a median of 3 s or less over five runs, measured by the doc's method, and the doc records the runs. Or, if the 3 s target is unreachable without a design change, the doc says why and a bead names the change.

Handoff: Most of the over-target time was the CPU token pool, not compiling. With load 14-22, the build's lease waited up to 24 s and the one-thread program's lease waited up to 8 s. The compile itself was about 4 s, of which about 2 s was the local ThinLTO pass at opt-level 2. Changes: (1) tools/src/beryl_tools/cargo_pool.py gains FLOOR_ENV (BERYL_CARGO_FLOOR). A build of an agent-or-lower class with the floor set takes the tokens that are free without waiting (Pool.top_up, so it writes no lease-log line), or else starts on N job slots with no tokens, then grows by top_up as tokens free. (2) beryl3d/cli.py: quick_build sets the floor to QUICK_JOBS=2 for tree/png/film. run_program with want=1 runs the program directly with BERYL_CPU_TOKENS=1, outside the pool, and b3d-render now passes want=1 because it ignores its token count. (3) rust/beryl3d/Cargo.toml: profile.dev lto=off; profile.test lto=false (Cargo's default) keeps the interface tests at 148 CPU-s instead of 195. Results are in docs/beryl-3d.md: the tree median over 20 runs is 3.0 s (set medians 3.0/2.4/3.2/2.9), and png is 4.5 s. Gotchas: the first build after this lands rebuilds every dev dependency once (about 35 s at -j12) because the profile changed. png and tree each build their own beryl_scene (different features). One stretch of disk stalls (20-33 s builds with the pool off) is unaddressed. The next lever is splitting beryl_scene, whose incremental front end is 1.3-2 s. A reviewer should check that cargo_pool's slots bookkeeping (max(held, floor)) stays right when a floor build yields tokens to a push.
