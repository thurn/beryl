Description

Beryl 3D is a native Rust client for Beryl that draws the table as a real 3D scene with the GPU and has no WebView, JavaScript or Tauri. It is built beside the web interface and replaces it when the user says so. The design is docs/beryl-3d.md ("the doc"). Every bead here is written against it. If a bead and the doc disagree on a detail, the bead wins, and the session that notices corrects the doc in the same change.

The requirements, most important first: performance on very old hardware with no dropped frame; built for coding agents; deterministic performance tests; deterministic interface tests; native iOS and Android; easy to program; high-fidelity 3D visuals that never cost a frame.

Decisions taken with the user (design interview, 2026-11-14)

The doc's Decisions table states each with its reason. In short:

  • C1. Both clients stay fully alive until the switch. The web interface keeps taking every fix and feature. This epic never freezes, changes or removes anything under ui/ or in beryl_app, except to move shared code out of beryl_app into a crate both shells use.
  • C2. The floor is a 2015-class device (iPhone 6s, a 2015 mid-range Android phone with an OpenGL ES 3.0 GPU, 2013 integrated graphics): 60 frames a second there, on a full board.
  • C3. Web-shaped, with no browser. A retained tree of named elements with flexbox and grid; tests and agents drive the client in-process with locators, presses, a stepped clock and tree printouts.
  • C4. A real 3D table with one fixed camera per layout, fitted to Arena's recordings.
  • C5. No check compares whole pictures. One renderer. Interface rules are checked on each frame's numbers. A few renderer tests sample single pixels of known scenes with a tolerance. Amended by the owner on 2026-11-16: checks may compare Beryl 3D's frame with the web interface's screenshot of the same moment, held by a ratchet file (milestone 7, by-q44s.91).
  • C6. Card faces are baked: one texture per face, board size (256 by 360) for every face in the match, full size for the few being read, in a compressed GPU format.
  • C7. Native Swift and Kotlin hosts on phones, winit on the desktop, one host interface, and a headless host for tests.
  • C8. Two visual tiers, Baseline and Enhanced, differing only in shading. The tier is chosen by a measurement at startup and steps down for the session when frames run late. Enhanced is built last (milestone 6).
  • C9. Search threads use every core one scheduling class below the frame thread. No core is reserved.
  • C10. The performance gate holds the worst single frame and the total, over recorded games and over built stress boards at the engine's capacity.
  • C11. The user calls the switch and the deletion. No bead in this epic makes Beryl 3D the default app or deletes ui/ or beryl_app. This is the user's own exception to the rule that plans do not wait for approval.
  • C12. Own layers on wgpu, taffy and parley. No game engine and no UI toolkit.
  • C13. GPU performance is held by counts alone: fragments shaded per frame and cycles per shader. No 2015-class phone is bought or attached. A count is a stand-in for the device: where the two are found to disagree the device is right, and no design choice is made to suit a count at the device's expense. The user said this when choosing it: good performance is the top priority, and the gates must not limit the design.
  • C14. Interface tests are fast enough to run all of them before every push (the doc's 'Test speed'). The user asked for this on 2026-11-14: thousands of interface tests in a few seconds, because browser checks were half of all check time that week. A test is one recording, one seat and one window; it checks the times at which something can go wrong instead of every tick, reads recordings from a cached file and never runs the engine. Targets: 2 ms a test, all of them in under 10 seconds before a push, every-tick checking after it.
  • C15. Default to good performance. Where a choice trades smoothness for something else, the faster choice is the default and the other is opt-in. The desktop app starts fullscreen, and a key leaves fullscreen. The frame log records the window mode, so the choice keeps being tested.
  • C16. An agent measures frame delivery without a person. Input comes from a script played on the display's clock, load from a load generator, and results go to a frame log an agent reads (just b3d app, just b3d frames).
  • C17. Beryl 3D's checks are its own. It is a separate program in a Cargo workspace of its own. A change to it runs only Beryl 3D's checks, and a change to anything else runs none of them and builds none of its code. The owner asked for this on 2026-11-14. The cost is that a change to the session can break Beryl 3D without its author being told: a sweep finds that afterwards, and Beryl 3D's own work fixes it (doc 'Checks and isolation').
  • Review. Full Enact roles: six milestones, a Mason and a Sage audit in a gate epic after each, a Warden per area inside each milestone, one Archivist. A gate waits for the Wardens of what the next work is built on, not always for the whole milestone (see 'Milestones').
  • Bead graph. Milestone 1 is filed in full. Each later milestone holds its planning beads, which file that milestone's task beads and Wardens against the code that exists by then. What runs beside what, and the tracks inside each milestone, are decided now (see 'Milestones' and 'Rules for planners'), because a planner does not question the shape it is handed.

Defaults recorded without asking

  • Crates, in a workspace of their own at rust/beryl3d: beryl_scene (the client core), beryl_render (wgpu), beryl_assets (work off the frame thread), beryl_host (host interface, headless and desktop hosts), beryl_inspect (the recordings pack, the interface test runner, the frame benchmarks and the text commands of just b3d, with no GPU dependency), beryl_record (the record program, the only crate besides the app that plays the engine, which builds the recordings pack), beryl_3d (the app, which also exports the C functions the phone hosts call and holds the program that draws just b3d's pictures). The image download queue and disk cache are beryl_art, a crate of the main workspace that the Tauri shell also uses.
  • The Baseline tier draws cards and the table opaque, nearest first, with a depth buffer, and everything else blended afterwards. Every floor GPU skips hidden opaque pixels and none can skip blended ones. A card is a rounded-rectangle mesh, not a quad with cut corners.
  • Nothing is decoded, composed or compressed on the frame thread. Every board-size face is prepared before the opening hand is shown. During play at most one full-size face is uploaded per frame, and a scan that arrives late replaces Beryl's drawn frame only while the table is still.
  • A battlefield row that cannot give every card a pointable strip scrolls sideways. Arena shows no board that large, so it is listed in UI Conventions under 'Not seen in Arena'.
  • Frames are drawn on demand. A still table draws nothing.
  • Design tokens move to one data file that generates the web interface's CSS variables and Beryl 3D's constants.
  • Platforms. macOS, iOS and Android ship. Windows builds and passes Beryl 3D's sweep on Cygnus. Linux builds the core, the renderer and the headless host, for the count machine.
  • iOS deployment target 15 (was 17), to reach the floor device. Android stays API 24, and is silent below API 26, where the audio crate has no backend.
  • Crate choices: winit 0.30 (stable) on the desktop, parley for text, taffy for layout, tiny-skia and swash for Beryl's drawn card frames, ctt for texture compression with uncompressed RGBA as the logged last resort, rodio for sound.
  • The live control socket exists in debug builds only.
  • Enhanced visuals come after the table plays, beside milestones 3 to 5: they need milestone 2's effects and nothing later. This was 'after parity' until the preflight review, which moved it so the run is wider.

Decisions and defaults from the plan review of 2026-11-14

A review of this plan put five questions to the user. His answers, the same day:

  • Step timing moves into Rust. The web interface worked out each step's timing case, its waits and its effects itself (ui/src/stage/timing.ts). The session now does it, in beryl_protocol's script::timing (rust/crates/beryl_protocol/src/script/timing.rs), and sends a StepTiming for every step to both clients (doc 'Timing a script'). This is the one change to the session's protocol and to the web stage that this epic makes, and it overrides C1 and rule 5 for exactly this. The timing types bead (by-q44s.1.30) and then three beads in lane:timing (by-q44s.1.24, .25, .26) make it, in that order. What stays in each client is laying a beat out in time (laid in ui/src/stage/beat.ts, ported to beryl_scene's beat module), which the timeline parity check of milestone 2 holds equal.
  • The web interface keeps changing at its current pace (about 500 commits a week touched ui/ when this was written). Nothing here slows it.
  • One install on the user's iPhone is allowed in milestone 1, for a frame log from the phone spike (by-q44s.1.23). He has no older device, so no bead measures the floor (C13 stands).
  • Out of scope: screen readers, keyboard-only play beyond the web interface's shortcuts, and text in scripts the bundled fonts lack. Roles and names stay on every element.
  • The prototype's camera and feel are good. Bead .1.3 starts from its camera, and milestone 2 fits it to Arena's recordings.

Defaults taken in the same review without asking:

  • The draw record is 80 bytes, not the prototype's 64, with a table in the doc of what each material reads from each field. Clips are scissor rectangles.
  • Shader cost is counted with naga (texture samples and expressions per material). Arm's offline compiler is not installed here and its installer needs a person.
  • Fonts are committed as TrueType files in rust/beryl3d/crates/beryl_scene/fonts, because the web interface's npm packages hold them as WOFF2, which the Rust text crates cannot read.
  • Commands leave the core as values (SessionCommand from Client::next_command) and their results come back as Input::Reply, because Sessions::click returns the prompt's next state and the frame thread may not call it.
  • Beads are self-contained. Every bead is written so that it can be built as specified from the bead, the doc and the code alone, as the user asked.

Preflight review of 2026-11-14, after the prototype

A review of this plan against the prototype's results and against the checks' own code. The owner approved its rework the same day.

  • Isolation (C17). As first written, the plan put Beryl 3D's crates in the main workspace and its checks in the existing lanes. Every other change would have built wgpu, run Beryl 3D's tests whenever the session changed, and been failed by its gates. Beryl 3D now has a workspace, paths, a tools package, a data directory, a virtual machine, a lane and a sweep of its own.
  • A wider run. Twelve of milestone 1's 28 beads were one chain. The contract now lands first and alone, each crate and module is a track of its own, beads were split where their halves needed different things, and the questions that could change the design are asked first. Milestones 2 to 6 no longer run one after another (see 'Milestones'), and 'Rules for planners' keeps the later milestones from narrowing again.
  • A tool an agent can use cold. just b3d and its options became just b3d <command>: commands that list what exists, one way to write a time, a moment, a locator and an action, bounded output, and files that no two runs share (doc 'The agent interface'). The crate that holds it was beryl_inspect and is beryl_inspect, because 'stage' already names the web interface's stage.
  • Agents come first for iteration speed. The owner said on 2026-11-14 that no tuning by hand is expected. So there is no hot reload, no watch command and no dynamic linking. What is held is the time from an edit to a command's output: 3 seconds for just b3d tree and 6 for just b3d png after a one-line edit to the client core, measured in milestone 1.
  • Nothing waits for the owner (rule 18). The review found and removed three steps that did: an acceptance criterion that needed a person to start the app, a milestone 4 bead that needed a phone attached, and a parity exit check that a missing numbered exception could hold open.
  • No model is named in this epic or in its beads. Labels follow AGENTS.md.
  • Step timing stays the one change to the session and the web stage (lane:timing). Its timing-parity check is a lane of the main checks, because what it checks is the web interface.
  • Names. The workspace is rust/beryl3d. Data is data/beryl3d (space.json, gates.json, timeline-parity.json, parity.json). The tools package is tools/src/beryl_tools/beryl3d. The count machine is beryl3d-bench. Checks are logged as b3d: and what they check.

Rules for every bead

  1. Read the doc sections your bead names before the code. Read the web interface's code for the same feature (ui/src/stage, ui/src/game) to learn the behavior, not to port its structure.
  2. beryl_scene stays pure: no clock, thread, lock, file, randomly seeded hash map, wgpu or winit. The scene-purity check enforces it. If you need one of them, the work belongs in beryl_assets or a host, and its result enters through Client::handle.
  3. Client::frame allocates nothing once a game has started. The allocation gate enforces it.
  4. Never add a stored reference image or any check that compares whole pictures (C5).
  5. Never change beryl_session's protocol or scripts, or the web interface's code, for Beryl 3D's sake (C1), except in the lane:timing beads, which move step timing into the session by the owner's decision. If the client seems to need a change there, file a bead under this epic that says why, and build without it.
  6. Timing, spatial and color values are data, never a literal in code: data/ui-conventions.json for timing, which the session reads; data/beryl3d/space.json for space, which only Beryl 3D reads; the design tokens file for the flat layer.
  7. Every interactive element has a role and a name. Every fix for an interface bug adds the broken state as a fixture or stress board, so the generic checks cover it. 7a. Interface tests stay fast. Never add a test that starts the engine, a renderer, a process or a timer, or that steps every tick where the check times would do. A test that needs more than the check times is a missing check time: add it. The engine runs in one place only, behind beryl_inspect::recordings, when the recordings pack is built. 7b. beryl_scene never chooses how a step is timed. A step's case, duration, delay, waits and effects are in the StepTiming the session sent with it. A change to those rules is a change to rust/crates/beryl_protocol/src/script/timing.rs, and reaches both clients.
  8. A performance limit is set from a measurement and then only goes down. Raise one only when the work itself changed, with the old and new numbers in the commit body. No limit of Beryl 3D's needs anyone's approval to rise.
  9. An agent opens no window, with one exception: just b3d app with a --window mode and --for, when a measurement of frame delivery needs one (C16). Use background unless the measurement is of fullscreen. Everything else uses just b3d and the windowless host, and renderer work is checked offscreen.
  10. The machine is always loaded (load 20 to 50 is normal). Compare counts, not times. Where a time is reported, give the load beside it and the median of at least five runs.
  11. unsafe is denied in both workspaces. Only beryl_host and beryl_render may allow it, on the one item that needs it, with a comment saying which platform call it is, and beryl_3d on the C functions it exports to the phone hosts.
  12. Every new dependency's Cargo.toml comment says what it replaces. Only beryl_render names a wgpu type.
  13. AGENTS.md's rules all apply: worktree and enact push, files under 800 lines, no procedural macros, no references to beads or plans in code.
  14. When your bead or the doc turns out to be wrong or impossible, do not redesign. Do the smallest thing that keeps to the doc's decisions (C1 to C17), say what you found and what you did in a comment on your bead, and correct the doc in the same change if it is a detail. If it is more than a detail (a decision, a type in the contract, another bead's work), file a bead under your milestone, block what needs it, and finish the rest of yours. That bead is worked by the run like any other; it does not wait for the owner.
  15. A type, a file name, a crate or a version that your bead or the doc gives is not yours to change for taste. Where they give none, copy the nearest existing code in the Beryl 3D crates.
  16. A bead is done when its acceptance criteria hold, its Run: commands pass, enact push has passed, the doc matches what you built, and the numbers it asked for are in a comment on it.
  17. Beryl 3D's files live only under rust/beryl3d, data/beryl3d and tools/src/beryl_tools/beryl3d (C17; doc 'Checks and isolation'). A bead adds a check, a command, a limit or a data value there. It never adds one to checks.py, slow_ci.py, the justfile, count-gate.toml, data/ui-conventions.json or a crate of the main workspace. The exceptions are listed in the doc's 'Checks and isolation', and each is a bead of its own. If your bead seems to need another, file a bead that says why, and build without it. If your fast check fails because a change to the main workspace broke Beryl 3D, fix the break in your change and say so in the commit body.
  18. Nothing in this epic waits for the owner. Four things are his alone, and each has a way for the bead to close without him: the switch and the deletion (C11: write them up, do not make them); a new or changed numbered exception in UI Conventions (build what Arena or the web interface does, and name the question in the epic's closing note); an install on his iPhone beyond the one run of milestone 1 (use the simulator, and name it); and anything only a person at the screen can judge (do what a command can check, and name the rest). No acceptance criterion needs a person, a window an agent may not open, or a device attached. A command that could stop at a prompt nobody answers is given a time limit.
  19. A command an agent runs follows the doc's rules for the tool ('The agent interface'): it is a just b3d subcommand with --help and two examples; its output begins with the command that reproduces it; it writes durations, moments, locators and actions the doc's one way; its output is bounded; and it writes only files named for the run.

Rules for planners

For the planning bead of each later milestone. The shape between milestones is in 'Milestones', and each planning bead lists its milestone's tracks. These rules keep the shape wide inside a milestone.

  1. The contract first. If two or more tracks will write against a new type or a new function's signature, the milestone's first bead lands those signatures alone, small, with no logic, and every track depends on it.
  2. One track per module or crate. A bead belongs to one track and edits that track's files, and data/beryl3d. Two tracks never edit the same file.
  3. Split a bead whose parts need different things. The part that can be tested on values built by hand depends only on the contract. The part that needs a recording, or another track's work, is a later bead of its own.
  4. Whole-recording and measuring beads come last, after the tracks they join, and are in no lane.
  5. A lane's beads depend only on each other, and on beads that will have closed before the lane's first bead is ready. A lane never stops in its middle for another track.
  6. Unknowns first. Whatever a bead would have to 'find out' that could change another bead goes in a spike bead that depends only on the contract, with a rule for each outcome.
  7. Isolation, waits and the tool: rules 17, 18 and 19 above. Every check and command a bead adds goes in the tools package, as a step of the lane or of the sweep.
  8. Measure the shape before filing. Run bd dep cycles. Then give, in a comment on the planning bead: the number of beads, the longest chain of dependencies, and how many beads are ready when the milestone starts. If the longest chain is more than a third of the beads, split again.

Confirmed

  • The split works. A core with no GPU, clock, thread or file turns GameUpdates and a time into 64-byte records, and a whole game draws from them.
  • frame allocates nothing on every board, including frames that start a script, when the whole script is compiled to absolute-time segments at its start.
  • Positions as functions of time: pause, catch-up speed and drawing any moment directly (--png <ms>) all came for free.
  • The opaque pass with a depth buffer, nearest first, then a blended pass: one instanced draw per pass, two calls a frame. The table and the shadows are the card mesh scaled.
  • Opaque with depth beat all-blended with no depth on this GPU by 1.2 to 1.6 times, more with more overlap.
  • A rounded-rectangle card mesh of 37 vertices and faces as layers of one array texture.
  • Everything draws within WebGL 2's limits.
  • Camera-relative hands, and a camera fitted to a required table rectangle by moving along its line of sight.
  • winit 0.30 with a user-event proxy wakes a still window from the session thread.
  • The AI's search threads did not lengthen frames at this load.

Refuted or corrected (the doc and milestone 1's beads now say so)

  • The 64-byte record has no room for a card's back layer. A card's uv is unused, so uv[0] holds it.
  • Overlap heights: every card in a row needs its own 0.3 mm height, overlapping or not, because tapped cards are wider than the row's step.
  • A shadow at a fixed height hides under tall stacks. Place it at the height of what lies below.
  • WGSL allows textureSample only in uniform control flow, so a per-instance material branch must sample first. Every table pixel pays one fetch.
  • 'Four to eight draw calls' was pessimistic: two.
  • Frame costs timed back to back understate a paced frame by 3 to 10 times on the Mac. Timing (frame_abba) must pace frames.
  • wgpu's timestamp queries on Metal return an end before the start, so they cannot give GPU times on the Mac.
  • The executable is 33.7 MB, not 4.6, once the game is linked.
  • With a stand-in agent, the session outruns the animation, which needs a catch-up rule for fixture playback.

Could not test

  • The floor's GPU. This Mac cannot show it: Apple's GPU is far faster, removes hidden pixels differently, and runs Metal, not OpenGL ES 3.0. WebGL 2 limits only check the feature set, not speed.
  • Fragments shaded (no pipeline statistics on Metal; the VM and the software Vulkan driver were not used) and shader cycles (no malioc).
  • Instruction counts under Callgrind.
  • Compressed textures, full-size faces, text, the flat layer, marks, arrows, the Enhanced tier, phones and Windows.
  • The window itself: an agent may not open one, so the window, the pointer lift, 120 Hz pacing and the late-frame counter in the title were built but only the headless path was run. Judge them with just proto3d.
  • Search-thread priorities (decision C9) under real load: the machine was quiet, at load 5 to 8.
