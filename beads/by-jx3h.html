Notes

Vizier: repeat of by-rtk6 (frame drops, combat). This report's build f4968bff contains 8088e535 'perf: the app logs the frames its animations drop', 44e1c5a2 and 2f4c3fdf, so the journal/ui.json may hold the dropped-frame log for this moment. Same lane as by-rtk6 (lane:frame-drops). Follow the bugfix skill's 'Worker: fixing one report' section. Worker (by-jx3h): diagnosed, not fixed. No code landed.

WHAT THE PLAYER WANTS: fewer dropped frames while the game animates, here the opponent's turn 16 (Jace cast, payment, +1, land) played at 18:38:53-18:39:19. Acceptance: in the app's own frame log (ui.json 'frames' entries / journal 'frames:'), runs that overlap the AI's search drop about as few frames as runs that don't (~1%).

EVIDENCE (real app, f4968bff):

  • Frame runs while the opponent is NOT searching drop ~1% (1/149, 2/318, 1/136...). Runs that overlap a search drop 5-31% (5/23, 7/39, 10/52, 5/16, 45/300). All 9 journal 'frames:' warnings (>=10% dropped) overlap a search; the reported 77/725 run spans four searches (2.0-3.2 s each, pimc72-hidden-30m-anchor, all 18 cores) because the bug-button freeze stretched it.
  • Drops are spread over every verb, including 6% of frames with no verb playing, so it is not one animation. Worst shares: streak 17%, announce:coin 16%, lift 15%.
  • A trivial sync IPC round trip (card_records, runs on the app's main thread) has median 1 ms while the player decides and 10 ms while the AI searches (291 samples, max 44 ms). So the search slows the app process's main thread/IPC.

RULED OUT:

  • Memory: the search peaks at 37 MB RSS.
  • Per-frame UI cost: Chromium main thread ~1 ms/frame (3.6 s over 54 s of the fixture), GPU similar.
  • Headless reproduction: headless WebKit plays the report's fixture at 0.5-2% dropped with no load, with an all-core default-QoS load in another process, and with 18 default-QoS spinning threads injected into WebKit's own UI process (DYLD_INSERT_LIBRARIES via a patched pw_run.sh). Headless never composites through WindowServer, so it cannot show this. Also perf.mjs waits for stage idle between views, so views never arrive mid-animation there.
  • Search QoS: Rust threads on macOS start at QOS_CLASS_DEFAULT whatever the parent's class (measured), so the search already runs below WebKit's user-interactive threads. Utility QoS (what just's 'low' uses) made the same turn-14 searches take 22-26 s instead of 3-4.6 s on this always-loaded Mac, so it is not acceptable for the app. (A prototype priority module making workers inherit the asker's class was written and dropped.)

NEXT ACTION: needs a measurement in the real app window, which agents cannot open. Candidates, cheapest first: (1) cap the app's search threads (it gets only ~6.6 cores of 18 under normal load anyway: 43.6 user-s in 6.6 s), e.g. leave the 6 perflevel0 cores; (2) run the search in a helper process instead of the app process, since the main-thread IPC slowdown suggests in-process contention; (3) pause or slice the search while the stage animates. Judge each by the frames log of a game played in the app: runs overlapping searches should drop ~1%.

Fixed by staging 290d7696 (by-rtk6), which implements this bead's candidate (3) as throttling rather than pausing: while the stage animates, the UI's new stage_animating command makes long-search workers beyond a third of the cores wait, handing their trees to running workers. Measured with a user-interactive frame-timing thread under load ~40: p99 wake lateness with no search 8.6-10.9 ms, with the full 18-thread search 12.5-23.5 ms, with the paced search 8.4-10.8 ms. Candidate (2), a helper process, was measured and rejected: in-process and cross-process searches caused the same lateness. Candidate (1), a permanent cap, made searches 1.5-2.1x slower. Judge in the app with this bead's acceptance (frame runs overlapping 'ai' searches vs not); see by-rtk6's handoff for the method.
