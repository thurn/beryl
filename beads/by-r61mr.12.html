Description

Read the epic by-r61mr first: it holds the decisions, the code map and the directory layout this bead assumes. The work is in the Enact repository (~/enact) unless this bead says otherwise, delivered with that repository's own enact worktree create and enact push.

Running sessions have bd commands in their prompts, so the cutover must not change the command. When the tk binary is invoked under the name bd, it behaves as the shim.

  • It reads the fleet-wide cutover state from the server (cached for the few seconds the contract allows). In state before it runs the real bd with the same arguments and passes everything through. In paused it waits. In after it translates the call into server requests and prints what the real bd would have printed, including --json shapes, human-readable shapes that prompts parse, and exit codes.
  • If the server cannot be reached in state before, it runs the real bd: the shim must never make today's system worse.
  • Cover exactly the subcommands and flags in the recorded corpus (tests/corpus/, from the corpus bead). An unsupported call fails with a message naming the tk command to use.
  • The replay test: import the corpus's snapshot into the local simulator with tk import, run every recorded call through the shim in state after, and compare output and exit code with the recording, and for calls that write, compare the resulting ticket with what the real bd produced. Differences that cannot matter (timing lines, colour) are normalised by rules listed in one place.

Replace the Python recording wrapper's installer with one that installs this binary as bd ahead of the real one.

Acceptance criteria

The replay test passes for every entry in the corpus, and its report lists the normalisation rules applied and zero unexplained differences. Tests cover the three cutover states and the fallback to the real bd when the server is unreachable.

Notes

The shim's states, cache rule and drain step are section 7 of the contract.
