Description

The user prefers set crates organized by calendar year (2026-11-12): 'I would prefer something like that just organizationally, we could do like 2024_h1 if we needed to.' Today tools/src/beryl_tools/set_groups.py (the generator behind data/set-groups.json, run by just card crates / by cards) groups first-printing sets oldest first into runs of 500 to 1,500 cards (MINIMUM, MAXIMUM, RULE, partition, penalty, extend, crate_name), so a crate such as cards_1994_1996 spans years and a set's crate depends on its neighbours. New rule: each first-printing set goes in the crate of its first printing's release year, cards_<year>. A year whose sets hold more than about 1,200 cards is split by release date into cards_<year>h1 (January to June) and cards<year>_h2 (July to December); the current year and later years are split from the start, since recent years are always large, so a set never moves when its year grows. If a half ever exceeds the cap, split it the same way into quarters (_q1.._q4) rather than raising the cap. Card counts by first-printing year in today's store (32,496 cards): 1993-2015 370-860 a year, 2016-2020 900-1,200, 2021-2025 1,820-2,070, 2026 2,471 and growing, so years up to about 2020 are one crate each and recent years two halves of about 900-1,250. Why the cap: the one-edit rebuild budget (2 s, just scale) is dominated by rechecking the edited set crate, about 0.9 s per 1,350 cards (by-w8gv.13.15), and new cards land in the newest, largest years. Work: rewrite the grouping and naming in set_groups.py (keep card_path, module and constant rules; update the module docstring and RULE); regenerate data/set-groups.json and move the existing card files with just card crates (git mv, never delete a card implementation); keep the Rust side consistent (beryl_card_build names.rs spells the path rules, card_crates.py writes each crate's Cargo.toml/build.rs/lib.rs, the workspace members); check tools/src/beryl_tools/scale_workspace.py still sizes its scratch crates from the tree's groups sensibly (it cycles the tree's group sizes to reach N cards); update K8 in docs/project-50k.md (the Decisions row's wording if needed, and the Measurements paragraph that says the 500-1,500 rule stays) and docs/engine-architecture.md if it describes the grouping; update set_groups' tests. Then run just scale (with --assert, read under normal load: this machine always runs at a load of 20 to 40, see by-w8gv.13.17) and record the four budgets on the bead.

Acceptance criteria

data/set-groups.json groups sets by first-printing year as cards_<year>, with years over the cap (and the current year) as cards_<year>_h1/_h2; every existing card file sits in its new crate and just test-rust passes; re-running just card crates changes nothing; K8 in docs/project-50k.md describes the rule; just scale's four measures are recorded on the bead.

Decisions: CAP=1200 is strict (>1200 splits), so 2019 (1,203 cards) and 2020 (1,264) are halves. 2026 h1 holds 1,504 cards, so it is already quarters (cards_2026_q1, _q2) beside cards_2026_h2. Quarters are the finest level; a quarter over the cap stays as it is. Splits are sticky: extend() reads the split levels from the crate names already in set-groups.json (parents()), so a year stays split after it stops being current or shrinks. Everything else is a pure function of the store's sets, so sets missing from the store are now dropped from the file instead of keeping their place (no card file can belong to them). Legacy names (cards_1994_1996) carry no split, which made the migration a plain regroup. 'just card crates' now regroups from the committed store (set_groups.update), renames misplaced card files (plain rename; git records them as renames), removes empty set dirs and removes crates that hold only Cargo.toml/build.rs/lib.rs; it refuses to remove a crate with any other file. Scratch crates of just scale (cards_s000) get a generic lib.rs line instead of years.
